**你需要阅读AI生成的每一行代码才能信任它吗？**

不一定。相反，只需检查五件事：变更背后的意图、验收标准、不能破坏的不变性（invariants）、过程中做出的决策，以及它能正常运行的证据。

在 [Aviator](https://www.aviator.co/)，这种转变使得仅凭原班 9 名工程师就合并了 4 倍的拉取请求（PR），将[中位合并时间](https://thenewstack.io/ai-code-review-pipelines/)从 2.1 天缩短至 3.4 小时，并将代码回滚率降低了 40%。人类仍然会对每个 PR 进行最终签字批准。改变的是人类所阅读的内容。

> “决策需要由人来做，而 diff（代码差异）是做出决策最糟糕的地方。”

我们通过对自己的审查意见进行分类，得出了这个洞察。审阅者在 PR 上写的大多数内容，要么是他们以前写过的规则，要么是一个决策。机器应该每次都检查规则。决策需要由人来做，而 diff 是做出决策最糟糕的地方。

## 问题：代码审查无法随着 AI 的发展而扩展

我们的代码从“在 AI 辅助下由人类编写”转变为“在人类辅助下由 AI 生成”。每周合并的 PR 从大约 100 个增加到 400 多个。我们 AI 生成的 PR 中位数达到了 640 行，远超 400 行这一普遍认为会导致Bug检测能力下降的极限。

无论如何，捉虫（Catching bugs）从来都不是代码审查的主要目的。在微软 2013 年的研究（Bacchelli & Bird）中，只有 14% 的审查意见是关于缺陷的。审查是[工程师分享知识](https://www.aviator.co/blog/ai-code-review-knowledge-sharing/)并保持对系统的心智模型（mental model）不断更新的方式，而这才是最值得保护的部分。当智能体编写了大部分代码时，这也是最容易面临风险的部分。

> “捉虫从来都不是代码审查的主要目的。审查是工程师分享知识并保持对系统的心智模型最新状态的方式，而这才是最值得保护的部分。”

自从我提出[代码审查已死](https://www.aviator.co/blog/how-to-kill-the-code-review/)的观点以来，我听到最常见的反对意见是：“所以你们只是停止审查了？”不，我们是停止审查 diff。

## 那么，什么方法行不通？

* **AI 审阅者。** 在我自己的一个 PR 上，它打开了 18 个线程中的 16 个：魔术数字（magic numbers）、数组索引 React 键、一个运行时间过长的组件。其中一个线程捕获到了一个真正的竞态条件（race condition）。那两个真正重要的评论——都来自队友的设计决策——却被埋没在了一堆琐碎的意见（nits）下面。
* **四小时审查服务等级协议（SLA）。** 我们无法增加审阅者，所以我们增加了一条规则。初次审查变快了，但批准变得更加空洞，因为审阅者为了赶时间而走马观花，他们自己的工作也停滞不进了。
* **针对我们规范微调的自我审查技能。** 它的发现远远好于通用的机器人。但它仍然是在代码编写完成后才去读取 diff，并且交流中最有价值的部分——它争论了什么以及我们决定了什么——在聊天窗口中湮灭了。

这三种方法都试图更好地阅读 diff。然而无论如何，diff 本来就是[代码审查中最不重要的部分](https://www.aviator.co/blog/move-code-review-before-the-code/)。它展示了变更了什么，却从未展示为什么。

为了弄清楚审查实际上包含什么内容，我回看了一个我在 2025 年审查过的 PR。它有 14 个线程。其中 8 个来自机器人，捕获了一个真正的Bug。我的 6 条评论中有 3 条是我已经在其他 PR 上写过的规则，比如“使用 GraphQLRetryableException 以便 Celery 在其上重试”。只有 2 条是真正的决策，比如“没有提取注释：我们应该在 PR 上告诉用户吗？”

![显示当9名工程师停止阅读AI生成的diff时发生了什么的信息图。](https://cdn.thenewstack.io/media/2026/11/df6598e4-image-1024x536.png)

## 什么方法行之有效：验证意图，而不是代码行数

代码审查过去同时承担着多项工作：捕获Bug、强制执行团队规范、敲定设计决策，以及让所有人对系统的理解保持最新。我们将这些工作拆分，并为每一项工作找到了更好的归宿。

**在 PR 存在之前进行辩论。** 我们的审查智能体对作者的智能体进行交叉质询（运行在不同的模型上），并写下每一个分歧。在最近的一个 PR 上，智能体提出了四个分歧，并带着陈述的理由解决了其中三个。留给人类的唯一工作是一个命名决断。

**捕获意图和验收标准。** 不是作为一份前置的规格说明书，而是从与智能体的编码会话中捕获。每当工程师纠正智能体或回答其问题时，我们就创建一个标准。过去，当会话结束时我们会把这些东西扔掉。意图回答了我们为什么要做出变更；验收标准回答了它应该如何表现。没有标准的意图无法被检查，没有意图的标准无法被评判。

> “意图回答了我们为什么要做出变更；验收标准回答了它应该如何表现。没有标准的意图无法被检查，没有意图的标准无法被评判。”

**将重复的评论固化为不变性（invariants）。** 我们通过三轮筛选了一年的审查历史：去除噪音（机器人摘要、光秃秃的“LGTM”），将每条评论分类为规则、提案、一次性修复或问题，然后合并重复项。11,400 条评论变成了 212 条候选规则和 64 条批准的[不变性](https://docs.aviator.co/verify/concepts/invariants)。每条不变性都有范围、验证方法、出处和所有者。

以“每个配置变更都会写入审计日志条目，且仅在内容发生变更时写入”为例。它涵盖了写入配置的 GraphQL 变更（mutations）和 API 处理器，通过保存两次并读取审计日志的预览运行进行验证，是从 17 个 PR 的 23 个审查线程中挖掘出来的，归平台团队所有。

在每个 PR 上检查每个不变性的模型速度很慢，且无法做到完全可重复，因此在可能的情况下，智能体会将不变性编译为 ast-grep 规则，在模型旁边以影子模式（shadow）运行，直到它们达成一致。我们曾在九个 PR 上留下过的一条评论——“添加超时，这挂起了一个工作线程（worker）”——现在变成了一条八行的规则。十九个不变性以确定性的方式在 0.3 秒内运行完毕。

**用证据证明每一个标准。** 每个标准都变成一个场景。智能体启动一个预览环境，像用户一样驱动它，并记录屏幕截图、请求和日志。对于审计日志不变性，它会保存一个设置，确认产生了一个新日志条目，在没有任何变更的情况下再次保存，并确认仍然只有一个日志条目。

后半部分正是阅读 diff 的审阅者永远不会检查的内容。并非每个标准都需要浏览器：API 契约可以通过记录的请求和响应来证明，代码规则可以通过 ast-grep 匹配或文件及行号引用来证明。选择解决问题成本最低的证明方式。[绿色的 CI 检查](https://thenewstack.io/ci-bottleneck-agent-verification/)只能说明你想到的测试通过了。

**辩论决策。** 决策来自三个地方：编码会话、智能体的争论以及失败的验证运行。PR 列出了每一个决策、它的来源以及是谁解决了它。在一个为失败的网络钩子（webhook）交付添加重试的 PR 上，五个决策中有四个得到了解决；智能体对于是否对重试的交付进行去重存在分歧，因此由人工解决了这一个分歧。

审阅者大致浏览那些已解决的事项，解决智能体无法解决的事项，重新审视任何他们会有不同叫法的事项，并与作者进行讨论。这种对话建立起了对系统的理解。

**拥有规则。** 工程师不再[阅读每一行代码](https://thenewstack.io/review-decisions-not-code/)。他们拥有检查每一行代码的规则，并通过阅读意图、证据和决策来保持对系统的理解。

## 结果

* 每周合并的 PR：提升 4 倍，且仍由原班 9 名工程师完成
* 中位合并时间：2.1 天 → 3.4 小时
* 每个 PR 的人工线程：6.2 → 1.3
* 每 100 个 PR 的回滚次数：下降 40%

审查工作并没有消失。它转移到了完善不变性、辩论决策和改进验证上。请预期这个转型过程会带来阵痛：第一个月是双倍的工作量，到了第二个月，不变性积累到足够多，审查就会缩减，而到了第三个月，你读的就是意图、证据和决策，而不是代码了。
