一项覆盖5个模型和22种编程智能体运行框架的测试发现，相同模型搭配不同框架的成本差异最高达5倍，近65%的推理支出浪费在失败或超时任务上，且步数是成本主因。

> 译自：[Rankings flip with the model](https://thenewstack.io/coding-agent-harness-costs/)
> 
> 作者：Amanda Caswell

一项针对五个开源权重模型和 22 种配置的新基准测试显示，即便使用同一个 AI 模型，搭配不同的编程智能体运行框架，其运行成本最高也可能相差五倍。

Runta 和 [Baseten](https://www.baseten.co/) 为 [FrontierHarness Eval v1.1](https://runta.com/blog/introducing-frontierharness-eval-v1-1/) 对这些组合运行了 27,280 次测试，在此过程中消耗了约 830 亿个 Token。

> 估算推理支出中，近 65% 都消耗在了未通过验证或超时的运行任务上。

虽然模型本身占成本差异的 92.8%，但运行框架依然带来了不可忽视的影响。某种配置对一个模型来说可能是最便宜的选择，但换到另一个模型上却可能跻身最昂贵之列，这让希望[通过更换运行框架来削减编程智能体成本](https://thenewstack.io/agent-harness-token-costs/)或改用更便宜模型的开发者面临更多变数。估算推理支出中，近 65% 都消耗在了未通过验证或超时的运行任务上。

## 排名随模型更换而反转

该基准测试涵盖了 22 种编程智能体运行框架配置，涉及通过 Baseten 托管的五个模型：GLM-5.3、GLM-5.3 Flash、DeepSeek V4.1 Flash、Muse Spark Open 和 Kimi-K3。每种配置在每个模型上分别运行 62 项基于终端的任务各四次，并记录通过率、推理成本和执行时间以供对比。

在搭配 GLM-5.3 时，Codex CLI 的单任务平均成本最低，排名第一，但在搭配 Kimi-K3 时却跌至 22 种配置中的第 16 位。DeepSeek Harness Creator 的波动更大，在搭配 Muse 时位居榜首，但在搭配 GLM-5.3 Flash 时跌至第 21 位。

> 在这五个模型之间，一旦更换模型，运行框架的排名中位数就会波动 11 个名次；即便模型保持不变，成本差异也高达五倍。

在这五个模型之间，一旦更换模型，运行框架的排名中位数就会波动 11 个名次；即便模型保持不变，成本差异也高达五倍。最大的差距出现在 DeepSeek 上：Cline CLI 的成本是 OpenCode v1 的五倍，但通过率仅高出两个百分点。

研究人员还将每个模型内部的测试结果随机打乱了 300 次，以检验随机波动是否能解释这些成本差异。结果显示，实际差距大于随机打乱后的差距，报告的 p 值为 0.003。

## 失败任务吞噬预算

失败的运行任务占估算推理支出的 52.7%，超时任务又占了 11.8%，仅有 35.5% 花在了成功运行的任务上。虽然这些费用是基于 Baseten 的公开费率计算的，但它们量化了一个业界常见难题的代价——[编程智能体在完成高难度任务时往往举步维艰](https://thenewstack.io/real-swe-coding-benchmark/)。

> 在性价比最高的五款运行框架中，68% 至 82% 的未成功任务最终都是由智能体提交了未能通过验证的最终答案，而非运行超时。

在性价比最高的五款运行框架中，68% 至 82% 的未成功任务最终都是由智能体提交了未能通过验证的最终答案，而非运行超时。研究人员还在执行日志中发现了 216 起奖励黑客（reward hacking）行为，其中包括 163 起在线联网查询作弊。这些情况全部被判零分。

## 推高成本的是步数，而非提示词

Runta 考察了提示词长度、工具数量、缓存命中率和智能体步数中究竟哪一项对成本影响最大。结果显示，步数是唯一与单次成功任务成本存在统计学显著相关性的因素，相关系数为 0.51。

Mini-SWE-agent 充分印证了[多步智能体执行会如何推高 Token 成本](https://thenewstack.io/agentic-ai-token-costs/)：它在基准测试中拥有最小的初始提示词（仅 882 个 Token），但每次成功任务平均需要 38 步，在单次通过成本方面仅在 22 种配置中排名第 17 位。

性价比最高的五款运行框架高度依赖 Shell 命令（占其工具调用的 61% 至 93%），很少使用子智能体或上下文摘要功能。不过，Runta 并未单独测试这些设计选择，因此研究结果尚无法确定更精简的架构是否就是降低成本的直接原因。
