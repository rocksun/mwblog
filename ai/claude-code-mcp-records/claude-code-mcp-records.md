本文探讨了在没有历史记忆的情况下，Claude Code如何通过构建平台自动生成的依赖记录和MCP快速恢复项目架构。作者认为，相较于容易过时的记忆文件，组件级别的依赖记录更能为AI智能体提供精准的代码结构上下文。

> 译自：[Claude Code found my app’s shared contract in two MCP calls. Then the records ran out.](https://thenewstack.io/claude-code-mcp-records/)
> 
> 作者：Ignacio Aldama

**每一个 Claude Code 用户都目睹过**新会话从零开始。你在上周构建的系统上打开它，要求添加一个小功能，而智能体却从重新发现你自己的架构开始：哪个服务拥有数据、哪个前端调用它、两者共享什么类型。解释这一切的对话已经消失或被压缩成摘要，而源文件只展示了存在的内容，却没有说明谁依赖于谁。

到目前为止，主要的解决方案是记忆。Claude Code 在每个会话开始时加载 CLAUDE.md 指令及其自己的自动记忆笔记，并且自 9 月 17 日起，Claude Code 云会话中处于 beta 测试阶段的重新设计的 Projects 在线程之间保留了共享记忆，因此 Claude 可以回忆起“发布推迟到了星期五”或“在碰计费服务之前应该与谁核对”。我想测试另一种上下文来源：构建平台在创建组件的每个版本时写入的依赖记录。

*免责声明：我是 Bit Cloud 的一名工程师，这是一个从第一个组件开始构建、托管和部署单个应用程序的平台，编码智能体可以通过 MCP 在其上工作。我让 Claude 在其上进行构建，以查看当平台记录每个部分及其随版本控制的依赖项时，智能体能做些什么。该项目及其构建记录是公开的。*

## **在没有记忆的情况下，全新的会话可以恢复什么？**

该系统是我之前用 Claude Code 构建的一个小型支持控制台，我另外撰写了[我如何构建和部署它](https://dev.to/nachoaldamav/how-i-built-and-deployed-a-support-platform-with-claude-code-k)的文章。开始该构建的提示词中用两个词提到了工具，“使用 Bit”，并在其他地方描述了该产品。它有四个组件：一个 React 应用、一个由 MongoDB 支持的 Express 服务、一个共享的工单实体，以及一个[将应用和服务置于一个网关背后的平台组件](https://thenewstack.io/agent-runtime-application-server/)。这四个组件都在[公共 scope](https://bit.cloud/bit-oss/support)（bit-oss.support）中进行版本控制，并且控制台通过 HTTPS 在生产环境中运行。

为了测试仅靠记录能承载多少内容，我在一个空工作区中打开了一个全新的 Claude Code session，没有对话历史记录，也没有本地代码，并询问：

```
Add filtering by ticket status and assignee to the support console in bit-oss.support.
```

Claude 检查了工作区，发现没有本地组件。它的下一条消息是：“工作区是空的，所以支持控制台远程存在。让我通过 MCP 读取 bit-oss.support scope。”它为 `bit-oss.support` 调用了 `read_scope`。这返回了四个组件及其依赖项。然后，它为应用、服务和工单实体调用了 `read_components`，在导入源码或编辑代码之前检索了 API 引用和文件清单。

应用和服务都依赖于同一版本的工单实体。其类文档写着：“在支持服务和面向智能体的应用之间共享”，并且 API 引用包含了这句话。项目可以在没有原始对话的情况下提供此上下文。

Claude 使用 `bit import` 导入了所有四个组件，检查了源码，并在应用内实现了客户端过滤。验证报告了 41 个通过的测试，包括 9 个新的过滤测试。MCP 帮助它发现了系统；源码检查和测试确定了如何修改它。更改留在了应用内部，使共享的工单实体和服务保持不变。知道什么是共享的也告诉了智能体什么不该碰。

## **记录在哪里用尽了？**

它们在行为上用尽了。应用的 API 引用确实在其测试使用的假服务的文档中列出了它调用的路由 `GET /tickets`、`POST /tickets`、`PATCH /tickets/:id` 和 `POST /tickets/:id/comments`，但没有任何东西对照真实服务检查该列表。记录告诉了 Claude 哪些组件共享了工单契约；每一侧的路由是否仍然匹配，必须通过人工阅读和测试来确定。

一个绿色的构建也比看上去证明的东西要少。当临时数据库无法在 CI 运行器上启动时，MongoDB 集成测试会跳过，因此通过的构建并不表明它们运行了。我通过人工检查了持久性：创建一个工单，添加一条评论，针对同一个数据库重启平台，并查看两者是否都还在。

这是一个演示，带有预定义的演示帐户和公开的签名密钥。并发控制、迁移、恢复程序和强制数据库测试都还有待完成。那是普通的工程工作，也是我希望工程师花费时间的地方。

## **记忆文件还是依赖记录？**

记忆保存了某人选择写下来的内容。在 Claude Code 中，这意味著人编写的 CLAUDE.md（或 AGENTS.md）指令、Claude 从纠正和偏好中编写的自动记忆笔记，以及重新设计的 Projects 添加的决策（例如为什么放弃某个导出），这些是任何构建系统都不会记录的。每个笔记在编写的那一刻都是准确的。Claude Code 记录了每个记忆文件的写入时间，其文档解释了原因：“时间戳显示了事实的时效性。”

构建系统在创建组件版本时会写入依赖记录，它是该版本的一部分。当支持应用进行版本控制时，构建系统记录了它对工单实体特定版本的依赖，无需任何人决定是否值得注意，并且记录不会偏离它所描述的版本。并且由于 `read_scope` 返回每个组件的最新版本，Claude 读取的记录是最新的。记忆笔记带有编写时间，但没有任何东西将其与代码版本绑定。在测试中，会话没有对话，也没有本地代码。工作区中唯一的记忆是 `bit new` 写入的通用 AGENTS.md，它告诉智能体在平台上查找内容，而记录完成了其余的工作：它们足以找到共享契约。

这两者涵盖了不同的领域，并且结合起来效果最好：记忆用于意图，例如发布日期、要询问的人或为什么削减功能；记录用于结构和意义，哪个版本的什么依赖于哪个。Nx 通过 MCP 向智能体提供其项目代码图，Sourcegraph 在各个仓库中提供代码搜索和导航；这两者都做得很好。对于这个测试，我想要更窄的东西：每个组件一个记录，在其版本创建时编写，当依赖项的另一端位于智能体尚未索引的地方时仍然有效。

## **团队应该什么时候开始？**

在第一个组件。此测试中的记录没有额外的成本，因为它们是在每个版本制作时编写的，从第一天开始。我用 `bit new` 创建了工作区，它在 `.mcp.json` 中提供了 Bit Cloud MCP 连接，并提供了带有智能体指令的 AGENTS.md，在初始构建开始时，Claude 使用该连接浏览[现有的设计系统 scope](https://bit.cloud/bitdesign/sparks)寻找它可以重用的部分；这四个组件现在依赖于 16 个已经存在的组件，其中 10 个来自该设计系统。以后再重建该映射，在一个团队重命名共享字段而另一个团队从其错误日志中发现之后，将是同一工作的高昂版本。

这一切都不需要我们的产品；它只需要在工作发生的地方记录依赖项。

智能体已经可以触及生产环境，并且在每次请求之后，它们仍然缺乏的是它们即将改变的系统的视图。在第二个组件存在之前构建该视图是最便宜的。
