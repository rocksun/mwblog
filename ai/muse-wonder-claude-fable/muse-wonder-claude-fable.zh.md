**Meta于10月12日推出了 Muse Wonder**，大约在 [Muse Spark 1.1](https://thenewstack.io/meta-muse-spark-api/) 开放 Meta 的付费 Model API 三个月后。Meta 表示，Muse Wonder 系列在个人和专业智能体任务表现强劲，在内部的 MemoryBench 内存测试中名列前茅，并且在 Full 版本中，在 DeepSWE 和 SWE-Marathon 等编程基准测试中领先。

其模型卡片将 Fable 5.1 列为对比模型之一，Meta 的发布文章也公布了 Fable 5.1 与其自研模型的分数。这些都是很有分量的说法，因为 Fable 5.1 是 Anthropic 的顶级模型之一。

Muse Wonder 分为两个版本。标准模型可通过 Model API 和 Meta 的编程智能体 Muse Code 获取。更高性能的版本 Muse Wonder Full 仅在 Muse Code 的顶级订阅计划中提供。

Muse Wonder 在 Meta 的 Model API 上的定价为每百万输入 Token 4 美元，每百万输出 Token 20 美元。Anthropic 于 9 月发布了 [Claude Fable 5.1](https://thenewstack.io/anthropic-fable-5-1-launch/)；其定价为 10 美元和 50 美元，可通过 API 和 Claude 的付费计划获取。这使得 Muse Wonder 每个 Token 的价格便宜了 60%。缓存输入缩小了差距：Meta 收取每百万缓存输入 Token 0.20 美元，而 Fable 5.1 为 0.25 美元。如果它的性能真的达到了 Fable 的水平，对于整天运行智能体的团队来说，这是一笔巨大的节约。

> 如果 Muse 的性能真的达到了 Fable 的水平，对于整天运行智能体的团队来说，这是一笔巨大的节约。

我将标准版 Muse Wonder 与 Fable 5.1 进行了三项高难度的智能体和内存任务的头对头测试，以验证 Meta 的说法是否属实。

## 测试

我通过由 Meta 提供支持的 OpenRouter 运行 Muse Wonder，并通过 Anthropic 的 API 运行 Fable 5.1。每个模型在每个测试中以其默认的推理设置运行一次。Meta 公布的对比使用了最大的推理努力程度。一个脚本根据我在两个模型看到它们之前构建并验证的密钥对每个答案进行评分。我每个测试只运行了一次，因此在另一次运行中结果可能会有所不同。

* **智能体错误修复** – 一个包含 27 个模块的 Python 作业队列库，其中包含三个相互影响的 bug 和一个本身错误的测试。每个模型使用工具来读取、搜索、编辑和运行测试，上限为 25 轮。
* **事故调查** – 在级联中断期间对 20 个假冒服务的日志、指标、部署历史和配置历史进行排查 – 根本原因是配置更改，隐藏在两个诱饵部署和一个时钟慢了 263 秒的服务器背后。
* **长会话内存** – 关于 Webhook 中继服务的脚本化 50 轮对话，包含 25 条项目规则，其中 8 条后来进行了更改，3 条仅为暗示。最后，每个模型编写了配置和代码，然后参加了八个问题的回忆测验。

### 智能体错误修复

两个模型都将第一个 bug 追踪到了正确的文件，尽管错误消息指向了别处。两个模型都修复了第三个 bug，没有破坏 22 个回归测试中的任何一个，放过了错误的测试不予理会，并解释了它为什么是错误的。

区别在于第二个 bug。Fable 通过了所有六个隐藏测试。Muse 通过了五个，因为它的修复仍然向作业的失败事件发送了旧的尝试次数。

在价格方面，Muse 使用的输入 Token 大约是两倍，因此尽管单价较低，但成本大约是两倍。两个模型的成本都包含提示词缓存折扣。

最终数据：

* Muse 15 轮，269,615 输入，4,627 输出，0.75 美元，55.9 秒。
* Fable 14 轮，138,213 输入，3,132 输出，0.39 美元，68.5 秒。

### 事故调查

两个模型都获得了 10 分（满分 10 分）。每个模型都将配置更改 CFG-4470 命名为根本原因，排除了两个诱饵部署，发现了结账服务上的时钟缓慢，并按正确的顺序例举了所有九个受影响的服务。

> ……尽管单价较低，但由于 Token 使用量高，Muse 的成本更高。

Fable 用了 6 轮就完成了。Muse 花了 13 轮并在此过程中读取了更多数据，尽管它花在等待模型上的总时间更少。同样，尽管单价较低，但由于 Token 使用量高，Muse 的成本更高。

最终数据：

* Muse：13 轮，327,587 输入，8,811 输出，1.03 美元，69.1 秒。
* Fable 6 轮，108,128 输入，8,593 输出，0.89 美元，88.3 秒。

### 长会话内存

第三项测试在模型性能上产生了最大的差异。Muse 在最终交付物上获得了 25 分（满分 25 分）。它对所有 8 个更改过的规则都使用了最新值，并且得到了所有 3 个暗示的规则，包括编写在 Python 3.8 上运行的代码，因为客户端的服务器正是如此。它还在测验中获得了 8 分（满分 8 分），并对聊天从未涵盖的三问题回答了“未知”。
  
Fable 在这项测试中得零分。在第 5 轮中，Anthropic 的 API 返回了一个类别为“网络（cyber）”的拒绝。那一轮要求模型从环境变量中读取中继的目标 URL。Fable 拒绝了 50 轮中的 34 轮，包括最终交付物和测验。该项目是一个普通的 Webhook 中继，与网络安全毫无关系。这特别有趣，因为 Anthropic 表示 [Claude Code 用户在使用 Fable 5.1 时，每个会话受到的网络安全保障干预应该比 Fable 5 减少约 60%。](https://thenewstack.io/anthropic-fable-5-1-launch/)Fable 5 从未以这个理由跳过我的测试工作。

我遵循 Anthropic 的指导，丢弃了被拒绝的输出，同时保留了聊天中的自我消息，因此 Fable 仍然拥有每一条规则。早期尝试将拒绝的轮次保留在历史记录中导致了 45 次拒绝，所以我重新运行了它。Anthropic 建议为被拒绝的请求设置退回到另一个 Claude 模型的备用方案。我没有这样做，因为那将测试不同的模型。Anthropic 自己的 Fable 5.1 基准测试将网络标记的任务交给了 Claude Opus 4.8。

因为 Fable 拒绝了这项工作，这项测试几乎无法说明其长会话内存。它确实展示了每个模型如何对待日常后端代码，而网络过滤器可能会将其误认为是安全工作。Muse 完成了工作并得到了 25 分。

Muse 的数据：

* 50 轮，93,977 输入，9,848 输出，0.46 美元，143.2 秒。

## 结果

|  |  |  |
| --- | --- | --- |
| **测试** | **Muse Wonder** | **Claude Fable 5.1** |
| 智能体错误修复 | 5 / 6 | 6 / 6 |
| 事故调查 | 10 / 10 | 10 / 10 |
| 内存交付物 | 25 / 25 | 0 / 25，拒绝 |
| 内存测验 | 8 / 8 | 0 / 8，拒绝 |
| 轮次 | 78 | 70 |
| 总 Token 输入 / 输出 | 691,179 / 23,286 | 365,528 / 16,456 |
| 总成本 | 2.24 美元 | 1.85 美元 |
| 模型总耗时 | 268.2 秒 | 256.8 秒 |

在智能体工作方面，Muse Wonder 的表现达到了 Fable 5.1 的水平，尽管 Meta 自己的基准测试表显示标准模型在某些智能体测试（包括 OSWorld）上落后于 Fable 5.1。它在事故调查中与 Fable 不相上下，在错误修复中只差一个隐藏测试。

不过，在我的测试中它并没有省钱。Muse 在每个任务中使用的 Token 更多，其总成本为 2.25 美元，而 Fable 为 1.85 美元。Fable 的总数包括了它拒绝的内存会话中的 0.57 美元和 119,187 个输入 Token；在两个模型都完成的两项测试中，Muse 的成本为 1.78 美元，而 Fable 为 1.28 美元。

> Fable 的网络安全保障阻止了一个 Muse 完成的常规后端项目

在内存测试中，Fable 的网络安全保障阻止了一个 Muse 完成的常规后端项目，因此在类似代码上使用 Fable 的开发者可能会看到请求中途停止。

### 我的看法

Muse Wonder 的性能比我预期的更接近 Fable 5.1。话虽如此，对于智能体调试和调查，我仍然会选择 Fable 5.1。在我的测试中，它稍微更准确一些，使用的轮次更少，总体成本也更低。

当 Fable 的网络安全保障阻碍工作进行时，Muse Wonder 是一个替代选择。只是我无法确认与其它模型相比，这个比率是否合理，因为我没有任何数据来对比 Meta 的价格。
