六个月前，我写过一篇关于[如何废除代码 review](https://www.latent.space/p/reviews-dead) 的文章，我当时错了。我依然认为逐行审查正在消亡，但我选错了替代方案。

## 我最初的提议

最初的文章提出了一个关于 AI 代码验证的“瑞士奶酪”模型，包含五层信任机制，旨在让人类不至于被淹没在阅读 AI 生成的 diff 中：

1. **比较多个选项。** 几个智能体尝试相同的修改，你根据通过的测试、diff 大小和引入的依赖项对尝试进行排名。
2. **确定性护栏。** Linter、类型和契约。这些是事实，而不是观点，智能体无法对类型错误进行诡辩。
3. **人类定义的验收标准。** 在代码编写之前，有人写清楚“完成”意味着什么。
4. **权限系统。** 限制智能体在没有人类参与的情况下可以触及的范围。
5. **对抗性验证。** 一个没有写入权限的独立智能体尝试破坏该实现。

![显示代码审查验证层的图表](https://cdn.thenewstack.io/media/2026/09/66e6846b-image-1024x566.png)

将足够多的不完美过滤器堆叠起来，漏洞就会停止重合。然而，在 AI 领域，六个月相当于十年，看着团队将其实际应用让我明白了该列表所缺少的东西。

## 为什么我们要审查代码

当被问及为什么审查代码时，大多数工程师会说他们是为了寻找 Bug。2013 年，Alberto Bacchelli 和 Christian Bird [研究了微软的代码审查](https://ieeexplore.ieee.org/document/6606617/)，并对 570 条审查意见进行了分类。44% 的开发人员将寻找缺陷列为他们审查的首要原因。但实际上，关于缺陷的评论仅占 14%。五年后，Caitlin Sadowski 及其同事 [研究了谷歌的九百万次审查修改](https://research.google/pubs/modern-code-review-a-case-study-at-google/)，得出了相同的结论。

代码 review 是团队构建其系统心智模型的方式。它是知识在团队中传递的方式。捕获缺陷一直以来都是较小的工作。

> “我们让编写变得廉价，而理解的成本却和以往一样昂贵。”

Addy Osmani 在 6 月份很好地指出了这一成本：“我们让编写变得廉价，而理解的成本却和以往一样昂贵。” 理解正是 review 所要保护的东西，也是唯一从未下降的成本。

## 我们已经停止阅读了

[Faros AI 的 2026 年工程报告](https://www.faros.ai/research/ai-acceleration-whiplash) 涵盖了 4,000 多个团队的 22,000 名开发人员，发现每个 PR 的事故增加了 242.7%，每个开发人员的 Bug 增加了 54%，工作重做增加了 13.8%。完全没有经过人工或智能体审查而合并的 PR 上升了 31.3%。没有人去阅读那些修改。

[DORA 的 2025 年 AI 辅助软件开发现状](https://dora.dev/research/2025/dora-report/) 报告描述了我们所处的生活张力。AI 的采用同时提高了交付吞吐量和交付的不稳定性。一个人向你展示速度图表；另一个人向你展示事故图表，两者的说法都是正确的。Gergely [Orosz 描述了](https://newsletter.pragmaticengineer.com/p/the-pulse-new-trend-concern-about) 这对仍在坚持的工程师造成的影响：

那些对代码 review 投入与以往相同精力和热情的开发人员，会觉得被向他们涌来的 [AI 垃圾](https://thenewstack.io/port-ai-builder-governance/) PR 压得喘不过气来。这既是一个团队健康问题，也是一个质量问题。

没有人开会投票决定停止审查代码。我们只是不做了。而且我们以前也并没有做得多好。Diff 并不是审查的好地方。一个审查员在五个智能体之间进行上下文切换时，凭记忆把 diff 读了一遍。

## 审查表演 (Review Theater)

显而易见的修复方法是将 AI 指向 diff。智能体编写，AI 审查，智能体修改，AI 再次审查，然后人类粗略浏览并合并。人类是唯一没有参与以该循环命名的活动的参与者。我称之为审查表演。

不过，AI 代码审查也有其用武之地。它从不疲倦，也从不匆忙。它每次都会阅读每一行，并在每个 PR 上保持相同的标准。它在凌晨 3 点也保持清醒。但它也从未见过所做的决策。它是在它所审查的代码类型上进行训练的。它永远不会告诉你不要去构建这个东西。而且它无法承担责任。

> “为 AI 擅长的事情构建工具，并保护它不擅长的事情。”

这些都不是模型质量问题。它们都是同一个问题：AI 审查看错了产物，在错误的时间，且无法访问已决定的内容。Diff 无法告诉你做出了什么决定。

我遵循的原则很简单。为 AI 擅长的事情构建工具，并保护它不擅长的事情。我们一直在做完全相反的事情。我们将机器指向了它唯一不擅长的东西——判断，却把力气活留给了人类。

## 审查的新形态

再次审视我的五个层级，其中四层回答了一个问题：它对吗？有一层回答了另一个问题：这正是我们的本意吗？没有一层问我们是否在构建正确的东西。我完全忽略了人类的判断，也忽略了发生这种判断的对话。

相同的概念以更好的顺序存活下来，并增加了一项。每一层都接管了代码 review 过去要做的一项工作。

| 层级 | 来源 | 它接管的审查工作 |
| --- | --- | --- |
| 1. 争论 (Argue) | 对抗性验证，前置。合并了多个选项的比较 | 替代解决方案 |
| 2. 捕获 (Capture) | 人类定义的验收标准，扩展到包含意图 | 知识传递 |
| 3. 规范 (Codify) | 确定性护栏，由 AI 垃圾注册表构建 | 寻找缺陷、一致性 |
| 4. 辩论 (Debate) | 新增。原本不存在的层级 | 我们在构建正确的东西吗？ |
| 5. 拥有 (Own) | 权限系统 | 把关 |

## 争论：在 PR 存在之前让智能体产生分歧

为什么要有两个机器互相交流的 UI？如果一个 AI 编写代码，另一个 AI 审查代码，PR 评论线程对于它们见面来说是一个奇怪的地方。让它们在 PR 创建之前争论，此时改变路线的成本最低。

这一层的输出是一个决策记录，不附加任何结论：提出了什么，拒绝了什么，以及原因。面对 4,000 行 diff 的人类几乎无所适从。阅读两个模型存在分歧之处的人类，将准确获得 diff 从未包含的内容，而这正是判断力发挥作用的地方。智能体无法解决的任何问题都是团队辩论的内容。

你今天就可以做到这一点。在不同的模型上运行两个审查员，编写一个捕获它们分歧点的技能，并将该记录作为 PR 的一部分进行审查。

开源工具已经涵盖了大部分内容：

* [PR-Agent](https://github.com/The-PR-Agent/pr-agent) (MIT) 通过 Ollama 在 GPT、Claude、Gemini、DeepSeek 或本地模型上运行审查。
* [Aider 的架构师模式](https://aider.chat/docs/usage/modes.html) (Apache 2.0) 在 PR 存在之前，让一个模型提出建议，另一个模型进行编辑。
* [AutoGen](https://github.com/microsoft/autogen) (MIT) 处理多智能体对话和群组编排。
* [CrewAI](https://github.com/crewAIInc/crewAI) (MIT) 提供基于角色的智能体，如果你想自己定义争论的双方。

## 捕获：在工作时记录意图和验收标准

针对智能体编写的代码的流行回答是预先编写规范。规范需要时间。它们没有反馈循环，因为它们是在工作还没有教给任何人任何东西之前编写的。实现几乎立即就会偏离它们。我们 20 世纪 70 年代就抛弃了这种模型，并称之为瀑布流。

有两个产物可以完成规范试图做的工作。**意图**回答了我们为什么要进行这项更改。**验收标准**回答了它应该如何表现。两者都需要，因为没有标准的意图无法检查，没有意图的标准无法判断。这对组合适用于单行 Bug 修复和 1,000 行功能。

它们已经存在于你的编码会话中了。每当智能体停下来问问题时，以及每当工程师反推或纠正它时，都会有人做出决定。这些就是你的验收标准，实时生成。

会话结束时不要扔掉它们。编写一个智能体技能，在决策做出时将其写下来，并发布在 pull request 上，以便审查员阅读你所决定的内容。没有人需要改变他们的工作方式，这就是它能坚持下去的原因。

审查意见有两种。“你有没有考虑过用不同的方式做这件事？”需要人类的判断。“使用 Money 类型，而不是 float”则不需要。

第二种属于 [AI 垃圾注册表，](https://docs.aviator.co/verify/concepts/invariants)即你的团队不断纠正的模式的运行列表。一旦写下来，这些模式就会成为在每次更改时检查的 [不变量](https://docs.aviator.co/verify/concepts/invariants)。

大多数团队都已经拥有这些，它们散落在 PR 评论中，被无休止地重复并存储在工程师的记忆中：

* 任何带有货币的东西都要用 Money 类型
* 禁止直接写入 users 表
* 只能使用结构化日志记录器，禁止 print
* 每个错误路径都要发出一个计数器

团队重复的每一个审查评论，都是你尚未编写的护栏。

这是成本最低的一层，也是本周开始的第一层。收集你最近的 1,000 条审查评论，并将前 20 条转化为不变量。你的 PR 历史记录已经包含了这个注册表。

## 辩论：人类参与决策

我最初的五个层级中没有一个涵盖这一点。这也是 [最让我担心](https://www.aviator.co/blog/ai-code-review-knowledge-sharing/) 的部分。

代码 review 是工程师们谈论系统的唯一预定时刻。自动化审查在捕获 Bug 方面花费的代价惊人地小。它夺走了你们的对话，而且没有什么可以取代它，因为没有人注意到它曾是一场会议。漫不经心地自动化代码 review，你就会抹杀共同的理解。

> “自动化审查在捕获 Bug 方面花费的代价惊人地小。它夺走了你们的对话。知识共享一直是代码审查的产物。”

图灵奖获得者 Peter Naur 在 1985 年的“作为理论构建的编程”中写道：“当拥有其理论的程序员团队解散时，程序的死亡就发生了。”用今天的话来说，这就是你的重组、人员流失和补员。如果一开始就没有人建立理解，你甚至不需要任何人辞职就能走到这一步。[知识共享](https://thenewstack.io/ai-code-review-cognitive-debt/) 一直是代码审查的产物。

辩论层保持了相同的 PR 和相同的工具，并改变了对话的内容。团队讨论智能体浮出水面但无法解决的决策，而把 diff 留给机器。这是这五个层级中行为改变最大的一步，所以要从小处着手。

## 拥有：决定谁来签署

模型没有声誉。它没有责任。不能问它为什么。

责任已经转移了两次。它过去属于作者，他编写代码并拥有它。然后它转移到了审查员身上，他阅读并批准了它。现在它属于编写验证更改的不变量的团队。

这改变了所有权的含义。我们的工作变成了拥有管辖代码的 [不变量](https://docs.aviator.co/verify/concepts/invariants)，并维护其背后的心智模型，而逐行审查则退出了这一范畴。明确谁拥有这些不变量以及所有权现在意味着什么，并在事故点名找你之前将其命名。
