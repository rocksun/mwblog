随着AI接管代码编写，传统逐行代码审查已失效。本文提出了一个全新的基于“决策审查”的框架，让团队聚焦于意图和关键技术决策的辩论而非代码本身，实现智能体验证、人类做决定的高效审查模式。

> 译自：[How to review AI code without reading the code](https://thenewstack.io/review-decisions-not-code/)
> 
> 作者：Ankit Jain

关于工程师是否应该[停止阅读代码](https://thenewstack.io/future-of-code-reviews/)的争论已经结束，因为我们已经不读了。

Faros AI 的[新报告](https://www.faros.ai/blog/ai-speed-trap-takeaways)显示，自 4 月份上一份报告以来，在未经审查的情况下合并的 Pull Request (PR) 数量增加了 76.3%。许多公司现在对 50% 到 80% 的 PR 进行 AI 审查。AI 审查接管了查找漏洞的工作。但它并没有接管团队辩论其决定的内容及其原因的对话，这也是我所怀念的部分。

## AI 审查无法解决的问题

大多数团队陷入了两种模式之一。他们审查每一行代码并成为[瓶颈](https://thenewstack.io/ai-code-bottleneck-myth/)，或者他们闭眼盖章（rubber-stamp），却追踪不到更改了什么以及原因。目前还没有中间地带。

> “关于工程师是否应该停止阅读代码的争论已经结束，因为我们已经不读了。”

AI 审查擅长工作中的机械性部分。它不知疲倦，能阅读每一行代码，并在每个 PR 上保持相同的标准。但它从未见过所做出的决定。它不会告诉你不要构建某样东西，也无法对结果负责。更好的模型也无法解决这个问题，因为工具在错误的时间阅读了错误产物。

正如我在“[废除代码审查形式主义，保留审查本质](https://thenewstack.io/kill-code-review-theater/)”中所写的那样，代码审查是团队建立其系统心智模型的方式。这是工程师之间关于该系统进行交流的唯一计划内时刻。将代码审查交给我们工具的团队很少注意到他们也放弃了那个时刻。

我也没有注意到。我在 3 月份提出的用于替换代码审查的[五层信任模型](https://www.latent.space/p/reviews-dead)都检查了代码。四个问：“它对吗？”一个问：“那是我们的意思吗？”没有一个问：“我们正在构建正确的东西吗？”

## 辩论决策取代了阅读代码

决策是指更改可能走向另一个方向的任何点：Token 桶还是滑动窗口、故障时开放还是故障时关闭、每个客户一个限制还是各自一个。AI 编写的 PR 中充满了这些决策，而其中几乎没有一个显示在 diff 中。

我的[审查瓶颈新框架](https://docs.aviator.co/verify/concepts/why-intent-driven-verification)也有五层。

* **挑战 (Challenge)。** 在 PR 存在之前，不同模型上的第二个智能体会对编码智能体的方案进行反推。输出记录了提出了什么、什么被拒绝以及原因，以及哪个智能体让步了。已解决的点也会保留在记录中，因为两个智能体也可以同意对某些事睁一只眼闭一只眼。
* **捕获 (Capture)。** 意图（我们为什么要进行更改）和验收标准（它应该如何表现）从与智能体的编码中[被捕获](https://docs.aviator.co/verify/how-it-works)并放入 PR 中。两者缺一不可：没有标准的意图无法检查，没有意图的标准无法判断。
* **规范化 (Codify)。** 团队不断重复的审查意见，比如“使用 Money 类型，而不是 float”，进入 [AI 废话注册表，](https://docs.aviator.co/verify/concepts/invariants)并成为不变式（invariants），即在每次更改时都会检查的常设规则。
* **辩论 (Debate)。** 人们讨论智能体浮现出来且无法解决的决策，而将逐行检查留给机器。这是唯一询问我们是否在构建正确东西的层。
* **所有权 (Own)。** 模型没有声誉，也不能被问及原因，因此由一个具名的团队对不变式和背后的心智模型负责，并对更改进行签字背书。

前三层是机器的工作，相关的工具今天已经存在。辩论和所有权是人的工作，而辩论正是缺失的那一层。

> “我们围绕的设计原则很简单：智能体验证，人类做决定。”

我们围绕的设计原则很简单：智能体验证，人类做决定。人类更擅长判断更改是否正确、权衡权衡和风险并拥有决策权。不变式是针对智能体的规则。决策是人类的判断调用，不断重复的调用最终会变成规则。

辩论也结束了关于工程师是否应该[阅读 AI 生成的代码](https://www.aviator.co/blog/stop-reading-the-code/)的争论。

我最近[采访了“Clean Code”的作者 Robert ‘Uncle Bob’ Martin](https://www.aviator.co/podcast/uncle-bob-martin-ai-clean-code)，他最近表示他不再阅读代码了。但他确实说过，人类应该对代码之上的系统负责。决策就处于那个层级。

一个讨论过决策的审查员不必逐行阅读代码来解释更改。

### 我们应该只审查规范吗？

显而易见的反对意见是，这只是把阅读转移到了其他地方，而在某个时候那个地方就是规范。我对审查规范的问题在于它似乎是倒退的。规范需要时间编写，在工作让你学到任何东西之前编写，并且在实现开始的那一刻就会偏离。

决策源于工作本身。它们是实时生成的，很短，并且每一个的存在都是因为更改可能走向另一个方向。这也是为什么“捕获”在工作完成后从编码会话中提取意图和验收标准，而不是要求任何人预先编写它们。

## 我如何看待决策审查的运作

基于我们在 [Aviator](https://www.aviator.co/verify) 上构建的内容，以下是我对它如何运作的看法。

### 决策从何而来

大多数决策已经在作者的机器上发生了，而今天我们把它们扔掉了。

* **捕获技能**从编码智能体会话中提取意图、验收标准和决策。每当智能体停下来询问而工程师做出决定时，它就会记录该决定。
* **审查技能**在提交 PR 之前运行对抗性审查智能体与编码智能体争论。它记录了他们不同意的地方以及他们是如何解决的。他们无法解决的内容就是团队进行辩论的内容。

### 决策是什么样的

此示例使用了一个向 webhook 引入添加每个安装速率限制的 PR。

![Aviator 决策 UI 的截图。](https://cdn.thenewstack.io/media/2026/10/39ad7164-image-1024x534.png)

意图是一句话：按 GitHub 安装限制 webhook 突发，这样一来，一个吵闹的客户就不会耗尽 broker，同时又不会丢弃事件或破坏其顺序。

PR 包含六个决策。仍然开放的一个是产品调用，而不是代码调用：突发限制对每个客户都是一个值。两个是被接受的风险：Redis 故障时开放，延迟事件将其有效负载保留在 broker 中。在本地 Grafana 看板上公开限制器指标成为了一个带有链接工单的后续任务。另外两个是由作者、审查员和智能体争论并解决的。

以其中一个已解决的为例：“Token 桶，而不是滑动窗口。”作者的智能体在线程中解释了它：每个事件一个 Lua 调用，而不是排序集扫描，这是在对 webhook 风暴的回放进行性能分析后选择的。持不同意见的审查员可以在同一个线程中进行反推或直接询问智能体。

这些在 diff 中都是不可见的。

### 审查员做什么

审查员的部分归结为三个步骤：

* 阅读意图和正在更改的内容。
* 遍历决策并在你不同意的地方进行辩论。
* 检查未通过的项目，然后批准。

这足以理解更改、建立心智模型并争论重要的事情，而无需逐行阅读。

每个决策都有其自己的线程，人类和智能体被单独标记，因此你知道是谁做出了哪个调用。审查员可以同意、挑战、覆盖或将决策转变为跟踪的后续行动。代码仍然在那里。你在决策指引你的地方打开它，对代码的评论会加入到相同的记录中。

### 合并后会发生什么

决策比审查更持久。

* **你团队的一周。** 你可以在不阅读 PR 的情况下，查看过去一天或一周内在代码库部分做出的关键决策。这就是知识共享代码审查的初衷。
* **智能体的记忆。** 编码和审查智能体为其接触的代码提取过去的决策，这样他们就不会重新争论已经解决的权衡。
* **坚持不懈的后续行动。** “以后再做”变成了一个链接的工单，而不是没人再读的 PR 描述中的一行。
* **来自模式的规则。** 当决策不断重复时，将其提议为不变式；只有在有人批准后它才会成为规则。

仍然有人必须签字。模型没有声誉，也不能被问及原因，因此每个经过辩论的决策都以一个同意它的具名人告终。这就是辩论将控制权交接给最后一层“所有权”的地方。
