本文探讨了将人类凭证授予AI智能体所带来的安全隐患。作者通过实际测量发现，智能体不仅继承了人类的全部权限与组身份，还导致操作归属混乱、权限范围失控以及审计日志缺失。文章最后提出了构建安全、独立的智能体身份模型的五项核心建议。

> 译自：[The audit log says my name: what an agent inherits when you hand it your credentials](https://thenewstack.io/ai-agent-credential-risks/)
> 
> 作者：Naseeb Ahmed Mian

我测量了一个AI智能体在以我的身份进行身份验证时实际持有的内容。结果证明，身份验证是一个字面量为 `user_impersonation` 的作用域字符串的 Token。授权几乎完全来自标准权限检查无法看到的群组成员身份。

在间隔一小时到达的两个生产存储之间，权限作用域相差了两个数量级，而审计覆盖率与凭证的功能成反比。智能体可以从安全数据库中删除数据的环境，反而是唯一没有审计追踪的环境。

当我测量我们自己的[无人值守智能体运行](https://thenewstack.io/incredibuild-ai-agents-sandbox-coding/)所使用的机器身份时（该身份构建得当且按资源进行了作用域划分），它在与我相同的地方失效了。

> “智能体可以从安全数据库中删除数据的环境，反而是唯一没有审计追踪的环境。”

我把自己的 Azure 凭证交给了编码智能体，这是标准做法，然后调查了它能访问的范围。答案是：在一个生产存储上有两个权限，而在另一个生产存储上有107个权限。它可以从安全数据库中删除数据的环境，是唯一关闭了审计的环境。这些都不是配置错误。当持有该凭证的唯一实体是人类时，这一切都是合理的。

## 没人称之为身份模型的设置

我们工作代码库中的11个智能体技能连接到数据库。它们的身份验证方式完全相同：

```

Bash
sqlcmd -S &lt;server> -d &lt;db> --authentication-method ActiveDirectoryAzCli -C -Q "&lt;query>"

```

该标志告诉 `sqlcmd` 向 Azure CLI 请求其缓存的 Token 并出示它。没有连接字符串，没有存储的密码，也没有属于智能体本身的凭证。当智能体运行查询时，数据库看到的是我。

工程师们将此描述为智能体“还没有身份”。它确实有一个。它有我的身份。

> “工程师们将此描述为智能体‘还没有身份’。它确实有一个。它有我的身份。”

使用借来的凭证是一种众所周知的坏做法。它会导致三个常见结果：归属感崩溃、智能体继承人类积累的任何权限，以及撤销智能体会同时撤销人类权限。我想针对一个真实的运行环境来验证这些预测。结果表明，这三个结果中有两个比表面看起来要奇怪得多。

首先，我检查了数据库记录的关于传入连接的信息：

```

SQL
SELECT login_name, program_name, host_name, client_interface_name 
FROM sys.dm_exec_sessions 
WHERE session_id = @@SPID;

Plaintext
login_name: naseeb.ahmed@<redacted> 
program_name: sqlcmd 
host_name: <my workstation> 
client_interface_name: go-mssqldb

```

这些身份字段反映了我的登录信息、我的机器和工具。无论是我键入了查询，还是智能体决定运行它，这些字段没有一个会发生变化。由于不存在第四个字段供智能体声明自己，因此智能体操作和人类操作在设计上是完全相同的。

这一点下游的所有防护栏都依赖于这相同的三个值。任何下游控制都不能以智能体为条件：不能是速率限制、不能是审批步骤，也不能是针对机器发起的语句的不同的保留策略。

> “记录对凭证是准确的，但对意图却保持沉默。”

这也产生了一个相反的问题。如果有人在六个月后对某条我键入的查询提出质疑，我将无法证明它是我的，而不是某个自动化工具执行的。记录对凭证是准确的，但对意图却保持沉默。

## 身份验证：Token 实际写了什么

我们对待身份验证的方法很简单：压根没有人设计过它。开发人员使用目录帐户和双因素认证登录一次，CLI 会缓存结果，代码库中的每个智能体技能都会获取它，而智能体身份验证只需搭便车使用人类那天早上早些时候所做的事情。它避免了存储密码，并且在你知道智能体是否有用之前，消除了配置身份的需要。

解码 CLI 为数据库连接交出的访问 Token，会发现以下声明：

```

Plaintext
aud: https://database.windows.net/
appid: &lt;Azure CLI 公共客户端 ID>
appidacr: 0
scp: user_impersonation
exp - iat: 84 分钟
groups: 37 个条目
amr: ['pwd', 'mfa']

```

其中有两项声明引人注目：

* **作用域是** **`user_impersonation`。** RFC 8693 将模拟（impersonation）定义为主体接收另一个主体的所有权利，同时保持与其无法区分。我的会话记录符合该定义。
* **amr** **（身份验证方法）声明携带了** **mfa****。** 智能体采取的每项行动都带有证明，即人类满足了双因素条件，即使该因素是数小时前针对不相关的任务完成的。

84 分钟的生命周期看起来像是一个安全边界，但其实不是。CLI 使用其刷新 Token 自动刷新，因此无人值守的运行不会在 84 分钟后停止。它只有在刷新 Token 过期或有人停用用户帐户时才会停止。

## 授权：毫无显示的检查

列出租户中每个订阅的角色分配只返回了一行：非生产订阅上的 `Reader`。

然而，群组成员身份说明了另一个故事：

* 34 个活跃的群组成员身份
* 7 个可见的订阅（包括生产环境）

与访问相关的群组反映了组织架构图：

* `<environment> - SQL Database Viewer`
* `<environment> - SQL Elevated`
* `<environment> - Resource Contributor`
* `<environment> - SQL Database Manager`
* `<environment> - Resource Viewer`
* `<environment> - Readers`

群组承载了授予实际数据访问权限的一切，并驻留在数据平面中，控制平面查询无法看到它们。通过标准角色分配检查智能体权限的安全审查员将获得单行记录，并产生 blast radius（影响范围）很小的错觉。

Token 的 groups 声明显示有 37 个条目，而目录的直接成员身份查询显示有 34 个。差异来自于嵌套群组。关于群组成员身份的两个权威答案并不一致，而数据库使用的是较大的那个数字。

其中一些成员身份是即时（JIT）管理的。查询哪些是临时的导致了一个错误：

```

Plaintext
Forbidden: PermissionScopeNotGranted 
PrivilegedEligibilitySchedule.Read.AzureADGroup, PrivilegedAccess.Read.AzureADGroup

```

那个可以在安全数据库中删除行的凭证，却无法读取其特权是永久的还是临时的。根据供应商关于 JIT 群组激活的文档，已经缓存了成员身份的应用程序在停用后可能会继续遵守它。该窗口绑定了目录记录，但它无法触及已经签发的 Token。

## 权限作用域：两个生产存储，相隔一小时

使用 `fn_my_permissions` 检查连接的主体在生产数据库服务器上实际拥有的权限，结果显示：

* **可见数据库：** 1,382 个（692 个业务层，687 个安全层）
* **业务层权限：** CONNECT, SELECT
* **安全层权限：** mssql: login error: Login failed for user ‘<token-identified principal>’

Token 拥有两个权限，安全层直接拒绝了连接。在必要的地方强制执行了读取访问权限，且没有通往敏感层的路径。智能体在这里继承了一个严格、正确的范围。

然而，使用相同的 Token 查询我们湖仓（lakehouse）上的生产分析端点显示：

* **表：** 430 个
* **权限：** 107 个（跨越读取、写入、架构定义和数据库管理）

一个身份在一小时内访问了两个生产存储，在一个存储上有 2 个权限，在另一个上有 107 个权限。如此广泛的授权不再是一份工作职责；它是一个分配给偶尔查看分析的人类的完整角色，现在却被交给了一个无监督运行数千条语句的工具。

供应商文档指出，分析端点对底层表是只读的，修改通过不同的引擎传递。在该端点上配置的安全规则控制着通过它的访问，但当另一个引擎访问它时，它们不会跟随数据。实际访问取决于路径，而不是主体。

> “代码强制执行了一种限制，而另一种则是文件中的一句话。智能体两者都读了，但两者都没有验证。”

此外，智能体在接触该端点之前读取的指令文件指出表面是只读的。智能体出示的凭证授予了 107 个权限。代码强制执行了一种限制，而另一种则是文件中的一句话。智能体两者都读了，但两者都没有验证，并且在与其真实特权相矛盾的指令集上运行。

在非生产环境中，作用域完全打开：

* **业务层：** CONNECT, SELECT, INSERT, UPDATE, DELETE
* **安全层：** CONNECT, SELECT, INSERT, UPDATE, DELETE

写入和删除权限适用于这两层。在大多数软件资产中，非生产环境允许团队成员按设计破坏事物。

## 审计追踪与误导性检查

检查数据库级审计配置返回了六个启用的规范：

```

SQL
SELECT name, is_state_enabled FROM sys.database_audit_specifications;

```

虽然数据库报告审计已启用，但查询监控接收器返回的是空结果，而不是权限错误。没有任何东西写入日志。

审计配置位于服务器资源上，而不是数据库内部。查询管理 API 表明，一个环境启用了服务器审计，并附加了语句级操作组：

* BATCH_COMPLETED_GROUP
* SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP
* FAILED_DATABASE_AUTHENTICATION_GROUP

第二个环境在服务器级别完全禁用了审计，且没有附加目标。这六个数据库规范对象是过去环境副本的残余。

内部数据库检查为一个记录零活动的纪环境报告了“已启用”。

审计覆盖率与借用凭证能做的事情成反比。生产环境受审计，而非生产环境则无人监控以节省[存储和处理成本](https://thenewstack.io/observability-can-get-expensive-heres-how-to-trim-costs/)。

这种逻辑一直成立，直到智能体取代了人类用户。智能体移除了这两种配置背后的核心假设，而没有向任何一个系统发出警报。

此外，目录身份验证下的失败登录无法到达 SQL 审计日志，因为凭证在接触数据库之前就得到了验证。保护安全层的拒绝在日志中仍然是不可见的。在高负载下，审计也是尽力而为的，超过 4,000 个字符的语句会被截断。

## 使用服务帐户时会破坏什么

我们的代码库还包含一个在 15 分钟计时器触发器上运行的无人值守智能体。它的身份为每个应用群组使用一个用户分配的托管身份，并具有显式命名的角色授权：

* Key Vault Secrets User (共享保险库)
* AcrPull (容器注册表)
* Storage Blob Data Contributor (存储帐户)
* Storage Queue Data Contributor (函数存储)
* Storage File Data SMB Share Contributor (文件共享)
* Storage Blob Data Reader (公共存储)

这种结构代表了一个正确配置的机器身份。但是，当连接到数据库时，不使用托管身份。相反，它通过在部署时设置的标准 SQL 登录名和密码进行身份验证。

数据库无法区分不同的调用者。机器身份在数据路径开始的地方停止。在数据库处，自动化智能体和人类用户一样不可归属。

这两种模型在同一个地方失效。[给每个智能体](https://thenewstack.io/databricks-electric-wasm-agentic-postgres/)分配自己的服务帐户会改变日志中的名称，但它不能解决归属问题。

## 专用身份模型需要什么

收紧权限并在非生产环境中开启审计限制了潜在的损害，但它并没有解决根本原因归属。系统仍然记录人类凭证用于自动化操作。

解决这些问题需要五个核心改变：

1. **在凭证级别将执行者与主体分离。** RFC 8693 区分了模拟 Token（仅携带主体）和委托 Token（同时携带主体和执行方）。智能体凭证应源自人类凭证并携带两个身份，以便会话日志可以记录两者。
2. **将实际权限强制执行为交集。** 智能体应该只减少访问权限，绝不能扩大访问权限。
3. **按操作而不是按主体进行作用域划分。** 权限应适用于特定操作，而不是授予广泛的、身份范围内的角色。
4. **将审计覆盖率与特权级别挂钩，而不是与环境挂钩。** 如果凭证对数据库持有写入或删除访问权限，则无论环境如何，语句日志记录都必须跟随该凭证。
5. **提供独立的撤销机制。** 切断智能体不应需要停用主要人类用户帐户。

模型上下文 Protocol (MCP) 授权规范明确禁止服务器转发客户端 Token，以确保下游服务能够验证调用者身份。命令行工具需要采用相同的标准。

## 未解决的局限性

这些发现代表了两天内在单个资产中进行的测量：

* 存储之间权限级别的差距可能源于平台默认值，而不是故意设计选择。
* 我们通过会话记录和配置的操作组评估了生产审计日志行，而不是直接批量提取用户查询日志。
* 验证哪些群组成员身份是永久的还是 JIT 的，需要在临时激活过期后对目录查询进行 diff。
* 实现每个智能体的授权流程会带来摩擦。无摩擦模型仍然很受欢迎，因为它开箱即用，但它留下了一个将机器决策归属于人类身份的审计日志。
