本文指出MCP生态中普遍存在安全凭证管理混乱的问题。研究发现超两成MCP访问策略缺失或失效，大量集成依赖长期静态个人令牌，且缺乏有效的可观测性与日志审计，企业面临极高的安全合规风险。

> 译自：[Researchers found that 1 in 5 MCP access policies came back broken or missing](https://thenewstack.io/mcp-vibe-coding-security/)
> 
> 作者：Shawn Petty

**Bob来自财务部，上个月构建了一个调度工具。** 他在周日下午向AI助手描述了需求，在晚餐前将其接入了Slack和三个内部API，到周一，三个部门就开始依赖它了。这个故事听起来很有趣，直到你检查它是运行在什么令牌（token）上的。

## **几周前发生了什么**

2026年7月28日，[Model Context Protocol（模型上下文协议）的维护者发布了一项规范更新](https://thenewstack.io/mcp-release-candidate-rewrite/)，其几乎完全围绕授权展开：发布者验证、绑定发布者的客户端凭据，以及将客户端ID元数据文档作为客户端注册的首选方式。简而言之，这是协议的维护者承认最初的信任模型在生产环境接触中并未奏效。

如果编写规范的人都需要在如此深入的阶段进行安全大修，那么Bob在周日构建的工具同样无法免责，而且Bob甚至从未听说过发布者验证。

## **三种实际的破坏方式**

工具描述不仅包含文档，还包含指令。2025年5月，Invariant Labs的研究人员展示了GitHub自身的MCP服务器如何通过中毒的公开Issue被劫持：攻击者在Issue主体中的文本被代理读取为指令，并利用受害者的令牌从私有存储库中提取数据。没有被篡改的代码，没有恶意工具，仅仅是一个没人想到要清理的描述字段。

2026年的一项名为 MCPTox 的基准测试针对45个实时MCP服务器和20个模型测试了这种模式，测得平均攻击成功率为36.5%，在表现最差的模型上成功率高达72.8%。Bob的工具具有相同的基本形态：它读取Slack消息和工单文本来决定优先处理事项。它无法区分同事的请求和伪装成请求的精心构造字符串，因为根本没人要求它这样做。

作用域（Scope）默认涵盖所有内容。常见的失败不是因为缺少权限模型，而是因为忽略了它。一个只需要只读日历访问权限的服务器，往往会请求全域的读、写和管理权限，因为教程里就是这么写的。在整个MCP生态系统中，88%的服务器需要凭据才能运行，但只有8.5%真正使用了OAuth。

大部分正在运行的工具从一开始就没有设置作用域，所以也就谈不上权限蔓延。Bob并没有坐下来选择一个作用域。他重复使用了两年前为报表看板设置的、存放在密码管理器中的管理员级API密钥，因为申请一个权限更小的密钥意味着要提交工单，而提交工单正是他试图避开的官僚主义。

静态令牌不会轮换，而且没人监控它们是否在轮换。Splunk自家的MCP Server应用在修补到1.0.3版本之前，一直以明文形式记录会话和身份验证令牌，该漏洞被追踪为 CVE-2026-20205。请注意，该厂商可是有专门的安全团队的。

据估计，野外超过一半的MCP服务器运行在很少轮换的静态API密钥或个人访问令牌上，且近一半的企业AI活动通过个人账户而非服务账户运行，这意味着执行操作的凭据属于某个人的身份，而不是系统本身。

Bob的令牌就是那个报表看板密钥。它自颁发以来一直有效；它将保持有效，直到有人记得将其吊销，而且它本月接触过什么内容的唯一记录只存在于Bob的记忆中——这可不是日志。

## **我们实际观察到的情况**

在过去几个月中，当我们自己在客户和潜在客户环境中设置自己的MCP集成时，我们发现我们审查的MCP相关访问策略中，有超过20%要么已经失效，要么完全缺失。

> 我们发现我们审查的MCP相关访问策略中，有超过20%要么已经失效，要么完全缺失。

在大多数情况下，相关的MCP服务器使用的是某人的个人令牌进行身份验证，而不是服务账户。这些令牌中没有一个有文档记录的轮换计划。没有一个服务器有接触过什么内容的日志。如果Bob的工具也在那一批中（从统计学上看很可能如此），在出现问题之前没人会知道，因为目前根本没有人监控它是否会出现问题。

## **诚实的告诫**

这并不意味着每一个“氛围编程”（vibe-coded）的集成都需要一个变更咨询委员会。Bob构建的大部分内容是无害的，将每一个周末项目都挡在正式审查流程之后，正是导致你重回没人怀念的那种18个月采购周期的原因。治理有其自身的成本，代价就是那些从未面世的好点子，因为流程吞噬了使它们成为可能的周末冲劲。

问题不在于这些工具的存在。问题在于，大多数组织目前无法区分无害的工具和那些持有通往生产环境令牌的工具，而他们正试图用那个当初导致Bob绕过他们的审查委员会来解决这个问题。

## **真正的决策**

每个平台团队现在面临的问题不是是否允许AI构建的集成。那个决定早在某个周末就做出了，而且当时房间里并没有其他人。问题在于，你是通过你自己构建的清单发现某个MCP服务器能访问什么，还是在事后通过事故报告发现的。Bob的调度工具仍在运行。它还没有造成事故，而且可能永远也不会。

但是，Bob的工具与下一个登上新闻的工具之间的区别不在于代码，而在于是否有人能说清它持有的是什么令牌、它能访问什么，以及它最后一次轮换是什么时候。
