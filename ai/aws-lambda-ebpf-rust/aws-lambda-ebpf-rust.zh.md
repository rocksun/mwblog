**在任何计算平台上，当安全警报触发时，**问题总是一样的：是哪个工作负载连接了那个端点？在什么时间？流量有多大？因此，你必须翻查日志，并祈祷它们完整。难点在于明确要寻找什么，以及去哪里找。在一台服务器上，成千上万个微虚拟机（microVM）运行几百毫秒后就会关闭。

每一个微虚拟机都属于不同的客户，运行着不同的函数。在几毫秒内，工作负载就会完成，而这几毫秒内捕获的日志是留下的唯一证人。

> “在几毫秒内，工作负载就会完成，而这几毫秒内捕获的日志是留下的唯一证人。”

这正是我们 AWS Lambda 所面临的情况。我们需要为每一个租户工作负载提供完整的网络分类账，无论其生命周期多么短暂，无论产生多少流量。这就是我们如何用 eBPF 和 Rust 构建的专用流水线取代老旧捕获系统的故事：为什么旧架构已走到尽头，以及哪些决策让新架构能够支撑 Lambda 的规模。

## 任务：一份不可篡改的记录

每个 Lambda 工作节点都是一台装满微虚拟机的裸机 EC2 实例，每一个都是独立的 Firecracker 客体。它们通过网络与 S3、其他 AWS 服务、公共互联网以及客户的 VPC 进行通信。必须有人对此进行诚实、完整的记录。

这就是网络流日志（network flow log）的作用。网络流日志有助于调查、事件响应、审计以及重构工作负载期间发生的情况。可以将其想象为系统数据记录，记录了流经系统的网络数据包发生了什么。同样的记录也会提供给网络使用情况和计量服务，这些服务对准确性的要求极高。最后，所有记录都必须为了[审计与合规](https://thenewstack.io/agentic-cicd-audit-compliance-gap/)目的进行持久化。

两个属性比其余的更重要：记录必须完整且归属正确，且捕获过程几乎不能增加网络流和平台的额外开销。

正确的归属意味着每个数据包/流都关联到它落地的微虚拟机以及产生它的租户。完整性意味着没有丢失的数据包。缺失或归属错误的记录会导致大规模环境下的计费、可观测性及监控问题。想象一下，当 Lambda 每秒处理数百万个请求时，每个微虚拟机都出现这种情况。开销很重要，原因在于它对客户不直接可见，但在 Lambda 规模下运行服务时起着重要作用。在 Lambda 的密度下，每多消耗 1MB 的内存和每微秒的 CPU 时间都会累积，从而降低利用率、运营利润以及负载下的请求处理能力。

## 为什么旧方式已走到尽头

在构建新的、由 Firecracker 微虚拟机驱动的多租户 Lambda 时，我们使用了从旧的、密度较低的单租户 EC2 时代借来的系统。它由两部分组成：一个内核级扩展，用于统计数据包并将其与每个流的租户和沙箱匹配；以及一个用户态守护进程，用于读取这些计数器、将其批处理为记录、序列化并频繁上传文件。这个解决方案在虚拟机数量较少时表现良好。然而，由于两个互斥的原因，该解决方案在 Lambda 的高密度下崩溃了。

首先是规则爆炸。iptables 对每个数据包进行大致线性的规则遍历，而每一个新的微虚拟机都会在链上堆叠更多规则。一个运行几千个[微虚拟机](https://thenewstack.io/nanoclaw-docker-sandboxes-ai-agents/)的节点，仅为了保持记录就需要超过十万条 iptables 规则。每一个数据包都要支付与主机拥挤程度及其所处槽位成比例的“税”。因此，随着主机变得越来越繁忙，数据包的记账速度反而变慢了，这与初衷背道而驰，因为整个计划是增加而非减少主机上的微虚拟机数量。

> “一份看不见一半地址空间的记录是不可信的，当有人提议为 Lambda 提供双栈 IPv6 支持时，旧方法就彻底终结了。”

第二个原因更棘手：借用的内核模块不支持 IPv6。一份看不见一半地址空间的记录是不可信的，当有人提议为 Lambda 提供双栈 IPv6 支持时，旧方法就彻底终结了，无论其性能如何提升。

## 设计考虑

在开启重写工作时，我们有几个不可妥协的设计考虑：正确的归属、显著的开销降低，以及将 IPv6 作为一等公民支持。现有的许多内部系统已经知道如何读取旧守护进程生成的 Amazon Ion 记录。如果我们能生成完全一致的字节级记录，就可以替换掉整个捕获引擎，而没有任何消费者、流日志或计量系统会注意到这种替换。

为了解决正确归属的问题，我们在微虚拟机级别实现了隔离。每个微虚拟机已经拥有自己的网络：一个带有专属虚拟设备的命名空间。该网络是其他一切组织的核心单元。

## 新系统的形态

新系统由三个协作部分组成，我们将根据其角色为其命名：

```

 一台工作节点主机

   控制平面
       |
       |  Unix 域套接字上的 gRPC
       v
   编排器 ....... 每个主机一个特权进程
       |                (加载 eBPF，配置 TC，
       |                 为每个网络生成一个标签器)
       v
   --- 每个网络（一个微虚拟机） ------------------------------

   eBPF 捕获  -->  环形缓冲区  -->  标签器  -->  Ion 记录
   在网络设备上       每个网络         Rust，
   挂载 TC 钩子        一个           用户态

   ------------------------------------------------------------
       |
       v
   与之前相同的计费 + 流日志流水线

```

最底层是[内核捕获层](https://thenewstack.io/groundcover-ai-observability-agents/)。这是一组挂载在每个网络相关虚拟 Linux 设备流量控制（tc）钩子上的小型 eBPF 程序。它们拦截数据包并为每个数据包向环形缓冲区发射一个紧凑事件。它们只是观察。这些程序中的任何代码都不能复制、阻塞、丢弃或重写数据包；实际上根本没有相应的代码路径。

中间是标签器（tagger）：一个用 Rust 编写的非特权用户态进程，每个网络一个。它清空自己专用的环形缓冲区，将原始的每个数据包事件汇总为每个流的记录，并以传统的 Amazon Ion 格式写入磁盘。最顶层是编排器，每个主机一个特权进程。它拥有所有需要提升权限的操作：加载 eBPF 程序、连接流量控制、生成和监督标签器集群。它通过 Unix 域套接字公开一个小型生命周期 API，以便控制平面可以在微虚拟机创建、分配、回收和销毁时管理标签逻辑。

解耦设计使得捕获发生在内核中，聚合发生在用户态，由每个主机上的单个进程编排一切。捕获的记录原封不动地发送给下游的现有消费者。

## 在内核中捕获，且不造成阻碍

捕获程序挂载在流量控制（tc）的 clsact qdisc 上，位于每个网络设备的入口和出口两侧。一个网络跨越两个设备，所以每个网络有四个挂载点。流量控制是一个很好的切入点，它能在下游任何组件触碰数据包之前及早看到它们。每个 eBPF 程序读取数据包并返回“继续”动作。我们从不丢弃或修改客户的数据包，我们所做的一切都不会增加明显的延迟。

对于每个数据包，程序遍历头部（以太网，然后是 IPv4 或 IPv6，再是 TCP、UDP 或 ICMP），并向该网络的 BPF 环形缓冲区写入一个固定大小的事件。事件刻意设计得很小，IPv4 事件约为 24 字节。简化版本如下：

```

/* 每个数据包一个事件，IPv4 约为 24 字节 */
 struct flow_event {
     u8  ip_version;       /* 4 或 6 */
     u8  protocol;         /* TCP / UDP / ICMP */
     u8  direction;        /* 入口或出口 */
     u8  device_id;        /* 网络的哪个设备 */
     u16 local_port;       /* "local" 始终指沙箱侧 */
     u16 remote_port;
     u32 flags_and_bytes;  /* TCP 标志位 [31:24]，字节数 [23:0] */
     u32 local_addr;       /* IPv6 为 16 字节 */
     u32 remote_addr;
     u32 received_time_ms;
 };

```

一个数据包，一个事件，一个字节计数。我们不在内核中计算数据包。标志和字节数共享一个 32 位字：高 8 位为 TCP 标志，低 24 位为字节计数。在内核中减少每个数据包的工作量就是核心目的，因此聚合是其他人的工作。

在事件离开内核之前，本地和远程字段会按方向进行归一化。无论是到达还是离开，本地始终指沙箱侧，远程始终指外部世界。这种小小的归一化意味着用户态在对流进行分组时永远不需要考虑方向，并且无论数据包朝哪个方向流动，记录读取的方式都是一样的。

> “在内核中减少每个数据包的工作量就是核心目的，因此聚合是其他人的工作。”

让我们看看 eBPF 如何在简化架构中发挥关键作用。这里的 eBPF 程序以“预留后提交”的顺序工作。每个 eBPF 程序维护一个专用的环形缓冲区来记录数据包元数据。你向环形缓冲区申请空间，原地添加事件并提交。这避免了通过系统调用复制数据，消耗极少的 CPU，并且不需要按 CPU 进行簿记。只需要一个按顺序清空它的消费者。

然而，所有这些用于解析和事件提交的复杂逻辑必须通过 eBPF 验证器。eBPF 验证器有一项关键工作：在内核加载程序之前证明其安全性，这需要严格的内存边界检查和指令限制。我们必须确保它能快速验证和加载程序，因此我们做了以下工作：首先，我们将头部解析器作为共享子程序，这样验证器只需证明一次，而不是在 eBPF 程序的每个挂载点进行内联重复证明。然后，我们将 IPv6 扩展头部遍历限制为固定数量的跳数，以便验证器确保其终止。我们还必须确保第一个 IPv4 分片之后的数据包分片报告零端口和标志，而不是向环形缓冲区事件中写入垃圾数据。我们还必须确保分段和接收卸载（GSO/GRO）产生的合并超级数据包的字节计数被正确处理。错误的端口或错误的字节计数会产生虚假的日志条目，因此我们在源头保持记录的真实性，并与旧系统保持字节级一致。

然而，我们并不完全信任验证器作为正确性的唯一来源，因为这段代码生成的记录对于计费、合规和审计系统至关重要；每个 eBPF 程序都用 C 语言编写，并在每次构建期间通过形式化模型检查器（CBMC）进行检查。其工具链断言，除其他事项外，事件结构的字节布局与每个已挂载程序所期望的一致。结构体静默偏移一个字节这类 bug 会静默损坏它接触到的每一条记录，直到有人需要日志那天才会发现。

## 基于第一性原理确定环形缓冲区大小

环形缓冲区是内核生产者和用户态消费者共享的东西，其大小是一个真正的权衡。太小会导致在突发流量下丢弃事件，这意味着丢失记录，这会在流量最关键时在日志中留下缺口。太大则浪费内存，并且你必须为宿主机上的每一个环形缓冲区支付这种浪费。

所以我们没有猜测。我们根据每个微虚拟机的数据包速率导出下限；例如，如果上限是每秒 100,000 个数据包（每个方向）。我们大约每 100 毫秒清空一次环。将峰值速率乘以清空间隔，再乘以事件大小，再乘以两个方向：

```

环字节数 =~ 62,500 pps x 0.1 s x ~24 字节 x 2 个方向
            =~ 300 KB

```

环形缓冲区 API 要求大小为 2 的幂，因此设计默认为 512 KiB。这是在客体自身最大数据包速率下，两次清空之间不会溢出的最小缓冲区。换句话说，下限确保了即使客体试图这样做，它也无法超过记录器的处理能力。大小是每个网络可配置的。在当前运行的部署中，我们在完成每工作负载的最佳值调优之前，配置得比该下限更充裕，大约在几 MB 级别。需要捍卫的是下限，而下限来自硬性的系统限制，而不是猜测。

清空节奏还有另一个好处：唤醒用户态进程并非免费，成千上万个不断唤醒的进程会消耗大量 CPU。因此内核决定何时进行干预。它检查环的满载程度，并且仅当环填充率超过 1% 时才强制唤醒。低于该值，它保持安静，让事件堆积。用户态这边，读取频率不会超过每 100 毫秒一次。一个安静的流会一直静止，直到下一次清空，基本上零开销。繁忙的流会触发那个 1% 的阈值并几乎立即被读取。没有任何东西处于固定计时器上，所以两种情况都不会因为时序错误而出现问题。

## 在 Rust 中进行清空与聚合

标签器将原始的每个数据包事件转换为流水线存储的每个流的记录。每个网络一个标签器，以非特权身份运行。

我们选择 Rust 是出于枯燥、实际的原因。在这种密度下，宿主机上运行着数千个此类进程，每个进程都持有少量必须正确的状态。垃圾回收语言（GC）会导致停顿时间和内存随负载增长，而在错误位置的停顿可能会导致记录丢失。Rust 为我们提供了可预测的内存，没有垃圾回收器，且编译器直接拒绝构建那些可能导致归属错误的整类 bug。每个标签器仅占用几百 KB 的 RAM，预算约为 1 MB。这就是为什么每台主机可以负担数千个标签器的原因。

在内部，它是一组在单线程异步运行时上协作的小型任务。一个任务读取环，另一个拥有流状态，第三个写入包裹。我们唯一隔离到阻塞池的工作是那些确实会阻塞的操作：接收环描述符和序列化 Ion，因为 Ion 编写器不是异步的。它通过 epoll 读取环，因此在没有任务时休眠，有任务时唤醒。

随着事件的到来，标签器将它们放入一个以设备、五元组和租户归属句柄为键的流映射中。该句柄来自控制平面在流激活时移交的元数据。匹配的事件累积字节数、数据包计数和 OR 运算后的 TCP 标志。分组发生在读取事件时，因此热路径始终是查找和加法。

归属究竟从何而来？这是因为映射是记录最重要的属性。内核事件本身不携带身份，它也不需要。每个网络都有自己专用的环和设备，所以数据包在标签器看到它们之前就已经被分开了。标签器并不是从某种共享的消防水带中提取某一个租户的数据包。它读取的流始终只属于那个租户，因为为它提供数据的环和设备只属于该租户。

每分钟一次，在与旧系统替换时间对齐的固定间隔上，标签器将已完成的流序列化为 Amazon Ion 记录，格式与旧守护进程产生的 schema 完全相同。每个文件被写入一个临时名称，刷新到磁盘，然后重命名到位。读取者看到的是完整的记录或什么都没有，绝不会是损坏的记录。一个单独的刷新循环（启动时带有一点随机抖动，以防止数千个进程在同一瞬间写入）即使在微虚拟机静止后也会清空已完成的流。一个静止的工作负载仍然会留下完整的记录。

由于记录与旧格式字节兼容，整个下游世界无需任何修改即可继续工作。当我们并排运行这两个系统时，我们可以记录对记录地比较它们的输出，并确认它们是一致的。这差不多是最直接的完整性检查了。

## 由文件描述符强制执行的最小特权

这是我最喜欢的设计部分，因为它使用了一种古老的 Unix 技巧，几乎不花什么代价就能获得强大的安全属性。

执行实际数据包工作的进程（数千个标签器）不持有任何提升的特权。它们不能加载 eBPF 或触碰流量控制。它们甚至不能自己打开环形缓冲区映射。所有这些权力都集中在一个地方：每主机的编排器，甚至它也只是以它需要的两种能力运行，而不是作为 root 用户运行。

> “通过套接字传递文件描述符是一个几十年前的 Unix 特性，它让我们能够让数千个进程保持无权状态，同时将特权集中在一个小地方。”

那么一个非特权的标签器是如何读取它不被允许打开的环形缓冲区的呢？编排器将其打开，并通过 Unix 域套接字将打开的文件描述符传递给标签器，使用内核的 SCM_RIGHTS 机制在进程间传递描述符。标签器获得了一个可以直接使用的环句柄，除此之外什么都没有。它从不需要，也从不需要权限去创建一个。整个系统的特权面就是每个主机上的一个小进程。接触客户流量的数千个进程几乎是我们能做到的最“无权”的状态。

## 生命周期 API 以及为什么它有两扇门

微虚拟机不断出现和消失，因此控制平面需要一种方式告诉编排器何时开始和停止记录网络。它通过 Unix 域套接字上的 gRPC API 实现这一点，包含少数几个方法：创建流集合、激活流、回收流、销毁流，以及健康检查。

开始记录的过程分为两个调用，一个是重型调用，一个是轻型调用，这种分割是有意的。“Create”（创建）是一个重型调用，昂贵的路径：它加载并挂载 eBPF 程序，配置流量控制，并生成标签器。挂载到网络设备需要一个主机上所有此类操作都要争用的内核锁，因此当主机同时启动许多网络时，我们将这些操作批处理，以防止所有人都在那个锁后串行化。“Activate”（激活）是一个轻型调用。当它运行时，机器已经存在，所以它只是移交客户元数据并将流切换到稳态记录。其延迟预算很紧：p90 下低于 2 毫秒，p99.9 下低于 10 毫秒，与它取代的系统基准相匹配。

## 诚实的权衡：杀死它，还是复用它

并非每个决策都是完美的。这对任何构建类似系统的人来说都是教训。

原始设计有一个严格的回收网络规则：总是销毁标签器并生成一个新的。从正确性的角度来看，理由是无懈可击的。一个全新的进程不可能携带前一个租户的过期元数据，因此一个租户的流落入另一个租户记录中的可能性在结构上是不可能的。杀死它，不要试图清理它。我们确信这是正确的选择。

生产工作负载下的现实向我们表明，随着网络周转，数千次 fork 和 exec 一个新进程在规模化时变成了 CPU 尖峰的真正来源。最安全的选择表现为火焰图。因此，交付的系统需要一个新的旋钮。复用其网络的工作负载可以在回收后复用标签器，牺牲了一点结构上的保证，换取了少得多的 CPU 抖动。希望获得严格、跨租户证明行为的工作负载则不开启该旋钮。我仍然认为严格版本是更正确的设计，但机群的 CPU 预算不允许这样做。

## 它为我们带来了什么

从杀死旧设计的那个数字开始：一台主机需要超过十万条防火墙规则来为两千个微虚拟机保存记录，而每增加一个微虚拟机都会堆积更多规则，对每个数据包造成额外负担。eBPF 版本将那种线性规则遍历替换为恒定时间的映射查找，其成本不会随着主机填满而上升。线性税消失了。这使得密度目标（每主机大约增加一倍的微虚拟机）触手可及，且没有每数据包税带来的突发时间间隔。

其余的回报源于我们开始时设定的约束：

1. 对旧工具不可见的 IPv6 流像其他流一样被记录，因此日志覆盖了整个地址空间而不是一半。
2. 每个标签器在几百 KB 的 RAM 预算内运行，相对于大约 1 MB 的预算，小到足以让每台主机运行数千个。
3. 将流激活为稳态记录在 p90 下保持在 2 毫秒以下，在 p99.9 下低于 10 毫秒。
4. 捕获层是仅观察模式并经过形式化验证，触碰客户流量的进程不持有特权。我们在缩小可能损坏记录的受信任特权面的同时，增加了显著的可视性。
5. 输出记录与旧格式字节完全相同，因此每个下游流日志和计量消费者无需更改即可继续工作。

## 值得带入其他系统的教训

其中一些教训远不止适用于 Lambda。Kubernetes Pod、边缘运行时、人们现在为了[运行 AI 代理](https://thenewstack.io/perplexity-portable-computer-nvidia/)而启动的沙箱。无论你在哪里拥有许多租户共享一台主机并且需要对其流量进行可靠记录，同样的模式都适用。

首先：从热路径之外进行观察。一旦你的记录逻辑位于数据包转发的在线路径中，其成本就变成了对每个数据包的税，而当记录最重要时，这种税最为沉重。同样的压力促使团队丢弃或采样数据，而审计追踪无法在采样中生存。eBPF 让你可以从侧面观察并发射一个紧凑的事件，而所有昂贵的事情都发生在其他地方。

第二：根据真实情况调整缓冲区大小。一个由实际速率限制乘以实际清空间隔确定的缓冲区大小，是一个你在审查中可以捍卫的数字，它让你能够承诺在突发流量下不会丢弃事件。我们本可以选择 512 KB，因为它感觉差不多，而且它可能在大多数时间都能工作，直到遇到它无法容纳的某个突发流量。

第三：在捕获点保持租户分离是我会最强烈坚持的部分。给每个租户自己的环和自己的设备，流就永远不会触碰，所以你标记的是干净的流量，而不是事后猜测。

第四：古老的原语被低估了。通过套接字传递文件描述符是一个几十年前的 Unix 特性，它让我们能够让数千个进程保持无权状态，同时将特权集中在一个小地方。

最后一个，也是最容易出错的地方：当你换掉引擎时，保持螺栓连接模式。字节级相同的输出让我们能够零下游迁移地替换整个捕获路径，并为我们提供了一种记录对记录的方式来证明新系统看到了旧系统所能看到的一切。
