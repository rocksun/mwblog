**一半的企业AI部署**在峰值负载下未能达到其自身的延迟目标。这是[Akamai的2026年AI推理现状报告](https://www.akamai.com/lp/the-state-of-ai-inference)得出的核心结论。该报告调查了200名AI从业者，发现82%的组织表示其最关键的用例要求端到端响应时间在500毫秒或以下。总共有64%的组织目前要求其最重要的用例端到端响应时间低于250毫秒，然而，50%的部署在峰值负载下未能满足这些延迟需求。

我的同事 Ari Weil 领导我们云计算业务的产品营销并负责这项研究，他[总结了这些发现](https://www.akamai.com/blog/cloud/ai-study-organizations-struggle-maintain-latency-scale)： “企业AI的蜜月期已经结束……他们正撞上延迟之墙。”

## **代理工作流并非“单次往返”**

延迟问题源于代理的工作方式。这是一个迭代过程，有点像国王派遣骑士、特使和信使去处理王国的事务。有许多往来，而不仅仅是一个人完成单次往返。

例如，当一个基于 LangChain、CrewAI 或 Pydantic AI 等框架构建的代理收到用户请求时，它可能会展开成数十个顺序操作，如推理调用、工具调用、API查询或上下文检索。然后，代理可能会执行另一次推理调用，以决定如何处理刚才返回的结果。这些必须跨越广域网才能到达集中式数据中心的每一个操作或“跳转”（hops）都会增加延迟，而一个包含50次跳转的链条本身就可以将传输时间乘数倍，无论模型生成 token 的速度有多快。

事实上，在[2025年11月发布于 arXiv 的一篇论文](https://arxiv.org/abs/2511.00739)中，研究人员发现 CPU 端的处理可能占代理工作负载总延迟的90.6%。换句话说，你的 GPU 可能在几百毫秒内完成了一个推理步骤，但随后它可能不得不等待远端数据中心 CPU 的额外工具调用运行。这就是导致 GPU 空闲时间激增的原因。

> “更多的 GPU 容量对此毫无用处。你无法通过暴力手段摆脱等待状态。”

更多的 GPU 容量对此毫无用处。你无法通过暴力手段摆脱等待状态。这是业界一直回避的谈话部分，主要是因为“购买更多 GPU”比“弄清楚你的 CPU 密集型工作到底在哪里执行，以及为什么它离所需数据那么远”更容易建议。

## **我们需要新的基准测试来解决延迟问题**

迫在眉睫的延迟之墙之所以让团队猝不及防，原因之一是他们没有为代理工作负载关注正确的基准测试。大多数 LLM 服务基准测试测量的是单台机器上的每秒 token 数和 GPU 利用率。如果工作负载确实在单台机器上（即一个模型回答一个提示词），那很好，但代理工作负载并非如此。这些基准测试无法解决这样的代理响应：例如，制造一个50跳的链条，跨越广域网4次以到达4个独立的服务。

> “预演（Staging）可能通过了基准测试，因为它测试的是模型，但生产环境测试的是整个链条，包括你的服务引擎从未设计过要看到的每一个跳转。”

这就是差距所在：预演可能通过了基准测试，因为它测试的是模型，但生产环境测试的是整个链条，包括你的服务引擎从未设计过要看到的每一个跳转。

## **500毫秒的围墙不是一个软目标**

由于代理进入生产环境的速度快于大多数团队架构演进以支持它们的速度，这个问题正在大规模显现。[LangChain的2026年代理工程现状调查](https://www.langchain.com/state-of-agent-engineering)涵盖了超过1300名专业人士，发现57.3%的组织现在有代理在生产环境中运行，高于一年前的51%。*在这些构建者中，延迟已成为仅次于输出质量的第二大生产障碍。*

这对应用团队来说是一个严重的问题。Akamai 调查中提到的500毫秒阈值不是团队可以承受失败的性能目标。对于实时客户交互或实时合规性检查，这500毫秒决定了应用程序是否有效。

## **我们以前解决过这个问题**

对于任何在1999年为网络进行构建的人来说，这感觉很熟悉是有原因的。Akamai 的存在正是因为一个几乎相同的问题。麻省理工学院的研究人员 Tom Leighton 和 Danny Lewin 创立了这家公司，以回应 Tim Berners-Lee 提出的挑战：解决媒体开始称之为“万维网等待”（World Wide Wait）的问题，即因将每个请求拉回到少数几个集中式服务器而产生的巨大延迟。当1999年《星球大战前传：魅影危机》的预告片导致互联网上的网站崩溃时，罪魁祸首是距离：数以百万计的浏览器在同一时刻都在寻找同一个遥远的源服务器。解决方案是将内容转移到距离请求者更近的数千个点，而不是试图构建一个更快的源。

代理 AI 正在撞上同一堵墙，只是换了一个载体。如果你谈论的是彻夜运行批量作业，AI 在集中式推理上运行得很好。但今天基于代理 AI 构建的应用程序是坐在实时交易中的实时循环，而代理延迟的解决方案是分发。我们需要的不是在中心扩展 CPU 和 GPU 机架，而是将代理执行移动到模型的工具、上下文数据和用户实际存在的地方。

## **代理 AI 需要分层架构，而不是更大的数据中心**

在实践中，代理 AI 需要一种分层架构，包括集中式核心、区域 GPU 集群和边缘 CPU。

* 集中式核心——非常适合在大上下文窗口上进行繁重推理，在这种情况下，往返大型模型的重要性不如模型的原始能力重要。
* 区域 GPU 集群——越来越多地建立在 NVIDIA 的 Blackwell 平台等硬件上，非常适合本地化推理，因此最繁重的计算位于需求实际集中的地方附近。
* 边缘 CPU——速度的关键组件。这是工具执行、编排和上下文检索的连接点，因为这些是在链条中最常发生的步骤，并且从位于它们调用的数据和 API 旁边中获益最多。

我们围绕这种分层框架构建了 Akamai 推理云。这与我们 AI 网格编排器（AI Grid Orchestrator）背后的分发逻辑相同。我们将 CPU 密集型的编排和工具调用路由到边缘，并将 GPU 密集型的推理保持在合理的地方，无论是区域性的还是集中式的。

## **在承诺之前你需要要求什么**

好消息是你不需要在第一天就将所有工作负载分发到边缘。但在承诺生产架构之前，你应该知道代理的几十个跳转中哪些对延迟敏感，哪些不敏感。然后为每一个跳转建立一个明确的性能预算。

> “那些将其视为 GPU 采购决策的团队将在六个月后回到这里，盯着同样的四秒响应时间，想知道为什么更多的计算没有帮助。”

我的建议是：在签署大规模推理部署之前，要求你的基础设施做到四件事：

1. 跨区域和提供商的可移植性
2. 吸收峰值负载而不崩溃的弹性
3. 数据本地化，这样工具调用就不需要跨越海洋来获取它们所需的上下文
4. 一个你已经在生产流量而非预演流量下测试过的性能预算。

现在解决这个基础设施决策的团队，将是当基准测试环境过渡到真实用户时，其代理依然能工作的团队。那些将其视为 GPU 采购决策的团队将在六个月后回到这里，盯着同样的四秒响应时间，想知道为什么更多的计算没有帮助。
