Meta 于 8 月 5 日[发布了 Muse Code](https://thenewstack.io/meta-muse-code/)，这是其首款 AI 编程代理，基于全新的 Muse Spark 1.2 模型构建。Mark Zuckerberg [表示](https://siliconangle.com/2026/08/05/meta-takes-anthropic-openai-first-ai-coding-agent-muse-code/)，它能够处理“跨大型存储库的完整软件工程任务”，并且大型任务会“分发给并行工作的独立子代理”。

Meta 的 AI 负责人 Alexandr Wang 对此策略直言不讳。他在接受 [CNBC](https://www.cnbc.com/2026/08/05/meta-debuts-muse-code-to-take-on-anthropic-and-openai-.html) 采访时表示，其差异化优势在于“比 Claude 或 Codex 更实惠”。

标准的 muse-spark-1.2 [运行费用](https://dev.meta.ai/docs/muse-code/?team_id=2306091636825706&project_id=1082575054202150)为每百万输入 token 1.25 美元，每百万输出 token 4.25 美元。作为对比，我运行 Claude Code 所使用的 Anthropic 模型 Fable 5，标价分别为 10 美元和 50 美元。此外还有一个“贡献者”层级，价格为 0.10 美元和 0.20 美元，Wang 称这“便宜了 10 倍以上”。

他是对的，但请留意细则。“贡献者”意味着“您的内容可能被用于产品改进”。您的代码、提示词、会话，所有这一切都将成为 Meta 的训练数据。而且该层级并非隐藏在设置菜单深处，而是默认选项。

因此，我测试的问题是 Wang 没有说完的后半句。确实更实惠，但实惠是以何种质量为代价的？我给 Muse Code 和 Claude Code 安排了相同的三个编码任务，并跟踪了每一个 token。

## 设置 Muse

设置过程很快。一条 curl 命令即可安装 Muse，通过常规的 Meta 账号登录，但在绑定银行卡之前它拒绝运行。（[Kimi 上个月也对我用了同样的一招](https://thenewstack.io/kimi-k3-fable-coding-benchmark/)。这些公司愿意把代码库托付给 AI，却不愿让你直接通过发票支付。）价格表就在添加卡的页面上，我就是在那里发现了默认层级。

我在“贡献者”模式下进行了测试，因为我的数据不值得保护。测试存储库是公开的开源代码。如果您的代码是私有的，并且您切换到标准层级，那么我花费 6 美分完成的任务，您预期的账单可能接近 2 美元。

## 测试过程

我使用了 [dayjs](https://day.js.org/)，这是一个 2KB 的 JavaScript 日期库，是 Moment.js 的标准替代品。它是真正的生产代码，拥有 773 个测试用例。日期计算如果出错，往往直到账单算错时你才会发现。

Muse Code（版本 0.1.0）运行的是 Muse Spark 1.2 贡献者模型。Claude Code（版本 2.1.2）在 Claude Max 计划下运行 Fable 5。提示词完全相同，每次测试都使用全新的文件夹和会话，因此代理是唯一的变量。以下是我进行的三个测试：

* 带有三个隐藏 bug 的调试测试
* 多文件重构
* 开放式推理测试

对于每个测试，我都记录了时间、token 消耗和成本。

## 测试 1：Bug 搜寻

**提示词：** *这个 JavaScript 库的测试套件无法通过。运行 npx jest 查看失败情况。找出导致失败的 bug，修复它们，并使整个套件通过测试。不要修改或删除任何测试文件，不要跳过测试，除了修复 bug 外，不要更改任何公共行为。解释您发现的每个 bug 以及您的修复方案。*

在测试之前，我在库中埋下了三个微妙的 bug——那种粗心重构后留下的隐患，并清除了 git 历史记录，这样两个代理都无法通过对比差异找到答案。这些 bug 导致 773 个测试中有 17 个失败。

两个代理都找出了全部三个 bug，并用库原本的代码修复了它们。包括日期差值的四舍五入错误、一个插件中反转的边界检查，以及一周开始计算中的偏移错误。两者都正确解释了每个 bug。Muse 甚至在总结中将其称为“注入的 bug”。它知道自己正在接受测试。

不过，修复我设置的三个 bug 并不是全部测试。在我的 Mac 上，还有两个不相关的测试也失败了，它们是带有预设时区假设的旧测试，每个代理都必须决定如何处理非自己导致的失败。Muse 识别出了它们，解释说它们不是真正的 bug，并没去动它们。这很合理。Claude 则找到了一种方法，在不触碰测试文件的情况下，通过更改设置使其通过。Claude 完成时，整个套件运行正常。两个代理都修复了我的 bug，但只有 Claude 留下了完全通过测试的套件。

Muse 用时 2 分 58 秒，消耗 225 万 token，花费 2 美分。Claude 用时 5 分 31 秒，消耗约 146 万 token，花费 3.02 美元。

## 测试 2：重构

**提示词：** *src/index.js 文件包含了该库的核心：日期解析、Dayjs 类及其所有内联方法，共 467 行。请重构它以提高可读性和结构：将解析逻辑及所需的辅助逻辑移动到新的专用模块中，并将大型方法分解为更小的重点功能函数。不要更改任何行为或公共 API。所有现有测试必须仍然通过（运行 TZ=UTC npx jest 进行检查），并且 ./node_modules/.bin/eslint src/* 必须报告没有错误。*

两个代理都达标了，全部 773 个测试通过，lint 错误为零。但它们构建的内容完全不同。

Muse 提取了一个新模块（一个 25 行的解析文件），并将大方法分解为原文件内的更小辅助函数。“巨石”代码从 467 行减少到 465 行。Claude 提取了三个模块（分别用于日期解析、本地化处理和格式标记），核心文件从 467 行减少到 353 行。Claude 在移动任何内容之前还检查了测试套件导入了哪些内部文件，因此它移动的任何内容都不会意外破坏测试。

两次重构都通过了。一个读起来像是代码库经过了整理（Claude），另一个读起来像是代码库被打扫了一下（Muse）。

Muse 用时 1 分 44 秒，消耗 118 万 token，花费 1 美分。Claude 用时 6 分 9 秒，消耗约 44.8 万 token，花费 2.40 美元。

## 测试 3：推理测试

**提示词：** *该库的测试套件在运行 TZ=UTC npx jest 时通过，但在其他时区运行（例如 TZ=America/New_York npx jest 和 TZ=Australia/Sydney npx jest）时会失败。调查原因，决定正确的修复方案，并使整个套件在任何时区都能通过，且不削弱测试覆盖率，也不改变库的公共行为。解释您的推理以及您选择的方法的权衡。*

这个测试没有唯一的正确答案，这就是我喜欢推理测试的原因。该库的测试在某些时区通过，在其他时区失败（纽约失败 2 个，悉尼失败 3 个，伦敦均通过）。每个代理在决定修复什么之前都必须弄清楚原因。两者都做对了。

失败的测试编写得很糟糕，因此两者都重写了它们以使其能在任何地方运行。在此过程中，两个代理都各自发现了一个库中真正的 bug——一个夏令时错误，该错误在某些时区显示了错误的时钟时间。两者都发现了它，并且都修复了它。

然而，它们在如何修复编写糟糕的测试上存在分歧。每一个都在不知道对方存在的情况下，明确否定了对方选择的方法。Muse 重写了测试，用 Moment.js 来检查 dayjs。Claude 保留了原始的预期值，并使测试在内部保持一致，理由是固定值可以捕获两个库都出错的情况。两种立场都是可以接受的。

你也可以从模型完成任务的方式看出质量差异。Muse 删除了一项它认为多余的断言，并留下了一些自己的修改作为无效代码。Claude 的修改很精准，并且在要求的基础上，它还运行了套件的完全覆盖检查。我自己验证了两个代理在七个时区（包括它们都没测试过的时区）的工作成果。两者都经受住了考验，773 个测试在任何地方都能通过。

Muse 使用了 552 万 token，花费 3 美分（我没记录这次运行的时间）。Claude 用时 9 分 8 秒，消耗约 129 万 token，花费 3.99 美元。

## 测试结果

| 指标 | Muse Code | Claude Code |
| :--- | :--- | :--- |
| Bug 搜寻 | 3/3 bug，套件通过 | 3/3 bug，套件在任何时区通过 |
| Bug 搜寻数据 | 2m 58s, 2.25M tokens, $0.02 | 5m 31s, 1.46M tokens, $3.02 |
| 重构 | 达标，1 个新模块 | 达标，3 个新模块 |
| 重构数据 | 1m 44s, 1.18M tokens, $0.01 | 6m 9s, 448K tokens, $2.40 |
| 推理 | 发现隐藏 bug，留下无效代码 | 发现隐藏 bug，修改精准 |
| 推理数据 | 时间未记录, 5.52M tokens, $0.03 | 9m 8s, 1.29M tokens, $3.99 |
| 总 token | ~8.9M | ~3.2M |
| 总成本（计费价格） | $0.06 | $9.41 |

关于该表格的几点说明。Muse 的成本是贡献者层级的价格。按照 Meta 的标准费率，相同的三次运行成本大约为 2 美元，也就是便宜了 5 倍，而不是 150 倍。Claude 的成本是 Max 订阅中 API 的等效价格。

这仅仅是三个数据点，而非基准测试。

### 我的真实看法

在正确性方面，两个代理打平。发现了相同的 bug，通过了相同的要求。在最难的测试中，两者都独立发现了一个无人告知的真正库 bug。但是，没有人仅仅根据表面的正确性来评价工程师的工作，所以我不能说这两者相等。

深度和润色也很重要，这就是它们分道扬镳的地方。Claude 的重构重组了代码库，而 Muse 的只是清理了它。Claude 彻底完成了 bug 搜寻，而 Muse 只是达到了够用的程度。Claude 在推理测试中的修改是精准的，而 Muse 则留下了无效代码。这些都没有在通过/失败栏中显示出来，但当一个了解代码库的人阅读差异报告时，所有这些都会显现出来。

> 你节省的 token，最终都会以审查时间的方式加倍奉还。

这就是折扣带来的问题。是的，Muse 便宜得多。但在这个实验中，每一个 Muse 的运行结果看起来表面上是正确的，但需要专家来判断其底层是否真正完成了工作。如果你运行它却无法信任结果，即使测试是通过的，那又有什么意义呢？你节省的 token，最终都会以审查时间的方式加倍奉还。

Wang 关于实惠性的说法成立，甚至更多。Meta 没有大声说出来的是：这种实惠为你换来的是“正确但不够彻底”的工作成果。

Muse Code 是全新的。我发现的差距是可以弥补的那种，而且 Meta 以前也弥补过差距。当下一次模型出现时，我会重新运行这些测试。
