**差异（Diff）并不是证据，它只是意图的声明。**

测试通过了。审查完成了。改动上线了。然后有人反馈应用运行缓慢，或者回答错误，甚至是两者皆有。你打开差异对比，你的辅助工具指向了它修改的函数，并给出一个合理的推测原因。

听起来很有道理，但可能并非事实。

这就是AI功能所暴露出的可观测性鸿沟。[Dynatrace的2026年SRE与平台工程状态报告](https://www.dynatrace.com/resources/the-state-of-sre-and-platform-engineering-17401248/)（调查了全球919位企业领导者）发现，虽然77%的平台工程团队在部分服务中嵌入了可观测性，但仅有40%实现了跨所有部署的全面集成。当你的服务是确定性时，这个鸿沟尚可控。但面对AI代理，它就变成了一种负债。

> 传统服务会以显著的方式失败……而AI代理会静默失败。它返回200状态码，它通过了忠实度检查，但客户收到的依然是错误答案。

传统服务会以显著的方式失败。比如500错误、延迟激增、依赖项停止响应。AI代理则会静默失败。它返回200状态码，通过了忠实度检查，而客户收到的依然是错误答案。

你无法为“错误”设置告警。你需要来自运行系统的证据——对于AI功能而言，这意味着不仅仅是请求追踪和错误率。

首先要找到那个请求。

## 一次发布，两种症状

假设你运行一个针对产品文档的支持代理。客户询问如何配置版本2026.3中的导出功能。你的编码助手帮忙重写了文档查找逻辑。CI通过了，现有的评估也通过了。

部署后，回答变慢了，并且部分答案描述的是旧版本产品。

从一个受影响的运行记录开始。你需要获取它的发布版本、检索配置以及功能标志状态，因此这些信息需要作为根Span（Root Span）的属性在Span开始时设置，而不是稍后从部署日志中重构。然后将该运行记录与改动前类似问题的运行记录进行对比。

对于代理而言，这意味着轨迹（Trajectory）：按顺序记录的每一次模型调用和工具调用，包括参数和结果。[分布式追踪](https://opentelemetry.io/docs/concepts/signals/traces/)将这些记录为Span，并通过上下文传播跨服务边界将它们串联起来。

这是一个简化后的运行示例，其评估结果被单独关联。

```

# 示意性遥测数据，非捕获的事故。

# 名称、ID、时序和标签均为虚构，非标准模式。

# 仅显示执行顺序中的部分Span，省略了其他工作。

trace: example-run-a | session: example-session-7 | release: 2026.9.2

requested.product_version: "2026.3"

agent.run                                         12.4s

  model.choose_tool                                1.0s

  tool.search_docs                                 0.9s

    args: {query: "configure export", product_version: null}

  tool.search_docs                                 0.8s

    args: {query: "configure export", product_version: null}

  tool.search_docs                                 0.9s

    args: {query: "configure export", product_version: null}

    returned.doc_versions: ["2024.1", "2024.1", "2023.9"]

  model.generate_answer                            8.1s

linked_evaluation:

  trace: example-run-a

  faithfulness: pass

  requested_version_answered: fail
```

有两个点需要排查：重复搜索，以及空的版本过滤器。

## 检查重复工作

三次相同的搜索花费了2.6秒。追踪记录显示了症状，但没有解释原因。

但看看它们之间是什么？什么都没有。顶部有一个 *model.choose_tool* 的Span，在第二次和第三次搜索之间没有任何模型调用。模型并没有请求这些重试。是工具运行框架中的某个部分在执行：即运行工具、处理重试并管理上下文的代码。如果在每次搜索之间有一个 *model.choose_tool* 的Span，则意味着相反的情况：模型一直在请求同一个工具，这是一个提示词（Prompt）或工具描述问题。同样的症状，需要打开不同的文件进行排查。

这并不代表重试本身是错误的。阅读重试策略，然后阅读工具结果。来自搜索后端的200状态码可能携带空的命中列表，或者返回的每个命中项都在相关性阈值之下，针对这种情况进行重试是合理的。

无论如何，生成调用占据了更大的时间份额，长达8.1秒。将其输入Token和持续时间与类似运行记录进行对比。如果框架将所有三次结果集都附加到了上下文中，那么重试过程就会膨胀提示词，你为此付出了双倍的代价——在延迟和Token消耗方面。在将变慢归咎于发布之前，请检查下游服务和流量。

将此过程带入IDE中？限制问题范围。将服务、发布版本、时间窗口和追踪ID提供给助手。让它将改动的代码路径与受影响追踪中的依赖调用对齐，然后将证据支持的内容与它假设的内容区分开来。

调试一个执行三次相同数据库调用的结算服务也是同样的工作流。你不需要构建一个AI代理来使用这种方法。

## 基于事实的回答仍可能出错

现在阅读答案。

在这个例子中，它准确地重复了检索到的文档内容。*忠实度（Faithfulness）*通过了，或者根据你所用工具的术语体系，称为*基于事实（Groundedness）*。

*但客户收到的依然是错误版本的说明。*

无论你称之为忠实度还是基于事实，该指标仅告诉你答案是否由你提供的来源支持，但它无法说明这些来源是否是正确的。

接下来显而易见的动作是使用检索评估器。但它依然捕捉不到这个问题。评估器衡量的是检索到的上下文与查询的相关性，而2024.1的导出说明对于“配置导出”确实是相关的，它们只是对于所询问的版本无效。这些文档与查询相关，但对于客户要求的版本而言并不有效。相关性不等于有效性。

> 这些文档与查询相关，但对于客户要求的版本而言并不有效。相关性不等于有效性。

所以，这并非生成阶段的失败，而是一个无人断言的检索前提条件。空过滤器指出了这一点：请求的版本从未到达查找阶段。在触碰提示词或模型之前，先复现这个问题。

大多数问题可以通过普通代码进行测试。给测试夹具（Fixtures）提供携带版本元数据的文档，然后直接对查找逻辑进行断言，无需模型参与：

```
def test_lookup_filters_to_requested_version(docs_fixture):

    hits = search_docs(query="configure export", product_version="2026.3")

    assert hits, "no hits for a version that has docs"

    assert {h.product_version for h in hits} == {"2026.3"}
```

这是确定性的、低成本的，应该放入CI中。然后单独评估答案，这是你无法断言的部分：它是否给出了可用的2026.3说明，或者指出现有文档无法支持？进行两项测试，因为它们失败的原因不同，你需要知道具体是哪一部分坏了。

这种断言无法捕捉每一个错误的答案，但它每次都能捕捉到这个缺失的约束，这比仅仅由评审员给出的1到5分的效果要好得多。

这就是为什么评估需要保留上下文。记录提示词版本、模型ID、检索配置以及文档ID和版本。保留足够的证据以便稍后回溯答案，并在导出前脱敏敏感内容。

通过Trace和Span ID关联结果。如果评分是在Span关闭之后进行的，则存储一个单独的关联结果。不要计划向已结束的Span写入属性：[OpenTelemetry追踪API](https://opentelemetry.io/docs/specs/otel/trace/api/#end)规定，实现在End调用后应忽略更新。

生成式AI的语义约定仍在演变，不同的检测项目用不同的属性名称暴露类似的概念。

## 将失败纳入下一次发布检查

确认了原因了吗？验证每一个修复措施是否针对了它本应改变的行为。

针对重复搜索，添加回归测试，在不影响合法重试的前提下复现重复行为。不要锁定某一个精确的工具序列，因为当多个顺序都能完成任务时，强制要求单一路径会导致每一次有效的重构都宣告失败。

针对版本不匹配，恢复过滤器。添加以下案例：当前版本、客户明确提到的旧版本、无关文档以及无法支持的回答。因为输出具有变异性，所以请反复运行答案评估，因为一次通过不代表结果。

对于任何可以直接断言的内容，请使用代码。对于答案质量，使用基于模型的判断器（Judge），并对照人工评审的示例验证该判断器。未经检查的判断器只是另一个你需要盲目信任的模型。

若要针对生产流量而非测试夹具运行评分，你需要一种方式来采样环境中的现有Span，用判断器模型进行评分，并将每个结果链接回源追踪——即上述的关联结果模式，而不是写入已关闭的Span。无论使用什么工具，请对评估器进行版本控制。看起来像是产品改进的评分变动，未必真的是改进。

发布后，比较类似请求的延迟和任务成功率，并将工具调用次数和Token计数放在同一个屏幕上。请结合起来阅读，否则它们会误导你。工具调用从三次降至一次看起来像是修复奏效了，但也可能看起来像是你意外删除了某个查找逻辑。输出Token减少看起来是成本上的胜利，但也可能意味着答案静默地停止了列出第四步操作。

## 带着调试问题上路

如果你不知道从哪里开始调查，说明你的监控检测（Instrumenting）还没做完。

对于传统服务，那是请求路径和依赖耗时。对于AI功能，请添加它检索到了什么、它产生了什么，以及你将如何决定这是否是正确答案。
