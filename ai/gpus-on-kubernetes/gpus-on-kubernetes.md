本文探讨了在Kubernetes平台上运行GPU工作负载时，传统CPU和内存的可观测性、成本分摊和资源管理方法不再适用。团队必须自行构建指标、权衡计算与内存利用率，并解决高昂的GPU成本分摊难题。

> 译自：[GPUs on Kubernetes are bring-your-own-everything, starting with the bill](https://thenewstack.io/gpus-on-kubernetes/)
> 
> 作者：Yasmin Rajabi

如果你运行一个 Kubernetes 平台，你可能至少有一个用于工作负载资源可观测性的 Grafana 仪表板。它显示了容器请求的资源与实际使用的资源之间的对比，这使得指出某个部署请求了四个核心但实际上只用了半个核心变得相对容易。如果你按命名空间进行细分，你可以大致了解哪个团队消耗了什么，这是团队多年来对 CPU 和内存所做的事情，而且它大体上管用。

然后人们开始将工作负载放到 GPU 上，而我们假设能够延续过去的很多东西却行不通了。几乎你对 CPU 和内存理所当然的每一项可观测性，GPU 都会逼着你自己去构建。你自己的指标、你自己的准确性、你自己的分账规则。这正是最让人痛苦的地方，因为 GPU 是账单上最贵的一行。

## **自备指标**

对于 CPU 和内存，内核已经为你追踪了每个容器的使用情况，因此获取每个 Pod 的数字基本上是免费的。而另一方面，GPU 并不会给你提供这些。每个人开始使用的工具——NVIDIA 的 DCGM exporter，默认是在物理设备级别进行报告。当一个 Pod 独占一个 GPU 时，这没问题，但只要你开始通过时间切片（time-slicing）或 MPS 在多个 Pod 之间共享一个 GPU，DCGM 就会给共享该 GPU 的所有 Pod 提供相同的值。因此，如果三个 Pod 共享一个 GPU，这三个 Pod 看起来都在使用全部资源，当你把它们加起来时，你会得到一个并不存在的 300% 的 GPU。通过时间切片或 MPS，驱动程序为整个 GPU 暴露了一组计数器，因此 DCGM 没有可供归属的每个 Pod 的数据，也无法区分哪个工作负载消耗了什么。

这些数字在图表上依然绘制得很漂亮，但团队却在明显错误且难以察觉的值之上构建了完整的仪表板和报告。

## **自备资源调整数学**

在 CPU 方面，我们都习惯了毫核（millicores）、超额认购（overcommitting）、突发（bursting）、只会对你进行限流的 CPU 限制、以及会导致你被 OOM 杀死的内存限制，但 GPU 把其中大部分都抛弃了。GPU 显示为一个整数字源：`nvidia.com/gpu: 1`。你请求整个 GPU，你的请求和限制必须匹配，并且在调度器处没有超额认购。推理所需的比例共享是通过调度器下方的的时间切片或 MIG 发生的，而 Kubernetes 的请求并不能很好地契合这一点。

因此，最基本的资源调整前提——比较工作负载请求的内容与它实际使用的内容并回收差额，对于 GPU 来说刚开始时几乎是不存在的。在你能开始讨论浪费之前，你最终不得不先算出工作负载究竟获得了 GPU 容量的多少。

## **自备护栏**

NVIDIA 容器运行时会查看一个名为 `NVIDIA_VISIBLE_DEVICES` 的环境变量，而基础的 CUDA 容器镜像将其默认设置为 `all`。在正常设置中，设备插件会覆盖该设置并仅注入 Pod 实际分配到的 GPU。但是，如果没有东西覆盖它，或者容器运行时的配置是尊重来自容器的环境变量，那么无论 Kubernetes 自认为分发了什么，Pod 最终都可以看到并抢占盒子上的每一个 GPU。因此，调度器记录的分配情况与硬件上实际运行的情况可能会产生巨大分歧。如果你想要真实的数字，你必须查看进程级别发生的事情，并将其与 Kubernetes 认为它所做的事情进行对齐。

## **自备利用率定义**

当 CPU 图表显示 80% 时，你大致知道你在看什么，但 GPU 利用率则更加含糊。通常的指标告诉你，内核在样本窗口的某个时间片内在 GPU 上运行。它不会告诉你你烧掉了多少实际的计算或内存带宽。你可以看着 GPU 保持在 100% 的利用率，而计算实际上几乎什么也没做。而且很多时候最先耗尽的是内存，因为像 vLLM 这样的框架在启动时就会抓取大部分 GPU，不管它们是否需要。尽早弄清楚哪个信号对你的工作负载有意义，无论是计算占用率、内存占用、带宽还是功率。如果你依赖那个巨大的标题数字，你可能会得出错误的结论。

## **自备归属**

NVIDIA 的 NVML 库会告诉你，在 GPU 上的每个进程持有多少内存，你可以将每个进程追溯到拥有它的 Pod 和团队。这些数字是可靠的，但有一个星号：它们加起来不会完全等于显卡的总量，因为驱动程序为自己保留了一块不属于任何工作负载的内存空间。

计算则是事情崩溃的地方，值得理解其中的原因。想象一个共享厨房：内存是操作台空间，你可以看到食材放在哪里。计算则是炉灶，每个人都在以毫秒级的突发轮流使用。NVIDIA 给你的不是“每个厨师得到了多少炉灶时间”。它更像是一个每秒被检查很多次的标志，问的是“这个厨师现在在做事情吗？”如果两个人都在工作，两个标志几乎在所有时间都读作“是”，所以你会得到两个看起来各有 90% 忙碌的任务，这既是事实，同时也无法告诉你谁干成了更多的工作。

这种测量在一种设置下是可用的：当 GPU 严格地一次一个任务轮流交替时，轮询诸如 DCGM 的记账模式或 nvidia-smi 的 PID 级别采样之类的内容可以近似估算出每个任务的份额。它在任务真正并排运行的设置中会失效，而这也是人们为了获得更好利用率而选择的设置。如果两个团队共享一个 GPU，现有的任何工具都无法告诉你哪个团队烧掉了 70%，哪个团队烧掉了 30%。

因此，实际的决定是按内存计费（此时数据站得住脚），并将计算视为一种信号，作为驱动成本回摊（chargeback）的东西。现实情况是，当你想要超越展示回摊（showback）时，团队之间通过准确性实现公平性确实很重要，而 GPU 内存是现有工具中最准确的归属方式。

## **自备共享范式**

事实证明，共享 GPU 意味着几种不同的事情，每一种都会改变底层的数学计算。有时间切片（time-slicing），它以循环（round-robin）方式对 GPU 进行轮流调度且没有隔离，允许你对其进行超额认购。然后是 MPS，允许来自不同进程的内核同时运行。MIG 非常受欢迎，它将 GPU 分割为固定的硬件分区，尽管值得注意的是，大多数云厂商即使在你只使用一个切片时也会对整个物理 GPU 收费，并且在 A100/H100 级别的 GPU 上，你最多只能将其分割为 7 个实例。然后是 DRA（动态资源分配，Dynamic Resource Allocation），它在过去的几个 Kubernetes 版本中一直在成熟，显然是未来的发展方向，但围绕它的生态系统（包括 Karpenter 等自动扩缩容工具）仍在赶上。所有这些都改变了“已分配”甚至意味着什么，因此可观测性取决于给定节点处于哪种模式。

## **自-备分摊规则（而且账单极其残酷）**

GPU 的每小时成本远高于 CPU，并且按工作负载进行分摊要困难得多。云厂商将 GPU 节点作为包含 CPU、内存和 GPU 混在一起的一个账单行项目计费。为了得出每个工作负载的真实美元数字，你必须拆开这一行，并按模型对 GPU 部分进行加权，因为 T4 和 H200 的价格相差十万八千里。然后你把它分摊到共享 GPU 的任何工作负载上。在 AWS 上，最便宜的兼容 MIG 的 A100 GPU 价格为每小时 22 美元，竞价实例（spot）大约为每小时 14 美元，而类似大小的纯 CPU 实例运行成本约为每小时 5 美元。即使在竞价实例上，这也是相当大的差距。

## **这到底花掉了你多少钱？**

把这一切加起来，真正的成本不仅是 GPU 账单，还有你为了重建曾经免费获得的可观测性而消耗的工程时间和苦工。指标、预期的准确性、护栏、归属、分摊规则，每一层都是你现在必须拥有和维护的东西。

这里的积极面是，这个领域正在快速发展。DRA 正在成熟，采用率也在随之增长，硬件分区变得越来越容易，每个版本都在缩小工具上的差距。因此，请慎重决定现在构建哪些层，以及让生态系统去追赶哪些层，绝对不要指望你的 CPU 和内存剧本可以直接套用。
