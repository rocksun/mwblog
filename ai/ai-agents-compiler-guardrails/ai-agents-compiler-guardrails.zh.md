**本月早些时候，Hydro 背后的团队开发了一种新方法**，用于检查分布式系统在故障后重发消息时是否仍能正常工作。

这产出了 [Shadaj Laddad](https://linkedin.com/in/shadaj) 向我描述的“类似于 5000 行 PR”的代码。Hydro 是一个用于分布式系统的开源 Rust 框架，这些软件同时在许多机器上运行，而智能体现在在人类的驱动下编写了其中大部分代码。这个 PR 很难拆分成更小的部分，因为它的组件是协同工作的。

对于开发人员用来捕获漏洞的工具来说，有大量的代码需要审查。AWS Hydro 团队的研究负责人 Laddad 表示，这是团队花大量时间思考的问题。上周，我在圣何塞举行的 AGNTCon + MCPCon 上与他进行了交流。他第二天将发表主题演讲，认为代码审查跟不上智能体编写代码的速度。

Laddad 告诉我说，智能体让团队设定了更高的目标，并表示 PR 的到达速度更快、运行时间更长。“你可以让功能在隔离状态下良好运行，然后将其与其它内容混合，突然之间保证就失效了，”他说。
  
而且你不能只相信测试。他说，在大多数智能体工作流中，智能体既编写代码又编写单元测试。“智能体很棒，但它们是不可预测的，”Laddad 说。这种不可预测性正是它们具有创造力的一部分，这也使得人类很难审查所有这些测试并确认它们是否达到了团队的期望。

他的解决方案是在智能体的“信任区”之外共享正确性检查，例如编译器强制执行的检查。Rust 的借用检查器就是他的例子：它在代码运行之前就能捕获竞态条件。Hydro 为分布式系统做出了类似的事情，在编译时捕获几种类型的 bug，以便智能体对其引入的错误获得即时反馈。更广泛的目标（该团队仍在探索中）是智能体可以共享的特定领域的护栏。

为了寻找候选者，团队研究了历史项目中的重复模式。幂等性（确保重试的请求不会运行两次）在设计审查中反复出现，因此团队正在探讨它是否可以成为通用的护栏。Laddad 将此视为老梯子上的下一个梯级。C 语言使程序员免于在汇编中弄乱函数调用。Java 将内存分配从他们的负担中解放出来。他认为，智能体使得下一层变得更加紧迫。

不过，编译器也有局限性。正如 *The New Stack* 在 8 月份报道的那样，[AI 生成的 Rust 代码可以完美编译但仍然是错误的](https://thenewstack.io/canonical-c-rust-apparmor/)。

同一团队还构建了 [Infinity](https://aws.amazon.com/blogs/opensource/introducing-infinity-a-runtime-for-extreme-agent-concurrency/)，这是 AWS 于 10 月 23 日宣布的开源智能体运行时。它会在智能体等待工具调用或 CI 作业时将其暂停，而不是让其继续运行。Laddad 引用了一个基准测试，显示在单个树莓派上有 75,000 个并发智能体。根据 AWS 的公告，该数字是从服务器测试中外推出来的，其中每个空闲智能体消耗大约 100 KB 的内存。

Hydro 本身是一个早期版本，专为运行高吞吐量、低延迟服务且不断担心分布式系统 bug 的团队构建。Laddad 指出，用户现在应该预料到粗糙边缘和学习曲线。回报是有信心更改系统，而不必担心几个月后它会崩溃。
  
*Hydro 和 Infinity 在 [hydro.run](https://hydro.run) 上开源，由 AWS 和 UC Berkeley 联合构建。*
