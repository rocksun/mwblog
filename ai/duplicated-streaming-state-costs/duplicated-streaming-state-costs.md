本文探讨了实时应用中分离处理与存储架构带来的隐性成本，包括数据同步延迟、CPU与网络开销以及状态冗余。文章分析了分布式系统中的一致性挑战、副本滞后与导出滞后问题，并介绍了将计算推向数据存储侧（如使用Hazelcast）以优化性能和降低数据传输开销的方案与权衡。

> 译自：[Where consistency gets complicated](https://thenewstack.io/duplicated-streaming-state-costs/)
> 
> 作者：Granville Barnett

![Colorful pixel grids dissolving into scattered squares on navy, evoking real-time state data moving between systems](https://cdn.thenewstack.io/media/2026/11/8df20e8c-anna-magenta-vfd7njx03ss-unsplash-1024x683.png)

**实时应用通常会结合**具有不同角色的工具。一个典型的设置可能会使用 Kafka 来处理事件，用 Flink 来进行计算，用 Redis 来提供最新的状态，并用数据库来维护系统记录。使用向量搜索的应用可能还会添加一个向量存储。

这种职责划分提供了灵活性和独立扩展能力。但当数据在组件之间移动，或者在多个地方维护重叠的状态时，也会产生相应的成本。

> “需要质疑的那些副本，主要是在一个系统中进行处理，而应用从另一个系统读取结果时所维护的副本。”

其中一些副本是必要的。副本可以防止故障，检查点有助于系统恢复，持久化的事件日志则能保留历史记录。这些是值得付出的代价。需要质疑的那些副本，主要是在一个系统中进行处理，而应用从另一个系统读取结果时所维护的副本。

以追踪支付卡过去五分钟交易情况的速率计数器为例。Flink 计算出计数值，并维护带键状态（keyed state）来支持该计算。

但防欺诈评分服务也需要检索该结果。Flink 的内部状态并不是为通用服务设计的，并且 Flink 已经在 1.18 版本中废弃了其 [Queryable State](https://flink.apache.org/2023/10/24/announcing-the-release-of-apache-flink-1.18/) 功能。一个常见的解决方案是将计数值发布到 Redis 中。

这为应用提供了一个专门的服务层，但它也带来了自身的扩展和运维需求。Flink 的工作状态与 Redis 的值可能会重叠，但不一定完全相同，并且在消费者看到它们之前，每次发布的更新都涉及序列化、网络流量和处理过程。

## 一致性变复杂的地方

当应用跨越可用区时，保持状态同步会变得更加复杂。

考虑一个假设的支付系统，它从多个可用区中的异步副本读取数据，以减少跨可用区流量。一笔退款已经完成，但该更新仍在向其中一个副本传输的途中。

从该副本读取数据的服务可能会认为这笔交易尚未退款，从而发出另一笔退款，尽管第一笔退款已经处理完毕。如果没有在退款路径之间进行协调，客户可能会被重复付款。

> “如果在退款路径之间没有协调机制，客户可能会被重复支付。”

无论决策是否依赖于异步复制的状态，这都是一个应用设计问题。将处理和存储放在同一个平台上并不一定能防止这种情况的发生。

紧迫的问题是副本滞后，再加上应用在没有原子性地检查和更新授权退款状态的情况下做出决策。如果退款调用了外部支付服务，该服务也需要一个幂等的请求机制，以确保重试不会导致同一笔退款被发出两次。

一个独立的处理与服务设计还引入了发布延迟：处理程序可能在服务存储接收到更新值之前就已经计算出了更新的值。这就是导出延迟，它不同于服务存储内部的副本滞后。在这种滞后期间，一笔欺诈交易可能会根据过时的计数值进行评分。导出延迟和副本滞后都可能导致应用读取到陈旧的数据，但这二者都不应与可能导致重复退款的“先检查后执行”（check-then-act）竞态条件相混淆。

对于计算直接针对存储状态运行的工作负载，Hazelcast 可以避免单独的发布步骤。它的 [entry processors](https://docs.hazelcast.com/hazelcast/5.7/data-structures/entry-processor) 可以在持有相关键的成员上原子性地更新单个映射条目。不过，这并不意味着系统在网络分区期间会自动达到强一致性。

需要更强协调性的应用可以使用 Hazelcast 基于 Raft 的 [CP subsystem](https://docs.hazelcast.com/hazelcast/5.7/cp-subsystem/cp-subsystem) 中正确配置的数据结构。使用它并不会将普通的 IMap 变成强一致性的映射，也不会使映射更新与外部支付保持原子性。独立的处理和存储系统也可以使用强一致性的协调机制。

## 移动状态的成本

在关于内存架构的讨论中，内存往往占据主导地位，但 CPU 和网络成本同样重要。

UC Berkeley 和 Databricks 的一篇 [2025年论文](https://conferences.sigcomm.org/hotnets/2025/papers/hotnets25-final80.pdf)，*Rethinking the Cost of Distributed Caches for Datacenter Services*（重新思考数据中心服务分布式缓存的成本），使用合成工作负载、Meta 跟踪数据以及 Databricks Unity Catalog 的生产数据，对缓存经济学进行了研究。

> “在关于内存架构的讨论中，内存往往占据主导地位，但 CPU 和网络成本同样重要。”

根据论文中假设的 Google Cloud 定价标准（大约每 vCPU-month 17 美元，每 GB-month 内存 2 美元），研究人员发现，添加内存缓存可以将运营成本降低三到四倍。CPU 的节省超过了额外内存的成本。

这不是 Hazelcast 与 Flink 和 Redis 的对比；该研究对比的是有缓存和无缓存的情况。其远程缓存与链接缓存的对比支持了这样一个更狭窄的论点：通信和序列化会消耗 CPU。

该论文还发现，为了更强一致性而进行的每次读取版本检查可能会抵消大部分成本效益，因此进行对比时需要具备同等的一致性要求。

Google 研究人员在 [2019年的一篇论文](https://research.google/pubs/fast-key-value-stores-an-idea-whose-time-has-come-and-gone/)“Fast Key-Value Stores: An Idea Whose Time Has Come and Gone”中报告称，在从远程键值存储迁移到[将应用逻辑和内存状态保持在一起](https://docs.hazelcast.com/hazelcast/5.7/getting-started/get-started-java)的架构后，Google 某应用组件 ProtoCache 的 p99.9 延迟降低了 40%。

另一项说明性的计算展示了维护两套等效工作集的内存成本。按照论文中假设的内存价格，400 GB 仅内存一项每月就要大约 800 美元，这还不包括备份、检查点和其他基础架构。

在处理层和维护层都维护等效的数量会使该数字翻倍，尽管 Flink 的中间状态和发布到 Redis 的结果可能会有很大差异。

此外还有保持系统同步所需的工作。每个更新都必须进行序列化、传输和处理，并且两个平台都需要监控、扩展和维护。

了解这种开销的一种方法是计算单个“读取-修改-写入”操作所涉及的步骤。在使用独立的处理和服务系统时，可能会经历事件被摄取、键控状态更新、结果被序列化并发布，然后写入服务存储，最后应用才读取它。对于一个更新来说，这可能涉及四到五个序列化或网络步骤。在存储状态的地方运行计算可以将其减少到单个步骤。这虽然不是精确的成本衡量标准，但追踪更新的路径可以帮助识别 CPU 时间和网络资源消耗在了哪里。

一个公平的总成本对比还需要考虑节点数量、实例类型、许可证、折扣以及同等的托管与自托管部署。800 美元的数字只是内存算术，并非总成本估计或测得的 Hazelcast 节省量。

## 让计算更靠近数据

[Hazelcast 提供了一种将处理过程拉近存储数据的方法](https://docs.hazelcast.com/hazelcast/5.7/getting-started/get-started-java)。它不是在独立系统之间来回发送信息，而是根据键将数据分布在集群成员中，并且可以在持有该数据的成员上运行计算。它会保留备份副本以防成员发生故障。

根据涉及的处理类型，Hazelcast 提供了两种方法。Hazelcast 的 [Jet 引擎](https://docs.hazelcast.com/hazelcast/5.7/pipelines/overview)可以为窗口化流计算维护内部状态，并将结果发布到应用可以读取的分布式映射中。

该中间状态和结果发布步骤仍然存在于同一个平台上；处理、映射写入和备份也可能涉及成员之间的流量。在这两种设计中，Kafka 都可以保留为持久事件日志，记录数据库也可以保持原位。

对于需要直接更新存储值的应用，Hazelcast 还拥有 [entry processors](https://docs.hazelcast.com/hazelcast/5.7/data-structures/entry-processor)。这些处理器针对映射条目本身运行代码，而不是在其他地方计算结果然后跨系统复制。

以之前讨论过的交易计数器为例。entry processor 可以在分布式映射中维护每分钟的交易计数，应用可以对最近的五个桶进行求和来计算总数。这避免了使用定时器来删除过期交易的需求，尽管结果的准确度精确到分钟而不是秒。应用仍然需要考虑迟到或重复的事件。

请保持 entry processors 轻量化，因为长时间运行的操作可能会阻塞同一分区上的其他工作。客户端和集群之间仍然会发生网络流量，Hazelcast 也会维护备份副本。

序列化成本还取决于[映射的内存格式](https://docs.hazelcast.com/hazelcast/5.7/data-structures/setting-data-format)：默认的 BINARY 格式存储序列化的值，而 OBJECT 可以减少 entry processing 的转换工作。不同之处在于，对于适合这种方法的工作负载，不需要单独的处理层不断向服务存储发布更新。

## 什么时候独立系统才合情合理

将处理和存储分开有一个显著的优势：两者都可以独立扩展。

考虑一个运行复杂决策权重的应用，它产生的结果不过是一个“是”或“否”的答案。它可能需要大量的 CPU 容量，但存储需求却极小。独立的处理层允许团队在不扩大服务基础设施的情况下添加计算资源。

其他应用则持有大量状态，但只进行相对少量的处理。将这两个工作负载放在一个集群上可能只会带来有限的节省，尤其是当 CPU 密集型任务与延迟敏感的读取竞争时。

独立的平台还允许独立部署、工作负载隔离以及访问专门的处理功能。Hazelcast 也可以在单个集群中提供其中一些灵活性。它的 [lite members](https://docs.hazelcast.com/hazelcast/5.7/maintain-cluster/lite-members) 处理计算任务而不存储数据，允许团队将常规成员专用于存储，并单独添加计算能力。

对于某些工作负载而言，将处理和存储放在完全独立的平台上仍然合情合理。但当应用频繁读取和更新相同的状态时，Hazelcast 可以减少系统之间的数据移动。

## 在进行切换之前需要测量什么

出发点应该是对现有部署进行剖析。多少 CPU 时间花在了应用逻辑上，多少花在了数据序列化或跨网络通信上？处理和服务之间实际复制了多少状态？

平均响应时间也无法说明全部问题。系统在大部分时间可能表现良好，但在某些请求上可能会明显变慢。这就是为什么值得检查 p99 和 p99.9 请求延迟，以及吞吐量和端到端延迟的原因：从事件到达到着陆结果可读的时间，包括任何导出延迟。

在相同的工作负载、相同的端到端延迟目标以及相同的持久性保证下进行对比。故障测试也很重要：检查恢复时间、重放行为、重复处理，以及在节点故障和网络分区期间的正确性。备份副本和恢复机制增加了基础设施的开销。

对于某些应用来说，独立扩展处理和存储仍然是更好的选择。而其他应用可能会发现，它们本可以直接对应用可访问的状态进行相同的工作，却还在为系统间移动数据支付代价。

并非每个副本都是多余的。副本可以防止故障，检查点支持恢复，流处理器也需要中间状态。真正值得质疑的副本，主要是那些因为处理和存储发生在不同系统中而不得不维护的副本。
