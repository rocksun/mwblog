在 BrowseComp-Plus 测试中，当直接提供支持文档时，GPT-4.1 对问题的回答正确率高达 **93.49%**。而当智能体使用相同的模型，但依赖 BM25 来搜索证据并传递给模型时，准确率骤降至 **14.58%**。

这种差异至关重要，因为一个准确率达 93% 的系统，其效用远高于一个准确率仅为 15% 的系统。

在受控的演示中，智能体可能表现得非常出色。语料库很干净，任务很熟悉，相关材料也很容易找到。但实际生产环境则要混乱得多。文档可能会重复，过时的草稿仍然可以被搜索到，团队也可能对同一事物使用不同的术语。政策的多个版本可能会共存，而任务本身的发展方式可能是评估集从未涵盖的。

> “更强的模型智能无法弥补智能体从未检索到的证据。”

在这种情况下，智能体检索到的可能是残缺的、过时的或完全错误的材料。更强的模型智能无法弥补智能体从未检索到的证据。

正是在这种情况下，检索开始决定模型实际能做的事情。

## BrowseComp-Plus 展示了什么

[BrowseComp-Plus](https://arxiv.org/abs/2508.06600) 提供了一种有效的方法来分离这些影响，因为它是在固定语料库而非不断变化的网页搜索服务上评估智能体的。该基准测试包含 100,195 份文档和 830 个研究问题，每个问题都有人工验证的支持文档。

其中一项评估直接向模型提供所有标记的正向文档。论文将此称为 *oracle*（神谕）设置。另一项评估则要求智能体搜索语料库并收集所需材料。

差异是巨大的。在提供标记支持文档的情况下，GPT-4.1 的得分为 **93.49%**；而当智能体使用 BM25 基线进行搜索时，得分为 **14.58%**。在相同的两个条件下，Qwen3-32B 的得分从 **83.25%** 跌至 **3.49%**。

Oracle 结果显示了当所需材料已经摆在面前时，模型的回答能力有多强。对于系统设计而言，比较检索系统甚至更有用。推理模型保持不变，而更好的检索提高了最终答案的命中率并减少了搜索调用次数。

> “这个教训非常实用：在更换模型之前，先检查一下什么能到达模型手中。一个基于糟糕检索结果运行的能力出色的模型，其用于推理的材料依然很糟糕。”

这个教训非常实用：在更换模型之前，先检查一下什么能到达模型手中。一个基于[糟糕检索结果](https://thenewstack.io/search-retrieval-reranking-funnel/)运行的能力出色的模型，其用于推理的材料依然很糟糕。

![显示模型使用 oracle 证据回答与使用 BM25 搜索证据之间准确率差异的图表。](https://cdn.thenewstack.io/media/2026/10/8cb05df2-image3-1024x768.png)

***图 1. 相同的模型，不同的证据获取方式：** BrowseComp-Plus：直接提供 oracle 证据与使用 BM25 进行智能体搜索。*

企业可以围绕竞争对手不具备的专有信息构建智能体，从产品和客户数据到内部知识和运营记录。这种优势取决于智能体是否能够找到正确的信息并对其进行良好排序，同时还要跟上底层数据的变化。

## 一个任务。几分钟。上千次检索。

在其[将搜索视为代码的研究](https://www.perplexity.ai/hub/blog/rethinking-search-as-code-generation)中，Perplexity 描述了能够在几分钟内触发数百次或数千次检索操作的任务。搜索成为智能体工作流中持续存在的一部分，而不再是偶尔的查找。

传统搜索通常为每个查询返回一个排序结果集。而智能体可以将任务分解为多个搜索，并行分发它们，组合结果，并在了解更多信息后发出后续搜索。

在这种规模下，分支分发（fan-out）成为工作负载的常态。如果智能体并行运行十个搜索，并且需要全部十个结果才能继续，那么最慢的搜索就会决定该步骤的节奏。如果智能体在任务期间多次重复这种模式，尾部延迟就会变得比单个交互式查询更加重要。

同样的乘数效应也体现在容量上。一个用户任务可以生成数百个搜索操作，而许多智能体可能同时在这样做。从用户请求的角度来衡量，服务看起来可能负载很轻，但检索层正在处理更大体量的搜索。

当一个任务分流为多次搜索时，检索质量就变得更加重要。人们会利用自己随着时间推移积累的上下文来判断搜索结果。他们知道自己信任哪些来源，并且通常能识别出某些内容何时看起来陈旧、不可靠或格格不入。智能体通常以少得多的背景信息开始，必须从它在任务期间检索到的证据中建立理解。它往往就像是上班的第一天。如果这些早期结果中有一个是错误的，接下来的搜索也可能是错误的，任务的其余部分可能会从那里开始偏离。

> “人们会利用自己随着时间推移积累的上下文来判断搜索结果。智能体通常以少得多的背景信息开始，必须从它在任务期间检索到的证据中建立理解。它往往就像是上班的第一天。”

一个简单的模型说明了为什么重复的检索步骤会提高风险。假设一个工作流需要五个检索步骤，每个步骤有 90% 的概率提供智能体需要的内容，并且假设没有重试或恢复机制。所有五个步骤都成功的概率是 0.9^5，大约为 **59%**。真实的智能体可以重试、使用冗余证据、分支和恢复，因此这只是一个图解，而不是一个被测量的智能体成功率。它展示了当后续工作依赖于先前的检索时，每个步骤中微小的弱点是如何累积的。

![显示端到端成功率如何呈乘法级失效的图表。](https://cdn.thenewstack.io/media/2026/10/85faf204-image4-1024x768.png)

***图 2. 微小的检索错误可能会在多步骤任务中复合**图解模型：如果每个必需的检索步骤都必须成功且没有恢复机制，那么随着步骤数量的增加，端到端成功率会下降。*

因此，智能体搜索要求检索层为每个用户任务处理更多查询、更多并行运行的搜索，以及其结果会影响后续工作的检索步骤。随着这些模式的扩展，容量、尾部延迟和检索质量都变得更加重要。

## 你的检索层是为不同的用户调优的

网络搜索花了数十年时间来适应人类的搜索行为。

正如 Jon Bratseth 在《[你的智能体想要像 2010 年的量化交易员那样进行搜索](https://blog.vespa.ai/your-agent-want-to-search-like-a-2010-quant/?utm_source=chatgpt.com)》中所写的，人们在搜索时通常“懒惰且茫然”。用词虽然直白，但观点很简单：人们往往会输入简短的查询，而对背后的语料库或搜索系统知之甚少。

搜索引擎正是围绕这些习惯演进的。简短、未充分说明的查询成为了常态，而大部分复杂性都转移到了界面背后，在那里，搜索系统推断意图并返回排序列表。

智能体可以使用丰富得多的接口。它可以搜索精确术语、构建过滤器、指定日期、对结果进行分组、在排序策略中进行选择，并根据已经发现的内容发出后续搜索。Jon 给出了各种示例，从法律案件中姓氏的邻近搜索到对高质量来源的语义搜索，再到按月份对事件进行分组。在[智能体工作流](https://thenewstack.io/ai-agent-infrastructure-performance/)中，当智能体缩小、扩展和验证其答案时，这些搜索可以串联在一起。

这意味着检索层接收到的不仅仅是一个简短的文本查询。它可能会接收几种输入的组合：词汇术语、查询嵌入（embeddings）、结构化过滤器或它们的组合。面向智能体的接口应该明确这些选择，以便智能体可以针对任务使用正确的检索方法，而不是将每个请求折叠为一个文本字符串。

评估也需要反映这种转变。一个主要在人类编写的短问题上测试的检索器，在智能体生成自己的过滤器、搜索 terms（搜索词）和后续查询时的表现可能会有所不同。因此，应该根据智能体在生产环境中实际发送的查询来衡量检索质量，而不仅仅是评估集中的问题。

在更改模型或重新调整检索之前，请先检查那些生产查询。

## 搜索 API 返回结果。智能体需要更多控制。

传统搜索通常暴露一个狭窄的契约：发送查询，让服务器运行检索管道，然后接收排序的结果列表。

当调用者只需要输出时，这运作良好。而智能体可能需要根据任务的要求，对运行时如何执行检索和排序拥有更多控制权。

Vespa 通过其查询语言和排序配置文件（rank profiles）暴露了这种控制。调用者可以在同一个请求中组合词汇或语义检索、结构化过滤器、排序选择和分组，从而影响候选者的选择、打分和返回方式。

接口之所以重要，是因为智能体只能使用它能够触及的控制项。系统可能在内部支持过滤、排序、聚合或多种检索方法，但如果智能体在任务需要时无法调用它们，这些功能就毫无用处。

![对比狭窄接口与更丰富接口的列表。](https://cdn.thenewstack.io/media/2026/10/96b3b55b-image5-1024x768.png)

***图 3. 智能体可以触及检索堆栈的多少部分？** 狭窄搜索接口与更丰富的运行时控制接口的图解比较。产品类别并不决定暴露哪些功能。受信任的应用代码强制执行授权。*

对于许多明确定义的应用而言，固定的管道依然是一个很好的选择。当任务从一个步骤变到下一个步骤，且智能体在运行时需要不同的检索行为时，智能体工作流就会变得更具挑战性。

目标是暴露智能体所需的控制项，同时将授权、验证、预算和其他保障措施保留在受信任的服务器端。

## 仅仅暴露控制项是不够的

引擎可以暴露过滤器、词汇匹配、最近邻搜索、分组、多个排序配置文件、重排序和运行时控制。只有当接口解释了有哪些可用功能以及何时使用它们时，这些功能对智能体才变得有用。如果排序配置文件、可过滤字段或分组操作未加描述，智能体可能会默认为自由文本查询，并将更多的工作推给后面的推理或工具调用。

处理这种情况的一种方法是在智能体和检索系统之间放置一个查询转换模型。转换器获取智能体的请求并将其转换为引擎的查询语法。当应用程序希望将查询构建集中在一个稳定的接口后面时，这会很有用。

当调用者本身就是智能体时，一个单独的转换器通常会在智能体和检索系统之间插入一个专门的模型。智能体已经在上下文中拥有了任务、先前结果和约束条件；转换器必须从一个较窄的请求中重建该意图并将其转换为查询。这种额外的交接增加了延迟，并带来了丢失或扭曲智能体意图的又一次机会，从而使检索变得更加困难和不可靠。

另一种方法是直接向智能体描述检索接口：哪些字段可用以及它们的含义是什么，以及提供了哪些排序配置文件。

我们称之为**智能体就绪架构（agent-ready schema）**：对智能体可以使用的字段、控制项和检索选项的描述，以及它们背后的特定于应用程序的含义。Vespa 已经描述了朝这个方向发展的便利工具的工作，其中大部分指导都可以直接从应用程序架构本身生成。

## 从架构到技能

[搜索架构](https://thenewstack.io/building-agent-friendly-apis/)已经包含了智能体所需的大部分信息：字段名称和类型、哪些字段可以被搜索或用作过滤器、可用的排序配置文件以及配置好的张量和模型。

它缺少的是对字段含义以及如何使用它们的描述。名为 `tier` 的字段可能代表账户计划、服务级别或其他完全不同的东西。诸如 `published` 的时间戳可能意味着首次发布、最后修改或摄取时间。名为 `exact` 的排序配置文件并没有向智能体透露多少关于它专为哪类查询而设计的信息。

这些含义可以作为解释添加到架构中。这不仅赋予了智能体名称和类型，还赋予了它足够的上下文，以便为任务选择正确的字段、过滤器和排序选项。

**架构到技能（Schema-to-Skill）**是提出的生成步骤：将 Vespa 应用程序架构、引擎指导以及特定于应用程序的知识组合成一个简短的 Markdown 技能，供智能体在构建查询时参考。架构提供了结构，引擎指导解释了如何安全地使用可用功能，而特定于应用程序的知识则增加了无法仅从架构中推断出来的词汇和含义。

![图解转换层和智能体就绪架构架构的工作流。](https://cdn.thenewstack.io/media/2026/10/040a5a3d-image2-1024x768.png)

***图 4. 为智能体转换，或教导它。** 转换层使用单独的模型调用来构建搜索查询。通过智能体就绪架构，智能体获得使用应用程序暴露的检索控制项构建查询所需的指导。“架构到技能”是拟议的生成工作流。*

智能体使用该技能在 Vespa 应用程序暴露的检索策略中进行选择。Vespa 仍然对语料库进行实际的检索工作，包括匹配、过滤、排序和聚合。智能体决定要查询什么；检索系统负责执行。

更好的模型可能会有所帮助，但当智能体搜索错误的证据、无法表达[正确的检索策略](https://thenewstack.io/the-precision-engine-why-agentic-rag-is-genais-next-leap/)，或者不理解它正在调用的搜索系统时，它们仍然会失败。

> “更好的模型可能会有所帮助，但当智能体搜索错误的证据、无法表达正确的检索策略，或者不理解它正在调用的搜索系统时，它们仍然会失败。”

智能体工作负载使这些弱点的代价更高，因为检索贯穿于整个任务。每次搜索都会影响智能体接下来看到的内容、它携带的上下文数量，以及它是否需要再次搜索。在大规模情况下，检索质量、尾部延迟和查询量本身就成了任务的一部分。

这给检索接口带来了更大的压力。智能体需要访问任务所需的过滤器、排序策略、分组和其他控制项，以及足够的指导来正确使用它们。**智能体就绪架构**使这些功能变得显式，而**Schema-to-Skill**是将这种结构、引擎指导和特定于应用程序的知识转化为智能体在构建查询时可用的东西的一种方法。

在升级模型之前，请检查智能体发出的搜索、这些搜索返回的证据，以及检索系统是否为智能体提供了所需的控制项和指导。更好的检索可以改善答案、减少不必要的工作，并使智能体系统的其余部分更加有效。
