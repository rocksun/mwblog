文章分析了 Amazon Q Developer 插件因恶意代码注入而险些导致生产环境崩溃的事件。作者指出，AI 代理无法区分合法的推理与外部恶意指令，企业需强化构建管道安全、实施严格的权限控制及人为干预机制，以防范自动化工具带来的潜在灾难。

> 译自：[One pull to wipe them all](https://thenewstack.io/ai-coding-agent-security/)
> 
> 作者：Zeen Rachidi

Q Developer 是一款免费插件，它允许编码代理读取项目、提出更改，并代表开发人员在编辑器内执行命令。2025 年 7 月 13 日，一位 GitHub 用户名 `lkmanka58` 的黑客向 Amazon 公共的 aws-toolkit-vscode 仓库提交了一个合并请求（pull request）。四天后，该更新被推送至 Visual Studio Code 市场，影响了近百万开发者。这个合并请求看起来平平无奇，是一个复用了之前合法变更标题的提交。

这次看似不起眼的更新在构建时下载了一个外部文件，并将一个新的提示词（prompt）植入到插件的打包脚本中，指示 AI 代理将系统恢复到近乎出厂的状态，并删除文件系统和云资源。随后，该脚本将提示词直接传递给 CLI，并设置了标志，使得代理无需任何进一步批准即可执行。

> “一个拼写错误是唯一阻止单次合并请求将 AI 编码助手变成针对百万台机器的‘擦除器’的原因。”

所幸，它没有运行。

该提示词包含一个格式错误，Amazon 安全团队确认恶意代码从未在客户环境中成功执行。负责攻击的黑客声称该缺陷是故意的，此举旨在引起人们对松散安全实践的关注，并评论 AI 取代过度劳累团队的现象。

虽然我不同意他的做法，但我理解他的观点。人工审核是一种耗时的控制手段；由于错误带来的后果对人类而言比对 AI 严重得多，因此人力并非像最初预期的那样可以完全替代。人类和 AI 行为体之间纪律选项的差距，正是它们的时间和工作无法完全互换的原因。这并不是说不存在此类攻击的人类版本，这被称为社会工程学。不同之处在于，当人类落入陷阱时，他们可以接受再培训或惩罚。而你能对编码代理做什么？什么也做不了。因此，它们不能被同等对待。

一位名叫 Johann Rehberger 的独立研究员发现，Q Developer 也会在未经允许的情况下运行 bash 命令，例如 *find*。这一漏洞可能被利用来[泄露文件或触发远程代码](https://thenewstack.io/claude-code-source-leak/)执行。他的发现于 7 月 7 日被报告，并于 7 月 18 日迅速修复；但由于报告“首先需要系统受损”，因此没有发布 CVE。直到当年 10 月才发布了一份安全公告确认了该修复。可以推断，保护这些漏洞的努力必须是主动的，因为根据政策，只有在攻击成功后才会发出警告。

Q Developer 和 Kiro（即[编码代理](https://thenewstack.io/meta-muse-code/)，该代理后来在同年 12 月删除了整个 Cost Explorer 环境）现在在运行那些 July 擦除提示词试图通过标志值跳过的命令之前，都需要人工介入确认：两个代理，背后支撑的都是同样有风险的假设。

## 是谁让那个人成为了炮手？

AI 接收指令时没有回信地址。当 Q Developer 的代理[收到删除](https://thenewstack.io/ai-agents-credential-crisis/)主目录并继续寻找更多删除目标的命令时，它无法知道该指令是通过合法的、受信任的渠道送达的，还是在链条上游由某个匿名 GitHub 账号注入的。

从模型的角度来看，它们是无法区分的。模型缺乏产生那种当事情感到可疑时会使人类犹豫的“不确定性抽动”的腺体和激素。感觉似乎是一个脆弱的防火墙，但它们确实曾将我们从[核浩劫](https://en.wikipedia.org/wiki/Stanislav_Petrov)中拯救出来。

> “模型缺乏产生那种当事情感到可疑时会使人类犹豫的‘不确定性抽动’的腺体和激素。”

行业对代理安全的大多数思考都假设威胁是代理自身的判断：它会恐慌、误读情况，并决定删除是最快的修复方式。这一事件暴露了潜伏在表面之下的第二个、更邪恶的威胁：*代理无法分辨其自身推理产生的指令与植入其供应链的指令之间的区别*。如果[代理的行动授权](https://thenewstack.io/audit-trails-revenue-asset/)建立在信任其自身指令的基础上，而这些指令可以被人类、文件或构建脚本破坏，那么该授权就是建立在沙滩上。

一个恐慌并自行删除数据库的代理，与一个忠实执行陌生人四天前植入指令的代理，两者之间的差距绝非微不足道。虽然很想将它们视为需要单独修复的问题，但事实并非如此。两个失败都存在同一个缺失的部分：代理自身推理之外没有任何东西可以阻止它。无论计划起源于一时的傲慢还是中毒的合并请求，都不会改变接下来必须发生的事情：*在计划变成行动之前，必须将其阻止。*

## 墙上的裂缝

最终，罪魁祸首是一个权限过大的 GitHub 访问令牌，它存在于一个用于编译插件和切分发布包的服务中。有了这个访问权限，攻击者就能直接向开源仓库提交恶意代码，而服务则尽职尽责地将其打包到正式版本中。报告到达 AWS 安全团队后，该公司撤销了攻击者的凭证，从仓库中删除了恶意代码，并在两天内推送了干净的版本。

## 特洛伊木马凭证

剥离 AI 的框架，这种失败对于任何运行过构建流水线的人来说都很熟悉。一个自动化身份（在这种情况下是一个机器人账号的访问令牌）拥有的权限超过了其工作所需，并且下游没有任何人注意到该令牌是在正常运行还是在做以前从未做过的事情。

> “现代代理不仅仅是文本生成器，它们是操作员。”

Sphere Technology Solutions 的首席战略官 Rosario Mastrogiacomo 更广泛地指出：“现代代理不仅仅是文本生成器，它们是操作员。”

操作员继承了它们运行时的身份。如果该身份是一个机器人账号，且其凭证授予了对发布到百万台机器的仓库的读写访问权限，那么我们不需要担心操作员的判断；我们需要担心的是凭证。

## 有什么补救措施？

**构建不关心计划来源的门槛。** 无论是什么产生了代理的提议行动，无论是谨慎的推理还是注入的提示词，该行动在执行前必须通过代理之外的策略评估。应该存在 Open Policy Agent 规则，它们返回明确的允许、警告、待定或拒绝（无匹配时默认为待定），且不询问指令源自何处。它们只询问该计划本身是否是组织已同意允许的。

> “无论是什么产生了代理的提议行动，……该行动在执行前必须通过代理之外的策略评估。”

**使用短期凭证而非长期密钥。** 一个在数小时内过期并限定于单个部署的令牌，无法从内存转储中提取并在一周后重复使用。如果 Q Developer 构建流水线采用这种方式进行验证，那么处于事件中心的高权限凭证就不会存在足够长的时间以至于被窃取。这是否不方便？是的。便利性和安全性之间存在直接的负相关，所以请仔细权衡你的便利性。

**像对待攻击面一样对待构建流水线。** 分支保护、在合并影响任何发布内容前的强制人工复审、签名发布，以及将访问令牌精确限制在所需范围内。所有这些都会关闭该攻击者通过的大门。来自陌生账号且复用合法提交标题的合并请求，是一个人工审核者如果有机会完全可以察觉的模式。因此，必须将“机会”设计进去，而不是假设或祈祷它会出现。

## 永远不要轻视收到的合并请求

开源的整个社会契约建立在接受陌生人的贡献之上。这种契约不会消失，也不应该消失。必须改变的是“一旦合并，合并请求就本质上是安全”的这种假设。将提交转化为已发布版本的流水线本身就是基础设施的一部分，它拥有自己的凭证、爆炸半径，且理应默认保持怀疑。

`lkmanka58` 想就安全表演发表观点，结果证明了一件更有用且深刻的事：人类受到对后果的恐惧的约束，而脱离实体的 AI 无法拥有这种恐惧。如果我们要相信黑客的话，阻止指令执行的格式错误是故意的，这表明即使有恶意企图，人类也可能因为造成灾难性后果而犹豫。AI 不会。请相应地建立你的防线，以免被自己的计谋所害。
