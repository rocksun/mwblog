本文探讨了MCP如何让AI代理连接API，但同时也带来了权限控制的安全挑战。文章提出，通过引入GraphQL的字段级契约，可以在不重构底层API的前提下，实现对AI代理访问权限的精准控制与安全管理。

> 译自：[MCP gets AI agents into your APIs. It doesn't decide what they should see.](https://thenewstack.io/mcp-ai-agents-api/)
> 
> 作者：Matt DeBergalis

**假设运营团队中的某个人想向他们的AI助手提问**：“哪些订单会错过今天的发货截止时间？检查其他仓库的库存，并在我们能够弥补短缺的地方创建调拨请求。”

这种类型的代理工作流需要调用API。代理需要当前的订单和可用库存；昨天的报告无法告诉它今天下午还有哪些库存可用。而且它需要将调拨请求写回履行系统。

为了使公司的内部订单管理API可供代理使用，工程师可能会构建一个MCP服务器。这是使这样的系统能够被访问的最快方法，但可访问性现在已经是容易的部分了。更难的问题——在MCP出现之前很久就已存在——是代理到达那里后应该看到什么。MCP只是让这个问题变得更加紧迫。

像订单管理这样的服务的API可能会返回大量信息，包括个人身份信息、敏感的财务和欺诈详情，以及绝不应离开受信任网络范围的运营信息。我们已经知道如何处理传统应用程序的访问权限控制：后端检查用户的权限，处理上游API调用，并仅返回适当的视图。

因此，启用这类灵活代理的工程师们陷入了两难境地。一个将来自其上游的所有内容都传递过去的MCP工具是一个安全风险。这就是两难中的“夹缝”。显而易见的解决方法是过滤工具的响应。但随后财务部门需要对订单有不同的视图，支持部门需要一些内部笔记，另一个团队连接库存系统，现在你必须维护数十个相似且重叠的工具。这就是“难处”。

出路是一个确定性的、字段级的契约，它精确指定每个代理可以看到和做什么，独立于上游API和下游代理。MCP定义了代理如何发现和调用工具。字段级契约定义了这些工具被允许访问的内容。它们是不同的层，你需要这两者。

GraphQL是一项流行且广泛部署的技术，为我们提供了一种实现这一目标的实用方法。

GraphQL的设计围绕着这样一个理念：API调用应该指定它们需要的确切字段。订单状态查询可以小到这样：

```
query {
  order(id: "order-1842") {
    status
    shipBy
  }
}
```

响应仅包含这些字段，无论上游系统提供什么其他内容。最初设计用于在移动网络上缩小大型API有效负载并避免编写BFF，这个理念现在为工程师提供了一个强制执行代理权限的地方。

因此，例如，如果代理请求诸如 `internalFraudScore` 或 `customerSSN` 这样的字段，GraphQL服务器可以阻止该请求，甚至使这些字段无法访问。该规则属于该字段，并适用于请求它的操作。每个工具的作者不必记住从另一个响应中删除相同的属性。

写入操作的工作方式相同。我们的运营员工需要请求库存调拨的权限。只读连接会阻碍工作；不受限制的访问也可能让代理更改库存数量、取消订单或发出退款。一个mutation（我们在GraphQL中称之为写入）例如 `requestInventoryTransfer` 暴露出特定的业务动作。运行时对其进行授权，底层服务在接受请求之前检查当前的可用性和任何所需的批准。

这一切都不需要替换运行业务的API。GraphQL层可以位于暴露REST、gRPC、SOAP以及任何其他协议的现有服务之上。订单API可以继续向集成层返回广泛的记录，而代理仅接收其被允许看到的字段。

帮助开发人员快速构建高效应用程序的精准性，在调用方是运行时组合操作的代理时更加有用。GraphQL向应用程序提供了这种字段级契约已有十多年之久，为Shopify、Netflix、Airbnb、Expedia Group和Walmart每天数十亿美元的交易提供动力。这些公司和无数其他公司已经积累了运行完全这种模型的十年经验和生产基础设施。

MCP使业务系统可被代理访问。字段级契约使这种访问成为组织可以控制的东西。GraphQL就是摆在我们面前的完美答案。
