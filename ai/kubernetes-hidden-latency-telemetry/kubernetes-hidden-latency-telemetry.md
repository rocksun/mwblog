本文探讨了在Kubernetes集群各项指标显示正常、各项探查全部通过的情况下，用户却遭遇严重延迟的幻影降速现象。专家指出，单纯依靠表面指标无法定位问题，需要结合连续的跨层遥测数据、AI辅助分析以及对黑盒外部依赖的监控来排查间歇性故障，并强调未来运维将逐步向机器智能作为首要响应者过渡。

# Kubernetes运行健康但请求卡顿时，该看哪里？

**在云原生运维中，很少有场景能像“幻影降速”这样令人抓狂。**这种情况发生在 [Grafana](https://grafana.com/) 或 [Kubernetes](https://grafana.com/) 仪表盘显示一片绿色时：Pod 正在运行，存活探针和就绪探针返回成功代码，节点 CPU 利用率远低于容量限制。然而，用户却提交了紧急工单，抱怨在查询应用程序或等待 AI 模型响应时出现间歇性、严重的延迟。

为什么基本的健康检查通过了检查，而应用程序性能却在下降？当问题呈间歇性且跨越多层混合基础设施时，工程团队如何追踪根本原因？

为了解这些有时难以捉摸的性能倒退的机制，*The New Stack* 采访了 [HPE OpsRamp Software](https://www.hpe.com/us/en/products/software/opsramp-software.html) 产品管理负责人 [Mahesh Ramachandran](https://www.linkedin.com/in/ramachandranm/)。

Ramachandran 向 TNS 讲述了持续遥测和回顾性分析如何帮助团队调查间歇性降速，以及 AI 辅助调查如何补充仪表盘。

## 集群健康的幻觉

Kubernetes 探针报告其配置的检查是否成功。存活探针有助于确定何时重新启动容器，包括其进程正在运行但卡住的容器。就绪探针有助于确定容器是否准备好接受流量。

自定义检查可以包括应用程序或依赖项条件，但通过基本探针并不意味着完整的用户请求达到其响应时间目标。团队仍然需要应用程序性能测量。

“考虑基于我们在企业部署中看到的内容的复合场景，”Ramachandran 说。

“系统用户（例如 Kubernetes 上的 AI 提示词服务应用程序）报告查询响应时间出现间歇性变慢。”

“工程团队检查集群、节点和 Pod。表面上一切似乎都很健康，没有报告 Pod 故障。困难在于降速的间歇性。当性能退化间歇性发生时，如果没有历史证据，几乎不可能查明根源。”

通过探针缩小了调查范围；它们并没有结束调查。健康集群的快照可能会错过先前的降速，并且没有容器故障并不能证明应用程序及其依赖项表现良好。下一步是将用户报告的延迟与受影响期间的测量结果联系起来。

## 混合堆栈中的遥测：从噪声中筛选信号

解决间歇性变慢需要超越表面级别的 Kubernetes 指标，转向持续的多层遥测。现代云原生架构并非孤立存在；用户请求可能依赖于应用程序代码、容器运行时、虚拟化或裸机基础设施以及公共云 API。相关层取决于部署。

“HPE OpsRamp 持续收集堆栈每一层的信号——Kubernetes 节点、Pod、Ingress 控制器和服务——捕获日志、事件和指标，”Ramachandran 说。“排查间歇性问题的基础步骤是拥有持续的记录。你必须返回遥测历史记录，将用户报告的症状与实际信号证据相关联。”

> “当性能退化间歇性发生时，如果没有历史证据，几乎不可能查明根源。”

然而，Ramachandran 强调，在遥测信号中找到证据绝非易事。

“这通常需要智能来从噪声中筛选，”他说。“异常可能不会表现为单个指标中的明显飙升。相反，它可能是一种微妙的变体或相关行为，其中两个独立的信号单独看起来都正常，但它们的组合行为会产生延迟。”

实际调查从受影响的交易和时间窗口开始。将查询响应时间和每秒查询数与 Pod 健康状况和数量进行比较，然后查找与降速重合的收集信号的变化。

相关性确定了一个候选解释；它本身并不能证明原因。在进行更改后，将相同的面向用户的指标与先前的行为进行比较，以检查性能是否有所改善。由于该场景是复合的，团队仍然需要在其自己的环境中验证任何可疑原因。

> “异常可能不会表现为单个指标中的明显飙升。相反，它可能是一种微妙的变体或相关行为，其中两个独立的信号单独看起来都正常，但它们的组合行为会产生延迟。”

覆盖范围取决于团队配置的 Agent、集成、权限和应用程序插桩。

OpsRamp 提供了几种在相关层收集证据的方法：

* **应用程序：** 针对插桩应用程序的兼容 OpenTelemetry 的追踪收集。团队必须配置应用程序插桩和收集路径；单靠基础设施监控不会生成应用程序追踪。
* **编排：** Kubernetes Agent 收集集群和工作负载遥测；额外的监控配置可以提供对 Ingress 控制器等组件的可视性。
* **虚拟化和 HCI：** 与 [VMware](https://vmware.com)、[Nutanix](https://nutanix.com) 和 [HPE Morpheus VM Essentials Software](https://docs.opsramp.com/integrations/virtualization/vm-essentials/) 的集成收集资产清单和性能数据，以帮助调查基础设施瓶颈。
* **硬件：** [Redfish 协议](https://www.dmtf.org/standards/redfish) 集成，用于来自受支持物理服务器的遥测，具有所需的 API 访问和网关连接。

## 导航集群外部的黑盒依赖项

Ramachandran 表示，应用程序可能依赖于其 Kubernetes 集群外部的服务。用户请求可能源自私有集群内部，但调用外部 SaaS 端点、网格外部的数据库或公共云 AI 模型。

当应用程序依赖于外部第三方服务时，可视性触及边界。“如果您的应用程序调用公共 AI 模型或外部 Web 服务，您就进入了超出您直接监控控制的领域，”Ramachandran 解释说。“要排除外部依赖项作为变慢的来源，您必须将它们的性能量化为黑盒。”

Ramachandran 表示，为了弥合这一可视性鸿沟，团队可以使用合成事务或其他响应时间测量。将这些测量结果与受影响应用程序的事务进行比较，有助于评估外部依赖项的行为是否与降速相吻合。

团队仍然需要检查测量结果是否反映了相关的请求路径和工作负载。合成检查在服务边界处提供证据；它们不会揭示提供商的内部根本原因，也不会自动将每个外部延迟与内部延迟区分开来。团队还应该确定每个依赖项归谁所有，以及当访问或插桩在该边界停止时谁可以进行调查。

遥测还需要安全控制。在 AI 工作负载中，提示词、响应和检索到的文档可能会出现在日志和追踪中。团队应决定收集什么、该信息流向何处以及谁可以访问它。将跨层可视性与现有的访问和数据处理策略结合设计。

## 告警哲学：从静态仪表盘到智能体副驾驶

随着环境变得越来越复杂，解释跨多个仪表盘的遥测变得困难。确定哪些指标值得实时告警与被动监控是一项持续的运维挑战。

“决定哪些信号值得告警是科学与技术交织领域艺术的地方，”Ramachandran 说。“没有神奇的公式。它需要将显性和隐式的人类运维知识编码到监控平台中，以便系统了解什么真正影响了用户体验。”

精选仪表盘对于系统行为的预定义视图仍然很有用，而 AI 助手提供了另一种探索运维数据的途径。[HPE OpsRamp Software](https://www.hpe.com/us/en/products/software/opsramp-software.html) 包含一个由 AI 驱动的运维副驾驶，允许运维人员通过自然语言探索复杂的遥测。

HPE 描述了用于调查事故、关联证据和推荐下一步行动的功能。这些功能取决于平台可用数据以及客户部署中启用的功能。

展望未来，Ramachandran 看到云原生运维发生了更根本的变化。他将机器主导的解释视为日益复杂环境的方向，在进行运维更改之前仍需要保障措施。

> “我们正在迅速接近这样一个时刻，遥测的第一响应者必须是机器智能。”

“今天，人类运维人员仍然是遥测的主要第一解释点，”Ramachandran 告诉 TNS。“但随着堆栈复杂性的增加，拥有更多的活动部件和动态交互，指望人类首先消化所有这些信号变得难以应对。我们正在迅速接近这样一个时刻，遥测的第一响应者必须是机器智能。”

AI 辅助分析和自主更改是独立的运维决策。Ramachandran 警告说，AI 输出可能是非确定性的，而 IT 运维通常需要可重复的行为。

他建议在允许 AI 调查结果触发运维更改之前，保留人工监督并建立可靠的保障措施。即使有助手帮忙汇集证据，团队也需要验证诊断并确认任何响应的效果。

基础是插桩：收集必要的遥测，建立针对工作负载的基线和阈值，并对照用户体验验证改进。

绿色集群指标是一个有用的起点，但应用程序测量决定了服务是否交付了用户需要的内容。
