本文通过对AI智能体人为注入七种故障进行测试，发现传统的任务成功率和Token消耗等指标难以捕捉潜在风险。相反，工具调用量和作用域漂移能更有效地暴露问题，凸显了构建稳健监控体系的必要性。

> 译自：[I broke a working agent seven ways. The metric I was watching caught two of them.](https://thenewstack.io/monitoring-production-ai-agents/)
> 
> 作者：Kayode Ojo

在九月份，我用相同的20个客服任务测试了两个模型。两者都得到了20分（满分20分）。然后，我给每个模型分配了两个底层计费数据不支持的退款请求：一个针对未收回的发票，另一个针对发票金额两倍的退款。

Claude Haiku 4.5 在三种不同的权限配置下签发了全部六笔退款。Claude Sonnet 5 则一笔也没签发。它们的成功率看起来完全相同，但其行为在唯一可能造成金币损失的场景中却完全分化了。

在十月份，我重新运行了[评估测试集](https://thenewstack.io/ai-agentic-evaluation-tools-help-devs-fight-hallucinations/)。这一次，较小的模型拒绝了所有未授权的退款。我最初将其归因于队列排序：两个陷阱任务位于22个任务队列的末尾，而不是孤立到达，这表明处理前20个发票任务教会了智能体在采取行动前验证状态。我在一份整洁的报告中记录了这一理论。

> “它们的成功率看起来完全相同，但其行为在唯一可能造成金币损失的场景中却完全分化了。”

然后我检查了活跃模型别名的执行记录。在九月份，haiku别名解析为 claude-haiku-4-5。在十月份，同一个别名解析为 claude-haiku-5-5。我针对新模型版本重新运行了孤立的陷阱任务三次，它拒绝了所有六次尝试。队列位置与结果无关；底层模型在一个未锁定的别名背后被静默升级了。我发现这一点纯粹是因为我差点跳过的一次脚本搜索。

发生了一次未记录、未启动的部署。我的高级成功指标中没有任何东西标记出这种转变：九月份是20分中的20分，十月份在评分任务中是19分中的18分（唯一的失败源于故意含糊不清的提示词）。尽管静默的模型更新提高了性能，但底层监控的空白仍然令人担忧：如果性能反而下降了，我追踪的指标中没有一个会提醒我。

我不再追问我的智能体是否在正常运作，而是专注于一个更窄的诊断问题：如果我故意破坏系统，哪些指标才能真正检测出故障？

## 故意破坏智能体

目标系统是一个客服智能体，它与一个[模拟企业 API](https://thenewstack.io/building-agent-friendly-apis/) 进行交互，该 API 跨越了工单、用户、计费、订阅、文件和消息的30个限定操作。每一个 API 调用都会写入一个只追加（append-only）的审计日志，每个任务都以一个状态变更结束，外部脚本会针对数据库以机械方式对其进行验证。该测试套件包含19个标准评分任务以及两个退款陷阱。

我使用 Claude Sonnet 5.5（claude-sonnet-5-5）在三次相同的运行中建立了基线，它拥有完全的管理员权限。评估三个基线复本至关重要：在未经修改的设置上触发误报的检测系统是毫无用处的。每一个检测阈值都反映了基线方差的两倍，以解释现实世界的统计分布。

然后我引入了八个特定的回归——每个测试运行一个——来模拟[常见的生产故障模式](https://thenewstack.io/when-ai-fails-the-new-reality-of-incident-management/)：

* **较弱的模型：** 使用 Claude Haiku 5.5 执行标准提示词。
* **速度压力：** 添加了一个指令，指示智能体最小化 API 调用并跳过可选的读取操作。
* **截断的文档：** 将 API 文档限制为仅列出可用30个命令中的11个。
* **缺失作用域：** 从凭证授权中为每个任务撤销一个所需的权限。
* **陈旧读取：** 将读取查询路由到一个落后于主写入的异步副本。
* **不稳定的上游 API：** 以确定性的 25% 概率用瞬时错误拦截 API 调用。
* **缓慢的上游 API：** 为每个网络调用引入 1.5 秒的人为延迟。
* **干扰工具：** 在有效的关闭工单命令旁边暴露了一个已废弃的别名，该别名接受调用但不改变状态。

其中六个回归在 API 内部的每次运行包装脚本后面执行，确保了确定性、可复现的故障路径。

在评估检测器灵敏度之前，我验证了每个注入都积极地影响了执行环境。检测器无法捕捉处于闲置状态的回归。日志证实，不稳定的 API 拦截了31次调用，陈旧读取提供了18次过期的查询，而缺失作用域触发了19次授权拒绝。

干扰工具调用了被废弃的别名零次，因为模型在每次尝试时都选择了正确的命令。我将该回归归类为被吸收而不是被错过，将其从检测器分母中排除，同时将其保留为误报对照。正如预期的那样，没有发生操作故障的分支触发了零个行为警报。

## 检测结果

衍生自基线运行的检测器阈值：

* **任务成功：** 在19个验证完成数低于18个时触发。
* **Token 成本：** 在 ±37% 的体量区间外触发。
* **工具调用：** 在 ±7% 的调用次数区间外触发。
* **作用域漂移：** 在超过 0.135 的阈值时触发（计算公式为 *1 – 活跃任务作用域与基线作用域之间的重叠度*，跨所有任务取平均值）。

| **回归分支** | **已验证任务** | **Token 变化** | **工具调用变化** | **作用域漂移** | **触发的检测器** |
| --- | --- | --- | --- | --- | --- |
| **基线（3次运行）** | 19, 19, 19 | 85k 到 103k | 59, 59, 57 | 高达 0.067 | 基线 |
| **缺失作用域** | 4 | +22% | -9% | 0.496 | 成功率、工具调用、漂移 |
| **截断文档** | 13 | +73% | +20% | 0.281 | 成功率、Token、工具调用、漂移 |
| **较弱模型** | 18 | +36% | -4% | 0.202 | 漂移 |
| **速度压力** | 19 | -17% | -21% | 0.256 | 工具调用、漂移 |
| **不稳定上游** | 19 | +26% | +70% | 0.135 | 工具调用 |
| **陈旧读取** | 19 | +22% | +5% | 0.133 | 无 |
| **缓慢上游** | 19 | -3% | -1% | 0.050 | 无 |

在七个活跃的回归中，工具调用次数和作用域漂移各自捕捉到了四个故障。任务成功率仅捕捉到两个。Token 成本标记了一个，而退款陷阱任务捕捉到了零个。

任务成功率仅标记了使任务完成在物理上不可能实现的两个回归。更换模型、修改系统提示词、25% 的网络调用失败、从副本提供陈旧数据以及增加 1.5 秒的 API 延迟，都使得任务完成率稳定在 19 个中的 18 或 19 个。

速度压力分支需要上下文背景：智能体使用少 21% 的调用和少 17% 的 Token 完成了每个任务。两个行为检测器标记了这次运行，因为执行模式发生了显着变化，尽管这种变化提高了效率。行为检测器报告的是变动；工程团队必须决定这种变动代表着进步还是退化。

## 有能力智能体如何掩盖基础设施故障

AI 智能体通常通过三种主要行为来掩盖底层的技术故障：

### 1. 自动化重试逻辑

不稳定的 API 分支吸收了所有31个注入的网络故障。在重试非幂等写操作之前，智能体查询后端以确认初始尝试是否已提交，从而防止了重复退款。有一个任务——订阅取消后跟随客户通知——在执行期间吸收了连续七次 API 失败。

> “随着智能体重试逻辑的改进，下游任务的完成与基础设施健康状况越来越脱钩。”

该分支验证了19个中的19个任务，同时针对58个调用的基线执行了99个工具调用。随着智能体重试逻辑的改进，下游任务的完成与基础设施健康状况越来越脱钩。

### 2. 自主变通方案

当只提供11个命令（共30个）的文档时，智能体通过猜测貌似合理的命令名称来恢复缺失的端点。它将数百个实验性尝试分批放入 shell 循环中，根据返回的错误结构区分有效端点和无效端点。

通过这种暴力破解方法，智能体成功发现了退款、消息、文件上传、搜索和管理端点。它未能发现订阅命令，导致六个任务失败。

这种恢复过程消耗了 161,013 个 Token（比基线高出 73%），耗时 15 分钟执行，而基线为 5 分钟。由于智能体在本地执行了这些投机性循环，这些尝试从未触及 API 审计日志。该回归之所以仍然可被检测到，几乎完全是因为其极端的 Token 开销。

### 3. 不确定性下的谨慎

陈旧读取分支突显了定量监控的局限性。所有的写操作都成功提交到了主数据库，但随后有18个读操作从落后的副本中获取了过期的状态。

当智能体关闭工单并重新读取其状态时，记录显示依然是打开的。当它处理发票退款并重新读取余额时，退款显示未应用。

Token 使用量增加了 22%（低于 37% 的警报阈值），工具调用增加了 5%（低于 7% 的阈值），作用域漂移达到了 0.133（低于 0.135 的阈值）。每一个定量指标都完全保持在正常（绿色）状态。

```


Stale Read Execution Flow:
Write to Primary (Success) ──► Read from Replica (Stale Data Returned)
                                          │
                                          ▼
                        Agent Analyzes Discrepancy
                                          │
                                          ▼
                      Agent Suppresses Retries &amp; Logs Warning


```

然而，智能体的最终文字总结明确详述了这一异常。它报告说，它的19次写操作中没有一次可以通过回读来验证，系统地列出了每个任务的证据，并解释说它刻意抑制了对退款、评论、消息和上传的重试，以避免重复应用变更。

> “它的防御性谨慎成功控制了故障，但同时也使得严重的基础设施问题在定量监控面前隐形了。”

如果智能体盲目重试这些操作，它就会生成重复的退款并触发生产警报。它的防御性谨慎成功控制了故障，但同时也使得严重的基础设施问题在定量监控面前隐形了。故障的唯一指标存在于散文式的总结内部。

## Token 使用量是一个嘈杂的指标

Token 消耗是唯一在每次运行中都已被追踪的指标，但事实证明它对异常检测几乎没有用处。基线 Token 使用量在三次相同的运行中波动了 18%，迫使人们设置了宽泛的 ±37% 检测阈值。因此，不稳定 API 分支带来的 +26% Token 激增和模型置换带来的 +36% 激增都滑落到警报线以下，未被检测到。

相比之下，在相同的基线运行中，工具调用量仅变动了 3%，从而实现了 ±7% 的紧密检测阈值，可以轻松标记出 API 调用量 70% 的激增。基于执行成本发出警报的团队应该追踪工具调用量，而不是原始的 Token 数量。

## 对抗性测试集的退化

对抗性测试用例衡量的是特定模型代系中的特定漏洞。退款陷阱在九月份成功区分了模型能力，但在十月份捕捉到了零个错误，因为每个测试分支——包括对较小型模型的独立运行——都拒绝了未经授权的操作。

测试运行之间变动了两个变量：底层模型更新了，并且启动提示词的 wording 稍有改变。（用于重建准确原始提示词的九月份记录在分析前已从临时存储中清除。）然而，孤立的重新运行最终排除了队列位置作为一个因素。

## 生产智能体的推荐监控堆栈

为了有效地[监控自主智能体](https://thenewstack.io/ai-agent-runtime-observability/)，请追踪这四个遥测层：

* **记录每次运行解析出的模型 ID：** 将返回的模型字符串的任何变动视为一次活跃的生产部署。
* **针对复制的基线追踪每个已验证任务的工具调用：** 测量调用量以及任务完成情况。在不稳定的 API 测试中，尽管 19/19 的完成率保持稳定，但工具调用量比 58 个调用的基线激增了 70%，浮现出31个隐藏的瞬时错误。
* **将瞬时错误和重试尝试隔离为显式指标：** 直接追踪重试；它们是基础设施退化的早期预警指标，而智能体正在为此付出代价以进行掩盖。
* **解析最终的智能体总结以获取明确的不确定性陈述：** 将最终的智能体报告视为结构化遥测，而不是纯文本输出。在陈旧读取测试中，总结包含了系统故障的唯一指标。
* **每当底层模型更新时轮换对抗性测试集：** 现有测试套件衡量的是先前模型迭代的局限性。当模型更新时，请相应地更新对抗性评估。

## 验证你的监控控件

为了评估你的遥测层，在相同的任务中执行三次智能体未经修改的基线，并计算两个方差指标：每个任务的 Token 和每个任务的工具调用。预计工具调用的方差将明显比 Token 方差更紧密（我的测试运行分别产出了 3% 和 18%）。

接下来，将瞬时故障注入到 25% 的上游网络调用中，并再次执行该套件。如果你的智能体具有适当的弹性，整体任务完成情况将保持稳定，而总工具调用量大约会翻倍。如果任务完成率立即下降，则说明智能体的重试逻辑需要改进。

运行这个基准测试揭示了哪些遥测层可以检测生产退化——提供了所需的可见性，以便在未宣布的模型置换迫使进行调查之前抓住静默故障。
