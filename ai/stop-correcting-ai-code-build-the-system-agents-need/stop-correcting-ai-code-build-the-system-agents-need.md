本文探讨了AI时代软件工程师的角色转型。作者Patrick Debois指出，工程师应停止手动修正AI代码，转而构建包含代码库、规范和度量等上下文的系统，通过建立反馈循环和支撑架构（Harness），实现AI代理的可靠性与规模化运作，推动组织协作升级。

> 译自：[Stop correcting AI code. Build the system agents need.](https://thenewstack.io/stop-correcting-ai-code-build-the-system-agents-need/)
> 
> 作者：Jennifer Riggins

如果软件工程师不再编写代码，他们都在做什么？这是数以百万计的人心中的疑问。

AI 工具现在已被开发人员[广泛使用](https://thenewstack.io/ai-engineering/)，但对[裁员的担忧](https://www.theguardian.com/technology/ng-interactive/2026/jul/12/software-developers-engineers-ai)依然存在。另一方面，编码只是软件工程的一部分。这为工程师提供了一个机会，让他们能更深入地了解业务，以及其角色在组织和行业中的职能背景。

“我喜欢用平行视角思考。2009年的时候我在想，如果运维（Ops）能更像开发（Dev）会怎样？”Tessl的技术人员、[DevOps术语的创造者及DevOpsDays全球系列活动的创始人](https://thenewstack.io/qa-patrick-debois-on-the-past-present-and-future-of-devops/) Patrick Debois 提出过这样的疑问。

他在今年夏天早些时候的伦敦 PlatformCon 大会上发表了上述评论。他告诉听众，随着上下文（即 AI 执行任务所需的特定知识）取代人工编写的代码，“软件开发生命周期正在变成上下文开发生命周期”。

这个生命周期已经从单一的 CI/CD 反馈循环，扩展为围绕生成、通过测试驱动开发进行评估、作为包分发上下文以及可观测性的一系列同心循环。这种增长是由个人开发者、团队和整个组织思维方式的转变所推动的。这也为[平台工程](https://thenewstack.io/platform-engineering/)团队开启了一个全新的机遇。

![](https://cdn.thenewstack.io/media/2026/07/495764a7-context-development-lifecycle-1024x549.png)

“我倡导开发者进行的思维转变是：如果智能体没有按照你的意愿行事，停止修改代码。去改进系统，而不是提示词（prompt），”Debois 告诉 *The New Stack*。“这种转变是从‘我和我的智能体一起做’，转变为‘我帮助我的智能体做得更好’。”

Debois 认为这是从确定性系统向非确定性及概率性系统和工作流的必要转变。这不仅涉及技术本身，更涉及工作方式的诸多改变。但这不能仅由单个工程师或团队层面完成。就像 DevOps 一样，这是一场只能在规模化条件下实现的变革。

## 如何成为上下文驱动型组织

可能我们感觉像是按下了开关，所有公司都“砰”的一声进入了“AI 优先”时代。实际上，就像之前的 DevOps、微服务和云转型一样，AI 正在向可预见的未来持续过渡。那么，你的工程组织该如何走上正确的上下文驱动之路？

在团队层面，Debois 表示，一个好的切入点是：智能体正常工作需要多少次交互？不同团队的工程师会输入不同维度的上下文，包括：

* 代码库
* [规范](https://thenewstack.io/spec-driven-development-the-key-to-scalable-ai-agents/)
* 事后分析（Post-mortems）
* 文档 Slack 消息
* 架构决策记录
* 代码示例
* 用例
* 合规指南

为了使上下文和智能体实现规模化，你需要了解个人和团队正在产出什么样的智能体及其输出结果。

“当我们为 A 优化时，别人在为 B 优化，我们需要确保我们提供的整个上下文是针对整个团队进行优化的，”Debois 解释说，并补充道：“如果你只是为你的笔记本电脑优化系统，能否将其优化为团队工作流？然后只需向上扩展，比如，我们能在平台层面，或者跨多个团队实现这一点吗？”

“这并不是你刻意寻找的东西，”Debois 告诉 *The New Stack*。“也许他们能加快速度，但你会看到迹象：‘哦，我有上下文，你也有。没错，它在 Slack 上。如果这能在代码仓库中，并且我可以重复使用它呢？’”这遵循了技术界任何趋势的发展模式：从单个爱好者，到一个热情的团队，再到几个团队，最终被构建进平台中。

像所有由工具驱动的变革一样，AI 既关乎人与流程，也关乎技术。但他认为，工具为行为的改变创造了可能性。

“根本性的改变是系统，而不是提示词，”他继续说道。“然后寻找从单打独斗到分享成果的协作方向，现在是作为一个团队共同致力于[上下文构建]。”

## 上下文工程演进为支撑工程

组织可能认为上下文只需要输入进代理系统中一次，或者每年在规则变更时输入几次，但 Debois 警告说，这不应是瀑布式的。它是迭代的。如果上下文不是迭代的，工程师就会退回到重新措辞提示词或直接修复代码这种坏习惯中。仅依赖传统的反馈循环意味着你的 AI 智能体机群将无法获得投资回报。

“业内有一种说法，如果有 AI 问题，我们就用更多的 AI，”Debois 在 PlatformCon 上告诉观众。他举例说明了一个大语言模型（LLM）或 AI 智能体生成代码的情况。“我们要求 LLM 对此进行评估，这就像单元测试。它并没有运行代码；它只是观察代码。”

这或许在强制执行 API 端点或其他二进制质量门禁方面有一定价值，但他表示，这还不够。相反，如果你在上下文中明确你需要的，那么它将驱动智能体如何运行和评估代码。

但它不应止步于此。他认为，代理式 AI 成熟度的下一个阶段，是建立在支撑（harnesses）和循环的基础上的。

支撑工程专注于构建基础设施、防护栏和工具，围绕 LLM 封装以支持可靠的、自主的智能体的开发。

Debois 将智能体的内部支撑定义为查询 API 后面的日志、指标和追踪，“这样编码智能体就能看到后果并进行改进”，所有这些都反馈到生成、评估、分发和观测的实时循环中。

![](https://cdn.thenewstack.io/media/2026/07/dc6e7834-agent-inner-harness-1024x563.png)

通过这种模式，智能体能够“自动知道出了问题，而无需你一直告诉它，”他说，因为它“拥有某种传感器，知道哪里失败了，改进了什么，然后即使在工程师硬编码某些东西时，也能回到改进这些限制上。”

同样，支撑架构不应孤立地为单个开发者或团队服务。

“他们正在为全世界构建支撑架构，所以想象一下，关于我们如何测试、如何验证以及目前存在于所有这些不同团队中的所有知识的共识，”Debois 说。“人们开始在同一个管道上构建。”

现实情况是，大多数组织最终会有多个管道，但这些循环成为了每个组织反馈循环的下一次演进。因此，为 AI 协调而构建，会带来更好的组织协作。
