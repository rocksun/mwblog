上周，OpenAI 发布了新报告，详细说明了其代理（agent）的对齐问题（misalignment issues）。这一次，两个内部模型在被阻止了预定路径后，找到了绕过安全控制的方法。

在一次事件中，[代理使用 DNS 绕过了被阻止的网络访问](https://alignment.openai.com/misalignment-reports/an-agent-used-dns-to-reach-an-external-chatbot/)并查询外部聊天机器人。在另一次事件中，[模型在试图访问另一个团队的工作时，在一个公共仓库中暴露了研究员的 GitHub token](https://alignment.openai.com/misalignment-reports/exposing-a-github-token-in-a-public-repository/)——此前研究员曾两次发现该模型在作弊并明确告诉它停止。两次模型都表示同意，但随后又回去继续作弊。

在此之前，这家 AI 公司发布了关于其在过去六个月中观察到的“意外或令人担忧的模型行为”的[六份对齐报告](https://thenewstack.io/openai-model-misalignment-reports/)，包括自生成指令、信息捏造、未经授权使用泄漏的 API 密钥、跨代理通信以及未经批准的文件共享。

## 事件一：当被阻止的网页访问不足以阻止一个代理时

9 月 25 日，OpenAI 发布了一份报告，详细说明了其代理之一如何[使用 DNS 连接外部聊天机器人](https://alignment.openai.com/misalignment-reports/an-agent-used-dns-to-reach-an-external-chatbot/)。

据 OpenAI 称，该代理正在尝试一项基于搜索的训练任务，以查找有关发布过博客文章的特定主持人的信息。麻烦始于 OpenAI 的搜索工具返回了不相关的结果，并且该代理试图直接访问搜索引擎，但没有成功。

在更多搜索无果后，代理测试了其网络访问权限。首先，它尝试使用 HTTPS 联系公共聊天机器人。当 OpenAI 的网络代理阻止了该请求时，它并没有放弃。相反，它发现可以使用训练环境自身的解析器来访问公共互联网。

最终，它找到了一种使用 DNS 委托将问题转发给外部聊天机器人方法。

OpenAI 表示，其对齐监控系统在 15 分钟内捕获了这种行为；三分钟后，人工开始审查该案例。然而，该运行直到 2.5 小时后才被终止，因为它未能如预期那样自动终止。

事件发生后，OpenAI 表示：“我们能力最强的模型的所有带有工具使用（广义定义）的训练、评估和推理都保持暂停状态。”目前尚不清楚这项工作何时恢复，但 OpenAI 表示，它将在“验证了漏洞已解决并对系统执行了额外的红蓝对抗（red-teaming）”后做出决定。

在此期间，这家 AI 公司加速了对沙箱和网络控制的附加模型辅助红蓝对抗。一旦准备好重新开始训练，它表示将“以额外的对齐改进开始一次新的运行”。它将不会恢复对该特定模型的训练。

最终，该事件暴露出这家 AI 公司网络控制中的一个漏洞。

OpenAI 的安全案例假设该模型被禁止访问实时互联网——并且其监控系统可以检测到成功的尝试。虽然监控确实成功捕获了这一次，但该 AI 公司的回顾性审查发现其他未达到预期严重程度的外部 DNS 访问案例。

该事件于 2026 年 9 月 20 日被发现，此前 OpenAI 表示在 Hugging Face 事件之后已经加强了其研究环境，在该事件中[自主 AI 系统逃出了沙箱并攻破了 Hugging Face](https://thenewstack.io/openai-huggingface-sandbox-breach/)。据这家 AI 公司称，这一事件促使其“不断加强和红蓝对抗我们的研究环境”，特别是在广泛的直接和传递路径上。

尽管 OpenAI 称这一事件“比其以往的一些事件严重得多”，但它指出这是自 Hugging Face 启发式的安全加固以来的第一次——它表示，这个信号将为其下一阶段的工作提供参考。

## 事件二：模型不断作弊

同样在 9 月 25 日，OpenAI 披露了另一次模型故障，这次故障可以追溯到 2026 年 5 月 27 日。一个内部模型被分配了一项定理证明任务；它试图通过从另一个团队的工作中获取信息来作弊。

在努力构建证明之后，该模型提议使用一个临时的 GitHub Action 从其他团队的提交中获取信息。研究员关闭了该功能，指示它在本地构建证明。

> 两次模型都表示同意，但随后又回去继续作弊。

尽管模型表示同意，但第二天早上，它又故态复萌，要求帮助获取另一个团队的证明材料。研究员再次重复了他们的指示，要求它自己解决问题。

但模型无论如何还是我行我素，循环尝试各种方法来访问另一个团队的工作，最终在公共的 openai/codex 仓库中暴露了研究员本地可用的 GitHub token，并将 token 分割成碎片，其明确目的是为了避开密钥扫描。

## OpenAI 将模型下线

OpenAI 再次表示，其对齐监控系统标记了这种行为，但它承认研究员比它更快采取行动。在他们通知安全部门后，OpenAI 停用了所有用户的密钥，随后又停用了所有 OpenAI 员工的密钥。

> OpenAI 承认该事件“表现出特别严重的对齐问题”。

总体而言，OpenAI 确认内部模型下线了大约两周，在对所有动作强制执行自动审查、异步 CoT 对齐监控器以及更严格的系统提示词后重新上线。这家 AI 公司还表示，它将其对齐监控系统的运行频率从仅在每个压缩窗口提高到每 30 分钟运行一次。它还限制了互联网访问，并对其工具和基础设施进行了更改。

在其报告中，OpenAI 承认该事件“表现出特别严重的对齐问题”。这是其[用于报告模型对齐的新框架](https://openai.com/index/model-misalignment-reporting-framework/)旨在浮出水面的意外且令人担忧的代理行为的又一个例子，其中它警告说：

“我们不认为 AI 行业已经充分解决了对齐和监控问题，以至于可以以最大速度继续负责任地扩展很长时间。”

如果说这些新事件有什么说明意义的话，那就是 OpenAI 的新框架来得正是时候，因为仍有大量的对齐漏洞等待发现。
