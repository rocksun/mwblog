OpenSSH 10.6 版本为了安全起见，主动禁用了 SSH 压缩中的 LZ77 字典编码以防止明文泄露，并在命令行用户名中屏蔽了特定字符以防注入，同时承认这些改动会打破部分现有工作流。

> 译自：[OpenSSH 10.6 deliberately breaks two features in the name of security](https://thenewstack.io/openssh-breaks-compression-usernames/)
> 
> 作者：Amanda Caswell

**周二发布的 OpenSSH 10.6** 降低了压缩效果，并拒绝了一些以前可以正常使用的用户名，维护人员在发布这些变更时就知道这两项改动会导致某些功能失效。

其中一项改动禁用了用于 SSH 压缩的 LZ77 字典编码器，此前研究人员发现，在多个通道之间共享压缩状态可能会暴露明文。另一项改动则阻止了命令行用户名中的 `$` 和 `\`，以防止它们被诸如 ProxyCommand 和 Match exec 等指令通过 shell 进行解释。

此次[发布](https://www.openssh.org/txt/release-10.6)正值 OpenSSH 面临更多利用 AI 模型进行的安全研究之际，同时[这些模型在发现可利用漏洞方面变得越来越强](https://thenewstack.io/claude-exploits-openai-forum/)。其他研究人员随后也独立发现了一些此类漏洞。OpenSSH 警告称，那些不公开自己发现的对手“也很可能会发现这些漏洞”，目前该计划打算更频繁地发布修复程序，而不是等待其通常的发布时间表。

> OpenSSH 警告称，那些不公开自己发现的对手“也很可能会发现这些漏洞”，目前该计划打算更频繁地发布修复程序，而不是等待其通常的发布时间表。

## 压缩上下文会泄露明文

SSH 可以在一个加密连接上承载多项内容，包括交互式 shell、端口转发或动态 SOCKS 代理。当启用压缩时，这些通道共享相同的压缩状态，尽管 [OpenSSH 默认关闭了压缩](https://man.openbsd.org/ssh_config)，因此这种攻击只有在有人将其开启时才有效。

波鸿鲁尔大学的安全研究人员 [Fabian Bäumer](https://www.linkedin.com/in/fabian-baumer/) 和 [Marcus Brinkmann](https://www.linkedin.com/in/marcus-brinkmann-57b39a1/) 在他们的论文中演示了这个问题：[“跨越流：通过多路复用通道中的公共压缩上下文进行 SSH 明文恢复。”](https://arxiv.org/abs/2609.07709) 攻击者可以将选定的明文馈送到一个通道中，并观察由此产生的加密流量，从而利用压缩来恢复在同一会话的另一个通道中传输的机密。

> 攻击者可以将选定的明文馈送到一个通道中，并观察由此产生的加密流量，从而利用压缩来恢复在同一会话的另一个通道中传输的机密。

该泄漏源自 LZ77 的内存。它不是再次编码相同的字节序列，而是可以指向它已经见过的匹配序列。OpenSSH 在各个通道之间共享了该历史记录，因此攻击者控制的数据可以改变会话中其他地方的机密是如何被压缩的。当猜测与该机密的一部分相匹配时，产生的流量可能会变得稍微短一些，从而为攻击者提供另一条信息。

这使得该攻击与针对 HTTP over TLS 的 CRIME 和 BREACH 属于同类攻击，尽管在这里成功需要相当特定的设置。攻击者控制的流量和机密必须共享同一个多路复用的 SSH 会话。在噪声最低的测试中，Bäumer 和 Brinkmann 在 100 次试验中，平均通过 276 次猜测，从 26 个字符的字母表中恢复了一个 8 个字符的机密。在噪声更大的基于浏览器的场景中，这一数字跃升至约 27,600 次。

这两位研究人员使用 Claude Code 为所有三种攻击场景构建了概念验证实现，而且他们并不是唯一对 OpenSSH 使用 AI 工具的人，因为 10.6 版本还将修复另外两个漏洞归功于与 Claude 和 Anthropic Research 合作的 [Chris Rohlf](https://www.linkedin.com/in/chrisrohlf/)。

## 保留哈夫曼，弃用 LZ77

OpenSSH 采用了直接的修复方法，彻底删除了共享字典。Deflate 使用 LZ77 来查找以前见过的数据的重复块，然后使用哈夫曼编码用更少的比特表示常用值。OpenSSH 10.6 在 `ssh` 和 `sshd` 中都禁用了 LZ77 部分，同时保留了哈夫曼编码。

压缩仍然有效，只是效果不如从前。OpenSSH 警告称，`Compression` 选项的效率会降低，并建议改在应用层处理压缩，它表示在应用层通常表现会更好，同时也不会受到此攻击的影响。

大多数交互式 SSH 会话可能不会注意到这种差异，但在受限连接上传输大量可压缩数据的自动化作业可能会注意到。这些工作负载可能需要在升级后将压缩从 SSH 移至应用程序中。

> 大多数交互式 SSH 会话可能不会注意到这种差异，但在受限连接上传输大量可压缩数据的自动化作业可能会注意到。

用户名的更改针对的是从外部输入构建的命令。内部工具、CI 作业或智能体可能会运行类似 `ssh "$INPUT_USER@host"` 的命令，该用户名随后可能会最终进入 `ProxyCommand`、`Match exec` 或传递给 shell 的其他命令中，在这些命令中，诸如 `$` 和 `\` 之类的字符可能会突然变成 shell 语法，而不仅仅是用户名的一部分。

这已经不是该项目第一次收紧这条路径了。[版本 10.3](https://www.openssh.org/txt/release-10.3) 修复了一个相关的漏洞：命令行用户名检查 shell 元字符的时间太晚了，此时它们已经可以通过 `ssh_config` 进行扩展。

在 10.6 版本中，在命令行上传递的用户名中拒绝 `$` 和 `\`, 但当用户名是通过 SSH 配置文件中的 `User` 指令设置时，此限制不适用。包含这两个字符的合法账户仍然可以通过这种方式工作，尽管直接传递这些用户名的脚本和智能体工具将必须做出更改。

## 后量子密钥，弃用的 scp

OpenSSH 10.6 中还有一些其他更改可能会给自动化工作流带来绊脚石。混合后量子 `ssh-mldsa44-ed25519` 签名算法失去了其实验性的 `@openssh.com` 后缀，这意味着使用早期实现创建的密钥需要重新生成或删除。该版本还开始逐步淘汰用于远程到远程复制的 `scp -R`；它在 10.6 中仍然有效，但现在会产生警告，并最终将被忽略。
