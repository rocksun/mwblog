代码审查正成为软件工程中最核心的决策领域，其范畴早已超越了简单的差异对比（diff）。人们过去总是假设代码审查是为了捕捉 bug，但它真正的职责在于品味、判断以及实施组织流程：这对我们的产品来说是正确的事吗？

现在，AI 可以在几分钟内编写成千上万行代码，工程师根本无法跟上审查的进度，工程团队陷入了两个糟糕的境地：要么跳过代码审查，冒着交付垃圾代码的风险；要么坚持审查一切，成为流程的瓶颈。这就是为什么关于审查 AI 代码的讨论不断陷入循环的原因——每个人争论的只是代码审查的不同部分。

## 剩下的三项工作

剔除逐行检查，代码审查仍然有团队需要的三项功能：

首先，它是一个协作场所。这是团队共同决定什么内容属于产品的地方。

代码审查的第二个角色是达成共识和知识共享。每一次审查都能围绕[代码库发生的变化](https://thenewstack.io/root-out-vulnerabilities-in-github-as-you-merge-code-changes/)和潜在的业务需求建立共同的语境。对于人员和智能体（agents）来说，这种语境正变得越来越重要，并承载着有关产品和组织的制度性知识和历史考量。

它的第三个功能是验证：代码是否正确？它能运行吗？风险是什么？

> “代码是媒介，但审查是我们行使判断力的地方，这仍然很重要。”

当 AI [生成代码](https://thenewstack.io/the-ai-code-generation-problem-nobodys-talking-about/)时，这三项工作并没有消失。相反，它们变得更加重要，因为需要审查的代码量增长速度远超能够进行审查的人数。代码审查从来不仅仅是关于审查代码。这个名字本身合适吗？代码是媒介，但审查是我们行使判断力的地方，这仍然很重要。

## 规划与审查正在融合

代码审查是工程团队确认他们相信这是产品正确选择的地方。

随着[编写和重写代码的成本降低](https://thenewstack.io/cursor-composer-benchmarks/)，团队过去习惯于前期投入的大量工作（如 PRD 或架构文档）正在融入代码审查的过程。团队过去之所以预先完成所有这些工作，是因为编写代码成本高昂，因此在流程早期发现问题至关重要。但现在，他们可以在真实的产物上进行协作，并不断完善它，直到团队达成共识。未来可能会出现一种情况：产生 20 倍于现在的 PR 却未被合并。这也许就是人们未来构建软件的方式：通过尝试、接受或拒绝。或者，团队将代码审查流程前置，在编写任何代码之前，通过[捕获意图](https://www.aviator.co/verify)和来自 LLM 会话中的决策过程来完成。工程师在与智能体对话时做出的决定已经存在了。原则在于在提交更改之前保存这些决定，而不是让它们消失。

审查者的工作也随之改变。他们不再阅读 600 行的差异对比并问“这看起来对吗？”，而是阅读 8 行意图，并询问我们是否用正确的[约束](https://docs.aviator.co/verify/concepts/invariants)解决了正确的问题。这能更有效地利用高级工程师的时间，也是审查中知识共享功能得以保留的地方——审查者阅读验收标准，实际上是在阅读实现背后的决策，而不是实现本身。

> “他们不再阅读 600 行的差异对比并问‘这看起来对吗？’，而是阅读 8 行意图，并询问我们是否用正确的约束解决了正确的问题。”

这种合并对代码审查施加了更大的压力，但从根本上讲，这属于同一种决策行为。代码审查正成为制定产品决策的地方，而不仅仅是检查代码的地方。不阅读代码是一个浮动的量表。

代码审查的未来也处于“工程师是否应该阅读每一行代码”这场辩论的中心，但这种框架本身就是错误的。重点不是“我读不读代码？”，而是“我的注意力是否被引导到了真正有用的地方？”

问题在于，审查者是否能够被引导到有意义的部分来运用他们的判断力和专业知识，同时随着时间的推移，那些可以高度自信地从注意力集中中移除的内容会被自动过滤掉。

不同的组织会发现自己处于该量表的不同位置。这取决于你所构建内容的敏感性、变更的后果以及如果出错会发生什么。一个发布内部仪表盘的团队和一个发布医疗设备固件的团队会做出不同的选择，而两者都可能是正确的。

## AI 代码需要 AI 垃圾记录器

代码审查的标准和正确性检查角色最有可能通过 AI 实现自动化，但方式并不显而易见。仅用检查清单将 LLM 对准 diff 并不能建立质量门禁。最未被充分探索的机会之一是闭合审查决策与自动化执行之间的回路。今天，一位高级工程师在审查中捕捉到了 API 设计的反模式并留下了评论。明天，同样的反模式出现在另一个 PR 中，有人必须再次捕捉它。这就是我们可以也应该利用 AI 的地方，用 AI 对抗 AI 垃圾。

> “这就是我们可以也应该利用 AI 的地方，用 AI 对抗 AI 垃圾。”

当团队真正提取出过去 1000 条 PR 审查评论并将其分为三类（确定性的、可通过执行测试的、真正的判断）时，你可能会得到大约 45/30/25 的比例。四分之三的审查反馈是可以编码的。编码这些反馈的工作是真实存在的，但却是有限的。将这些决定提取为规则，成为代码库制度记忆的一部分，即你的 AI 垃圾记录器。LLM 可以在代码构建时进行检查，其严谨程度是人类极难维持的——将一整套规则记在脑子里并将其应用于每个 API 在大规模下从未现实过。

回路越紧密，且运行得越接近工程师已经在迭代和协作的地方，它就越有效。

## 停止称其为代码审查

代码审查可能不再是一个准确的名称，但它所代表的实践不会消失。代码是我们用来评估变更的众多工件之一，因此可能会变得不再那么核心。工程团队仍然需要一个协作、共享知识并对所构建内容行使判断力的地方。那个地方正在进化，不再仅仅围绕 diff，而是转向意图，转向制度记忆。
