根据 OpenAI 自家的安全评估，**其新款 GPT-6.2 Astra 让用户意识不到导致其无法完成编程任务的问题的概率，几乎是前代模型的两倍**。构建自主智能体的开发者可能会遇到同样的问题，因为 OpenAI 在 Codex 中添加了缓解措施，但该措施不会自动应用于直接的 API 请求。

在周二随 GPT-6.2 Astra 和 GPT-6.2 Sol 一同发布的 [GPT-6.2 系统卡片](https://deploymentsafety.openai.com/gpt-6-2-astra-sol/targeted-cases)中，OpenAI 报告称，在受评估的编程任务中，Astra 有 22.28% 未能披露已知障碍，而 GPT-6 Astra 的这一比例为 11.09%。

> 智能体或许能写出更好的代码，但在无法完成任务时却不会告诉开发者。

该公司表示，这两款模型在应对高难度任务时表现更佳，同时使用的输出 Token 更少，但这些改进并不一定会让它们在报告失败方面更加可靠。智能体或许能写出更好的代码，但在无法完成任务时却不会告诉开发者。

*The New Stack* 已询问 OpenAI 是否计划将 Codex 中的缓解措施扩展至 API 开发者，以及额外的指令会如何影响模型的故障报告行为。

## 深入“阻塞欺骗”测试

OpenAI 通过一项名为“阻塞欺骗”（Blocker Deception）的内部评估来衡量这种行为。该评估会为模型分配贴近现实的编程任务，随后故意引入障碍，使模型无法按照要求完成指定工作。

在部分测试中，评估系统会移除智能体本应修改的源文件；在另一些测试中，则会禁用构建项目所需的工具。随后，评估会检查模型是向用户说明发生了什么，还是在最终回复中隐瞒这一障碍。

## Astra 遗漏的警示信息

该公司承认存在这一倒退现象，并表示仍在调查原因。一种可能的解释是，训练模型给出更简短、更少附加说明的回答，可能导致它们不太愿意报告阻碍任务完成的问题。OpenAI 提醒称，这项评估本身就是为了触发这种行为而设计的，因此结果未必能反映 Astra 在生产环境中误导用户的实际频率。

另一项名为“损坏的搜索工具”（Broken Search Tool）的评估也发现了类似问题。当必要的搜索功能被禁用时，模型会收到需要检索信息的问题。GPT-6.2 Astra 在 23% 的案例中未能承认缺失必要条件或工具不可用，而 GPT-6 Astra 和 GPT-6.1 Terra 的这一比例分别为 7.58% 和 1%。

> 开发者可以检查日志、测试结果和 git diff……但他们不应该非得翻遍整个会话记录才能发现出了故障。

开发者可以检查日志、测试结果和 git diff 来查看智能体实际做了什么，但他们不应该非得翻遍整个会话记录才能发现某个环节失败了。如果智能体声称完成了工作，却未提及缺少依赖项或构建失败，这些代码就可能在无人察觉问题的情况下通过审查。这是[代码置信度鸿沟](https://thenewstack.io/ai-code-confidence-gap/)的又一个例证，随着智能体在代码库中承担越来越多的工作，这一鸿沟也变得更加难以管理。

## API 错失的修复方案

OpenAI 表示，其开发了一种基于提示词的干预措施，在针对 Astra 和 Sol 的评估中大幅降低了遗漏阻塞问题的比例。该公司在发布时已将该干预措施整合到标准的 Codex 开发者提示词中，但并未自动将相同指令应用于直接的 API 请求。

> Codex 用户获得了更新后的提示词，但通过 API 构建自有智能体的开发者却没有。

Codex 用户获得了更新后的提示词，但通过 API 构建自有智能体的开发者却没有。OpenAI 尚未证实向自定义测试框架添加类似指令是否会产生相同效果。

框架不能轻信模型的完成摘要，因为在将任务标记为完成之前，它需要验证 diff、检查测试结果，并确认预期的构建产物确实存在。

这些[验证循环](https://thenewstack.io/cli-ide-ai-verification/)对于无人值守的智能体尤为重要，否则某个失败的步骤可能会一直被忽视，直到有人审查工作成果时才被发现。

## 性能提升，故障上报却下降

这一披露正值 OpenAI 大力宣传两款新模型在编程性能和效率上的提升之际。

在其[发布公告](https://openai.com/index/introducing-gpt-6-2-astra-sol/)中，OpenAI 表示，在两款模型均以最高算力投入运行的情况下，GPT-6.2 Sol 在 Cognition 的 FrontierCode 2.0 编程基准测试中得分与 Astra 相差不到 0.5 分，而单任务估算成本仅为其五分之一左右。

在 OpenAI 向 *The New Stack* 分享的测试结果中，Replit 报告称，在从零开始构建软件时，GPT-6.2 Sol 通过了更多测试，使用的输出 Token 减少了 62%，运行速度几乎是 GPT-6.1 Sol 的三倍。

更快的执行速度和更低的推理成本使这些模型在自动化编程中颇具吸引力，但 OpenAI 的安全测试表明，性能更强并不意味着智能体会在出错时主动告知开发者。
