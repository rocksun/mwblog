本文探讨了容器镜像精简与安全性之间的矛盾。传统的臃肿镜像带来巨大攻击面，而“去重化”的distroless镜像又会导致漏洞扫描器失去元数据。文章提出通过自底向上的构建方式（如切片和声明式构建），在保持极小攻击面的同时确保完整的安全可视性。

> 译自：[The distroless security gap: Why bottom-up containers are the next evolution in OCI images](https://thenewstack.io/distroless-container-security-gap/)
> 
> 作者：Lily Rivers-Klee

尝试过缩减容器镜像以减少攻击面吗？如果你尝试过，你可能会发现一个令人沮丧的悖论：缩减容器往往会使你的漏洞扫描器对内部情况“视而不见”。

我们正面临着全行业的一种紧张局势：既要减少[容器攻击面](https://thenewstack.io/open-source-and-container-security-are-fundamentally-broken/)，又要保持所需的安全性可见性。要理解我们是如何走到这一步的，以及如何解决它，我们必须回顾我们历史上是如何构建容器的，以及为什么当前的方法在第二天（Day 2）运维中显得捉襟见肘。

## 容器臃肿的剖析

长期以来，完整容器镜像一直是行业标准。工作流程很简单：开发人员拉取包含完整操作系统的基础镜像，在其之上打包应用程序代码，然后将其发布到生产环境中。

虽然很方便，但这带来了巨大的安全问题。这些镜像包含一个shell、一个包管理器以及无数应用程序在运行时永远不会使用的工具和实用程序。容器中每一件未使用的软件都代表着潜在的漏洞和不必要的大攻击面。如果恶意行为者侵入了应用程序，他们突然就拥有了一个完整的工具包来下载额外的实用程序并升级攻击。

## 无基底镜像（Distroless）的安全缺口

为了解决这些安全问题，“无基底”（distroless）运动应运而生。这个想法是有道理的：虽然完整的容器镜像由于无数不必要的组件而具有更大的攻击面，但无基底方法试图将容器剥离到应用程序运行所需的最低限度依赖项。没有shell，没有包管理器，没有额外的实用程序。

这确实减少了攻击面，但付出了高昂的运维代价。创建一个无基底镜像既复杂、脆弱又容易出错。在精心挑选和积极裁剪镜像的过程中，包元数据——即已安装内容的清单——往往被完全剥离。

意料之外的后果就是我们现在所说的“无基底安全缺口”。

这不仅是一个理论问题；这是一个有据可查的行业盲点。像 Trivy 这样的扫描器在缺少 OS 包元数据时会主动发出警告标志，而 Yotam Perkal 的 [2022 年 Rezilion 漏洞报告](https://www.linkedin.com/posts/yotam-perkal_scanning-the-scanners-vulnerability-scanner-activity-7086727226372587521-pd94?utm_source=share&utm_medium=member_desktop)表明，容器扫描器遭受了显著的假阴性（漏报）困扰——仅仅因为缺乏必要的上下文而无法检测到活动漏洞。

> “你可能构建了一个极其微小的容器，但如果你的安全团队无法对其进行扫描并从数学上证明它是安全的，它就会成为一个巨大的合规负债。”

诸如 Chainguard 之类的组织也指出，如果扫描器无法收集[完整的包元数据](https://thenewstack.io/sbom-sniff-test-hardened-images/)，扫描结果将无法准确反映镜像的真实内容。你可能构建了一个极其微小的容器，但如果你的安全团队无法对其进行扫描并从数学上证明它是安全的，它就会成为一个巨大的合规负债。

在完整容器镜像和无基底容器镜像之间，我们只能做出不完美的抉择：要么是具有大攻击面的臃肿容器，要么是无法审计的极简容器。

## 对决：命令式裁剪 vs 自底向上组装

幸运的是，还有第三种方法。与其拿一个大镜像并将其裁剪下来，冒着删除准确安全扫描所需的关键元数据的风险，如果我们从底向上构建容器会怎么样？

前提很简单：从头开始构建你自己的最小化容器镜像，只包含你需要的精确元素。因为你是自底向上构建它，而不是自上而下剥离它，所以你可以放心，元数据保持完整。在开源生态系统中，这种新一代最小化、可审计的 OCI 镜像的一个例子通常被称为“rocks”。

自底向上的容器构建就像一条带有三个不同站点的传送带：切片（Slice）、构建（Build）和运行（Run）。

## 站点 1：精确切片

在自底向上的构建中，你的容器最初完全是一个空镜像。使用像 Chisel 这样的开源工具，你可以将标准、受信赖的 Linux 软件包（例如来自 Ubuntu 档案库的软件包）切成更小、更细粒度的碎片。

你无需拉取整个软件包，只需挑选应用程序实际需要的确切“切片”。因为这些切片直接来自精选档案库，所以你可以保持具有外科手术般精度的受信赖软件供应链。至关重要的是，这些切片的元数据得以保留，因此你的安全扫描器可以完全正常运行。

## 站点 2：声明式构建

传统上，容器是通过命令式 Dockerfile 组装的，其中每个命令的顺序都很重要，并且层缓存通常会造成臃肿和脆弱。

> “它将开发人员的体验从‘编写构建脚本’转变为‘声明状态’。”

自底向上的构建用[声明式方法](https://thenewstack.io/buildpacks-container-security-scale/)取代了这一点。使用像 Rockcraft 这样的开源构建工具，开发人员编写一个简单的 YAML 文件（例如 rockcraft.yaml），描述应用程序及其需求。该工具获取该定义，获取源代码，拉取请求的特定软件包切片，编译所有内容，并输出标准的、兼容 OCI 的容器镜像。它将开发人员的体验从“编写构建脚本”转变为“声明状态”。

```

name: chiseled-python
base: bare

build-base: ubuntu@26.04-lts
version: "3.14"
summary: Chiseled Python3.14 rock
description: Chiseled Python rock
license: Python-2.0
platforms: { amd64: }

run-user: _daemon_

parts:
    install-python:
        plugin: nil
        stage-packages:
          - base-files_release-info
          - python3_core

```

## 站点 3：在运行时驯服 PID 1

极简容器的最后一个运维障碍是它们运行时的行为。在标准操作系统中，操作系统会自动处理进程管理。但是在容器内部，如果你的应用程序派生出子进程并且这些进程死亡，它们会留下“僵尸”——仍然占用系统资源的死进程。

如果没有适当的 init 系统，僵尸进程会堆积直到容器崩溃，从而导致大规模的级联故障。传统的基础镜像包含进程管理器，但无基底镜像通常会剥离它们以节省空间。为了保持极简容器的稳定而又不会重新引入臃肿，自底向上的容器使用诸如 Pebble 之类的工具，这是一个微小的、轻量级的服务管理器，作为 PID 1 运行，充当容器的入口点，并安全地回收僵尸进程。

## 下一步

长期以来，云原生生态系统一直将安全可见性和容器极简主义视为零和博弈。无基底运动在强调臃肿镜像的危险性方面是必要的一步，但由此导致的漏洞扫描盲点对于企业生产环境而言已不再可接受。

> “长期以来，云原生生态系统一直将安全可见性和容器极简主义视为零和博弈。”

通过从命令式的、自上而下的裁剪方法转变为声明式的、自底向上的组装过程，工程团队可以两全其美。我们可以构建经过安全维护、可审计且运维稳定的极简容器。容器安全不应以牺牲开发人员体验或第二天（Day 2）可见性为代价。
