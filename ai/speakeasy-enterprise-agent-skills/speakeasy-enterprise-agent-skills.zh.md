“指望管理员掌握公司中每一项技能的最佳表现方式是不现实的，” [Speakeasy](https://www.speakeasy.com/) 的创始人兼首席执行官 [Sagar Batchu](https://www.linkedin.com/in/sagarbatchu/) 对 *The New Stack* 表示。

随着企业采用 AI 代理，开发人员构建了庞大的技能库，其中包含部署运行手册、代码审查清单、风格指南、事件处理流程和内部工作流，上述问题也随之变得愈发严峻。

这些繁杂的技能通常始于个人实验，随后散布在代码仓库、本地机器、Slack 会话和插件中。更令人困惑的是，它们往往缺乏明确的归属权，也没有可靠的方法来确认你所使用的技能是否为最新版本。

周五，Speakeasy 发布了 [Skills Management](https://www.speakeasy.com/blog/release-skills-management)，该系统旨在将技能视为企业级的中心化注册资产，具备不可变版本、作用域访问权限以及对技能使用情况的**可观测性**。

今年早些时候，我们开始看到开发人员创建提示词合集，并结合配置供代理使用。短时间内，用于技能文件的 [Agent Skill 规范](https://agentskills.io/specification) 便应运而生；该规范采用 [Markdown](https://thenewstack.io/obsidian-and-the-case-for-using-more-markdown/) 编写，并带有一定的 YAML 元数据。而技能仍然是将特定企业知识传授给任何代理的最佳方式。

## **代理技能库呈指数级增长**

Speakeasy 关于企业技能提出了一个简单的观点：随着组织采用 AI 代理，他们正在迅速构建技能库——如部署运行手册、代码审查清单、风格指南、事件处理程序、内部工作流以及其他特定于公司的知识。

问题在于，这些技能库的增长速度超过了公司的管理能力。技能最终散落在代码仓库、本地机器、Slack 会话和插件中，导致团队无法清晰地了解现有资产、当前版本以及技能的归属者。

Speakeasy 声称，“一家中型金融科技客户最近发现公司内部正在使用超过 500 种独特的 AI 技能。”这是因为 AI 实验本质上一直是个人行为。使用聊天机器人感觉非常私密；即使是 Claude Code 依然像聊天机器人一样与你对话。因此，与团队共享提示词可能不会立即发生。这导致了大量的重复造轮子，因为员工在不知道他人工作的情况下创建了类似的技能。

## **集中式技能管理**

为了解决这个问题，Speakeasy 首先将技能视为一种需要某种集中式注册的企业资产——即该公司所定义的“技能管理”（Skills Management）。

技能管理对待技能的方式类似于 Git 处理代码——提供不可变版本的注册表，以及对现有资产的共享视图。因此，如果你编辑现有技能，就会获得一个新版本。但 Speakeasy 还增加了一定程度的**可观测性**，以便企业了解哪些技能使用最频繁，以及不同部门编写类似内容的情况。更好的是，如果某项技能表现不佳（即使用它的代理在执行时注意到问题），LLM 裁判可以分析它并提出改进建议。

技能管理强制用户在创建技能文件时遵守上述的 Agent Skills 规范，以便系统能将元数据名称作为权威标识。尝试以不同名称输入相同内容的行为将被忽略。

## **不可变版本与访问权限**

作用域访问权限允许根据角色设定谁可以创建和整理技能，以及谁可以使用它们。

当代理使用这些技能时，由 Speakeasy 控制平面进行监控，这种方式显然比仅仅将技能文件堆入 Git 仓库要好得多。

根据 Agent Skills 规范验证技能是一个非常好的主意。毕竟，Markdown 基本上就是带有符号的英语。但元数据中的一些可选条目（如“许可证”）可以使用企业模板来简化流程。

Sagar 告诉 *The New Stack*，他尚未在客户那里看到这种情况。

“我们目前没有公司特定模板的第一方概念，”他说，“然而，公司可以创建一个用于验证技能的技能，并将其引入我们的‘LLM 作为裁判’流程中。”

> “我们跟踪每项技能的元数据，以便管理员可以快速查看哪些技能得到了维护（最后更新时间），以及使用频率（以及在团队成员中的传播情况）。”

那么，人类（或流程）是否容易阻止最新的错误变更传播？

“是的，”Sagar 说。“我们跟踪每项技能的元数据，以便管理员可以快速查看哪些技能得到了维护（最后更新时间），以及使用频率（以及在团队成员中的传播情况）。我们正在积极开发一些自动分类功能。”

“管理员”这个词引发了大型企业的另一个问题。许多不同的角色可能需要共同协作来处理公司技能。你可能希望安全专家建议使用新版本的技能，但更关键的是，*废除现有的技能版本*。然而，你不会希望他们能够编辑现有技能的内容。这能实现吗？

Sagar 解释说，技能版本是不可变的：“不可能更新现有的技能版本。”

不过，“当你发布新版技能时，现有版本会被自动化流程‘取消发布’。这解决了此场景下的两个问题：安全专家起草新版技能，发布它将从员工机器上撤下旧版本，而我们的**可观测性**栈会显示任何差异——例如滞后的插件版本或故意的本地副本。旧版本可以在适当的情况下回滚。

“然而，出于安全原因，目前还没有技能版本锁定的概念。”

Speakeasy 系统的真正明智之处在于，它了解一项技能是如何从开发者的笔记本电脑上开始，并需要通过企业内部的推广才能被完全采用，这暴露了关于角色的更多问题。

对于需要识别推广进度有多快的管理者来说，需要大量的 UI 支持——但他对技能本身的任何其他方面都不感兴趣。

> “由于技能遵循 Agent Skills 开放格式，我们在存储技能的方式上没有任何专有内容。”

## **企业技能可移植性**

对于任何构建知识的系统，用户必须知道如何离开它。Sagar 表示 Speakeasy 已经考虑到了这一点：“由于技能遵循 Agent Skills 开放格式，我们在存储技能的方式上没有任何专有内容。用户可以自由导出其技能语料库并将其迁移到其他平台。我们还提供了一条路径，允许用户将其所有的 MCP 服务器和技能克隆到 GitHub 仓库，因此他们可以在想要离开时随时离开。”

企业正处于遏制内部 AI 代理激增的阶段，同时也在评估代币成本的增加是否真的值得。这种类型的管理和**可观测性**平台将在评估“代理时代”的真实价值方面发挥越来越大的作用。
