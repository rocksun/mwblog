在Universe大会上，GitHub高管回应了前CEO推出的竞品挑战，强调世界不需要另一个GitHub，而是需要其在智能体时代进化。面对智能体带来的后端架构压力与验证瓶颈，GitHub正通过重构基础设施和分离计算与存储来应对新开发范式。

> 译自：[“I don't think the world needs a new GitHub”: What GitHub's leaders really think about their new rivals](https://thenewstack.io/github-agentic-infrastructure-rebuild/)
> 
> 作者：Frederic Lardinois

**在本周于旧金山举行的年度 Universe ’26 大会上，** GitHub 正面回应了[关于平台稳定性的问题](https://thenewstack.io/github-2-9b-monthly-commits/)。

这家代码托管公司在活动的主旨演讲中花了大篇幅来谈论其正在进行的投资。这包括[增加 400 万个核心和 160 PB 的存储空间](https://thenewstack.io/github-7-4b-commits-september/)，并对其后端基础架构进行了全面重新架构。

但在主旨演讲结束后的新闻发布会上以及接受 *The New Stack* 的采访时，微软 CoreAI 执行副总裁、现负责人 Jay Parikh 以及 GitHub 首席运营官 [Kyle Daigle](https://www.linkedin.com/in/kyledaigle/) 领导层团队还回答了关于 GitHub 在这个不断变化的开发者格局中所扮演的角色，以及他们如何看待为应对这些变化而[涌现的竞争对手](https://thenewstack.io/cursor-origin-github-alternative/)。

这是一个非常及时的问题，因为前 GitHub 首席执行官 Thomas Dohmke 在 GitHub 大会召开前几天刚刚推出了一个[GitHub 替代品](https://thenewstack.io/entire-trails-agentic-code-review/)。

在新闻发布会上被问及 [Dohmke 的初创公司 Entire](https://thenewstack.io/thomas-dohmke-interview-entire/) 以及微软 M12 投资部门对 Entire 的资助时，Daigle 外交辞令般地指出，微软经常投资那些“不仅与 GitHub 竞争，而且与整个微软产品资产产生竞争的工具。这是一件好事。这不是一件坏事。”

Daigle 指出，GitHub 在全球范围内运营，服务于超过 2.25 亿开发者，并不断迭代以更好地服务他们。

> “我认为世界不需要一个新的GitHub。”  
> ——GitHub 首席运营官 Kyle Daigle

他说：“我认为世界不需要一个新的GitHub。”“他们可能需要不同的工具。这很好，但他们需要的是[GitHub]为智能体时代进行演进，这正是我们正在做的事情。

“我们今天展示的 Git 层的统计数据本身就说明了一切。”

![](https://cdn.thenewstack.io/media/2026/10/1973762f-img_5949-edit-1024x768.jpg)





*图片来源：The New Stack*

Daigle 向 *The New Stack* 强调了 GitHub 在整个软件开发生态系统中扮演的角色——涵盖独立开发者、大型开源项目和财富 100 强企业。

Daigle 认为，关于新的 Git 托管平台（或更广泛的版本控制托管平台）的讨论，过于狭隘地集中在公司和这些平台的经济用途上。“我认为这忽略了核心问题，”他告诉 *The New Stack*。

“我们从来都不是唯一的 Git 托管商。我们从来都不是唯一的 SCM 托管商，”Daigle 说，他提到了 Perforce 以及企业多年来一直依赖的其他选项。他认为，GitHub 的与众不同之处在于以规模化方式将所有开发者汇聚在一起，而不是只关注企业或只关注开源。“我没看到有人试图去解决那个问题。他们试图解决问题的一部分，”他说，“在某些地方，他们非常有主见，并以独特的方式这样做。我认为这一直是事实。”

Daigle 的核心观点是，构建专注于企业的工具要容易得多。至少目前，Entire 和大多数其他 Git 托管平台都将重点放在这里。

更尖锐的是，Daigle 表示，当前这一时刻“类似于零利率时代的结束”，当时“有很多非常优秀、有趣的开发者工具，但它们实在太狭隘了。”他补充说：“幸运的是，许多这样的人最终加入了 GitHub——并做了一些非常棒的工作。”

> “GitHub 可能认为不需要一个新的 GitHub，但开发者显然这么认为。”   
> ——Entire 首席执行官 Thomas Dohmke

## Entire 的反应

当 *The New Stack* 请 Dohmke 对 Daigle 关于“世界不需要一个新的 GitHub”的评估发表评论时，Dohmke 提供了以下声明：“GitHub 可能认为不需要一个新的 GitHub，但开发者显然这么认为。难道我们真的想把软件开发和开源的未来交到一个大型科技公司手中吗？我们正在构建 [Entire](https://thenewstack.io/entire-trails-agentic-code-review/)，以便社区的新家园是开源的、可扩展的，并且驻留在世界各地的许多区域。”

## 平台与产品

随着 Dohmke 的 Entire 平台作为新竞争者首次亮相，Parikh 在周三的新闻发布会上强调了 GitHub 用户社区及其提供的平台的重要性：“鉴于我们构建软件的方式和软件生命周期的世界变化如此之快，我认为社区的力量比以往任何时候都更加重要，无论是在我们创造什么、我们如何分享，还是我们如何一起学习方面。”

Parikh 在后来接受 *The New Stack* 采访时表达了类似观点，当被问及 GitHub 现在面临的竞争格局时，他在个人开发工具和支持它们的平台之间做出了区分。

“GitHub 和微软一直是平台公司，”他说。“外面有很多产品，是的，我们有产品，我们也有平台。”

对 Parikh 而言，这意味着提供完整的开发工作流，同时也让开发者选择他们使用的部分。或者正如 Daigle 所说，“我们将为您提供完整的流程，或者我们将为您提供基本要素，我认为这是大多数公司想要的。每个人都对如何做到这一点感兴趣，但没有人想买唯一的方法。他们希望拥有选择权和自主权。”

## 智能体打破平衡的地方

支持这些多样化的工作流最终迫使 GitHub 重新考虑团队之前关于哪些服务最容易失效的假设。

“出问题的地方并不是我们历史预期中会出问题的地方，因为智能体的行事方式与人类截然不同，”Daigle 说。“一些完美扩展的服务，我们认为在相当长一段时间内都可以正常运行，却出现了令人惊讶的故障。”

![](https://cdn.thenewstack.io/media/2026/10/91c580ab-img_5947-1024x768.jpg)





*图片来源：The New Stack*

这些故障在初夏开始出现，促使 GitHub 寻求超越增加容量作为主要解决方案的方法。

“这不仅是增加核心数量、整体横向扩展，还要审视那些需要完全重写的核心服务，因为行为模式实在是太不一样了，”Daigle 说。

Parikh 的经验包括在 Facebook 和 Akamai 扩展基础设施，他表示当前的增长率使得渐进式改进变得毫无意义。

“你必须从整个系统的角度来看待它，”他说。“在这里或那里获得 5% 或 10% 的提升，现在只能持续两周或一周。”

使这一切变得更加困难的是，GitHub 必须在保持服务运行并与现有工作流兼容的同时进行这些更改。与此同时，流量模式也在发生变化，Parikh 说。

“目前的流量模式也不是静态的……我们优化了 CPU，突然间瓶颈转移到了其他地方，然后你会想，‘哦，我以为它会出现在这里，结果它出现在这里。’好消息是，你现在可以分阶段进行推出。你测试这些东西，然后进行调整，”他说。

团队承诺的一个重大架构更改是将 GitHub 的 Git 基础设施中的计算与存储分离。这现在允许公司根据需求更轻松地扩展每个部分。

“根据流量、一天中的时间、谁在使用它以及运行在其之上的产品类型，你可以独立扩展这些事情，并针对计算工作负载的变化和存储工作负载的变化进行优化，”Parikh 在新闻发布会上说。

Parikh 表示，[从 GitHub 自己的数据中心迁移到 Azure](https://thenewstack.io/github-will-prioritize-migrating-to-azure-over-feature-development/) 也提供了更多的容量、地理灵活性和冗余，这是现有设施无法提供的。但他同时也强调，这项工作尚未完成，还包括额外的更改，例如加固和扩展 GitHub Actions。

“我们无法增加容量。我们没有 GitHub 一直运营的那些固定数据中心所具备的规模，因此迁移到能给我们带来灵活性、规模、位置、冗余和网络等优势的云基础设施，对我们来说要好得多，”Parikh 告诉 *The New Stack*。

## 保持免费仓库免费

有趣的是，这些架构更改也影响了在 GitHub 上托管所有开源代码和免费仓库的经济效益。

Daigle 表示，分离计算和存储应该会降低存储 Git 仓库的成本，随着开发者和他们的智能体创造更多工作，帮助 GitHub 维持访问权限。

Daigle 表示，GitHub 对其社区负有责任。突然将开发者限制在少数几个私有仓库中“打破了 GitHub 的整个契约，”他说。

Daigle 表示，任何编写代码的人，无论是做了多年还是刚刚开始，都应该在 GitHub 上有一个家。“一个仓库不应该藏在你的笔记本电脑上，或者[成为]朋友之间共享的 HTML 文件，”他说，“我们为此提供了一个地方。”

然而，他确实将这种承诺与提供 AI 模型的成本区分开来。他说，GitHub 无法给每个人提供无限的免费 Token，并且不得不决定[在哪里补贴访问权限](https://thenewstack.io/github-copilot-usage-billing/)。

## 重新思考 Git 与验证

除了 GitHub 自身的基础设施，Daigle 还看到了改变 Git 本身的空间。他希望公司与社区合作开发其底层，并看到了类似“Git 之上的瓷器层（porcelain layer）”的作用，他将其描述为简化对底层系统访问的高级接口。

Daigle 表示，GitHub 需要“巩固我们在社区中的角色”，并与老牌和新玩家合作，重新思考 Git 的一些底层架构。“在智能体改变之前，它们有点说不通，”他说，“而现在它们真的、真的说不通了。”

不过，与此同时，Daigle 对于这个智能体时代是否需要一个完全不同的版本控制系统仍然保持谨慎。

“我想在采取行动之前确认我们确实需要行动，”他说。还没完全抛弃 [Git]。“我只是觉得我们需要更多地投入。”

“你实际上需要审查它，你需要将其推送到生产环境，你需要运行其他工作流，你需要进行 AI 安全扫描，”Parikh 在新闻发布会上说。

> Daigle 预计验证——审查、测试以及决定软件是否应该进入生产环境——将成为下一个瓶颈。

Daigle 预计验证——审查、测试以及决定软件是否应该进行生产环境——将成为下一个瓶颈。他认为，即使拥有无限的 CPU，也不会让人希望在每个智能体提交后运行每个构建。

“如果我同时运行 5 或 10 个智能体，为了智能体本身的利益，我实际上并不想要或不需要所有这些构建，”他说。“这需要智能体或相关人类行为的改变。”

他提出的可能性包括签署本地执行的构建并与智能体的工作一起提交、选择一小组合适的测试，以及探索由证明驱动的开发。测试、评估和实时验证的正确组合将取决于应用程序。

“如果你是一家汽车制造商，你不会说，‘好吧，我会让我的智能体检查制动卡钳是否接合，’”他说。
