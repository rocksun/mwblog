Lauren Tan 是 SpaceXAI Grok 团队的一名工程师，曾就职于 Cursor 和 Meta。她最近发布了一份关于其个人代理工作流的指南：pstack。最引人注目的是，pstack 让她能够[以极高的置信度每月向生产环境交付 2,000 个拉取请求 (PR)](https://x.com/poteto/status/2094457600259842065)。这意味着一名工程师每个工作日要交付近 100 个 PR。

这个数字令人难以置信，无疑是一个异常值，但这个方向并不令人惊讶。我之前曾指出，编码代理将[使团队能够在人数相近的情况下生成十倍的代码](https://thenewstack.io/coding-agents-cicd-fix/)。令人惊讶的是，这些不仅是代码输出数量，而是实际落地到生产环境的变更。

据 Tan 称，该工作流中最关键的部分是验证。验证技能让代理能够检查自己的工作，并持续运行直到任务完成。她将其视为“关键基础设施”，而不是众多技能中的一种。

验证技能的基础是它底层的某个东西：一个代理可以驱动、检查并从中获得结构化答案的丰富运行时。对于单个应用程序，该运行时就是应用程序本身，按需启动。对于由数十或数百个服务组成的系统，默认情况下不存在这样的运行时，而提供一个能够跟上数百个并行代理的运行时是困难所在。

## 验证是整个游戏的全部，数学逻辑证明了这一点

她对代理验证的论点是一个吞吐量论点。一个能够检查自己输出的代理会一直工作直到任务完成。一个不能自动完成并交出 diff 却要等待的代理，会让你成为循环中最慢的一环。这就是为什么她声称强大的验证技能可以将团队的产出提高 100 到 1,000 倍。

> “一个能够检查自己输出的代理会一直工作直到任务完成。一个不能自动完成并交出 diff 却要等待的代理，会让你成为循环中最慢的一环。”

在[每月 2,000 个拉取请求](https://thenewstack.io/ai-generated-code-crisis/)的情况下，如果手动审查每个变更，整个工作月内每个 PR 大约只有五分钟的时间。在这种数量级下，人工审查无法成为验证层。无论是什么进行检查，都必须在没有人工介入的情况下运行，并且必须与生成工作的代理并行运行。

## 该模型假设代理可以运行整个应用程序

她所描述的验证技能生成了一个命令行界面 (CLI) 和一个应用程序的功能映射。CLI 允许代理启动应用程序、导航、检查状态并读回结构化的 JSON 结果。每个代理都会获得应用程序的完整副本，并可以端到端地测试变更。

她直言不讳地指出了这种运行时的重要性：“我个人认为代理验证非常重要，以至于我会不加讽刺地建议构建自己的丰富调试工具，甚至选择不同的技术栈，以便在构建软件时拥有不公平的优势和极高的生产力。”

她为[代理提供运行时](https://thenewstack.io/agent-runtime-application-server/)的方法之所以有效，是因为应用程序适合在单个进程中运行。前端、编译器或带有数据库的单个服务可以在几秒钟内从 CLI 启动，并在之后被丢弃。

> “我会不加讽刺地建议构建自己的丰富调试工具，甚至选择不同的技术栈，以便在构建软件时拥有不公平的优势和极高的生产力。”

对于构建复杂分布式应用程序的团队来说，他们的系统不具备这种特性。应用程序是订单服务、支付服务、库存服务、队列、多个数据库和少数第三方 API 之间的交互。在大型企业中，数量可达数千。对一个服务的拉取请求只能通过调用它所发出和接收的调用来验证。CLI 可以启动已更改的服务，但无法启动整个系统。

## 没有现有的运行时能够支撑数百个并行代理

带有 Mock 的本地运行时成本低廉，并且可以使用工作树或 CDE 完全并行运行。它们的问题在于保真度。Mock 编码了依赖项上次被查看时的状态，一旦真实服务发生变化，它们就会产生偏差。一个针对 Mock 进行验证的代理是在“虚构”的基础上完成闭环，而失败会在合并后显现。

每个变更拥有全栈的完整副本是忠实且隔离的。但其成本随着服务数量乘以并发变更数量而扩展，在数百个代理的情况下，这种成本是无法维持的。时间是更大的问题。全栈配置需要几分钟，而她描述的循环要求代理在处理变更时测试每次迭代。在代理已经转向下一次尝试后才准备好的环境对它没有用处。

共享暂存环境（Staging）忠实且廉价，因为只有一个副本，而这正是所有问题的所在。一个单一的可变环境无法承载数百个并发变更。代理会覆盖彼此的部署，一个代理的错误变更会导致其他所有代理的测试失败，从而使工作流得以实现的闭环属性消失。

## 当调用者是代理时，验证需要什么

将 Lauren 的工作流视为需求文档，会出现五个属性：

* 变更必须针对真实依赖项运行，否则验证毫无意义。
* 数百个并发变更必须互不可见。
* 环境成本必须随变更大小而扩展，而不是随系统大小扩展。
* 环境必须在几秒钟内启动，因为代理等待配置是在支付并行成本却未使用。
* 所有这一切都必须通过代理已经在使用的 [CLI 或 MCP 服务器](https://thenewstack.io/new-python-cli-tool-catches-mcp-server-issues-before-agents-do/)访问，因为调用者是代理。

第一和第三个需求方向相反。真实性倾向于系统的完整副本，成本倾向于尽可能多的共享。共享暂存环境通过放弃隔离来解决这种紧张关系，而每个变更的全栈副本通过放弃成本效率来解决它。一个满足所有五个需求的设计必须同时共享和隔离。

## 虚拟化全栈环境：共享系统并隔离变更

实现这一点的架构将环境视为运行系统的一个“视图”而非副本。一组共享的稳定服务持续运行，从主分支部署并像生产环境一样保持健康。当代理需要验证变更时，它仅在自己的机器上或作为集群中的轻量级部署运行它修改的服务，并将其作为新的隔离环境加入共享栈。

> “实现这一点的架构将环境视为运行系统的一个‘视图’而非副本。”

在该环境内部，更改后的服务是记录版本，而所有其他调用都会回落到共享的稳定版本。代理看到了一个完整、真实的系统，其他一百个代理也是如此，每个代理看到的系统与基准相比仅有其自身变更的增量。请求在跨越服务边界时携带其环境标识，这防止了一个代理的流量到达另一个代理正在测试的版本。无法安全共享的有状态副作用（如队列主题或可写数据库）在需要时会获得每个环境的副本。

![显示“代理 1 环境”和“代理 2 环境”与共享集群交互的图表。](https://cdn.thenewstack.io/media/2026/09/1b47c76e-image-1024x530.png)

成本模型直接由此得出。一个环境的成本是一两个运行的服务，而不是六十个；它在单个服务启动的时间内准备就绪，并且你可以从代理自己的循环内部创建和销毁它。这就是 [Signadot 为 Kubernetes 封装的模式](https://thenewstack.io/kubernetes-native-ai-infrastructure/)，其中共享的稳定堆栈运行在团队现有的集群中。

## 以代理为执行者的完整循环

将这两部分结合起来，使她能够每月向生产环境交付 2,000 个 PR 的工作流几乎可以原封不动地移植到分布式系统中。代理获取一个任务并更改一个服务。它请求该变更的环境，并在其服务启动的时间内获得一个环境。然后，它通过系统的入口点驱动真实的请求，并观察它们遍历真实的依赖图，只有它自己的服务在运行新代码。它读取结构化结果，修复失败的部分，并再次运行。当检查通过时，它打开 PR，环境在合并时消失。

> “环境不再是平台团队分发的东西，而是代理根据需要创建、使用和丢弃的东西。”

对于平台团队来说，工作单元发生了变化。今天它配置环境，无论这意味着保持共享暂存环境存活还是生成其完整副本。在这种模型中，它运行一个共享的稳定堆栈以及虚拟化它的层：跨每个服务的上下文传播、为无法共享的有状态依赖项提供隔离，以及创建和拆除环境的工具。环境不再是平台团队分发的东西，而是代理根据需要创建、使用和丢弃的东西。

## 验证能力是吞吐量的新上限

Lauren Tan 的文章讲述的不是一个异常高效的工程师的故事。它展示了当代理运行完整循环——编写变更、验证它并迭代——而无需中间人介入时会发生什么。验证基础设施是整个循环赖以生存的基石。

在分布式应用程序中，该基础设施必须是一个运行时环境，为每个代理提供真实的依赖项，防止数百个并发变更相互干扰，按变更成本而非系统副本成本计费，并且在代理愿意等待的几秒钟内就绪。这就是将代理并行性转化为已交付代码，而不是更长审查队列的关键。那种运行时环境的模型正是我们构建 [Signadot](https://www.signadot.com/?utm_source=tns&utm_medium=sponsorship&utm_campaign=q3_26_sponsored_content) 所要启用的。
