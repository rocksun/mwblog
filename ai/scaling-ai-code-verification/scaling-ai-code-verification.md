文章指出，在氛围编程（Vibe coding）等AI工具推动下，GitHub代码提交量呈指数级增长。然而，代码验证能力仍停留在人工效率水平，导致开发与验证之间的鸿沟扩大，成为现代工程架构面临的核心挑战。

> 译自：[Commits on GitHub have doubled in four months. Verification capacity has not.](https://thenewstack.io/scaling-ai-code-verification/)
> 
> 作者：Arjun Iyer

**我一直在等待AI代理生成的代码**出现在公共基础设施数据中，而不是仅仅停留在供应商的基准测试里。8月份，这一情况发生了。GitHub现在每月处理 [29亿次提交，并表示其系统已难以负荷](https://thenewstack.io/github-2-9b-monthly-commits/)。每月提交量在四个月内 [翻了一倍多](https://www.engadget.com/2241272/github-says-commits-have-doubled-in-the-last-four-months/)，从4月份的14亿次增长到8月份的29亿次。

这种增长压垮了平台。8月17日，GitHub因其美国中部数据中心的一个核心基础设施组件未能随流量增长而扩展，导致平台 [瘫痪了7小时47分钟](https://github.blog/news-insights/company-news/the-august-17-outage-and-the-work-ahead/)。CTO Vladimir Fedorov在事后复盘中直言不讳：如果你那天正试图发布软件，GitHub辜负了你。补救措施是当需求超过供应时大型服务商通常的做法：新增超过300万个CPU核心、120PB高速存储，并加速迁移至Azure，后者 [目前承担了平台58%的负载](https://www.theregister.com/devops/2026/08/21/we-let-you-down-github-pledges-to-scale-up-before-developers-give-up/5291031)。

大多数报道将其视为一个容量问题，对GitHub而言确实如此。但真正让你感到担忧的数字，却是那篇复盘中从未提及的：这29亿次提交中的每一次，都隐含着“改动有效”的声明。而在生成、传输并合并这些代码的系统中，几乎没有任何环节是在运行系统环境中校验这一声明的。

> “代码生成已进入机器节奏，其增长曲线呈指数级。而验证工作仍保持人类节奏，其能力曲线几乎是平坦的。”

这是GitHub数据中隐藏的警示。代码生成已进入机器节奏，其增长曲线呈指数级。而验证工作——即证明变更符合预期且不会破坏现有功能的过程——仍保持人类节奏，其能力曲线几乎是平坦的。这两条曲线之间的距离，正是未来三年内最具决定性的基础设施问题。

## 提交曲线是机器化开发留下的首个公共痕迹

GitHub的遥测数据是你所在组织的一个缩影：它汇集了成千上万个工程团队同时在做的事情。除了提交数量，复盘报告还提到每月约有1.3亿个合并的拉取请求（Pull Request）和2400万个新仓库。Engadget的报道指出，GitHub将这种激增归因于AI生成的代码。

曲线的形状比高度更重要。多年来，提交量的增长速度与开发者人口增长大体一致，因为提交是人为跟踪的。随后，它在四个月内翻了一番，因为它不再是人为跟踪了。一个同时 [运行三个氛围编程（Vibe coding）会话](https://thenewstack.io/github-mcp-security-scanning/) 的开发者，其提交速度是任何招聘计划都无法预见的。

> “一个同时运行三个氛围编程会话的开发者，其提交速度是任何招聘计划都无法预见的。”

你的内部仪表盘几乎肯定也在以微缩形式展示出同样的形状：拉取请求数量逐季攀升，每位工程师的提交量更多，同时打开的分支更多。这个公共数据之所以重要，是因为它证明了你的曲线并非局部异常。当生成代码不再是稀缺环节时，开发就是这副模样。

## GitHub的瓶颈是容量，你的瓶颈是信心

GitHub的问题，尽管极其严重，但有一个已知的解决方案：当流量超过基础设施承载能力时，就增加基础设施。核心、磁盘和数据中心可以随资金投入而扩展，而Microsoft财力雄厚。

但在你这一侧，问题并不能简单通过砸钱来解决。提交不是流量。它是关于行为的声明：该变更符合描述且不会破坏下游任何功能。在一个分布式、云原生的系统中，校验这一声明意味着要将其与合并后会遇到的服务、数据和流量进行对比运行。

验证环节之前的流水线速度越来越快。AI代码审查工具在人工介入前会对差异（diff）进行分类，CI（持续集成）也学会了测试选择和缓存，静态分析比以前更强大了。这些都是实实在在的进步，但没有一个环节真正运行了这些变更。验证行为、集成和针对实时系统的端到端测试，仍然需要汇集到共享的预发布环境（Staging），或者等待完整的堆栈副本，这对于每个变更来说，成本太高且耗时太长。

这一步骤有一个硬上限。预发布环境通常每个组织只有一个，因此它就像一个队列。全栈副本成本高昂，团队往往会配给使用。这两者都不会因为你批准了一笔预算就在四个月内翻倍。现在，生成代码的能力像GitHub一样实现了扩展，而验证工作仍以一次一个变更的速度缓慢进行。

## 验证是为了人类节奏设计的，而AI代理打破了这种平衡

这一切并非新鲜事。在氛围编程（Vibe coding）出现之前，大型工程组织多年来就一直在抱怨预发布环境竞争和审查积压。这套装置建立在人类打字的速度之上，以那种速度，这些成本是团队可以承受的税负：偶尔的预发布冲突，周五前能清理完的审查队列。在变更稀缺时，将昂贵的全保真测试推迟到流水线末端是一个合理的权衡。

AI代理并没有引入瓶颈，它们只是将瓶颈放大到了旧有的应对策略失效的地步，并将问题带到了小型团队中。以前需要500人规模平台才能产生的吞吐量，现在一个运行并行代理的50人小团队就能做到。所有这些设计决策背后假设“代码是稀缺输入”的前提已经消失，而建立在此之上的检查机制却原地踏步。曾经大致重合的两条曲线已经分道扬镳。GitHub的图表正是这种分离的宏观写照。

## 曲线之间的间隙填满了未经核实的合并

团队通过几种方式应对不断扩大的鸿沟。第一是加快审查速度。AI代码审查工具位于人类审查者之前，识别差异中的真实缺陷，并不断改进。但它们也有局限性：无论是人类还是模型，都是在推理并未运行的代码，差异对比无法告诉你变更是否经得起真实依赖关系的考验。

第二是限制AI代理，限制进入流水线的生成代码量。这通过牺牲AI代理原本能带来的大部分吞吐量，来保护验证队列。

第三是强制合并，然后吸收下游故障。未在真实系统中运行过的变更，以提交到来的速度进入主分支，成本随后以崩溃的预发布环境和冗长的调试会话形式显现。更糟糕的是，引发生产事故和回滚。

8月17日的停机就是这种结局的预演。根本原因不是一个糟糕的变更，而是一个所有人都依赖、却没人进行扩展的组件，在流量终于超过设计上限的那一天崩溃了。在大多数交付系统中，验证环节就是那个组件。

## 验证必须与生成保持相同的节奏

结构性的解决方案是使验证与生成的形态保持一致：并行且针对每个变更。对于单个应用程序，这几乎已解决：AI代理在笔记本电脑或CI容器中运行应用程序并检查变更是否有效。难点在于云原生场景，变更的行为仅在与其他服务、数据库和队列交互时才会显现。在AI代理的高吞吐量下，两种常见的选择都失效了：共享预发布环境会将一切串行化进队列，而为每个变更复制完整堆栈既昂贵又耗时。

还有第三种形态。保持一个共享环境运行每个服务的稳定版本，对于每个变更，只部署受影响的服务。测试流量携带变更的路由键，因此在每一跳中，该变更的请求会到达变更后的版本，而所有其他请求流经稳定版本。每个变更在需要的地方实现了隔离（即所修改的服务），并共享其他所有资源：相同的集群、相同的数据、相同的下游依赖。

![展示共享环境中请求路由的工作流图](https://cdn.thenewstack.io/media/2026/08/2aa97818-image-1024x443.png)

这种形态改变了经济学逻辑和参与主体。验证额外一个变更的成本仅是一次额外部署，而不是复制整个堆栈，因此数百个变更可以在你现有的集群上并行检查。

由于环境可以在几秒钟内生成，AI代理可以在循环中使用它：打开一个变更，针对真实的上下游服务进行功能检查，读取失败信息，并进行迭代直到通过。到达人类审查者手中的拉取请求，已经经过了真实系统的验证，审查时间可以专注于意图和设计。
