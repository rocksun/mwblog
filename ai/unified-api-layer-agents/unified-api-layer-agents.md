随着AI智能体加速应用开发，获取实时运营数据的缓慢成为新瓶颈。传统数据访问繁琐且存在安全隐患，而统一API层通过集中管理访问控制、字段级权限及智能体身份，为解决这一痛点提供了高效方案。

> 译自：[AI agents speed up development — data access slows them down](https://thenewstack.io/unified-api-layer-agents/)
> 
> 作者：Doug Sillars

**构建应用从来都不是最难的部分。** 现在，随着AI智能体协助开发，团队比以往任何时候都更快地完成应用程序和内部工具的构建。问题在于获取实时运营数据。团队为了解除构建的阻塞，正以最快的速度为每个项目手动重建访问规则和连接。有时直接访问被拒绝，导致构建被迫在副本上运行：按定义这就是陈旧的数据，对于任何需要写回源数据的需求来说都是死胡同。

## 访问的代价

应用程序使用数据来完成关键任务，因此它们需要访问提供数据的API、数据库和云服务。每个连接都是定制的，需要不同的访问级别和可用数据的不同子集。为了获得这种访问权限，团队需要向每个系统所有者提交工单来请求权限。于是，漫长的等待游戏开始了。你可能不得不为你的访问理由进行辩护，跟进未回复的电子邮件，仅仅因为获取数据的速度太快而卡在等待工具完成的阶段。

快进到三年后——PostgresDB正在迁移到一个新服务器。你知道连接到它的每一个工具吗？漏掉一个都可能导致中断。一名员工离职了。你确定你已经从每个工具中移除了他的访问权限吗？随着AI智能体的兴起，你知道是谁将它们连接到生产系统的，又是出于什么目的吗？

随着团队的成长和连接数量的倍增，创建和维护连接的繁琐工作如滚雪球般增加。访问控制涉及跨系统的十几个不同的登录名，并占用了原本用于构建的时间。繁重、重复的任务降低了每个团队的生产力。

统一API层可能是解决之道。

## 什么是统一API层？

将统一API层视为任何包含业务关键数据的数据源的单一受监管访问层。团队无需向每个数据库、API和业务工具的所有者提交请求，而是在一个地方请求访问。

这也意味着每个数据源的访问控制都集中在统一API层中。无需依赖许多不同的系统（每个系统都有不同的访问参数和规则），现在只有一个地方，包含一套规则，以及对该数据所做每次更改的一致记录。

统一API层中的访问对组织中的每个数据源使用最低权限、基于角色的访问控制。除了团队成员之外，应用程序和AI智能体也拥有身份，每个身份都精确限定在其需要的数据范围内。

> “因此，两个智能体可能会发出相同的请求，但会得到不同的响应，具体取决于各自被允许看到的内容。”

正如 [Monospace](https://monospace.io/) 的产品副总裁 [James White](https://linkedin.com/in/james-white-directus?originalSubdomain=uk) 所说：“网关覆盖了连接。我们走得更深，因为我们了解schema，我们知道是谁在提问，并且我们理解响应。因此，两个智能体可能会发出相同的请求，会得到不同的响应，具体取决于各自被允许看到的内容。”

团队可以通过 MCP 将他们的智能体指向统一API层，每个智能体都能准确获得其身份允许的数据。开发人员获得一个强类型的 SDK，无论底层是什么，都只有一个一致的接口。

White 补充道：“无论数据位于何处，你请求数据的方式都是相同的。如果是一个数据库，我们会将请求转换为 SQL。如果是一个API，我们会将其转换为该API的调用，并处理过滤和分页。从开发人员的角度来看，一切都只有一个强类型的接口。”

## AI改变了什么：智能体身份和访问控制

智能体继承了交予它的任何凭证。开发人员可能会将他们的个人API密钥和凭证交给智能体——将智能体的身份与开发人员绑定。当开发人员轮换密钥时，智能体会发生什么？当开发人员离开组织时，智能体会发生什么？

智能体需要它们自己的基于角色的访问权限，与其它用户和应用程序断开连接。统一API层为每个AI智能体创建一个身份并对其访问控制进行范围限定。

将AI智能体连接到生产数据是大多数领导者感到紧张的地方。他们担心智能体会失控并使生产系统面临风险。字段级权限是你可以对智能体施加的最强有力的护栏之一，因为它们是在数据层强制执行的，而不是依赖智能体去遵循提示词指令。在智能体的身份上设置这些权限，它们可以控制智能体可以读取什么以及可以在哪里写入。统一API层在这方面已经非常出色。

想象这样一条规则：“智能体可以更新订单上的收货地址，但不能更新支付方式，并且只能针对尚未发货的订单。”字段级权限允许智能体写入 shippingAddress 但不能写入 paymentMethod，而记录级权限将其限制在未发货的订单。通过落实离散的规则，对记录系统的更改得到了严格的控制。

访问控制和离散权限是统一API层的核心，这正是它们非常适合AI智能体的原因。

## 统一API层要发挥作用必须具备的条件

* 该层必须按原样触及系统——在原地跨系统联合数据，而不是将其迁移或合并为副本
* 每个消费方都应该有自己限定范围的访问控制集
* 对进入每个系统的每个连接和请求进行统一记录：无需再深入挖掘多个服务器来拼凑连接日志
* 无论底层源是什么，消费方都获得一个一致的接口。应用程序和智能体查询该层，绝不直接查询其背后的系统
* 智能体通过具有唯一身份的 MCP 进行连接，它们的角色和策略决定了它们可以访问什么

## Monospace

Monospace 是这种统一API层模型的例子之一。只需连接一次数据库（例如 PostgreSQL、Supabase、MySQL、MariaDB）、SaaS 平台和内部API，它就会内省现有的 schema 或端点，并在不迁移底层系统的情况下将它们映射到公共数据模型。这就是在实践中“按原样”触及系统的含义：Monospace 在顶部保留了一个元数据层，而数据则保留在它所在的地方。

每个身份都被赋予一个带有特定策略的角色。策略按操作（创建、读取、更新、删除）设置访问权限，并进一步限制对特定字段和项目的访问。诸如“可以更改收货地址，但不能更改支付方式”之类的规则会在每个请求上进行评估。Monospace 还可以过滤响应，以防止向错误方暴露数据。

开发人员获得直接从 schema 生成的强类型 SDK，并在 IDE 中具有自动补全功能。智能体获得一个 MCP 端点——一个受管制的入口点，而不是为每个工具手动连接一个单独的连接。无论哪种方式，底层访问模型都是相同的。

## 谁能想到访问控制会拖慢我们的脚步？

这从来都不是关于构建应用程序。而是关于快速安全地向它们提供数据。

为智能体限定访问范围是许多企业一直拖延解决的另一个问题，因为他们知道总有一天必须解决它。

统一API层并没有让这个问题消失。它为你提供了一个可以解决该问题的地方——只需解决一次，而不是针对每个系统、每个应用程序、每个智能体各解决一次。[Monospace](https://monospace.io/) 就是这样一种解决方案。
