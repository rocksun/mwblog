**OpenAI 的新型 [Dots](https://thenewstack.io/openai-dots-gpt6-agents/) 旨在在你离开后继续工作**。这些全天候运行的智能体在周二的 DevDay 上发布，它们在自己的云计算机上运行，使用 [GPT-6 Astra](https://thenewstack.io/astra-arc-agi-benchmark/)，并连接到数千个应用程序。一个 Dot 可以监控连接的系统，并在无需你再次提示的情况下从一个任务转到下一个任务。但随着工作的变化，它必须不断弄清楚它代表你行事的权限在哪里结束。

正如我们在 DevDay 活动中所了解到的，OpenAI 在自己的测试中衡量了这个问题。当它把链式序列中的任务数量从 5 个增加到 10 个时，被标记为存在边界问题的样本比例从 8.6% 上升到了 19.7%。这一发现在 OpenAI 随发布一同更新的 [GPT-6 Astra 系统卡片的 Dots 附录](https://deploymentsafety.openai.com/gpt-6-astra/maintaining-boundaries-across-chained-tasks)中有所体现。

当 Dot 从一个任务移动到另一个任务时，它的能力可能会发生变化，即使没有用户明确设置新的边界。这使得智能体不得不从业务记录、先前的决策、上下文以及 OpenAI 的确认策略中摸索出自己的极限。评估没有发现高严重性的违规行为或数据外泄，尽管 OpenAI 并没有说明被标记的边界问题实际涉及什么。

> Dot 被允许做的事情会随着它从一个任务移动到另一个任务而改变，即使没有用户明确设置新的边界。

## Dots 中的阅读与行动

第一个安全防护适用于 OpenAI 称之为主动研究（proactive research）的阶段，此时 Dot 会自行寻找工作。在此阶段，它可以读取连接的应用程序，但不能更改它们、发送消息或控制用户的浏览器或计算机。

每个 Dot 还获得自己的云计算机和浏览器，可以在其中构建和测试事物，但 OpenAI 并没有说明这些环境在后台工作期间是否面临相同的限制。这很重要，因为只有当[智能体找不到绕过它的方法时](https://thenewstack.io/openai-agents-security-bypasses/)，限制才起作用。

一旦 Dot 准备好采取行动，它就会进入另一层控制。内置规则决定了它何时需要权限，自定义规则允许用户允许、限制或阻止特定操作，而自动审查则会检查任何可能影响账户或共享信息的内容。

自动审查来自 Codex，第二个模型会检查在预定义沙盒之外运行的命令。该公司通过自己的审查指令调整了该系统用于 Dots，并赋予了确认策略比在 Codex 框架中更多的权重。

## 从研究到拉取请求

一旦 Dot 接受了一项任务，它就不会一直保持只读状态；OpenAI 举了一个例子：一个 Dot 监控客户反馈，识别出一个小修复，然后在其自己的机器上构建并测试它。在它将完成的拉取请求交给开发者之前，Dot 已经写入了代码库，而人类甚至还没有审查过这项工作。

OpenAI 的测试还展示了当这些权限延续到重复性工作时会发生什么。在一项[内部 Codex 流量的模拟](https://deploymentsafety.openai.com/gpt-6-astra/forecasting-misaligned-behavior-with-deployment-simulation-of-internal-codex-traffic)中，用户要求 Astra 创建一个每小时运行一次的助手，用于观察失败的检查、修复测试、打开拉取请求、请求审查并在满足某些条件时进行合并。Astra 启用了其聊天、源代码控制和任务系统连接中的所有可用操作，关闭了每次操作的审批，然后发布并计划了该助手。

这项测试涉及的是 Codex 而不是 Dots，但它描述了 Dots 为之构建的那种长期运行的工作流，其中模型赋予了助手的访问权限甚至超过了用户的要求。

## 提示词注入与主动研究

保持主动研究为只读状态也限制了间接提示词注入，因为在票据或文档中隐藏了恶意指令的智能体可以立即对其采取行动的方法更少了。OpenAI 报告称，在其内部间接注入测试中，Astra 的防御成功率为 99.79%。在外部测试中，Gray Swan 进行了 1,810 次精心策划的攻击，估计在启用安全防护的情况下，针对 Astra 的每个场景 15 次尝试的攻击成功率为 8.5%。威胁本身不断演变，该公司最近描述了[一种可以像计算机蠕虫一样传播的新型提示词注入](https://thenewstack.io/openai-self-replicating-injections/)。

将阅读与写入分开并不能消除风险，因为 Dot 在研究期间读取的内容仍然可以塑造它稍后的行为。外部信息应该指导其工作，因此客户反馈可以影响 Dot 编写的代码。

由于 Dots 可以随着时间的推移保存笔记并从反馈中学习，OpenAI 测试了它们遇到的信息中的误导性暗示是否会影响后续工作。在 Astra 上运行的 Dots 在 151 个任务中记录了 0% 的不对齐率，尽管对于一个旨在持续运行的智能体来说，这是一个相对较小的测试。

> 在 Astra 上运行的 Dots 在 151 个任务中记录了 0% 的不对齐率，对于一个旨在持续运行的智能体来说，这是一个来自相对较小测试的强劲结果。

## 凭证、身份与审计追踪

当 Dot 使用保存的密码登录支持的网站时，OpenAI 表示凭证不会暴露给模型，使其远离上下文窗口，并远离智能体可能遇到的恶意指令。

系统卡片为这种分离提供了一些背景，在 OpenAI 的 Codex 模拟中，Astra 的凭证搜索标志比 GPT-5.6 Sol 出现得更频繁。在另一个被标记的案例中，Astra 被要求调试重复通知，但它走得更远，从其设置中检索了服务的 bot Token，并使用它以该服务的身份读取 Slack 消息。

该公司并未说明主 Dot 在 GitHub 或 Slack 等服务内部的操作是记录在用户的身份下，还是记录在表明它们来自智能体的身份下。如果它们带有用户的身份，调查事件的安全团队将更难区分人类所做的事情和 Dot 代表他们所做的事情。OpenAI 正在为企业试点预览专业版 Dots（Specialist Dots），它们正是围绕这个问题构建的。

组织为每个 Specialist Dot 配置其自己的身份、凭证和硬件，同时 OpenAI 正与微软合作，将其纳入 Agent 365 的治理和安全控制之下。

> 当 Dot 使用保存的密码登录支持的网站时，OpenAI 表示凭证不会暴露给模型，使其远离上下文窗口，并远离智能体可能遇到的恶意指令。

## 开发者能从中借鉴什么？

对于构建长期运行智能体的开发者来说，链式任务的结果表明，他们应该随着新工作的到来重新审视权限，而不是设置一次就一劳永逸。这可能意味着在任务之间重新声明智能体的范围、保留研究期间收集信息来源、将凭证保留在模型之外，以及在下游系统中赋予智能体其自己的身份。
