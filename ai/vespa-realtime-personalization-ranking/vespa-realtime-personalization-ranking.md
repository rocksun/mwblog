本文指出个性化并非简单的功能叠加，而是排序问题。传统碎片化架构导致数据同步滞后。通过构建统一的实时排序流水线，利用张量运算整合用户行为、业务逻辑与语义信号，可显著提升个性化推荐的实时性与准确性。

> 译自：[Personalization is a ranking problem — architecture makes it work](https://thenewstack.io/vespa-realtime-personalization-ranking/)
> 
> 作者：Jenny Morris

**每个产品团队都在追求同一个时刻：** 用户打开页面并心想，“这系统真懂我”。

喜爱花卉图案的购物者应该看到更多花卉图案；关注本地政治的用户应该在打开应用时看到有关本地政治的新闻；不断点击远程工作岗位的求职者不应再被推荐办公室坐班的工作。

这不再是一个小众功能，而是基本预期。用户能迅速判断一个产品系统是否“懂他”，且他们通常不在乎这种体验的缺失是因为搜索、推荐、营销规则还是数据过时导致的。

一个令人不安的事实是：大多数团队遇到的并不是个性化*质量*问题，而是个性化*架构*问题。

个性化不是挂载在搜索上的一个小插件，而是一个排序决策。系统必须针对当前用户和当前请求，决定什么内容应该出现在下一个位置。这意味着要同时权衡用户、物品、上下文和业务目标。在许多技术栈中，排序层往往是唯一一个无法同时获取所有这些信号的地方。

> 难点不在于收集信号，而在于当用户还在页面上时，就将这些信号整合起来。

## 为什么个性化本身就很难

为了将正确的物品放在正确的位置，系统必须同时理解多项因素：

* **意图：** 用户此刻在寻求什么？
* **物品质量：** 每个候选项究竟包含或代表了什么？
* **用户历史：** 此人点击、购买、阅读、观看或忽略过什么？
* **可用性：** 该物品是否有货、是否是新品、位置是否邻近、是否合规或能否立即发货？
* **业务优先级：** 业务方应该推广、保护或淡化什么内容？

这些信号往往存在冲突。最相关的物品可能利润率不高，利润最高的物品可能缺货。用户可能搜索“跑步鞋”，但其行为却显示“越野跑、宽版型、价格低于120美元”。

它们还以不同的节奏变化。产品属性变化缓慢；库存和价格可能全天波动；偏好随着每次点击而改变；外部环境——天气、突发新闻、冠军赛、文化热点——都可能在毫无预警的情况下产生影响。

个性化意味着在每次请求中，在几毫秒内将所有这些因素折叠成一个有序列表。瓶颈不在于信号本身，而在于查询时的排序过程。

## 传统技术栈让问题复杂化

大多数个性化系统是由一系列工具拼凑而成的，每个工具只负责相关性的一小部分。

**关键词搜索引擎**擅长词法匹配，在查询语言与目录语言一致时表现良好。但购物者、读者和求职者很少使用标准的索引术语进行表达。你索引的是“运动性能跑步鞋”，而他们输入的是“跑步鞋”。同义词规则可以提供帮助，但无法优雅地扩展到长尾语言、不断变化的目录以及新的用户行为中。

**向量数据库**则从相反的角度切入。它们擅长语义相似度计算：“帮我找到类似的东西”。这非常强大，但最近邻搜索不等同于个性化。真正的排序必须将语义相似度与实时行为、库存、价格、利润、新鲜度、合规性以及业务规则进行融合。

**重排序器、推荐服务、特征存储和规则引擎**通常被用来粘合这些组件，这正是碎片化产生的原因。

![一个碎片化的个性化技术栈与统一的查询时排序流水线对比](https://cdn.thenewstack.io/media/2026/07/9927cdb1-image1-1024x603.png)

*图1. 碎片化的个性化技术栈与统一的查询时排序流水线对比*

当检索和排序位于独立的系统中时，排序器通常基于局部、过时或预计算的世界视图进行工作。点击历史、会话上下文和用户的实时偏好向量到达得太晚。业务规则最终变成了过滤器或覆盖项，而不是排序信号。库存或价格的变动需要跨多个系统进行协调。

每一次切换都会增加延迟。每一个边界都创造了信号漂移的机会。每一个“快速规则”都变成了硬约束，可能意外地将“展示最匹配项”变成“什么都不展示”。

> “每一次切换都会增加延迟。每一个边界都创造了信号漂移的机会。”

更深层的问题在于对时间性的假设。许多架构是围绕离线排序构建的：处理目录、在批处理作业中计算分数，并一直使用这些分数直到下次重建索引。这在偏好稳定时有效，但在最有价值的信号是两秒前发生的点击时，这种方式就失效了。

## 在单一实时流水线中排序会有什么改变

实时个性化架构将检索、排序和推理视为同一个服务问题。

这是 [Vespa 方法](https://vespa.ai/)背后的核心理念：文本搜索、向量相似度、结构化过滤、排序表达式、张量计算和模型推理可以存在于同一个查询流水线中。系统无需在某处检索，在另一处进行特征增强，最后再进行排序，而是在决定返回什么内容的同时，就能利用相关信号进行排序。

这种架构选择改变了问题的形态。

### 1. 检索从一开始就是混合的

词法搜索、语义搜索和结构化过滤可以同时运行，而无需事后再进行协调。一个产品查询可以在一个请求中结合文本、嵌入向量、过滤器、会话行为和物品属性。

这很重要，因为个性化很少由单一信号决定。用户的查询很重要，语义相似度也很重要，品类、可用性、价格和业务约束同样重要。混合检索在排序开始前就保持了这些信号的可用性。

### 2. 排序可以表达实际目标

个性化分数不应被锁定在单一的 [相似度函数](https://thenewstack.io/spark-4-2-ai-workloads/)中，它应该是一个反映产品目标的公式。

该公式可以结合 BM25、向量相似度、用户亲和度、库存水平、利润、流行度、折扣力度、新鲜度、评分、距离或天气项。其中一些信号需要先进行归一化，一些只对特定品类或用户有效，一些应作为权重进行测试。

重要的是，它们都是同一个排序表达式中的项，而不是散落在各个服务中。

一个简化版本可能如下所示：

```

final_score =
    0.30 * lexical_relevance +
    0.25 * semantic_similarity +
    0.25 * user_affinity +
    0.10 * availability +
    0.10 * business_priority

```

在生产环境中，公式可以更加精细。但原则很简单：个性化、相关性和业务逻辑属于同一个评分决策。

### 3. 模型推理可以在数据所在之处运行

某些信号应该来自训练好的模型，而非手工调整的规则：购买倾向、流失风险、质量预测、欺诈风险、查询分类或学习排序模型。

当推理在服务路径上运行时，这些模型输出可以成为排序特征，而不是延迟的批处理分数。这减少了将数据发送到独立推理服务、等待响应并将其拼接回排序结果的需要。

### 4. 更新即刻生效

“实时”不应意味着“在下次索引重建之后”。如果库存发生变化，库存状态应立即参与排序。如果用户点击了两件黄色连衣裙，那么“黄色”属性在下一次请求中就应产生影响。如果运营团队调整了排序权重（假设权重作为查询时输入暴露出来），实验应该立即开始产生有效的反馈。

这就是每晚运行一次的任务与作为实时排序决策的个性化之间的区别。

## 张量让个性化变得具体

最有效的思维模型很简单：将用户和物品表示在同一个特征空间中，然后根据匹配程度进行排序。

在 Vespa 中，张量使其实践变得可行。张量可以是标量、稠密向量、特征权重对的稀疏映射、矩阵或更复杂的结构。这意味着同一个框架可以表示语义嵌入、产品属性、用户偏好、业务目标和模型特征。

![用户和物品张量组合成个性化分数，再与其他排序信号融合](https://cdn.thenewstack.io/media/2026/07/ac21c1d5-image2-1024x585.png)

*图2. 用户和物品张量组合成个性化分数，再与其他排序信号融合*

例如，每个 **物品** 可以携带一个稀疏特征张量：

```

{
  "floral": 0.90,
  "yellow": 0.70,
  "short_sleeve": 0.80,
  "crew_neck": 0.65
}

```

每个 **用户** 可以携带一个具有相同特征名称的张量：

```

{
  "floral": 1.00,
  "yellow": 0.37,
  "short_sleeve": 0.33,
  "crew_neck": 0.31
}

```

由于两个张量共享形状，个性化就变成了点积运算：将匹配的特征相乘，对结果求和，并在排序中使用该分数。

在 Vespa 排序配置文件中，核心表达式非常简洁：

```

# schema: item attributes stored as a sparse tensor
field item_features type tensor&lt;float>(feature{}) {
    indexing: attribute | summary
}
 
# rank profile: the user's live preferences arrive as a query tensor
rank-profile personalized {
    inputs {
        query(user_features) tensor&lt;float>(feature{})
    }
    first-phase {
        expression: sum(query(user_features) * attribute(item_features))
    }
}

```

这一个表达式并不是全部的排序函数，它只是个性化项。BM25、向量相似度、库存、利润、新鲜度、距离或模型分数可以作为其他带权重的项添加进来。

用户张量是实时行为发挥威力的地方。点击一件花卉商品，“花卉”权重就会上升；点击两件黄色商品，“黄色”权重就会上升；应用程序将点击事件馈送到用户配置文件中。下一次查询可以立即使用这些更新后的偏好，而无需等待每晚构建一次用户画像。

## 业务目标不再与个性化冲突

在碎片化的技术栈中，业务规则往往变成了粗糙的工具：提升此品类、隐藏该品牌、强制将这些项目置顶、过滤掉那些项目。这可以在短期内满足营销目标，但会损害相关性。

当业务逻辑成为排序表达式的一部分时，它可以变得更加微妙。你可以在不忽略用户意图的情况下提升库存过剩的产品；可以在预报有雨时推广雨伞，而无需将每次搜索都变成“雨伞搜索”；可以给予新卖家一点探索提升；可以在新产品系列发布前优先处理库存积压；可以在冠军赛期间展示团队周边商品。

> “当业务逻辑成为排序表达式的一部分时，用户依然能获得相关结果，业务方依然能影响结果。”

用户依然能获得相关结果，业务方依然能影响结果。区别在于两者都被表达为排序信号，而不是竞争的系统。

这也使实验变得更加容易。运营或增长团队可以在不要求工程部门重写整个流水线的情况下测试权重、流量拆分和排序配置。相关性变成了一个可控的增长杠杆，而不是一个脆弱的副产品。

## 同样的模式不仅适用于商业

上述示例在服装领域很容易想象，但该架构并非局限于商业。个性化在许多产品中都是同一个排序问题：

* **内容流：** 融合主题亲和度、新鲜度、互动率、创作者质量和业务规则。
* **新闻：** 根据阅读历史、主题兴趣、地域性、新鲜度和来源多样性进行排序。
* **招聘：** 将远程工作、资历、薪酬、地点和技术栈等候选人偏好与职位属性进行匹配。
* **地理搜索：** 将距离视为与相关性、质量和偏好并列的归一化排序项。
* **视频与音频：** 结合嵌入向量、观看历史、元数据、新鲜度和学习到的排序模型。

不同领域需要不同的特征，但架构模式是相同的：检索候选对象，利用关键信号进行排序，随着行为改变更新这些信号，并将决策保持在靠近数据的位置。

## 规模化不必成为权衡的对象

人们自然会担心，一个更具表达力的排序系统必然会变慢。实际上并非如此。

Vespa 从一开始就是为大规模服务构建的：支持数十亿文档、高查询量和低延迟排序。其成功的秘诀在于多阶段排序。系统不会对每个可能的结果都运行最昂贵的逻辑。相反，它使用快速的第一阶段缩小候选集，然后对剩余的较小群体应用更精确的排序。

例如，一个廉价的第一阶段会缩小巨大的候选集。然后，当候选集较小时，Vespa 可以应用全精度评分、更丰富的 [张量运算](https://thenewstack.io/vectors-tensors-ai-search-explained/)、业务逻辑和模型推理，将算力用在最重要的地方。

结果是一种务实的平衡：在整个语料库上保持速度，在最终排序上保持准确度，并具备足够的灵活性来个性化每个查询，而无需将服务栈变成一连串脆弱的服务链。

## 接下来要做什么

个性化的失败并非因为团队缺乏数据。大多数团队已经拥有足够多的信号：查询意图、点击、产品属性、库存、利润、新鲜度、位置和业务优先级。更棘手的问题是，这些信号往往存在于不同的系统中，以不同的速度变动，且到达得太晚，无法影响最终的排序决策。

这就是为什么个性化应该被视为一个排序问题。当检索、排序、个性化和业务逻辑被拆分在不同的系统中时，排序器被迫在 [过时或不完整的上下文](https://thenewstack.io/vibe-coding-context-debt/)下工作。用户的行为变化速度超过了架构的响应速度。每一个新信号都变成了另一个集成项目。

统一的实时排序流水线改变了这一切。用户行为、物品属性、语义相似度、词法相关性、库存和业务目标都可以成为同一个评分函数的一部分。张量使这些信号可以直接在查询时进行比较和使用。与其在系统末端“打补丁”式的添加个性化，不如将其变成引擎为每次查询所做决策的一部分。

目标很简单：在用户发起请求的那一刻，利用现有的最佳上下文对每个结果进行排序。这才是个性化不再像是一个突兀的功能，而真正感觉像是“相关性”的时刻。
