当人们讨论AI基础设施时，话题几乎总是围绕着GPU和TPU展开。*The New Stack* 与 Arm 的 [Bhumik Patel](http://linkedin.com/in/bhumikpatel) 以及 Google 的 [Mo Farhat](https://www.linkedin.com/in/mofarhat0/) 进行了深入交流，讨论了一种似乎不再引人注目的芯片：CPU。探讨了为何随着AI从聊天机器人向智能体（agents）转变，CPU的重要性反而日益凸显。

[Farhat](https://www.linkedin.com/in/mfarhat/) 是 Google Compute Engine 中 Axion 和基于 Arm 的虚拟机的产品管理负责人，他告诉 *The New Stack*：“CPU 的角色，或多或少就像是空中交通管制员。”

在这一集中，我们讨论了从对话式聊天机器人向自主智能体的转变，如何悄然演变成一个关于 CPU 的故事。

“当今的 60 亿到 80 亿参数模型表现远超以往，”Farhat 说。对于某些专门的工作负载，他说，CPU 可以提供大约每秒 25 个 token 的速度，这对于智能体工作负载来说已经足够。

## 工作负载从“回答”转向“行动”

早期的聊天机器人只是给出回复，但智能体可以基于回复采取行动。它们通过调用工具来执行任务，并在需要时创建环境来运行它们编写的代码。

“智能体工作负载的编排本身就是一种始终在线的、分支型的控制流逻辑，而这正是 CPU 所擅长的，”Farhat 说。

Farhat 表示，虽然大语言模型通常在加速器上运行，但 CPU 也负责处理编排、数据准备、语义搜索和向量数据库等任务。

[Patel](https://www.linkedin.com/in/bhumikpatel) 负责推动 Arm 在云和 AI 领域的软件生态系统工作，他表示公司专注于在大规模运行这些工作负载所需的软件和基础设施层。他指出，不同类型的智能体正在执行“不同类型的代码执行、API 调用以及典型的 CPU 工作”。

在此过程中，运行模型本身也有 CPU 的一席之地，但我们讨论的是非常小的模型，包括摘要器、推荐器和评估器。

“当今的 60 亿到 80 亿参数模型表现远超以往，”Farhat 说。对于某些专门的工作负载，他说，CPU 可以提供大约每秒 25 个 token 的速度，这对于智能体工作负载来说已经足够。

## 为什么智能体需要沙箱，而且需要很多

然而，为了让智能体能够运行代码，它们需要一个环境，使其能够在不危及生产系统的情况下安全地执行。

“智能体正在执行代码，所以你要确保 LLM 生成的代码是可信的，”Patel 说。“或者，如果它不可信，那么你就要对环境进行沙箱隔离。”

Google 提出的解决方案是 gVisor，这是一个开源项目，充当应用程序与主机操作系统之间的隔离层。正如 Farhat 所言：“我们在零信任环境中运行。这就是为什么智能体需要运行在隔离技术中的确切原因。”

Google 认为，GKE Agent Sandbox 还可以处理这一智能体时代所需的大规模需求。

“GKE Agent Sandbox 将允许客户每个集群每秒启动 300 个沙箱，”Farhat 说。Patel 表示，该平台使用 pod 快照和挂起环境的预热池，帮助客户更快速地扩展，而无需让所有这些环境始终处于完全配置状态。

## 效率之道

Google 表示，Axion 在成本和能源使用方面都具有优势。

“今天的 Axion 可以为你提供相当于当前一代同类虚拟机 2 倍的性价比，”Farhat 说，“而且我们的能源效率提高了 60% 以上。”

Google 提供用于持续高性能的 Axion C4A 机器，以及用于性能与成本优化平衡工作负载的 N4A 机器。对于计算密集型、长时间运行且完成时间至关重要的工程任务，Farhat 表示 C4A 提供了所需的性能。对于密度和成本更重要的小型代码执行任务，他提到了 N4A。

“Google Cloud 中选项的好处是，正如 Mo 刚才所说，你有用于高性能工作负载的 C4A，还有 N4A，”Patel 说。“如果你想扩展大量的智能体，而且不同类型的智能体在做不同类型的代码执行和 API 调用以及典型的 CPU 工作，N4A 是一个很好的选择。”

Farhat 更广泛的观点是，随着智能体的规模化，CPU、GPU 和 TPU 资源将继续协同工作。

“我们处于一个流动的计算世界中，”他说。“我们建议客户审视所有选项，包括基于 CPU、TPU 和 GPU 的资源，并确保他们的应用程序是为未来的扩展而构建的。”
