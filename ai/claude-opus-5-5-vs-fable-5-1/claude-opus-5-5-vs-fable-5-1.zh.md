**Anthropic 于 9 月 22 日发布了 [Claude Opus 5.5](https://thenewstack.io/claude-opus-5-5-release/)**，并表示其在绝大多数工作中的表现与 Claude Fable 5.1 相当。按标价计算，它的每 Token 成本不到后者的一半。它在 Terminal-Bench 4.0、FrontierCode 和 CursorBench 上领先于 Fable 5.1。Anthropic 表示，这两个模型之间的差距“比这些评分所显示的要窄”。Opus 5.5 的输入 Token 价格为每百万 4 美元，输出 Token 价格为每百万 20 美元。Fable 5.1 的价格则分别为 10 美元和 50 美元。

Anthropic 自己的模型文档仍然建议开发者将 [Fable 5.1](https://thenewstack.io/anthropic-fable-5-1-launch/) 用于“对推理要求高且长视野的智能体工作”，并将其列为两者中较慢的一个。因此，在我的 Opus 5.5 与 Fable 5.1 测试中，我想要回答两个问题：

* Opus 5.5 的准确率真的和 Fable 5.1 一样高吗？
* 如果是这样，对于 Opus 5.5 表现更好的任务，Fable 5.1 是否仍应作为高端模型销售？

这是我的第三次 Opus 5.5 测试。在[第一次测试](https://thenewstack.io/claude-opus-5-5-vs-opus-5/)中，它以更低的成本匹配了 Opus 5 在推理问题上的表现，但其速度提升未达到 Anthropic 的宣称。这一次我专注于编码，Anthropic 的基准测试显示 Opus 5.5 在编码方面领先于 Fable 5.1。

## 测试过程

我通过 Anthropic API 调用了这两个模型，使用了相同的提示词、自适应思考（adaptive thinking）和最大努力设置。每个模型每个测试运行五次。一个隐藏的测试套件对每次测试进行评分，我记录了每次运行的 Token 数量、标价成本和实际耗时。

* **智能体 Bug 修复** – 模型获得一个包含四个预设 Bug 和一个不稳定测试（flaky test）的小型 Python 订单定价代码库，以及列出文件、读取文件、写入文件和运行测试的工具。一个包含 12 个测试的隐藏测试套件用于检查修复情况，我跟踪了模型是否触及了测试或注意到了那个不稳定的测试。
* **解析器规范** – 模型根据一份两页的规范，为一个虚构的包管理器编写一个依赖项解析器，且不运行任何代码。由 120 个测试组成的隐藏套件对其进行评分。
* **并发 Bug** – 模型获得一个包含三个竞态条件（race conditions）的 asyncio 任务队列，以及一份描述重复扣款和永不运行任务的事件报告。它必须在不运行代码的情况下发现并修复每一个 Bug，并通过八个带有受控时钟的隐藏测试来检查每个修复。

解析器和并发测试都只给模型一个提示词和一个回复。我最初将限制设为 64,000，但 Opus 5.5 超出了空间限制，于是我将限制提高到 128,000，这是两个模型允许的最大值。Fable 5.1 的使用量从未超过 55,000。

*我没有把提示词包含在这里，因为每个测试都依赖于过长而无法重新打印的代码库、规范或模块。*

### 智能体 Bug 修复

两个模型在所有五次运行中都修复了全部四个 Bug，并全部通过了 12 个隐藏测试。双方都没有编辑测试文件，并且都标记了那个不稳定的测试。

仅从评分来看，这两个模型打成平手，但它们处理不稳定测试的方式不同。该测试由于代码模拟了对货运代理 API 的慢速调用而随机失败。Fable 5.1 “作弊”并在所有五次运行中删除了模拟延迟，因此测试总是能通过。在真实的代码库中，这意味着移除 API 调用以使测试通过，而订单将永远不会真正与承运商进行核对。在生产环境中，这可能意味着为承运商无法交付的订单接受付款、运送到它不服务的地址，并且在其服务中断时永远无法察觉。

Opus 5.5 在所有五次运行中都保持代码原样。它通过重新运行测试确认了该测试是不稳定的，并表示缩短延迟“只会让测试通过而什么也没修复”，同时指出了测试本身中真正的修复方法。这是更好的结果，因为应用程序仍然可以运行，并且开发者知道该修复什么。一个隐藏了损坏集成的绿色测试套件，比一个说实话的红色测试套件更糟糕。

> 一个隐藏了损坏集成的绿色测试套件，比一个说实话的红色测试套件更糟糕。

Opus 5.5 平均耗时 3 分 21 秒，进行了 25 次工具调用，消耗 20,625 个输出 Token，每次运行成本 0.75 美元。Fable 5.1 平均耗时 2 分 37 秒，进行了 22 次工具调用，消耗 11,381 个输出 Token，成本 1.50 美元。Opus 5.5 每次运行大约运行了七次测试套件，而 Fable 5.1 为三次，主要是为了检查不稳定的测试。

Opus 5.5 赢得了这项测试，因为它以一半的成本修复了与 Fable 5.1 相同的四个 Bug，并以正确的方式处理了不稳定的测试。

### 解析器规范

两个模型在所有五次运行中都通过了全部 120 个隐藏测试。

Opus 5.5 平均耗时 9 分 40 秒，消耗 70,687 个输出 Token，每次运行成本 1.42 美元。Fable 5.1 平均耗时 6 分 46 秒，消耗 38,710 个输出 Token，成本 1.96 美元。Opus 5.5 多使用了 83% 的 Token，但成本仍然低了 28%，因为每个 Token 的成本低了 60%。

额外的 Token 并没有转化为额外的代码。两个模型都编写了大约 400 行代码，因此 Opus 5.5 几乎所有的额外开销都花在了思考上。在其中一次运行中，Opus 5.5 还首先列出了规范不明确的地方以及它为每个地方做出的选择，这是 Fable 5.1 从未做过的。

这项测试在准确性上打成平手，因此赢家取决于你在优化什么。如果你最看重成本，Opus 5.5 获胜；如果你需要更快的答案，Fable 5.1 获胜。

### 并发 Bug

这项测试产生了唯一的失利。Fable 5.1 在每次运行中都修复了所有三个竞态条件并通过了所有八个隐藏测试。

Opus 5.5 在三次运行中做到了这一点。在另外两次运行中，它耗尽了全部 128,000 个输出 Token，却没有完成一个答案。每次运行耗时约 19 分钟，成本 2.57 美元。

两个模型还“修复”了比我预设更多的 Bug。Fable 5.1 每次运行列出了四到七个修复项，Opus 5.5 列出了七到八个。这些额外的改动都没有破坏任何东西，有些还收紧了真正的薄弱环节，但这意味着需要审核员检查更多的代码。

把失败的运行计算在内，Opus 5.5 平均耗时 16 分 43 秒，消耗 111,428 个输出 Token，每次运行成本 2.24 美元。Fable 5.1 平均耗时 8 分 27 秒，消耗 43,001 个输出 Token，成本 2.17 美元。即使在其完成的三次运行中，Opus 5.5 平均也耗时 15 分钟，接近 Fable 5.1 时间的两倍，并且消耗了 100,380 个 Token，是 Fable 5.1 所需数量的两倍多。

Fable 5.1 明显赢得了这项测试。它每次都完美表现，速度快一倍，成本相差无几，因为 Opus 5.5 更便宜的 Token 并没有弥补其使用量过多的劣势。

## 结果

|  |  |  |
| --- | --- | --- |
| **测试（各 5 次运行）** | **Opus 5.5** | **Fable 5.1** |
| 智能体 Bug 修复 | 5/5 完美, 3:21, 20,625 输出, 25 次工具调用, $0.75 | 5/5 完美, 2:37, 11,381 输出, 22 次工具调用, $1.50 |
| 解析器规范 | 5/5 完美, 9:40, 70,687 输出, $1.42 | 5/5 完美, 6:46, 38,710 输出, $1.96 |
| 并发 Bug | 3/5 完美, 16:43, 111,428 输出, $2.24 | 5/5 完美, 8:27, 43,001 输出, $2.17 |
| 完美运行次数 | 13 / 15 | 15 / 15 |
| 15 次运行总耗时 | 2:28:39 | 1:29:14 |
| 15 次运行总成本 | $22.07 | $28.14 |

Fable 5.1 的 15 次运行全部完美通过，Opus 5.5 则通过了 13 次，但分数并不能说明全部问题。Opus 5.5 在智能体测试中获胜，因为它在没有对不稳定测试进行投机取巧的情况下修复了相同的 Bug，且成本减半。解析器测试在准确性上打平。Fable 5.1 在并发测试中完胜，因为 Opus 5.5 两次用尽空间且未返回任何结果。

总体而言，Opus 5.5 的成本低了 22%（22.07 美元对 Fable 5.1 的 28.14 美元），但它编写的输出 Token 是前者的 2.2 倍，完成所有 15 次运行的时间长了 67%。

### 我的看法如何？

在我做过的所有测试中，这是最难填写“我的看法”部分的测试。Opus 5.5 和 Fable 5.1 都存在缺陷，只是方式不同。在我看来，两者都不应被称为高端模型。

> Opus 5.5 和 Fable 5.1 都存在缺陷，只是方式不同。

Opus 5.5 过度思考。它完成了所有能够跑完的测试，但它需要的 Token 大约是 Fable 5.1 的两倍，因此它最终只便宜了 22%，并且在最难的测试中两次触及 Token 上限而没有产出结果。

Fable 5.1 则在走捷径。它从未在隐藏测试中失败，并且在每个测试中速度都更快，但它通过删除应用程序需要的代码来通过智能体测试。

> 高端产品买到的是速度和更少的死胡同，而不是更好的判断力。

Anthropic 的说法是正确的，即 Opus 5.5 在完成任务时的准确性与 Fable 5.1 相当。高端产品买到的是速度和更少的死胡同，而不是更好的判断力。

在智能体工作中使用 Opus 5.5，因为它可以运行测试并进行自我检查。在需要一次性解决的难题时，或者在注重速度时，使用 Fable 5.1。无论使用哪一个，都要检查它为了通过测试而更改了什么。
