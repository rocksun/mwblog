DevOps 运动在大约 20 年前拉开帷幕，它打破了软件开发人员与 IT 运维人员之间的传统隔阂，并采纳了“你构建，你运维”（you build it, you run it）的[准则](https://queue.acm.org/detail.cfm?id=1142065#:~:text=You%20build%20it%2C%20you%20run%20it.)。然而，在 [Kubernetes 环境](https://thenewstack.io/kubernetes/)中，当应用团队同时被要求操作数据库和数据服务时，这一模式可能会变得不切实际。在实践中，DevOps 数据库运维所需的结构化程度远超许多团队的预期。

作为云原生服务提供商 [**anynines**](https://anynines.com/) 的高级云平台工程师，我一次又一次地看到这种情况：在构建软件方面技术高超且卓有成效的开发人员，不得不处理那些处于完全不同领域、需要不同运维专业知识的数据库。

> 在构建软件方面技术高超且卓有成效的开发人员，不得不处理那些处于完全不同领域、需要不同运维专业知识的数据库。

在平台工程数据库管理中，这一点尤为突出。其目标应该是减轻运维负担，而不是将其转嫁给应用团队。一个强大的[内部开发者平台](https://thenewstack.io/7-core-elements-of-an-internal-developer-platform/ "internal developer platform")应该让平台工程数据库更易于使用，而不是更难运行。

只需几个步骤即可轻松部署 Postgres、Redis 或 OpenSearch。例如，运行一个 Helm install 命令，如果一切顺利，服务就能正常运行。当出现故障时，挑战就来了，这些服务需要保持可靠性，这意味着需要进行打补丁、监控、备份和适当的恢复。大多数产品团队本不应在这些方面建立深厚的专业知识。

现代应用程序很少依赖单一的数据服务。SaaS 应用程序可能需要在 Kubernetes 上运行 Postgres 来处理核心数据，在 Kubernetes 上运行 Redis 来进行缓存，以及在 Kubernetes 上运行 OpenSearch 或 Elasticsearch 来进行搜索和索引，所有这些都在高可用性配置中运行。这就是为什么我认为“你构建，你运维”只有在开发人员能够通过自动化请求所需服务，而复杂的运维工作在后台完成时才有效。

## 团队在哪里受阻

通常情况下，当你不得不更新数据库时，第一个故障点就会出现。想象一下，Postgres 部署在特定版本上，几周后，发现了一个严重的安全性漏洞，需要你更新系统。根据升级情况，你可能需要仔细阅读变更日志，决定运行它是否安全，或者在继续之前准备几个步骤。这就是数据库自动化和 Kubernetes 变得至关重要的原因，因为升级是数据库生命周期管理的一部分。它绝不可能是“一劳永逸”的设置。

在单节点上运行 Postgres 时，处理和更新很容易。然而，为了避免停机，你需要一个 Postgres 集群（通常由三个节点组成），以便在一个节点宕机时，另一个节点可以接管。这种设置提高了弹性，但也引入了问题，并可能造成它原本旨在预防的停机。这就是为什么 Postgres、Kubernetes 和其他数据库需要仔细的所有权管理。

## 当故障转移出错时

升级三节点集群必须一次一个节点地进行，因此故障转移可能会变得很混乱。如果决定哪个节点接管的选举失败，两个节点最终可能都认为自己负责，从而导致写入不一致，最坏的情况是数据损坏。有时，重启集群并重新建立领导者可以在几分钟内解决问题。但如果数据确实损坏了，或者你无法找出问题所在，那么宕机时间可能会延长到数小时。

> 如果决定哪个节点接管的选举失败，两个节点最终可能都认为自己负责，从而导致写入不一致，最坏的情况是数据损坏。

业务影响变得难以忽视。假设我正在为一家大型连锁酒店运行预订平台，数据库宕机了；这些酒店都无法接受客房预订。如果备份没有正常工作，恢复问题就会恶化：你可能不仅损失了正常运行时间；你可能还损失了实际的预订，完全不知道明天或下周谁会来。

对我来说，这就是核心问题。开发人员最终花费时间去理解数据库故障模式、恢复程序和备份问题，而不是构建应用程序本身。这会拖慢他们的速度，因为他们被迫不断地进行故障排除，并使他们脱离了自己最擅长的工作。

## 你不能仅仅依靠招聘来解决

更深层的问题是，你无法简单地通过招聘来解决这个问题。首先，你必须找到合适的人，这说起来容易做起来难——数据库运维专家很难找到。美国劳工统计局预计，从 2024 年到 2034 年，数据库管理员和架构师的[增长率仅为 4%](https://www.bls.gov/ooh/computer-and-information-technology/database-administrators.htm)，大多数职位空缺来自人员更替，而不是爆炸式的新增供给。

即使你找到了他们，他们也无法独自覆盖所有事情。这些问题不仅在你用笔记本电脑时出现；它们经常发生在晚上，所以你需要一个适当的随叫随到（on-call）时间表，而且一名专家通常是不够的。请记住，人们会生病、休假或可能离开公司。对个人专家的依赖是有问题的。

另一个挑战是广度。不同的数据库需要不同的专家，很难找到一个能同样出色地操作所有这些数据库的人。这意味着你不只是在建立一个随叫随到时间表；你正在建立多个，每个都与不同的技术栈相关联。它可能在拥有固定数量数据服务的小型团队中有效，但随着团队的成长、应用程序数量的增加以及数据库资产的扩展，这使得整个模型变得更难管理。

## 让运维变得不可见

好的数据库运维在*大多数*时候应该是不可见的。安全补丁会自动应用，备份按计划运行，并且这些备份在需要时确实可用。换句话说，开发人员醒来时应该发现数据库处于更安全的状态，而不必亲自去追踪它。

> 好的数据库运维在大多数时候应该是不可见……开发人员醒来时应该发现数据库处于更安全的状态，而不必亲自去追踪它。

这就是为什么我认为应用团队和平台团队之间的分工如此重要。在数据库生命周期中，只有少数时刻开发人员真正需要参与。例如，当他们想要一个新的数据库、需要凭据，或者想在有风险的发布之前触发备份时。其他一切都应由自动化和背后的平台来处理。仅仅因为开发人员在 Kubernetes 上部署应用程序，并不意味着他们就应该成为数据库运维专家。我理想的情况始终是：开发人员专注于他们擅长的事情——交付应用程序本身。

多年前引入的“你构建，你运维”宗旨出色地解决了部署问题，但没有解决运维问题。然而，通过集中式自动化，它可以在规模上变得现实。随着组织的发展，集中式控制平面特别有用。你拥有的数据库越多，了解哪些需要打补丁、哪些合规以及哪些需要立即采取行动（而不是下周）就越重要。在大型公司中，这种治理不能依赖团队手动协调。它必须能够在一个地方实现可视化和可管理。
