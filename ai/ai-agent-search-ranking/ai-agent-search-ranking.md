本文探讨了AI智能体结合实时网络搜索与内部数据时面临的“双重证据源与单一上下文窗口”的挑战。文章指出，虽然网页搜索解决了信息查找问题，但真正的核心在于如何通过精细的检索、混合匹配以及多阶段排序策略，来解决信息冲突、时效性和权限控制，从而确保智能体做出准确判断。

> 译自：[The problem: two pools of evidence, one context window](https://thenewstack.io/ai-agent-search-ranking/)
> 
> 作者：Bonnie Chase

AI 智能体长期以来一直存在 URL 问题。当智能体需要最新信息却没有搜索工具时，它往往会凭空捏造它认为答案所在的网页地址。它可能会猜测诸如 `docs.example.com/v4.2/auth` 的地址，尝试加载该地址，并因为页面不存在而收到“找不到页面”的错误。然后，它要么继续猜测，要么退回到其训练中过时的信息。

> “实时网络 search 为智能体带来了全新的页面。但在你的自身数据中决定信任哪些页面仍然是一个排序问题。”

基础设施提供商已经注意到了这一点。10月，[InfoQ 报道称](https://www.infoq.com/news/2026/10/cloudflare-web-search-api/)，Cloudflare 在其 AI Gateway 中推出了 [Web Search API 的 Beta 版本](https://thenewstack.io/deepseek-web-search-api/)。智能体可以通过单一接口调用多个搜索提供商，并获得包含源链接、日志和访问控制的实时结果。Cloudflare 的理由非常直接：如果没有搜索，智能体往往会靠猜测。

这是一个受欢迎的转变，实时搜索可能在一年内成为智能体的默认工具，但它只解决了问题中“寻找”的一部分。一旦新鲜的页面呈现在智能体面前，仍然需要某种机制来决定智能体实际应该依赖其中的哪些页面，以及你自己的哪些文档。这个决定取决于你的检索层。

## 问题所在：两个证据池，一个上下文 window

在企业内部工作的智能体很少仅仅依靠网络来回答问题。它还拥有让其对公司有价值的数据：产品目录、文档、合同、支持历史、账户记录和权限。接入网络搜索后，任务的每个步骤现在都可以从两个截然不同的数据池中获取信息。

|  |  |  |
| --- | --- | --- |
|  | **网络结果** | **内部数据** |
| **时效性** | 通常是几小时或几天前 | 在无人察觉的情况下可能过时数月 |
| **质量** | 参差不齐：官方文档与论坛帖子并存 | 经过整理，但针对的是产品的过去状态 |
| **结构** | 大多是非结构化文本 | 文本、元数据和结构化记录的混合 |
| **权威性** | 必须从来源推断 | 已知，但很少作为字段存储 |
| **访问控制** | 公共 | 按客户、区域、合同或角色划分 |

智能体必须对这些进行调和，通常在单个任务中需要进行多次。而且它需要回答的问题是搜索 API 从未构建来处理的。当昨天的供应商更新日志与去年春天的内部知识库文章相矛盾时，哪个胜出？这个结果是否适用于该客户的版本和区域？是否允许智能体展示它？

这些都是排序和过滤决策。它们取决于你的数据和业务规则，因此你必须在两者都可用的地方做出这些决策。

## 为什么在生产环境中简单拼接结果会失效

最简单的集成是运行网络搜索、运行内部搜索，将一个列表追加到另一个列表后面，然后让模型自行排序。这在开始时可能运行良好，但一旦针对不断增长的数据和流量运行，它往往会以几种可预测的方式失败：

* **冲突无法解决。** 模型看到了两个相互矛盾且都表现得很有信心的来源，却没有任何信号表明哪个更新或更具权威性，因此它会随机选择一个，或者将它们融合成一个与两者都不匹配的答案。
* **陈旧性被隐藏。** 仅凭相似度，一篇与用户用词几乎完全吻合的 3 个月前的知识库文章，就会击败 4 天前的更新日志。嵌入中没有任何内容表明该文章已经过时。
* **权限应用得太晚。** 如果访问规则在检索之后运行，受限制的内容可能已经进入了 prompt。如果它们的运行方式很粗糙，有用的结果就会与敏感结果一起被丢弃。
* **成本和延迟叠加。** 一个人进行一次搜索并阅读结果。一个智能体在规划、检查和完善任务时，可以在单个任务中触发十几甚至更多的检索调用。在每次调用中将每个候选对象发送给模型会迅速累积成本，并且更多的上下文并不能可靠地产生更好的答案。

更大的上下文 window 并不能解决这些问题。向模型发送更少、挑选得更好的证据可以。

> “更大的上下文 window 并不能解决这些问题。向模型发送更少、挑选得更好的证据可以。”

Clarm 是一家为开源软件公司构建销售和支持智能体的 Y Combinator 初创公司，[很早就遇到了这个问题](https://blog.vespa.ai/agentic-ai-powered-sales-for-developers-with-vespa/)。其创始人 Marcus Storm-Mollard 表示，团队意识到“搜索，而不是生成，才是真正需要解决的问题。”生成答案是容易的部分。寻找合适的、作为其基础的信息是困难的部分，这就是为什么 Clarm 通过单个查询运行文本搜索、向量相似度和结构化过滤，而不是将不同的存储拼凑在一起。

## 当智能体跨来源搜索时会发生什么变化

当智能体将实时网络结果与内部数据结合时，它们需要考虑不同的检索方法、元数据、权限和排序信号。有四个设计考量尤为突出。

### 1. 在一个查询中跨多种方法进行检索

关键词匹配可以捕捉精确的产品名称、错误代码和版本字符串，而这是嵌入（embeddings） notoriuously（出了名地）擅长解决的盲区。向量搜索则可以捕捉同义词和意图。结构化 filters 则强制执行诸如客户、版本和权限等硬性约束。

在单个索引集合中，混合检索可以结合关键词匹配、向量相似度和结构化过滤。仅凭这一点，并不能将外部网络搜索 API 的结果与内部索引的结果进行融合。双源集成需要单独的设计决策。

```

select * from evidence where
  ({targetHits: 200}nearestNeighbor(embedding, q) or userQuery())
  and visibility contains "customer"
  and product_version contains "4.2"

```

更广泛的教训是，检索系统需要能够同时处理词法匹配、语义相似度和过滤。无论选择何种搜索平台，这些需求都至关重要。Perplexity 在为其答案引擎自主构建搜索时也遇到了这堵墙。其 CEO Aravind Srinivas 曾将公司的切入点总结为“首先解决搜索，然后解决其他一切”。但当团队[评估现有工具时](https://vespa.ai/case-studies/why-perplexity-chose-vespa-ai-search/)，他们发现向量数据库甚至无法可靠地支持简单的布尔过滤器，而传统的搜索后端只提供原始的语义排序。它需要在一个引擎中实现词法检索、语义检索和过滤，并达到消费者规模，因此最终选择了 Vespa 来构建它。

### 2. 基于超越相似度的维度进行排序

与查询的相关性只是其中一个信号。智能体还需要权衡时效性、来源权威性和业务规则：官方文档优于论坛帖子，上周的更新日志优于去年的维基页面，客户合同对应的版本优于最新版本。

[多阶段排序（Multiphased ranking）](https://docs.vespa.ai/en/ranking/phased-ranking.html)是实现这一点的一种实用方法。成本较低的第一阶段根据一系列信号对数千个候选对象进行打分，而更昂贵的学习模型则对剩下的少数对象进行重新排序：

```

rank-profile agent_evidence {
    inputs {
        query(q) tensor&lt;float>(x[384])
    }
    rank-properties {
        freshness(published_at).maxAge: 7776000
    }
    first-phase {
        expression: bm25(body) + closeness(field, embedding) + 0.5 * freshness(published_at) + attribute(source_authority)
    }
    second-phase {
        rerank-count: 100
        expression: xgboost("evidence-ranker.json")
    }
}

```

重要的不是具体的权重。而是时效性和权威性是评分中明确的、可检查的输入，而不是你希望模型从文本中推断出来的东西。（`maxAge` 设置控制[时效性衰减](https://docs.vespa.ai/en/reference/ranking/rank-feature-configuration.html)的速度；此处设置为 90 天。）

> “重要的不是具体的权重。而是时效性和权威性是评分中明确的、可检查的输入，而不是你希望模型从文本中推断出来的东西。”

[Metal AI](https://blog.vespa.ai/agent-driven-intelligence-on-vespa-cloud/) 为私募股权公司构建情报平台，在尽职调查问卷中遇到了这个问题。公司必须回答投资者提出的数千个问题，模型不能自由生成这些答案。它们必须来自法务部门已经批准的回复库，并且该库会随时间变化，存储在文档和电子表格中。单纯的相似度很容易浮现出已被取代的已批准答案。因此，Metal 在索引答案库时考虑了时效性，并将时效性与语义相似度一起排序，以便智能体提取当前批准的答案，而不仅仅是最匹配的答案。

### 3. 将网络结果视为候选，而非最终答案

网络搜索和内部检索通常返回独立的结果集，每个结果集都有其自己的相关性信号。简单地将这两组结果传递给模型，会让模型自己去调和时效性、权威性和相关性方面的差异。

一种更慎重的方法是，在选择进入 prompt 的内容之前，根据一致的准则对[来自两个来源的证据](https://thenewstack.io/building-trust-agentic-rag/)进行评估。Vespa 灵活的排序功能可以支持这种方法，但具体实现取决于如何将外部结果集成到检索管道中。

根据提供商条款和系统限制，团队可能会将允许的外部内容索引到共享的搜索集合中，或者从单独的系统中检索并应用后续的融合或重排步骤。没有一种通用的融合方法。每种选择在延迟、时效性、分数可比性和运营复杂度上都有所权衡。

### 4. 经受住智能体调用量的考验

这并不是一个假设的负载模式。在 Metal，AI 智能体处理了 [95% 的检索](https://blog.vespa.ai/agent-driven-intelligence-on-vespa-cloud/)，而不是人类。当有人询问投资组合公司的 EBITDA 时，智能体决定查询哪些实体类型（文档、公司、指标、活动），应用时效性和工作流过滤器，运行查询，然后继续进行，分页或提取相关实体，直到拥有足够的上下文来回答。[Clarm 从另一个方向看到了类似的情况](https://blog.vespa.ai/agentic-ai-powered-sales-for-developers-with-vespa/)：与其智能体并肩工作的开发人员每天发送数千个查询，会话时间甚至长达 22 小时。

> “它们需要专家搜索的精确度和控制力，同时具备消费者搜索的低延迟和高吞吐量。”

每一次这样的调用都位于智能体回答的关键路径上。检索和排序需要在这种负载下保持可预测，这就更倾向于[在数据原本驻留的地方运行推理](https://blog.vespa.ai/improving-llm-context-ranking-with-cross-encoders/)，而不是通过网络将大量候选集发送到单独的排序服务。你消除的每一个网络跃点，都是你在每次调用中夺回的延迟，并会在任务的每个步骤中被放大。Vespa 的 CEO Jon Bratseth [将此描述为](https://vespa.ai/vespa-voice/#relevance-is-your-moat)智能体的核心工程挑战：它们需要专家搜索的精确度和控制力，同时具备消费者搜索的低延迟和高吞吐量。

## 一个实际案例：支持智能体与更新日志

这是一个大多数支持团队都会熟悉的场景。客户将支付 SDK 从 4.1 升级到 4.2，他们的结账集成停止工作，于是他们提交了一个工单。

智能体做了你希望它做的事，首先搜索网络。它找到了四天前的 SDK 更新日志（其中废弃了集成所依赖的认证调用），以及另一个开发人员发布临时变通方案的论坛线程。然后它在内部进行搜索，返回了一篇 3 月份的知识库文章（该文章仍然告诉客户使用旧的调用）、显示客户正在使用 4.2 版本的客户账户记录，以及关于同一漏洞的受限工程工单。

如果作为长长的一串列表交个模型，这就是一个陷阱。知识库文章与客户的用词几乎完全吻合，因此它在相似度上的排名很高。论坛的变通方案读起来信心十足。工程工单包含客户绝不应该看到的注释。

当检索层在发挥作用时，两组证据都会通过相同的管道。在这个例子中，团队使用了一个共享集合：网络结果作为短期文档与内部数据一起被索引到 Vespa 中，通过一次查询检索，并由与相同业务规则对齐的 rank profiles 进行打分：

![图表展示了网络搜索 API 数据和内部数据如何通过相同的管道。](https://cdn.thenewstack.io/media/2026/11/1ed4d624-image-1024x843.png)

对于这个工单，这意味着：

1. 可见性过滤器在查询时排除了内部工单，因此它永远不会到达 prompt。
2. 版本过滤器只保留适用于客户账户上库版本的内容。
3. 排序提升了更新日志的权威性和近期性，降权了较旧的知识库文章，并保留论坛线程作为支持证据。
4. 模型收到 3 到 4 个排列有序的段落，而不是 20 个，每个段落都带有其来源。

在这个说明性的结果中，答案引用了更新日志，解释了变更，并指出了受支持的修复方法。搜索 API 有助于找到新鲜的证据，而检索设计决定了智能体接收哪些证据。

## 在将网络搜索接入智能体之前

* **在所有内容上存储日期和来源类型。** 无论是内部还是外部，每个文档都需要一个你可以根据其进行排序的发布日期和来源类型。
* **将信号直接写入文档本身。** 在每个文档上保留时效性、权威性和来源类型，而不是放在单独的特征存储中。这样，它们从第一阶段就开始塑造排序，而不仅仅是在对前几个结果进行重排时。
* **始终包含词法信号。** 即使你的 embeddings 很强，关键词匹配依然是捕捉智能体依赖的精确版本号、错误代码和产品名的关键。
* **在查询中进行过滤。** 在检索时应用权限，而不是在后处理中。
* **发送段落，而不是页面。** 对每个检索到的文档中的文本块（chunks）进行排序，并且只将最相关的文本跨度传递给模型，大小根据每次调用实际需要的内容来定。
* **独立评估检索效果。** 构建一个真实智能体问题的测试集，并追踪正确的证据是否落在了前几个结果中，这与模型如何组织答案的措辞是独立的。
* **在智能体调用量下进行负载测试。** 用典型任务实际发起的检索调用次数进行基准测试，而不是每次请求查询一次。

## 最后的思考

为智能体提供的托管网络搜索消除了一个真实且令人沮丧的失败模式，随着它离开 Beta 阶段，更多的团队将采用它。这使得下一个问题变得更加紧迫。当智能体可以同时看到公开网络和你的私有数据时，其工作质量取决于它在两者之间做出选择的能力。

Bratseth 对此做了更简单的总结：[相关性就是你的护城河](https://vespa.ai/vespa-voice/#relevance-is-your-moat)。随着模型变得越来越强大、应用越来越广泛，大多数公司最终都可以获得大致相同的智能水平。真正让它们脱颖而出的是它们自己的信息以及它们的系统如何利用这些信息。他将相关性分为四个部分：全面性、时效性、召回准确性和排序质量。实时网络搜索有助于前两部分。后两部分仍然需要你自己去构建。

模型不应该在每次调用时即兴做出这种选择。它应该属于一个你可以检查、测试和调整的检索层，在那里你可以将时效性、权威性、权限和相关性结合起来权衡。网络搜索帮助智能体寻找证据。排序则是它们决定相信什么的方式。

对于构建智能体的团队来说，实际的下一步是[评估检索质量](https://thenewstack.io/retrieval-ai-agent-architecture/)，将其与答案生成分离开来：测试正确的证据是否出现、权限是否在上下文组装之前强制执行，以及在文档冲突时是否优先考虑新鲜且权威的来源。

如果你想尝试这种模式，[Vespa](http://www.vespa.ai) 将词法、向量和结构化检索与多阶段排序结合在一个管道中，它既可以作为开源软件提供，也可以作为 Vespa Cloud 上的托管服务提供。[RAG Blueprint](https://github.com/vespa-engine/sample-apps/blob/master/rag-blueprint/README.md) 逐步演示了如何设计架构、检索策略和排序阶段，你可以通过启动[免费试用](https://vespa.ai/free-trial/)来亲自构建它。
