**DeepSeek于8月21日发布了V4 Flash Vision Exp**，这是其首款支持图像输入的模型。图像输入意味着模型可以像处理文本一样理解图表、截图或照片文档。

DeepSeek V4 Flash Vision Exp于8月27日进入OpenRouter等API网关。它为公司原有的经济型V4 Flash模型增加了图像理解功能，并保持了每百万输入Token 0.22美元、每百万输出Token 0.66美元的低廉价格。工作日高峰时段价格会翻倍。

8月13日发布的谷歌Gemini 3.7 Flash是显而易见的对比对象。它是目前开发者默认使用的经济型视觉主力模型，在OpenRouter上的定价为每百万Token输入0.75美元，输出3.75美元。

DeepSeek将该模型主打用于文档和图表理解，以及视觉问答。谷歌则称Gemini 3.7 Flash为[其迄今为止最智能的主力模型](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-3-7-flash/)。由于双方都声称性能卓越，我想探究哪一个更适合处理图像输入。

## 测试过程

我让这两个模型分别完成了三项模拟真实后台工作的图像测试：

* **图表读取** – 一个带有第二Y轴成本折线图的堆叠柱状图，由于比例不同，无法仅凭肉眼判断折线与柱状图的交点。
* **发票审计** – 一张包含三个预设错误（行总额计算错误、小计金额不符、到期日在开票日期之前）的供应商发票。
* **故障诊断** – 四十行生产日志，其中支付服务崩溃位于底部，但真正的原因（批处理任务耗尽数据库连接池）出现在五分钟前。

我通过OpenRouter向两个模型发送了相同的图像和提示词，并记录了每次调用的准确性、Token消耗、成本和速度。我在测试章节中包含了图像，并在文章末尾提供了提示词，供读者复现测试。

### 测试1：双轴图表

![](https://cdn.thenewstack.io/media/2026/08/354276a3-image.png)

提示词：  
*“仔细查看此图表并回答所有三个问题。请为你的回答编号。1. 运营成本在哪一个季度超过了总收入？2. 哪一个收入板块每个季度都在增长？3. 估算该公司全年的总收入（以百万美元为单位）。”*

我设置的陷阱是双轴。左侧收入刻度为0到12，右侧成本刻度为0到16，因此成本线在视觉上永远不会高于柱状图，即使在成本超过收入的季度也是如此。

两个模型都没有上当。它们都正确指出了第一季度，都认定“订阅（Subscriptions）”是四个季度都在增长的板块，并且都得出了3610万美元的年度总收入，这与我的原始数据完全吻合。DeepSeek的回答简洁，仅有三行。Gemini则展示了它对每一根柱子的读取结果。两者得分相同。

## 测试2：错误的发票

![](https://cdn.thenewstack.io/media/2026/08/354276a3-image-1-1024x749.png)

提示词：

*“你正在审核这张发票。回答所有三个问题。请为你的回答编号。1. 检查每一个项目：金额是否等于数量乘以单价？指出任何错误的行并给出正确金额。2. 正确的总应付金额应该是多少？展示你的计算过程。3. 除了算术错误外，这张发票还有其他问题吗？”*

两个模型都捕获了所有三个预设错误。它们都标记了显示器支架那一行，其中10个单位单价45.99美元被印成了505.89美元，而不是459.90美元。它们都重新计算并得出了3958.89美元的正确总应付金额。它们也都指出7月28日的到期日在8月12日的开票日期之前。DeepSeek更进一步，指出了打印的小计金额与打印的项目明细不符，甚至在修正错误之前就发现了这一点。

此测试产生了唯一的异常。DeepSeek花费了30.5秒并计费3467个完成Token，而答案仅有几段长。这表明有大量的内部推理被计入输出。Gemini在7.9秒内回答，消耗了944个完成Token。Token差异在输入端则完全相反。DeepSeek将每张图片计为约500个提示词Token，而Gemini计为约1150个。这清楚地表明两家公司对图像的处理方式截然不同。

### 测试3：隐蔽的根本原因

![](https://cdn.thenewstack.io/media/2026/08/b89c906c-image-1024x643.png)

提示词：

*“这些是宕机时的生产日志。回答所有三个问题。请为你的回答编号。1. 此次宕机的根本原因是什么？2. 问题实际开始的时间是几点？3. 你会采取的第一项恢复服务的操作是什么？”*

日志显示支付服务因超时错误崩溃。理解力较弱的模型会归咎于该服务。真正的原因出现在14:05:12，当时一个手动触发的分析任务对一个拥有4800万行的表发起了全表扫描，消耗了所有20个数据库连接。

两个模型完全忽略了诱饵。它们都将批处理任务认定为根本原因，都精准定位到14:05:12为开始时间，并都建议首先终止该批处理任务。Gemini甚至给出了执行该操作的具体PostgreSQL命令。

DeepSeek在11.9秒内回答，使用1636个Token，成本为0.00088美元；而Gemini在7.6秒内回答，使用1854个Token，成本为0.00351美元。

## 结果

两个模型都对所有问题给出了准确的答案。每一个预设陷阱都没能难倒它们。区分它们的是速度和成本/Token使用量。Gemini平均回答时间为7.2秒，而DeepSeek花费了16.8秒，是前者的两倍多。DeepSeek的总账单为0.0039美元，相比之下Gemini为0.0122美元，价格约为后者的三分之一。

|  |  |  |
| --- | --- | --- |
|  | **DeepSeek V4 Flash Vision Exp** | **Gemini 3.7 Flash** |
| **准确性** | 9/9 | 9/9 |
| **总Token** | 6904 | 6014 |
| **总成本** | $0.0039 | $0.0122 |
| **平均响应时间** | 16.8s | 7.2s |

这是我们第一次遇到这种情况。准确率完全持平，决胜点在于成本与速度的权衡。

## 我的看法

实际的区别在于成本和速度。DeepSeek以大约三分之一的价格完成了同样的工作。Gemini在不到一半的时间内完成了任务，且其速度保持一致，而DeepSeek的任务响应时间在8秒到30秒之间波动。DeepSeek的价格在工作日高峰时段还会翻倍，我是在周末进行测试的，所以我的成本差距对比对DeepSeek最有利。

对于像我这样的个人用户来说，小规模使用时，价格和速度的差异可以忽略不计。7秒还是17秒其实并不重要。除非你进行大规模操作，否则这些价格差距很难产生实质影响。如果你是在进行大规模任务并整夜批处理发票，DeepSeek能够胜任。如果你在运行一个海量任务且用户正在等待答案，请使用Gemini。
