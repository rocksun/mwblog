**智能体验证；人类做决定。** 如今运行AI代码审查的大多数团队却反其道而行之。他们让模型针对代码差异（diff）进行检查，询问它修改是否优秀，然后让开发人员大致浏览结果并点击批准。

模型会阅读每一行代码，永不疲倦，并在每个PR（Pull Request）上保持相同的标准。但它不具备的是你的代码库标准。它并不了解这些标准，无论你给出多么优秀的指令，它也无法始终遵循你所写下的规范。

> “判断需要意图，而问责需要人类。”

它从未见过当时做出的决定，没有先前决策的上下文，无法告诉你不要去构建某个功能，也无法承担责任。代码差异（diff）无法提供任何这些内容。判断需要意图，而问责需要人类。

那么，当验证交由智能体、判断留在人类手中时，[代码审查会是什么样子](https://docs.aviator.co/verify/concepts/why-intent-driven-verification)？在 Aviator，我们一直在将这种审查构建到 [Aviator Verify](https://www.aviator.co/verify?utm_source=tns&utm_medium=content&utm_campaign=q3-2026-tns-verify&utm_term=net-new&utm_content=awareness) 中。以下是它的七个部分，按顺序排列。

每一次更改都会[对照两个层级进行检查](https://docs.aviator.co/verify/concepts/verification-layers)。验收标准描述了此次更改应该做什么。[不变式（Invariants）](https://docs.aviator.co/verify/concepts/invariants)则是工程组织或团队的既定规则：无论如何更改，这些标准始终成立。

只有标准而没有不变式，就会让团队规范流于记忆。每个工程师都必须记住每条标准，否则就必须有人在代码审查中揪出智能体犯下的明显错误。只有不变式而没有标准，你得到的代码虽然符合规则，却没有考虑结果应该是什么，导致智能体偏离方向、过度设计或解决错误的问题。

这七个部分共同构建了这两个层级，对照它们验证更改，并将决策权交还给人类：

1. **不变式**（在任何更改之前定义）：团队的常设规则，源自自身的代码审查。
2. **意图与验收标准**（从编码会话中捕获）：更改存在的原因以及它应如何表现。
3. **核心决策**（从编码会话中捕获）：过程中做出的选择，以及是谁做出的。
4. **测试计划**（在提交时构建）：标准加上适用的不变式，转化为具体场景。
5. **证据**（在提交时收集）：每个判定背后来自运行环境的证明。
6. **审查**（由人类决定）：意图、决策和证据，予以批准或推回。而不是代码。
7. **刷新不变式**（合并后更新）：使不变式更加精细的豁免和反复出现的评论。

## 1. 不变式

每次审查都是对照某些内容来检查更改。在大多数团队中，这些内容存在于高级工程师的脑海中，并以审查评论的形式呈现。例如：任何涉及货币的内容都要使用 Money 类型；禁止直接写入 users 表；每个错误路径都要发出一个计数器。其中每一项都被输入过多次，而编码智能体却一直在重复相同的错误，因为这些规则从未写在智能体或验证器可以使用的任何地方。

不变式就是这样一条规则，被编写一次并在每个匹配的更改上进行检查。总的来说，你的不变式将成为一个[AI垃圾代码注册表（AI slop registry）](https://www.aviator.co/blog/how-an-anti-slop-registry-stops-ai-generated-code-from-violating-your-engineering-standards/)，也就是团队不断纠正的模式的运行列表。

诸如 CLAUDE.md 之类的智能体指令文件有所帮助，但它们只是生成过程的输入。编写代码的同一个非确定性智能体被要求遵循这些指令，却没有任何证据证明它确实做到了。不变式位于验证端，由确定性脚本或至少由一个不同的智能体进行检查，该智能体为每条规则返回一个判定结果。

你的 PR 历史记录已经包含了其中大部分内容。Verify 会读取团队在 GitHub 中发布的评论，并从中提取的模式草拟不变式。它还会从 CONTRIBUTING.md 和智能体指令文件中草拟它们，或者当有人在 PR 评论或 Slack 线程中标记 `@aviator invariant` 时即时草拟。通过 [Aviator Verify 免费账户](https://www.aviator.co/code-review?utm_source=tns&utm_medium=content&utm_campaign=q3-2026-tns-verify&utm_term=net-new&utm_content=awareness)生成团队的不变式，即使你决定不再继续使用 Verify，也可以保留它们。

三件事决定了一个不变式是有帮助还是会变成噪音：

* **所有权。** 每份草案都会发送给所属团队，并附带提出该草案的原因，只有在该团队批准后才会上线。未经人类同意，任何 AI 草拟的内容都不会成为常设检查。
* **措辞。** 断言结果并让实现保持开放，以便规则在重命名和文件移动后依然适用。
* **范围。** 规则只能在其可能被打破的地方运行。前端不变式没有理由去检查数据库迁移。

## 2. 意图与验收标准

向审查者传达意图的直观方法是提前编写规范（spec）或将其记录为详细的 JIRA 任务。规范需要时间，在工作让人学到任何东西之前编写，并且在实现开始的那一刻就会偏离。

最准确的意图已经存在于编码会话中。每当智能体停下来提问而工程师做出决定时，验收标准就会实时定义。会话结束时没有理由把所有这些统统抛弃！

意图说明了为什么要进行更改。验收标准说明了它应该如何表现。

Verify 从工程师已经进行的会话中捕获这两者。在智能体打开 PR 之前，智能体技能和钩子（hook）会运行 *verify submit*。智能体会从它在会话中看到的所有内容中提取意图和标准，工程师在提交任何内容之前对其进行审查和纠正。

## 3. 核心决策

决策是更改可能走向另一个方向的任何节点。状态存储在哪里、依赖项失败时会发生什么、是复用现有辅助函数还是编写一个新函数。AI 编写的 PR 充满了这样的调用，但几乎没有一个显示在代码差异（diff）中。

> “AI 编写的 PR 充满了这样的调用，但几乎没有一个显示在代码差异（diff）中。”

Verify 将决策与意图记录在一起，并对人类和智能体分别进行标记，以便审查者知道是谁做出了哪个调用，并可以对其提出异议。我在[如何不读代码来审查 AI 代码](https://thenewstack.io/review-decisions-not-code/)一文中写了更多关于为什么决策才是人们应该审查的内容。

## 4. 测试计划

提交更改时，Verify 会读取意图和标准，并使用代码差异来识别要应用的不变式。这两个层级合并为一个场景列表：智能体为验证行为而采取的步骤，这些步骤源自需求而不是代码。  
  
这就是这两个层级带来回报的地方。工程师专注于更改，而注册表则负责标准。

## 5. 证据

当同一个模型编写并审查代码时，它们拥有相同的盲点。验证在结构上必须与生成相分离，并且它产生的结果必须超越单纯的意见。

> “当同一个模型编写并审查代码时，它们拥有相同的盲点。”

Verify 会启动一个预览环境，并分派验证器智能体来运行场景。它们捕获截图、数据库状态、服务器日志和控制台日志，并且针对标准或不变式的每个判定都指向该证据。对于 UI 更改，验证器实际上会点击浏览界面并确认结果。

你不需要在第一天就拥有预览。代码扫描可以直接从差异中处理结构化检查，无需基础设施，并且许多不变式被转换为确定性脚本。一旦你的代码开始询问差异无法显示的行为什么行为时，预览就会体现出它的价值。

## 6. 审查

这是人类重新介入的地方，工作看起来有所不同。作为审查者，你是在查看证据，而不是逐行阅读代码。你阅读意图，查看核心更改所在的重点区域，浏览每个标准和不变式的决策和判定，如果你想亲自查看更改，还可以打开实时预览。

## 7. 刷新不变式

大多数审查在合并时结束，它们学到的一切也随之消失。下一个 PR 会犯同样的错误，同样的评论会再次出现。

不变式保留了每次审查所学到的知识。当不变式在 PR 上失败时，作者可以有理由地豁免它：也许它不适用，也许不变式不正确，或者可能需要单独修复。拥有该不变式的团队会看到每一次豁免。
