**对于在 Kubernetes 上运行 AI 工作负载**的团队来说，完全分配的 GPU 池和不断增长的批处理任务队列可能会让扩展 GPU 池成为显而易见的下一步。但不断增长的队列可能指向时机、服务能力或模型和硬件的选择。在扩展 GPU 池之前，团队应该明确成功的定义、必须完成的时间以及交付成本。

> “一个被分配的 GPU、一个忙碌的 GPU 以及一个产生有价值结果的工作负载并不是同一回事。”

这首先需要做一个区分：一个被分配的 GPU、一个忙碌的 GPU 以及一个产生有价值结果的工作负载并不是同一回事。了解它们之间的关系可以帮助团队在真正需要配置额外容量之前，更有效地利用现有容量。

## 从结果和截止时间开始

审视工作负载及其支持的底层用例。客服聊天室可能需要全天候的推理能力，而模型评估任务的结果可能只需要在下一次内部发布同步之前得出。将工作负载粗略分类为“推理”和“训练”并不能决定其紧迫性。一些批量推理可以等待，而训练任务可能有严格的截止时间。

对于每个工作负载，记录其截止时间、预期运行时间、资源需求以及是否可中断。同时定义什么是宝贵的输出。推理服务应具备特定任务的质量阈值和延迟目标。仅凭已完成的请求或有效的 JSON 响应并不能说明工作负载是否达到了目标。

将启动时间的灵活性与对中断的容忍度分开。一个可以等待启动的任务可能仍然需要不间断地运行。

## 在扩容 GPU 池之前利用调度灵活性

假设有四个兼容的 GPU 可用于从中午到下午 5 点的批处理工作。四个独立的评估任务在中午准备就绪。每个任务需要两个 GPU 运行一小时，并且所有结果必须在下午 5 点前交付。

立即启动所有四个任务需要八个 GPU。但是，如果在中午运行两个，下午 1 点运行另外两个，就可以在下午 2 点之前完成所有四个任务，且仅使用现有的四个 GPU。假设运行时间和支持资源保持不变，两个调度方案都消耗了八个 GPU 小时（不包括启动开销）。

> “错峰可以减少峰值需求。任务仍然按时完成，无需扩容 GPU 池。”

错峰可以减少峰值需求。任务仍然按时完成，无需扩容 GPU 池。在配置更多 GPU 来清理队列之前，请考虑启动时间有多大灵活性。

诸如 [Kueue](https://kueue.sigs.k8s.io/docs/overview/)之类的工具提供了一个准入控制点，使用配置的配额和策略来决定何时准入工作。团队仍然需要决定如何表示和强制执行截止时间和工作负载需求。灵活的排队可以支持容量规划，并减少提前启动任务却在稍后被抢占的需求。

## 衡量部署能够维持多少有用工作

灵活的调度可以缓解容量限制。但推理团队还必须检查模型和服务的配置与该工作的匹配程度。

高 GPU 活动并不能确定有多少额外的吞吐量可用。[Nvidia 的性能分析文档](https://docs.nvidia.com/datacenter/dcgm/latest/learn/modules/profiling.html)解释说，流式多处理器活动可能包括等待内存的 warp。运行中的请求、等待中的请求和缓存占用率等服务指标增加了上下文，而抢占次数有助于解释行为。在 vLLM 中，[KV 缓存使用率衡量占用缓存块的比例](https://docs.vLLM.ai/en/latest/usage/metrics/)，但它并不能直接衡量总服务容量。

> “高 GPU 活动并不能确定有多少额外的吞吐量可用。”

通过具有代表性的负载测试来衡量可持续容量。保持模型、硬件、服务设置和请求组合恒定。然后，增加到达率并观察吞吐量、质量和延迟。在满足工作负载要求（包括错误限制和选定的延迟百分位数）的前提下，最高的可持续速率提供了一个有用的容量估计。对于交互式生成，请包括首 Token 时间和后续 Token 交付时间，而不仅仅是平均完成时间。[DistServe](https://arxiv.org/abs/2401.09670) 展示了为什么应该对照延迟等应用级目标来评估服务容量。

将生产流量与测试容量进行比较。低缓存占用率可能需要进一步调查，但声称吞吐量提高十倍需要进行吞吐量测试。短暂的队列可能代表临时的突发，而持久的队列可能需要诊断。它们本身都无法识别出受限资源。

## 将 OpenCost 数据与经过验证的结果连接起来

FinOps 社区围绕[成本和有用的结果](https://www.finops.org/insights/token-economics-the-atomic-unit-of-ai-value/)来构建 AI 效率。对于 [AI 工作负载](https://thenewstack.io/agentic-ai-kubernetes-management/)而言，当成本与基础设施帮助交付的结果联系起来时，它就变得更有用了。Kubernetes 团队可以通过结合工作负载成本、服务行为和应用程序结果，使这种关系变得具体。

使用 [OpenCost 的分配 API](https://opencost.io/docs/integrations/api/) 获取定义时间间隔内的工作负载成本，然后使用工作负载身份和时间戳将该数据与服务遥测和结果记录结合起来。OpenCost 还提供可选的[推理成本跟踪](https://github.com/opencost/opencost/blob/v1.121.3/docs/inference-cost-tracking.md)，包括每百万个 Token 的成本。在计算每个结果的成本时，请包括适用的 GPU、CPU、内存和其他基础设施成本，并记录如何分配共享和空闲成本。单独添加 OpenCost 之外的相关成本，避免重复计算。

一个有用的指标是[每个验证结果的成本](https://thenewstack.io/greenops-and-finops-a-dual-strategy-for-sustainable-ai/)：总归属成本除以满足定义的质量要求并在所需时间内交付的结果数量。考虑对重试、失败、启动和空闲时间产生影响的总成本。计算最终业务结果一次。当正确性是从抽样审查中估计的时，记录抽样方法和不确定性。

OpenCost 提供成本分配细节；应用程序提供结果定义和评估证据。容量仍然需要单独测量。[OpenCost 提案 3915](https://github.com/opencost/opencost/pull/3915) 探讨了将服务引擎遥测引入成本模型。该提案仍然是一个草案，而不是一个发布的饱和度或正确性评分。

## 测试备用容量是否与其成本相符

考虑一个说明性服务，它每小时接收 1,000 个任务，正确性要求为 98%。达到 90% 的小模型是不合适的，即使它的 GPU 很便宜且完全被占用。

一个更强的模型可能会以每小时 2 美元的价格产生 990 个正确且及时的结果，同时只使用其测试服务容量的一小部分。每 1,000 个合格结果的成本约为 2.02 美元，这种备用容量可能是满足质量要求和吸收突发活动的可以接受的价格。

下一个测试是更小的 GPU、更少的副本或不同的批处理设置是否可以保持这些结果和所需的可靠性。如果经过测试的配置以 1.50 美元产生相同的 990 个合格结果，则成本降至每 1000 个合格结果约 1.52 美元。节省来自使用更少的资源来交付相同的成果。在不改善结果的情况下提高原始 GPU 上的利用率不会提供可比的价值。

> “目标是构建一个能够以合理的成本交付所需结果的部署，并留有足够的余量来满足其要求。”

当两个模型都满足最低要求时，如果能提供更少的后果性错误或需要更少的人工审查，额外的质量改进可能会证明更高的成本是合理的。将该价值与实际需求进行比较。当被比较的结果具有相似的价值和错误后果时，每个正确结果的成本最有用。

一次更改一个主要变量，然后在具有代表性的需求下比较成本、验证结果、延迟和截止时间达成情况。为突发和故障保留容量，并确认低活动对应于可用容量。专为一个 Pod 分配的 GPU 在释放之前不能重新分配给另一个 Pod。

然后，团队可以选择证据支持的更改：延迟灵活的任务、改进批处理、调整部署大小、选择不同的模型或[配置额外的 GPU](https://thenewstack.io/kubernetes-gpu-management-just-got-a-major-upgrade/)。目标是构建一个能够以合理的成本交付所需结果的部署，并留有足够的余量来满足其要求。
