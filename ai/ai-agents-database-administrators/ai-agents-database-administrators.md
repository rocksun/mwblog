随着AI Agent数量在未来几年激增，数据库管理员的角色将从手动维护转向监督自主系统。YugabyteDB AMP等技术通过多租户架构与服务器less模式，帮助数据库团队应对管理15万个Agent的规模化挑战。

> 译自：[What managing 150,000 AI agents could look like for database teams](https://thenewstack.io/ai-agents-database-administrators/)
> 
> 作者：Carly Page

**未来的数据库管理员**将花费 considerably 更少的时间来管理数据库。

听起来这很矛盾，但 AI 正在接管这部分工作。几十年来，DBA 一直在处理那些亲力亲为的工作，以保持数据库可用、高性能、安全且经济。他们配置容量、排查慢查询、管理迁移，并在某些事情不可避免地出问题时介入。

AI 已经在承担其中的一部分工作。与此同时，它正在创造一个规模大得多的数据基础设施舰队需要管理。

其结果很可能是一种截然不同的 DBA：他们花在照料单个数据库上的时间更少，而花在监督为其完成这项工作的自主系统上的时间更多。

## **恭喜，你现在开始管理机器人了**

这种转变始于一个熟悉的问题：需要管理的基础设施比可用于管理的人手还要多。

数据库自动化并不是什么新鲜事，但 Agent 的潜力可以超越 DBA 已经依赖的脚本和规则。Agent 不是自动化某个预先确定的任务，而是可以检查正在发生的事情、决定需要关注什么、使用工具采取行动，并检查其干预是否奏效。

这改变了 DBA 与数据库的关系。过去需要某人深入查阅指标、识别问题查询并决定如何响应的性能问题，现在越来越多地可以在人类介入之前由 Agent 进行调查。

这并没有将 DBA 从等式中移除。仍然需要有人决定 Agent 可以做什么、在哪里需要人类批准，以及当它出错时会发生什么。但工作上升了一个层面。DBA 不再亲自执行每个运营任务，而是开始管理执行这些任务的系统。

> DBA 不再亲自执行每个运营任务，而是开始管理执行这些任务的系统。

在任何人对这个想法感到过于舒适之前，这些系统的数量可能会变得庞大无比。

## **15万个 Agent 走进数据库……**

Gartner 预测，到 2028 年，全球财富 500 强企业的平均企业将使用超过 15 万个 AI Agent，而 2025 年这一数字还不到 15 个。目前只有 13% 的组织认为他们拥有合适的治理机制来管理这些 Agent。

并非每个 Agent 都需要自己的数据库，但会有很多。它们将创建状态、检索数据、记住先前的交互，并与其他许多 Agent 交换信息。许多 Agent 的行为也将与 DBA 习惯支持的应用程序截然不同：快速启动、长时间闲置，以及在有工作要做时突然变得繁忙。

没有人会雇佣 15 万名 DBA 来管理它们。

---

**这就是 [Yugabyte](https://www.yugabyte.com/) 借助 [YugabyteDB AMP](https://www.yugabyte.com/amp/)（即 Agentic Multitenant PostgreSQL，智能体多租户 PostgreSQL）所瞄准的规模问题。** AMP 没有将每个新的 Agent 工作负载视为管理员需要配置和照看的另一个数据库，而是将数据库作为舰队进行管理。

该平台将数百个小型 Postgres 工作负载打包到共享的分布式基础设施上，同时保持其数据库隔离。生命周期操作（包括配置、分支、扩展、迁移和销毁）可以通过 MCP 暴露给 Agent。Yugabyte 还构建了专门用于设置、迁移、性能调优和集成的专业 Agent。

在这种模式下，DBA 不再是在配置第 14,372 个数据库。有趣的工作是制定规则，规定如何在没有他们的情况下配置、运行和微调第 14,372 个数据库。

## **少花钱多办事（真的可以）**

规模只是问题的一半。总得有人为所有这些东西买单。

Agent 工作负载使传统的容量规划变得特别尴尬，因为许多工作负载具有突发性且经常处于闲置状态。为每个实验性的 Agent 提供永久配置的基础设施，可能会让公司为许多大部分时间几乎什么都不做的数据库买单。

这就是为什么整合既是一个经济问题，也是一个运营问题。

AMP 的方法是无服务器多租户和缩减至零（scale-to-zero）。多个小型工作负载共享底层分布式基础设施，而客户按 CPU 分钟付费，闲置的 Agent 不消耗计算资源。资源治理可以对单个工作负载施加 CPU 限制，防止某个过于急切的 Agent 消耗本意留给其邻居的容量。

人类层面的对等物也很重要。如果日常设置、迁移、调优和其他数据库操作可以越来越多地被委派，那么较小的数据库团队就有可能管理大得多的资产规模。

这并不意味着公司可以解雇 DBA 并把钥匙交个机器人。这意味着稀缺的数据库专业知识可以花在架构、治理和真正困难的问题上，而不是重复做软件可以处理的工作。

## **你 2028 年的数据库问题从现在开始**

更棘手的问题是，当没有人真正知道两年后企业 AI 资产会是什么样子时，应该在所有这一切之下构建什么。

今天作为一个实验开始的 Agent 可能下个月就会消失。另一个可能会突然变成在整个业务中使用的生产应用程序。为廉价实验构建一个基础设施栈，为严肃的工作负载构建另一个基础设施栈，这就带来了每当实验成功时就会出现迁移问题的风险。

Yugabyte 打赌，这段旅程的两端都应该建立在同一基础之上。

YugabyteDB AMP 允许工作负载从无服务器 Postgres 开始，随着其规模和关键性的增加，无缝过渡到完全分布式的 YugabyteDB，而无需重写应用程序或将数据迁移到不同的数据库平台。

然后是单个数据库之上的问题：Agent 需要记住发生了什么，而且不仅仅是在一个孤岛中。

这就是 [**Meko**](https://mekodata.ai/) 契合 Yugabyte 技术栈的地方。Meko 是一个专为多 Agent AI 系统设计的 Agent 原生上下文引擎。它在多个 Agent 之间提供持久内存、共享知识、决策追踪和可审计性，而不是让每个 Agent 在其自己的隔离上下文中工作。Agent 可以获取另一个 Agent 学到的信息，而不必再次检索或重新启动推理过程。

综合来看，它为 Agent 的整个生命周期提供了一个单一的数据栈：Meko 用于 Agent 之间共享的上下文，YugabyteDB AMP 用于智能体化管理 Postgres 数据库集群，而分布式 Postgres 兼容的 YugabyteDB 则用于超出其无服务器起步阶段的工作负载。

当然，无法保证 2028 年会完全像今天的预测那样。这恰恰是重点所在。最安全的架构选择可能是那种不需要你提前知道今天哪个微小的 AI 实验会成为明天关键应用程序的选择。

在这个世界中，DBA 仍然至关重要，但工作将会看起来有所不同。未来的 DBA 可能会直接管理较少的数据库，同时对更多的数据库负起责任。相反，去管理那些负责行政管理的自主系统。
