文章指出，MCP的安全问题本质上并非基础设施缺陷，而是权限治理失效。由于AI代理常继承人类的不当授权且缺乏独立身份，导致权限过度扩散。作者强调应将代理身份、权限范围与生命周期视为统一配置，通过动态凭证和严格的隔离边界，从底层重构权限模型以应对AI安全风险。

> 译自：[Why MCP security is about permissions overhaul](https://thenewstack.io/mcp-security-permissions-overhaul/)
> 
> 作者：Mohit Bansal, Topher Chung

Anthropic 的模型上下文协议 (MCP) 于 2024 年末投入生产，随后迅速普及。

此后，成千上万个 MCP 服务器被创建。Microsoft、Google 和 OpenAI 都采用了该协议，Linux 基金会也接手了协议的维护工作。如今，MCP 被视为关键基础设施，位于 AI 代理与其交互的工具和数据之间。大多数团队采用与其他集成标准相同的方式来实施它，即简单地安装并信任默认设置。

2026 年形成的一个共识是，问题并不在于基础设施本身，而在于该基础设施之下的权限设置。

这一点至关重要，因为它改变了人们处理 MCP 安全问题的方式。补丁只能解决特定服务器上的特定问题，而权限变更则需要提出一个复杂的问题。

> “2026 年形成的一个共识是，问题并不在于基础设施本身，而在于该基础设施之下的权限设置。”

为什么那台特定的服务器需要访问它本不需要访问的东西？根据调查了 500 多位安全专家的《SANS 2026 身份威胁调查》，76% 的企业注意到非人类身份有所增加，74% 的企业使用的 AI 系统依赖长期凭证来独立工作。同一项调查显示，没有超过 40% 的企业使用了审批流程、沙箱或日志记录等保护措施。

跳出单一的披露案例看，根本原因始终一致。2025 年 5 月，攻击者利用提示注入攻击 [GitHub MCP server](https://invariantlabs.ai/blog/mcp-github-vulnerability) 以获取私有仓库数据，这不是因为服务器在传统意义上存在漏洞，而是因为其背后的个人访问令牌（PAT）权限范围远超任务所需。几天后，[Asana MCP integration](https://www.bleepingcomputer.com/news/security/asana-warns-mcp-ai-feature-exposed-customer-data-to-other-orgs/) 中的逻辑缺陷导致了跨租户访问，原因在于权限层从未在客户之间强制执行隔离边界。

安全研究人员现在将其归纳为几种可识别的模式：工具中毒（tool poisoning），即服务器自带的工具描述中携带隐藏指令；以及困惑的代理问题（confused deputy problem），即代理继承了比当前任务所需更多的信任。

## 权限重设计实际要求你检查的内容

目前提出的解决方案不是更强大的扫描器，而是对访问权限进行划分。GitHub 的 [Engineering Blog](https://github.blog/ai-and-ml/generative-ai/how-to-build-secure-and-scalable-remote-mcp-servers/) 在讨论开发安全远程 MCP 服务器时建议：每个实例必须针对特定任务拥有自己的密钥，所有请求必须限制在执行用户范围内，授权必须基于操作而非用户认证后的预设。应使用动态生成的临时凭证替换固定的永久令牌。

> “使用动态生成的临时凭证替换固定的永久令牌。”

该方案是分级的，目前行之有效。在 [Webflow](https://webflow.com/)，我们将 MCP 集成与访问客户数据的其他第三方组件同等对待。

![MCP 服务器凭证范围审查周期。](https://cdn.thenewstack.io/media/2026/09/22933462-image1-1024x582.png)

团队给予 AI 代理的每个凭证在配置时可能都是合理的。关键难点不在于当时授权是否明智，而在于现在是否依然合理，而大多数团队并不习惯进行这种回顾。

在集成任何 MCP 时，需考虑以下几点：

**该凭证现在能访问什么，而不是它原定范围是什么？** 访问范围很可能会发生“蠕变”。在出事之前，通常不会有定期的审查。

**授权是基于站点、仓库、工作区，还是全有或全无的？** 警惕任何只提供组织级访问权限的集成。如果在连接时无法控制范围，那就是一个严重的问题，而非脚注。

**AI 代理是继承了人的现有凭证，还是创建了绕过这些权限的全新凭证？** 后者就是 GitHub 个人访问令牌可能比授权用户拥有更多仓库访问权限的原因。

**日志记录是否像对待人类一样明确代理的操作责任？** 如果代理的行为不可见或无法归因，事件响应将从零开始。

**代理的更改是直接进入生产环境，还是通过草稿、分支和审批队列等可审查流程？** 这只是将团队针对人类访问控制的安全准则应用到一类新的实体上。

## 身份先于访问

在谈论代理被允许做什么之前，必须回答一个更难的问题：从身份角度来看，什么是代理？目前大多数行业的诚实回答是“穿着风衣的人类 OAuth 令牌”。代理没有[自己的身份](https://thenewstack.io/can-dns-become-the-basis-for-ai-agent-identity/)，它继承了启动它的人的范围、影响半径，往往还有真实的凭证。

当代理不再是瞬时的时候，这就成了问题。如今大多数代理存活时间从几分钟到几小时不等：任务开始，代理运行，然后销毁。但这正在改变。我们正朝着运行数周或数月的代理迈进，存在这么久的实体需要自己的身份，而不是借用的身份，且随着寿命增长，权限应变得更严而非更宽。

> “目前大多数行业的诚实回答是‘穿着风衣的人类 OAuth 令牌’。”

将其想象成下午请来的承包商与嵌入系统中一个季度的临时员工的区别。你不会给下午的承包商发永久胸卡，同样也不该给长期运行的代理与五分钟脚本相同的权限。

OAuth 并非为此而生，这不仅是一个缺失的功能，更是一种结构性错位，从根本上讲是 UX 的失败：一种为人类设计的同意模型，被应用到了没有人类参与的流程中。

其整个模型假设人类坐在范围对话框前做出知情选择，但我们都知道结果如何：没人会读范围列表，只会点击“允许”。当没有人类阅读任何内容时，这种本就脆弱的假设会彻底崩溃。

基础规范没有“该客户端是代理”或“该授权预计运行六个月”的概念，只有事后设置的服务器到期时间。一些 IETF 草案正试图修复此问题：将令牌寿命绑定到任务的实际生命周期，并为[具有稳定身份的代理](https://thenewstack.io/agent-workload-identity-authentication/)打上标签，使其区别于调用它们的人类。不过，这些仍处于早期阶段，尚未成为部署的标准。

对于“短寿命任务、宽泛访问”与“长寿命代理、严格锁定”之间的界限，我们还没有清晰的答案。Webflow 的安全团队正在积极解决这一问题，我们正在与业内同行交流，而不是假装已经解决了它。但这种框架本身很重要：将代理的生命周期视为权限模型的一等输入，而不是事后考虑的问题。

## 权限不是配置时的勾选框

权限重设计、协议更新和身份模型代表了同一问题的三个不同层面。要使每一层有效，其他两层也必须有效。

如果你在第一天创建了范围正确的凭证，但之后没有人验证该凭证是否依然有效，那么你的努力就浪费了。同样，如果你开发了一个终于能将代理与人类区分开来的新协议，但所有集成默认继续提供“全有或全无”的访问权限，那也几乎没有意义。这两种方法都没有解决二者共同的根本问题：代理被允许做什么，应取决于它将存在多久。

> “能做好这一点的团队，将是那些停止将范围、身份和生命周期视为三个独立评估，并开始将其视为单一设置的团队。”

目前，技术栈中几乎所有组件都不知道如何提出这个问题，更不用说回答它了。能做好这一点的团队，不会是那些开发了[更高效扫描](https://thenewstack.io/why-docker-scout-is-changing-how-developers-scan-for-vulnerabilities/)工具的团队。相反，他们将是那些停止将范围、身份和生命周期视为每个代理实例仅发生一次的三个独立评估，并开始将其视为必须在代理功能或存在状态改变时重新评估的单一设置的团队。
