本文探讨了工程团队如何通过将不同职责分配给专职智能体，并在共享工作空间中与人类工程师协同，从而减少深夜不必要的告警并提高事件处理效率。文章强调精细化职责划分、权限控制以及保留完整的调查历史对于优化工作流的重要性。

> 译自：[A shared workspace for people and agents](https://thenewstack.io/specialized-ai-agent-workflows/)
> 
> 作者：Rak Siva

**我们是一个由五名工程师组成的团队，过去常常因为生产环境的故障**，一周内把值班工程师叫醒三四次。大多数只是虚惊一场，并非严重的宕机，但在凌晨两点，过度谨慎总好过漏掉真正的问题。

自那以后，我们通过迭代分诊流程并将调查进行到底以修复问题，减少了不必要的夜间打扰和重复出现的问题。[专化的AI智能体](https://thenewstack.io/durable-ai-agent-operations/)帮助我们调查事件、组织后续工作并准备变更，而工程师则在整个过程中进行审查和纠正。

令我们惊讶的是，我们对这种流程的依赖变得越来越自然。工程师可以检查评估结果、对其假设提出质疑，并利用这些纠正措施来改进我们处理后续事件的方式。随着后续修复解决了重复出现的问题，对于何时该叫醒值班工程师，我们感到更有底气了。

这段经历让我们开始审视我们分配给智能体的工作形态。一个[有能力的编程智能体](https://thenewstack.io/ai-coding-tools-in-2025-welcome-to-the-agentic-cli-era/)完全可以调查事件、提出工单并准备修复方案，那么为什么要人为割裂这些职责呢？

> “当智能体的工作需要纠正时，你能识别出所涉及的职责并做出能够独立评估的更改吗？”

对我们而言，关键在于改进工作流的一个部分，并判断这一改变是否起到了帮助。当智能体的工作需要纠正时，你能识别出所涉及的职责并做出能够独立评估的更改吗？

## 人与智能体的共享工作空间

我们正在构建 [Sugabots](https://sugabots.ai)，这是一个开源的、自托管的工作空间，团队可以在其中与多个智能体共同处理同一任务。工程师可以提问、提供证据、审查发现并引入另一个智能体，所有这些交流对其他参与者都是可见的。

我们将这些工作组织到被称为 pod 的共享环境中，并通过 [MCP 连接到外部系统](https://thenewstack.io/model-context-protocol-a-primer-for-the-developers/)。每个智能体都可以拥有自己的模型和指令，而 pod 的连接和工具策略则定义了其智能体共享的访问权限。团队可以为特定职责配置智能体，并随着工程师对工作的审查来精细调整它们的指令。我们的事件工作流帮助我们探索了哪些职责可以从中受益。

## 我们如何在 Sugabots 中运行事件分诊

我们的事件工作流依赖于每位工程师或智能体，能够基于调查过程中记录的证据、决策和纠正措施继续推进。

我们的 Sentry 分诊智能体负责调查新的、回归的或升级中的问题，并决定是[向值班工程师发出警报](https://thenewstack.io/ai-sre-agent-autonomy-phases/)、请求工作时间内的审查、将小修复直接交给实现智能体，还是将问题留在 Sentry 中进行监控。它会在 Linear 中记录后续工作，积压工作（backlog）智能体会在此协助组织工单，而实现智能体则可以准备一个 GitHub 拉取请求供人工审查。

![Sugabots中事件分诊的工作流图](https://cdn.thenewstack.io/media/2026/11/a2056af1-image1.png)

*我们的事件工作流：智能体处理不同的职责，而工程师则参与到共享的调查中。工程师可以承担图中所示的任何贡献。*

工程师自始至终参与其中，审查发现、性质紧急程度评估、纠正假设，并决定是否发布建议的变更。随着工作在人与智能体之间流转，调查过程始终保持可用。

这种日益增长的信心背后有安全保障作支撑。指令要求，当某个问题可能是一次生产宕机且紧急程度不确定时，必须进行紧急升级。被归类为噪音的问题将被归档，直到升级时再触发，而 Sentry 保留了一条直接通往 incident.io 的尖峰警报（spike-alert）路由作为备份。

后续工作与初始评估同等重要。过去，值班工程师可能会调查一个警报，确定它能等到上班时间再处理，然后便返回处理其他工作。将底层问题记录在积压工单中并对其进行优先级排序，让团队有机会在下一个值班工程师遇到相同警报之前将其解决。

让积压管理智能体在 Linear 中记录后续工作，为团队提供了一种一致的方法，来优先修复干扰背后的重复问题。

## 围绕决策进行专业化分工

我们为每个智能体配置特定的职责，根据工作内容选择其模型和指令，并定义什么才算是有用的结果。

我们为 Sentry 分诊选择了 Opus 5.5，其指令涵盖了证据收集、分类、升级、交接以及从工具故障中恢复。这个精简的摘录展示了我们要求它做出的决策：

检查完整的 Sentry 问题，包括客户影响、受影响用户、发布版本和事件趋势，然后检查现有的工单或事件。

选择一个结果：

* **紧急：** 造成活跃客户损害，需要立即关注；通过 incident.io 提醒值班工程师。
* **工作时间审查：** 需要工程判断但可以等待的缺陷；以低紧急度通知值班工程师。
* **自动修复：** 处于身份验证、计费和数据库迁移等受限区域之外的小型、非紧急代码变更；简要通知实现智能体准备一个 PR。
* **不采取行动：** 预期的或暂时的噪音；进行归档直到升级时将其重新唤醒。

说明决策背后的证据和不确定性。实现简报必须独立成文，并包含相关的发现和链接。

积压管理器的指令反映了组织后续工作所涉及的决策：检查重复项、查找当前的 Linear 周期，以及将可执行的工作与需要工程师澄清范围或做出设计决策的问题区分开来。这些规则提供了默认值，同时保留了团队对优先级、分配和调度的明确选择，我们可以独立于评估事件紧急程度的标准来精细调整它们。

分诊和实现形成了有益的对比。分诊询问现有证据是否足以打扰工程师；实现询问什么样的变更能解决问题以及如何进行验证。这些决策具有不同的失败模式：漏掉紧急事件、不必要的打扰，或者引入另一个 Bug 的看似合理的修复。

> “分诊询问现有证据是否足以打扰工程师；实现询问什么样的变更能解决问题以及如何进行验证。这些决策具有不同的失败模式。”

我们发现保持这些职责独立是非常有用的，因为我们可以精细调整事件的分类方式，同时保持实现指令的稳定。如果一次调查导致了无效的修复，我们可以检查评估的准确性、工单中保留的证据，以及实现方式是如何解决所记录的问题的。每一个都为我们提供了工作流中可供改进的具体部分。

每项职责还为我们提供了用于评估的具体问题：

* **分诊：** 它是否升级了真正紧急的事件？它是否对工程师造成了不必要的打扰？
* **积压管理：** 它是否记录了后续工作、识别出现有工单，并保留了足够的证据据此采取行动？
* **实现：** 提出的变更是否解决了问题，工程师在接受它之前需要纠正什么？

我们需要将唤醒呼叫的减少与我们处理真正紧急事件（包括分诊漏掉的事件）的方式结合起来进行评估。更少的打扰既能反映更好的分类，也能反映减少到达事件数量的修复。这些结果有助于我们判断工作流的表现以及改进的方向。

同样的问题也适用于你工作流中现有的智能体：当它们的输出改进时，你能解释是什么得到了改进以及什么证据支持这一判断吗？分离职责为你提供了一个更狭窄的决策检查点，以及评估变更的更清晰基础。

## 将权限与职责相匹配

职责的分离还帮助我们决定每个智能体需要哪些工具操作，以及工程师应该在什么时候批准它们。

我们的分诊指令包含特定的写入操作：创建 Linear 问题、通过 incident.io 发送警报，以及归档 Sentry 问题直到升级。工具访问权限需要反映这些职责，包括哪些操作需要工程师的批准。

特定于智能体的指令在 pod 可用的访问权限范围内定义了职责；它们不强制对共享该 pod 的智能体进行单独的权限隔离。

在 Sugabots 中，团队在 pod 的连接上配置工具级别的关闭（Off）、询问（Ask）和允许（Allow）策略，该 pod 中的每个智能体都会继承这些策略。将它们配置一次，就能为团队提供一套关于自动操作、工程师批准和禁用工具（包括另一个智能体加入工作时）的一致规则。

分诊需要访问证据和升级的途径，而实现则需要足够的访问权限来准备变更。真正不同的访问边界需要单独的执行机制，可能通过具有不同工具策略或适当作用域连接的不同 pod 来实现。合并和部署权限也需要明确的策略以及（在可能的情况下）适当作用域的凭证。

## 将工作上下文与调查过程分离

这里有三个具有不同有效生命周期的东西：

* **配置：** 针对某项职责维护的模型、指令、工具和期望。
* **执行上下文：** 模型在处理特定任务时可用的消息和工具结果。
* **共享历史：** 人类和智能体积累的证据、假设、纠正和决策记录。

考虑这样一次调查：智能体排除了宕机可能，并得出结论认为问题可以等到上班时间再处理。在经过多次工具调用后，其上下文可能需要被压缩。摘要可能会保留结论，同时省略排除宕机的证据。

当工程师对评估结果提出质疑时，这些细节就变得至关重要。保留原始历史记录为他们提供了一种检查摘要背后的推理和证据的方法。智能体可以在压缩的上下文下工作，而更完整的记录则保持可用以供检查或检索。

为了继续调查，下一个智能体需要从该记录中选择相关的证据和纠正措施，并在简报中传递或在工作时检索。保留对话为我们提供了一个可提取的源泉；选择工作上下文仍然是交接中明确的一部分。

## 让人类参与调查

当工作在工程师之间流转时，同样的区分也很重要。工程师可能会认出智能体漏掉的模式，或者解释为什么一个看似合理的修复会在代码库的其他地方引入回归。这种贡献需要对继续调查或准备修复的工程师或智能体保持可用。

在独立的聊天中，人类需要负责将这些纠正措施传递过去。即使两个智能体都可以检查相同的代码库和工单，每个对话也包含了对团队已学到知识的不同描述。

![显示审阅者和作者在各自独立聊天之间转达发现的图表。](https://cdn.thenewstack.io/media/2026/11/b70aaf1b-image3.png)

*审阅者和作者在各自的独立聊天之间转达发现和纠正措施。*

在 Sugabots 中，工程师可以参与到共享讨论中，将他们的纠正留在引出这些纠正的发现旁边。下一位工程师可以看到调查是如何改变方向的，继续工作的智能体也可以在其简报中收到该纠正。

![显示工程师和智能体参与共享讨论的图表。](https://cdn.thenewstack.io/media/2026/11/b9bafbeb-image2.png)

*工程师和智能体共同参与共享讨论，从而保留他们的发现和纠正。*

**MCP 为智能体提供了访问证据的途径，而共享工作空间则为团队提供了访问调查过程的途径。**

*在 Sugabots 实际界面中呈现的分阶段 Sentry 分诊对话。消息、事件计数、工单引用和交接是脚本化的演示数据，展示了工程师的纠正如何能够与评估和实现简报并存。*

## 什么时候才值得引入另一个专家？

每个额外的专家都带来了需要维护的配置，以及其上下文需要精心照料的交接。当这种边界有助于团队维护和评估工作时，按语言、服务或部署环境拆分智能体是很有用的。

我们当前的划分遵循了原本就存在的职责：值班工程师评估紧急程度，团队在积压工单中组织后续工作，工程师准备并审查修复方案。为这些职责赋予智能体不同的配置，使我们能够独立改进工作流的每个部分。

对于尝试这种做法的团队，我建议从一个可以描述有用结果并能识别出糟糕结果的经常性职责开始。写下成功标准，包括重要的错误：对于分诊来说，这意味着检查漏掉的紧急事件以及不必要的升级。定义智能体所需的证据，选择执行所需工具访问权限的配置，并指定工程师应该在什么时候审查其发现或批准操作。

保留调查历史，包括决策背后的证据以及工程师所做的纠正，以便下一位工程师或智能体能够据此继续。审查这些纠正，以决定是否需要更改指令、可用证据、权限或交接方式。然后，早期的调查可以与新工作一起提供可复盘的案例，检查某个更改是否解决了最初的错误而没有引入新的错误。

> “越来越引起我兴趣的是，我们是否能够清晰地定义一项工程职责，以至于每一次调查、纠正和审查过的修复，都能帮助我们改进处理下一次事件的方式。”

这可能需要一个专门的智能体，或者当任务出现时加载一个可复用的配置就足够了。关键在于这种分离是否能使工作更易于维护和评估。

我们最初是在想是否应该让智能体专业化。越来越引起我兴趣的是，我们是否能够清晰地定义一项工程职责，以至于每一次调查、纠正和审查过的修复，都能帮助我们改进处理下一次事件的方式。
