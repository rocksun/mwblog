[Stripe](https://stripe.com/) 是全球数百万企业使用的支付和金融基础设施平台。为了支持产品的大规模持续交付与迭代，他们构建了人工智能工具，帮助全公司的员工提高生产力。Stripe 的 AI 平台团队负责维护为公司所有 AI 应用提供支持的底层架构。他们最受瞩目的产品是 *Stripe 知识 AI 平台*（Stripe’s Knowledge AI Platform），即 Kai，这是一个基于 LangChain/LangGraph 架构和 [Deep Agents](https://www.langchain.com/deep-agents) 智能体框架构建的企业级生产力智能体。

## 构建内部智能体框架

随着代理式 AI 的普及，Stripe 的各个工程团队开始在现有的 Ruby 和 Java 技术栈上构建编排层。将这些系统与 Stripe 的内部基础设施集成相对简单，但构建一个可靠的、生产级的智能体框架带来了额外的挑战。

有效的智能体系统不仅需要连接性，还需要强大的性能、稳健的评估机制以及稳定处理复杂任务的能力。各团队发现，最初的实现方案虽然适用于简单场景，但要在大规模应用中提供可靠的结果，仍需进一步投入。

随着 2024 年末 Claude Code 的发布，Stripe 的每位员工都突然想要构建智能体。但对于非工程人员来说，终端、数据访问和安全组件是巨大的障碍。智能体基础团队的工程经理 Sharadh Krishnamurthy 和高级软件工程师 Anupam Upadhyay 采取了相反的思路：与其推动非技术员工去学习开发工具，不如在他们现有的工作流中提供专门构建的工具。换句话说，*“如果每个人都有一个始终在线、可随时投入生产的助手会怎样？”* 这个问题的答案就是 Stripe 的知识 AI 平台。

## 为每位 Stripe 员工配备具备上下文感知能力的 AI 同事

Stripe 的知识 AI 平台对每位员工开放。它专为大多数 Stripe 员工的日常工作而设计——即合成数据、头脑风暴、起草文档、分析趋势和跨职能协作——所有这些都在一个连接到 Stripe 内部数据仓库、Slack 和 Google Suite 的会话式界面中完成。

用户开启一个会话，通过聊天进行交互，Kai 随之生成伴随对话存在的产出物（Artifacts）、报告、仪表板或文档。随着对话的进行，这些产出物也会不断演变。对于非技术员工而言，它就像是一个编码智能体。

与通用的 AI 助手不同，Kai 通过工具和技能预加载了 Stripe 的上下文信息。它了解 Stripe 的工作方式，并理解公司的内部系统、数据源和规范。用户在执行每项任务前，无需向 Kai 解释自己的职位或公司背景。公司各领域的专家通过技能库贡献他们的领域知识，目前已有超过 100 组团队贡献了 1000 多项技能。

## Deep Agents 为 Stripe 提供了基础，让团队专注于领域特定工作流

Kai 的基础是 LangChain 的开源智能体框架 Deep Agents。Deep Agents 提供了连接工具调用循环、中间件组合、流式处理和状态管理的基础，若从零开始构建并加固这些功能，通常需要数月时间。

Stripe 的分层架构包括：

1. **以 Deep Agents 为底座**：基础层处理所有 LLM 交互原语，包括请求管理、智能体执行和中间件组合。
2. **基于 Deep Agents 构建的 Stripe 专属框架**：中间层将 Kai 集成到 Stripe 的安全态势、基础设施和内部服务中，从而创建一个具有特定偏好的环境。
3. **配置层**：在框架之上，团队可以配置自己的自定义 Kai 智能体，即拥有不同技能集、行为和角色的专用智能体实例，而无需触及底层的框架。
4. **Kai UI**：大多数 Stripe 员工与之交互的产品界面，向下连接至上述三层架构。

*“Deep Agents 层解决了所有非 Stripe 的问题，这样我们就可以专注于解决 Stripe 专属的智能体问题，”* Sharadh 解释道。*“你可以直接使用现成的中间件。可组合的技能模式和复合后端提供了正确的结构，同时保留了足够的灵活性。”*

### 是什么让 Kai 具备了生产级能力

Anupam 在一周内构建了 Kai 的初始版本。实现这一速度的 Deep Agents 中间件包括：

1. **文件系统中间件**：Kai 是在云端运行的生产服务，而非本地进程。Stripe 构建了一个由 S3 支持的虚拟文件系统，以便智能体可以在多轮对话中读取、写入和引用文件作为上下文。文件系统非常适合 LLM 上下文，因为它们将上下文转换成了模型可以随时检查、更新和组织的内容。Stripe 为每个沙箱 `execute` 调用封装了一个“同步进入/同步输出”模式：执行前，所有相关文件被载入沙箱；执行后，任何新建或修改的文件会被同步回虚拟文件系统。因此，智能体及其驱动的 LLM 在整个会话生命周期内都能体验到一致、持久的文件环境。
2. **沙箱中间件**：Kai 通过沙箱环境执行代码，主要用于两类工作：*分析*（编写并运行 Python 来查询数据、生成图表）和*处理任意文件格式*（PDF、演示文稿、结构化文档）。沙箱作为工具暴露给智能体，而不是作为智能体自身的执行环境。智能体在沙箱外运行并调用沙箱，保持了执行边界的清晰，从而防止了 [一类与 LLM 生成代码相关的安全问题](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)。
3. **总结中间件**：对于管理长周期、多轮会话中的上下文至关重要，否则累积的上下文会降低性能或触及模型限制。Kai 在处理长轮次会话方面表现尤为出色。为了在平衡成本的同时最大限度地利用可用的 LLM 上下文，Kai 利用了 `deepagents` 库提供的各种调节旋钮，如总结阈值、总结器模型和输出大小等。大多数用户断续使用 Kai 会话，因此避免大上下文导致的缓存未命中有助于控制成本。

### 技能：Kai 如何导航数百种内部工具与技能

Kai 通过“技能”在数百种内部工具和工作流中运作。Deep Agents 中的技能是结构化的、可由智能体执行的模块。每个技能都封装了如何完成特定任务、需要加载哪些工具以及如何处理某类工作。

Stripe 采用了一种联邦方法，即由各个团队拥有并维护他们自己的技能。基础的 Kai 智能体附带了一套涵盖广泛 Stripe 导航的基础技能，并根据用户资料和当前使用的特定 Kai 智能体配置加载额外的分层技能。例如，销售运营人员获取的技能集与财务人员不同；用户级的资料层允许个人在其职能默认设置之上添加更多技能。

面对 500 多种内部 MCP 工具和不断增长的技能库，Kai 无法将所有内容都加载到上下文中。[Agent Skills](http://agentskills.io) 的 `allowedTools` 列表驱动了动态工具加载，创建了一个双重检查系统，通过技能选择来锁定工具上下文，而不是预先加载所有工具。选择依赖于已经拥有相关上下文的 LLM。*“LLM 花费精力找出需要加载哪些技能，因此我们随后也依赖它来加载相关的工具，”* Anupam 解释道。某些基础技能被固定，无论模型决定加载或卸载什么，它们始终保持可用，从而确保了 Stripe 上下文和策略行为始终一致。

由于 frontmatter 有 1024 个字符的限制，团队发现当技能数量超过 150 个并结合系统提示词时，前沿模型的质量会下降。技能数量仍然是一个挑战，团队正在积极寻找更好的未来解决方案。

1 名工程师，1 周：Stripe 的 Python 押注如何获得即时回报

Stripe 花了十多年时间围绕 Ruby 和 Java 构建内部工具、安全层和部署支持。采用 Python 原生技术栈意味着要围绕一种新语言重建 Stripe 的内部服务框架，这是一笔巨大的投资。

Kai 通过演示证明了 ROI（投资回报率）。一名工程师在一周内就构建了 Kai。Deep Agents 提供的原语意味着困难的智能体基础设施已经解决。这种速度证明了为 Python 构建内部 Stripe 支持所花费的时间得到了即时回报。*“Kai 彻底巩固了人们对 Deep Agents 是正确发展方向的信念，”* AI 平台负责人 Chrissie 强调。

## 一周内达成 Kai 的季度采用目标

当 Kai 进入公开预览版时，它在一周内就达成了团队的季度采用目标，并在大约 4 周内从 296 名用户增长到 5,000 多名，增幅超过 16 倍。*“它瞬间火了。人们使用它，然后就自然而然地爱上了它，”* Sharadh 说。

大多数新用户属于团队设计的目标群体：销售、财务分析师、业务运营人员——这些员工之前被告知要“使用 AI”，却从未找到适合他们实际工作方式的工具。*“很多人说，‘我发现以前的东西很难上手。我得调整一大堆旋钮。虽然有人要求我使用 AI，我也确实试过。’然后现在他们说：‘这太棒了，我根本不需要做那些复杂的操作，’”* Sharadh 解释道。

如今，83% 的 Stripe 员工每周都在使用 Kai，每周产生超过 6 万次会话。市场部（95%）和 GTM 团队（87%）等业务职能部门的采用率甚至超过了工程部门；他们认为 Kai 在交易准备、从多个内部来源提取数据、合成数据并生成可用产出物方面具有变革性。财务团队也发现它在数据分析和仪表板生成方面同样实用。

一些最生动的早期反馈包括：

* *“Kai 对销售人员来说绝对不可思议。能节省数万小时的时间。”*
* *“我的 Stripe 职业生涯分为 Kai 之前和 Kai 之后。”*

新员工开始使用 Kai 来加速入职流程。工程团队尽管是为非工程人员构建了 Kai，却发现自己将其用作工作的副驾驶：使用 Kai 回答关于自身系统的问题，并针对自己的跟踪记录和使用数据运行它，以识别技能差距并改进覆盖范围。

接下来是什么：产品市场匹配之后

在快速采用之后，团队现在面临一个“幸福的烦恼”……有成千上万的用例需要修复和构建。

**扩展技能选择。** Stripe 已经超过了 500 多种内部 MCP 工具和 1000 多种技能。没有 LLM 可以在没有辅助的情况下在如此规模的技能目录中进行可靠的选择。团队目前正在构建一个混合选择系统。纯 LLM 选择在当前规模下运行良好，并且在完整上下文可用时产生的效果优于 RAG，但在大规模场景下，需要在 LLM 做出最终决定前引入 RAG 或分类器层进行预过滤。

**治理与护栏。** 随着采用范围扩大到数千名员工，团队正在投入安全和合规护栏，以确保 Kai 的触及范围不会超过企业环境所需的监督结构。

**行为层面的个性化。** 不同的团队需要不同的智能体行为。有些人希望 Kai 在行动前总是先进行规划并提出澄清问题；而另一些人则希望在进行快速头脑风暴时得到快速、直接的回答。*“这个产品的全部承诺就是你不需要调整旋钮，”* Sharadh 重申。*“因此，我们承担起构建智能来为人们自动识别这些需求的责任。”* 团队正在评估 ML 分类器和 AI 驱动的机制，以自动根据用户上下文调整行为。

**跨会话协作。** 目前的模型是单用户会话。路线图扩展到了共享技能、共享产出物，最终将实现协作会话，多名员工可以在此共同迭代相同的 AI 输出。
