在AI编程代理编写一行代码之前，它就已经消耗了大量Token。例如，在处理源文件、工单描述、构建日志、质量检测结果和依赖警报时。你支付的费用大部分并非源于最终的Pull Request，而是源于代理在达到目标之前所阅读的一切内容。

团队往往将成本控制的重点放在模型选择、提示词长度和请求限制上。这些杠杆固然有效，但还有一个不太显眼的地方存在于代理和开发者工具之间的接口中：即返回给模型的数据格式。

> “Token成本不仅取决于编程代理读取了什么，还取决于开发工具如何封装这些信息。”

当工具返回一长串形状相似的记录时，发送冗余的JSON会让代理为字段名、引号和结构化语法重复付费。内容是有用的，但大部分的展现形式并非如此。对于 [代理化开发工作流](https://thenewstack.io/what-agentic-workflows-mean-to-microservices-developers/) 而言，输出格式是一个工程决策，而非外观问题。

这并不意味着所有的集成都应该放弃JSON。JSON仍然是一种广泛支持的交换格式，对于嵌套或不规则数据来说，它可能是更紧凑的选择。实际的问题更具体：当模型需要处理大量均匀集合时，工具能否以一种专为该数据结构设计的表现形式返回相同的信息？

## 为什么结构化方式会影响Token账单

以问题列表为例。每条记录可能包含标识符、规则、严重程度、文件、行号、消息、状态和预估修复工作量。在传统的JSON中，这些标签会出现在每一条记录中：

```

{
  "key": "AZ1002fQ9x",
  "severity": "BLOCKER",
  "component": "src/main/java/com/acme/UserRepo.java",
  "line": 29,
  "status": "OPEN"
}

```

对于许多系统来说，这既可读又有用。但一个正在检查25、100或500个检测结果的代理，不需要数百次被告知“严重程度”或“组件”的含义。重复这些标签会占用原本可以存放更相关证据、指令或源代码的上下文。

Token-Oriented Object Notation (TOON) 是解决此问题的一种方法。它为均匀数组保留一个类似模式（schema）的标题，然后将每条记录作为一行发送。字段名只出现一次，而值保持不变。对于其目标数据形状而言，这是一种无损的JSON数据模型编码。

> “规律的结构为模型提供了一套明确的预期字段，这可以使审查和验证过程更具可预测性。”

结果不仅仅是文本变小了。规律的结构为模型提供了一套明确的预期字段，这可以使审查和验证过程更具可预测性。代理接收到了相同的发现结果，但周围少了重复的脚手架信息。

## 衡量实际工作流，而非合成的承诺

有效的分析单位是团队实际的工具输出和实际的模型。字符数是一个有用的初步信号，但 [不同模型的Token化方式不同](https://thenewstack.io/agent-harness-token-costs/)。与其假设一个通用的百分比，不如捕获一个具有代表性的响应，通过工作流相关的分词器或格式化工具进行处理，并与当前的默认值进行比较。

例如，Sonar CLI可以将问题列表以JSON或TOON格式返回：

```

# 默认JSON输出
sonar list issues -p my-org_my-app --severities BLOCKER,CRITICAL --format json > issues.json

# 用TOON CLI评估相同的数据
npx @toon-format/cli issues.json --stats

# 直接向代理返回紧凑、无损的输出
sonar list issues -p my-org_my-app --severities BLOCKER,CRITICAL --format toon

```

第一个命令保留了基准。第二个报告了实际负载的节省情况。第三个仅在消费者是代理时才应用替代方案。

我在生成一个25个问题的代表性比较时亲眼见证了这一点：TOON比格式化后的JSON减少了49%的字符，比压缩后的JSON减少了33%。[TOON项目发布的基础测试数据](https://github.com/toon-format/toon) 也显示，对于均匀的表格数据集，它的Token使用量更低，同时在测试集中的检索准确率相当。这些结果应被视为方向性证据，不能替代团队在使用所选模型对生产负载进行的实际测量。

## 使用适合阅读者的格式

一条持久的规则是根据消费者和数据的形状来选择格式：

* 当人员需要在终端扫描简短结果时，使用表格。
* 当脚本、API客户端或深度嵌套的负载受益于其熟悉的结构时，使用标准JSON。
* 当LLM正在阅读许多具有相同字段的记录时，考虑使用像TOON这样紧凑、模式优先的表示法。

最后一种情况很重要，因为编程代理越来越多地在循环中调用工具。代理可能会列出检测结果、检查受影响的文件、进行更改、运行分析，并列出剩余的问题。当相同的工作流跨越存储库和迭代运行时，单次响应中微小的减少会产生叠加效应。

> “导致决策变弱的低价上下文并非真正的成本优化。”

尽管如此，紧凑性并不是唯一的要求。格式必须保留代理做出正确决策所需的字段。它必须被工具链接受。并且它应该针对重要的任务进行验证：识别最高优先级的问题、定位受影响的代码，并确定修复是否已完成。导致决策变弱的低价上下文并非真正的成本优化。

## 将工具响应视为代理设计的一部分

更广泛的教训是，代理成本在一定程度上是一个上下文设计问题。团队可以通过几种互补的方式 [减少不必要的上下文](https://thenewstack.io/how-to-reduce-mcp-token-bloat/)：仅检索相关文件、以适当的详细程度返回工具结果，并避免重复传输结构性开销。这些改变都不需要降低代码或安全问题的质量标准。

从代理工作流中调用频率最高的结构化请求开始。测量基准。更改一种格式设置。然后将Token消耗、响应质量和任务完成情况结合起来评估。

这种方法是有意为之的稳健。它避免了平台重写，并使权衡变得可见。随着AI辅助开发日益成为工程工作的常规部分，关于代理“看到”什么以及“如何看到”它们的审慎选择，将与它们所使用的模型同样重要。
