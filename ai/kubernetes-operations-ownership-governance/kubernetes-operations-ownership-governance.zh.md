**部署 [Kubernetes](https://kubernetes.io/) 的第一天通常让 IT 部门感到是一个里程碑：** 集群已配置，网络已路由，初始的应用程序容器正在运行。但第二天却暴露出一个更严峻的现实：集群可能很健康，但应用程序却不健康。那么，一旦 Kubernetes 正式上线，谁来为接下来发生的事情负责？

在接受 *The New Stack* 采访时，[Hewlett Packard Enterprise (HPE)](https://www.hpe.com) 旗下 [HPE Morpheus Software](https://www.hpe.com/us/en/products/software/morpheus-software.html) 的首席产品经理 [Karthik Subramanian](https://www.linkedin.com/in/karthik-subramanian-lnkd/) 介绍了团队如何划分 Kubernetes 上线后的运营责任，包括访问权限、配置漂移和集群升级。

## **划分平台团队与应用团队的责任**

上线后治理的核心是构建平台的团队与消费平台的团队之间有清晰的划分。Subramanian 表示，责任通常在紧密合作的两个群体之间进行分解：

* **平台团队：** 云架构师、Kubernetes 平台管理员、安全团队和监控专家。他们监督整体 Kubernetes 环境、配置集群、分配命名空间、管理版本控制策略、管理存储和容器网络接口 (CNI) 插件、强制执行安全策略以及管理基础设施漂移。
* **应用团队：** 由核心应用程序开发人员、QA 人员和生产部署工程师组成，他们充当租户消费者。他们在指定的命名空间内部署工作负载、管理应用程序代码发布，并在不管理底层控制平面的情况下使用集群功能。

Subramanian 表示，这些都是职能责任，即使一个人处理多项任务。随着团队的成长，为每个职能指派一个负责人可以明确交接和访问决策。

## **云级别和集群级别的标准**

Subramanian 描述了平台团队可以设定标准的两个级别：跨云环境共享的策略以及为单个 Kubernetes 集群定义的设置。

**云级别定义**：团队可以建立访问和基于角色的访问控制 (RBAC) 策略、网络和准入要求、备份和恢复目标、诸如 [Terraform](https://www.hashicorp.com/en/solutions/accelerate-innovation) 等基础设施即代码标准，以及环境的服务级别指标。

**集群级别标准化**：单个集群强制执行针对特定环境限制量身定制的本地化设置，例如 Kubernetes 版本支持节奏（例如，维持对两到三个活跃次要版本的支持）；命名规范、资源标签和多租户命名空间模型；以及针对 Pod 到 Pod 通信的集群特定网络策略。

## **使用 HPE Morpheus Software 自动化治理与升级**

[HPE Morpheus Software—企业版](https://www.hpe.com/us/en/products/software/morpheus-software.html)为平台团队提供了一种连接云资源、Kubernetes provisioning、蓝图、工作流和基于角色的访问控制的方法。团队可以配置目录访问、配额、预算和审批策略，包括与 IT 服务管理系统的集成。平台团队仍然决定哪些请求需要审批以及谁可以进行更改。

对于通过 HPE Morpheus Software 管理的 Kubernetes 集群，可以通过指定用于 provisioning 集群的软件和依赖项的集群布局来交付支持的版本。Subramanian 表示，客户可以通过 HPE Morpheus Software 界面或 API 查看可用的升级，具体取决于其环境的 Kubernetes 服务、版本和支持矩阵。

### **规划滚动升级以限制中断**

Subramanian 描述了一个旨在限制应用程序中断的分阶段升级过程。他确定的步骤包括：

* **预验证检查：** 在启动更新之前，平台团队会检查受支持的 Kubernetes 环境暴露的节点健康状况和兼容性警告，然后在应用更改之前修复问题。
* **按顺序进行控制平面和工作节点更新：** Subramanian 表示，受支持的 Kubernetes 环境可以分阶段更新这些组件，而不是一次性更新所有节点。平台团队监控集群健康状况，而应用团队在整个过程中验证工作负载可用性和关键应用程序路径。
* **金丝雀和蓝绿部署方法：** 对于生产更改，团队可以运行现有集群以及使用较新 Kubernetes 版本的集群，然后使用其应用程序交付和负载平衡工具将一小部分流量发送到新集群。Subramanian 给出了 1% 到 5% 的例子，只有在应用程序满足其商定的检查后才会增加流量。

当节点恢复到就绪（Ready）状态时，升级并未完成。只有当应用程序的关键路径工作正常、服务目标保持在容差范围内，并且团队知道是什么会触发暂停或回滚时，它才算完成。

## **逐项任务责任矩阵**

为了消除整个运维生命周期事件中的歧义，团队应将特定任务映射到应负责的拥有者和所需的审批关卡：

| **生命周期领域** | **具体任务** | **负责团队** | **交接或审批关卡** |
| --- | --- | --- | --- |
| 架构与规模调整 | 集群拓扑、自动缩放边界 | 云架构师/平台管理员 | 根据工作负载需求和配额进行审批 |
| 集群与命名空间 provisioning | 命名空间创建、版本策略定义 | Kubernetes 平台管理员 | 平台团队定义目录访问权限以及任何所需的审批 |
| 工作负载 provisioning 与管理 | 应用程序部署、配置、缩放和生命周期管理 | DevOps 团队 | 平台团队提供经批准的命名空间、策略和集群服务 |
| 安全与密钥 | 用户 RBAC、密钥和证书轮换、双向 TLS (mTLS)、可选的 Istio | 安全与治理团队 | 安全团队定义轮换程序并审查策略更改 |
| 升级与漂移 | 预验证、滚动更新、漂移检查 | 平台运维团队 | 平台团队安排更改并审查升级前警告 |
| 监控与恢复 | 容量跟踪、集群健康状况、状态备份 | 监控 / SRE 团队 | 监控团队跟踪警报；恢复负责人对照恢复目标测试恢复 |

## **测试韧性并衡量运维成功与否**

Subramanian 表示，团队应在发生事故之前在实验室环境中测试其所有权模型。这些测试可以包括：

* **升级失败测试：** 在实验室中，测试失败的升级场景，确定其原因，并在更改生产集群之前确认团队的恢复程序。
* **硬件和工作节点故障：** 模拟节点中断，以确认节点更换期间 Pod 的重新调度和应用程序的连续性。
* **RBAC 边界验证：** 验证租户隔离，以确保未经授权的用户无法访问隔离的命名空间。
* **备份和恢复验证：** 测试状态备份恢复，以确认数据完整性和恢复时间目标 (RTO)。

为了确定上线后的运维是否成功，Subramanian 建议跟踪具体的运维指标，例如：

* **升级成功率：** 在没有人工干预或回滚的情况下完成的集群升级百分比，且对运行中的工作负载的影响最小。
* **MTTI 和 MTTR：** 识别运维事件的平均时间 (MTTI) 和解决运维事件的平均时间 (MTTR)。
* **备份和恢复率：** 成功创建并验证恢复就绪性的计划备份百分比。
* **审计审查：** 检查记录是否确定了是谁或什么执行了重大操作、更改了什么以及是否发生了所需的审批。

清晰的负责人、经过测试的恢复程序以及经过仔细配置的自动化，为团队在上线后运营 Kubernetes 提供了更好的基础。实际的测试是他们能否识别谁批准了一项更改、谁在它失败时做出响应，以及什么证据表明应用程序仍在工作。
