AWS推出了Kiro bots，旨在赋予AI智能体持久记忆和独立工作能力，帮助开发者摆脱繁琐的会话管理，将重心从监督智能体转移到决定构建内容上。

> 译自：[Why AWS wants developers to stop babysitting their AI agents](https://thenewstack.io/kiro-bots-agent-memory/)
> 
> 作者：Adrian Bridgwater

**AWS首次推出了 Kiro**，这是其基于智能体的[规范驱动开发](https://thenewstack.io/spec-driven-development-the-key-to-scalable-ai-agents/)环境，发布于2025年7月。今年[8月](https://thenewstack.io/spec-driven-development-the-key-to-scalable-ai-agents/)，它还推出了 [Kiro Crew](https://kiro.dev/crew/)，这是一个能够记住上下文的持久化开源开发工作区。现在，为了帮助开发者同时处理更多并行执行的复杂任务，[AWS于周四推出了Kiro bots](https://kiro.dev/blog/crew-bots/)，为该工具集增加了持久的智能体内存和委派的工作流管理。Kiro Crew 已经能够在会话之间传递内存，而 bots 则为每个智能体赋予了专属的内存。

Kiro bots 被描述为一个“具名、长运行的智能体，由你定义并针对工作的特定部分进行定制”（例如阅读工单队列中的新问题），它们保留自己的内存，并且在创建时仅拥有分配给它们的工具。

bot 功能还运行自己的会话（AWS 指的是 bot 启动和监控的并行工作线程会话），因此软件工程师不必逐个追踪它们或将它们交织在一起。

根据 AWS 的说法，[Kiro](https://kiro.dev/) bots 的到来预示着从委派任务向委派流程的转变。

## 保姆式照顾 vs. bots 构建更好的产品

AWS Agentic AI 工程总监 [Kathy Kam](https://www.linkedin.com/in/kathykam/) 告诉 *The New Stack*，只有当开发者能够信任智能体自主行动时，它们才是有用的，但当会话结束时，就没有人再对这些工作负责了。

Kam 说：“开发者最终成了中间人，把上下文从一个会话传递到下一个会话。Kiro bots 接手了这项工作，因此开发者现在可以花一整天时间决定什么值得构建，而不是去照顾会话。”

> “开发者现在可以花一整天时间决定什么值得构建，而不是去照顾会话。”

到目前为止，如果没有这种保姆式的照顾，用更持久的记忆小心翼翼地引导智能体从一个点走到下一个点，那么负面后果就会很快显现出来。

Kam 解释说：“你会遇到许多开发者现在所说的[上下文腐烂](https://thenewstack.io/context-rot-enterprise-ai-llms/)，这会让人感觉像是在唠叨智能体重做你昨天告诉它的事情。当并行任务各自持有自己漂移的现实版本时，这种情况就会迅速蔓延。因此，我们为每个 Kiro bot 赋予了其专属的[持久内存](https://thenewstack.io/how-to-add-persistence-and-long-term-memory-to-ai-agents/)，配有一个它可读写的 notes [[.md] 文件](https://daringfireball.net/projects/markdown/)，并且开发者可以直接对其进行编辑。修复一次错误——它就会保持修复状态，而不会在所有进行中的任务中再次出现。”

每个 Kiro bot 仅使用其工作所需的工具和权限。

例如，研究 bot 可以搜索网络和读取文件，但不能更改它们。部署 bot 可以运行部署脚本并在每次更改前请求批准。bot 可以向开发者索取更多工具，但在软件工程师真正批准该请求之前，什么都不会改变。由于每个 bot 都有自己的内存，部署 bot 对发布流程的了解不会与研究 bot 的了解混淆。正如开发者在最初所判断的那样，各自独立的经验教训使每个 bot 都与其自身的职责保持一致。

## 信任来自过往记录

如果这让人感觉 bots 和智能体正在发展出更多自己的个性，并被拟人化成某种层级结构，其中一些扮演着比其他智能体更高阶的角色，那么 AWS 的 Kam 表示，这种想法是错误的。

Kam 强调：“纯粹基于 IQ 的智能体层级是一个错误的衡量标准。重要的是智能体被允许接触什么，而 Kiro bot 是通过建立过往记录来赢得信任的。”

> “纯粹基于 IQ 的智能体层级是一个错误的衡量标准。重要的是智能体被允许接触什么，而 Kiro bot 是通过建立过往记录来赢得信任的。”

虽然目前还没有拟人化，但每个 Kiro bot 都有一个名字、一个头像、它自己的内存以及一个持续的聊天频道，开发者可以在这里设定其方向并回来查看结果。

在该聊天背后，bot 会并行启动并监控会话。它可以重定向偏离计划的会话，并在会话结束时合并结果。如果某个任务需要人类做出决策，bot 可以在继续处理不需要答案的部分时向工程师咨询。开发者可以在聊天中设置常规任务，这样 bot 就可以在编码团队开始一天的工作之前，在夜间调查构建失败的原因。

## 是的，AWS，但是如果……？

这里似乎仍然浮现出许多“是的，但是如果……”的问题。当被指示等待人类开发人员决策，但 bot 和更广泛的智能体框架已经拥有足够的机构或历史知识来表明不需要人类介入时，会发生什么？这难道不意味着应该用自动化来覆盖人类程序员以减少浪费时间吗？

AWS 的 Kam 澄清说：“随着越来越多的公司转向[软件工厂](https://thenewstack.io/warp-software-factory-infrastructure/)，智能体最终可能会在整个团队中记住比单个开发者更多的信息和上下文，但这并不意味着智能体在掌权。人类仍然是负责任的人，而智能体则负责执行工作。软件 engineer 为每个 Kiro bot 设置了其工作所需的访问权限级别，因此部署 bot 可以在每次更改之前要求批准，而研究 bot 则可以减少检查点。”

Kam 进一步指出，Kiro bot 可以“要求获得更多权限，但它绝不能在未经管理的情况下获取权限”。然而，正如已经强调的那样，在等待答案的同时，它会继续推进所有不需要人类介入的事情。

## 每个 Kiro bot 都了解其专业领域、结果、权衡、限制和决策

在其官方发布博客中，AWS 表示，使用 Kiro bots 的开发者会发现，给予 bot 的方向保持可见且可修改。它是通过持续的对话和反馈来设定的，Kiro Crew 的学习在每个 bot 内部构建。这使得开发者可以移交一项持续的责任，而不是单个任务。对于其专业领域，每个 bot 都了解其应瞄准的结果、权衡背后的原因、围绕更改的限制以及已经做出的决策。

一个 Kiro bot 可以拥有问题接入权，而另一个拥有发布就绪权，并且每个 bot 都遵循为该工作设定的规则。AWS 指出，综合来看，每个开发人员的“bot 团队”都支持程序员独特的开发方法和工作要求，而不会被扁平化为一个通用的工作流。

Kam 强调：“Bots 不能将工作委派给其他 bots——这是出于设计考虑，以防止上下文腐烂并确保 Kiro bots 能够保持独立。”“Kiro bot 将大型工作拆分到其自己的并行工作流中，并将结果汇总为一个建议。开发者仍然是定义各自边界并将 Kiro bots 相互连接的人，因此任何你想要提供输入的决策都不会在没有你参与的情况下在它们之间流转。”

AWS 还解释说，随着时间的推移，开发者的 bot 团队将“反映你实际的开发方式”，因为每个 bot 都携带了其所需那部分工作的要求和边界。软件工程师仍然决定这些流程如何变化以及判断力归属何处。

为了开始使用，AWS 鼓励开发者打开 Kiro Crew 侧边栏中的 bots 工作区，添加一个 bot，并选择默认或自定义智能体作为其基础。自定义智能体提供提示词、模型、工具和技能，因此用户可以在他们已经使用的设置上进行构建，而无需更改现有的聊天。总之，鉴于周围盘旋的自主性，我们或许可以认为，AWS 并不是要求开发者放开方向盘，而或许是让他们在 AI 驾驶时坐得离副驾驶座位更远一些。
