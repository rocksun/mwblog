本文介绍了 Amazon EKS 如何通过延长支持周期、提供升级就绪性洞察及引入可逆升级功能，解决 Kubernetes 集群升级中的风险与流程冗余问题，旨在将升级从高风险事件转变为标准、安全的运维流程。

> 译自：[Kubernetes upgrades don’t have to break things: How EKS is making cluster lifecycle management simpler and safer](https://thenewstack.io/eks-kubernetes-upgrade-rollback/)
> 
> 作者：Spyros Angelopoulos, Vikram Venkataraman

Kubernetes 的迭代速度为每年三个小版本更新，如果您关注安全补丁、支持范围和对新功能的使用，保持版本更新至关重要。但在该项目的大部分历史中，升级控制平面意味着一旦执行便无法撤销。这种限制从根本上塑造了企业对待集群生命周期管理的方式。

## 不可逆操作的运维成本

管理全球集群舰队的平台团队一致反映，每次就地升级周期都需要数周的准备工作、用于验证的并行基础设施以及广泛的预检验证，这使得整个流程延长为耗时多天的任务。一些组织构建了完整的蓝绿部署策略，仅仅是为了作为抵御升级失败的“保险单”，这不仅使控制平面基础设施增加了一倍，还需要维护复杂的流量镜像程序。另一些组织则将升级描述为“不归路”，迫使他们采取昂贵的缓解模式，原本只需几小时的工作变成了几天，主要是因为如果出现问题，没有回滚路径。

其自然结果就是拖延。团队将升级推迟了数月，在旧版本上停留的时间比预期的更长，有时直到支持终止期限临近而别无选择时才被迫升级。

升级的阻力已成为客户沟通中最受关注的问题之一。这一信号促成了 EKS 团队长达数年的工程投入。在过去的三年中，我们一直致力于实现一个目标：让保持 Kubernetes 的最新状态成为阻力最小的路径。

## 为团队预留规划空间

2023 年底，EKS 推出了扩展支持（自 2024 年 4 月起全面可用），将每个 Kubernetes 版本的可用性延长至 26 个月。受监管的行业需要更长的验证周期，大型企业在触及生产环境前需要协调数十个团队，而独立软件开发商 (ISVs) 则需为其平台认证特定的 Kubernetes 版本。扩展支持适应了所有这些现实需求，让团队能够按照自己的时间表进行升级，而不必被迫做出仓促的决定。

> “在过去的三年中，我们一直致力于实现一个目标：让保持 Kubernetes 的最新状态成为阻力最小的路径。”

同时，我们也认识到，对于许多组织而言，选择不升级并不总是因为需要更多测试时间。升级本身带有固有的风险，需要大量的协调工作，且一旦出现问题也没有回退方案。虽然扩展可用性给予了团队灵活性，但它并未解决许多团队犹豫不决的根本原因。

## 实现升级就绪性的清晰可见

从 2023 年底开始，EKS 推出了升级洞察 (Upgrade Insights)，这是一套自动化检查工具，用于扫描每个集群是否存在可能影响升级的问题，并在您继续操作前明确指出需要关注的内容。在随后的两年中，它从被动的咨询检查演变为带有按需重新评估的可强制执行的安全关口，涵盖了已弃用的 API 使用、集群健康状况、kubelet 和 kube-proxy 版本偏差以及 EKS 托管插件的兼容性。

那些以前将大部分准备时间花费在搜索潜在不兼容问题的团队，现在可以看到一份带有可操作修复步骤的优先级列表。该列表可以在应用修复后按需刷新，这意味着“这次就地升级会出问题吗？”这一问题得到了明确的、自动化的答案。

不过，检测是有局限性的。对于大规模生产环境，某些不兼容问题只有在最繁重的 API 使用模式下，或者在任何测试环境都无法完全重现的流量模式的集群中才会显现。自动化检查显著降低了风险，但降低风险并不等同于拥有安全网。

## 让就地升级变为可回滚

2026 年 7 月，EKS 实现了就地 Kubernetes 控制平面升级的可回滚化。版本回滚 (Version Rollback) 允许您在升级后的 7 天内回退到之前的小版本，通过您已经在使用的 `UpdateClusterVersion` API 即可完成，无需新工具、无需更改工作流，也无需额外成本。

> “2026 年 7 月，EKS 实现了就地 Kubernetes 控制平面升级的可回滚化。”

7 天的窗口平衡了两个需求：它既让团队有足够的时间在真实的生产流量下验证新版本，并[观察行为](https://thenewstack.io/taking-your-observability-strategy-to-the-next-level/)（这些行为可能仅在运行数天后才会显现），又限定了窗口期，以防止集群状态与先前版本可安全支持的状态之间出现长期分歧。

那些以前花费数天进行分阶段准备和验证的团队，现在可以显著缩短该周期。由于可以进行回滚，团队可以选择在新版本发布后的几周内主动升级，在真实生产条件下进行验证，如果出现意外情况则执行回退，因为他们知道原生回退比在压力下进行实时排障要快得多。可回滚性改变了团队对升级的看法。曾经的高风险事件逐渐变成了常规的生命周期任务。组织作为保险而构建的昂贵缓解模式——并行集群、冗余节点、手动脚本——变得不再必要，而是可选的。

Salesforce 运行着 EKS 上最大的 Kubernetes 集群舰队之一，他们就遇到了这种情况。他们的升级计划围绕着大规模的交错发布而构建，但某些回归问题只有在最大的生产集群中，在任何早期阶段都无法复制的流量模式下才会显现。当这些问题出现时，唯一的选择是在应用受损的情况下进行向前修复。有了 EKS 版本回滚功能，Salesforce 现在将原生回退直接整合到他们的升级工作流中，实现了更快的发布，并拥有了一个真正的安全网，而不是基于希望的缓解措施。

在进行回滚之前，EKS 会通过“回滚就绪性洞察 (Rollback Readiness Insights)”评估集群。这是一组与升级洞察基于相同架构构建的并行检查，现在涵盖了回滚就绪性，验证 API 兼容性、版本偏差、插件兼容性和集群健康状况，以确保集群在其当前状态下能够安全地恢复到之前的版本。

对于运行 EKS 自动模式 (Auto Mode) 的集群，回滚遵循与升级相同的完全托管模型：EKS 会在还原控制平面之前自动回滚工作节点，并在整个过程中遵守配置的 NodePool 中断预算和 PodDisruptionBudgets。操作员保留了在回滚完成速度与他们愿意接受的工作负载中断程度之间进行权衡的完全控制权。一个新的 `CancelUpdate` API 允许操作员在必要时停止正在进行的 [Auto Mode 节点](https://thenewstack.io/eks-auto-mode-kubernetes/)回滚并改变计划。所有 etcd 数据、工作负载和持久卷均被保留。对于使用托管节点组或自管理节点的集群，操作员在启动控制平面回滚之前，通过现有的 `UpdateNodegroupVersion` API 手动回滚其数据平面。

开源 Kubernetes 社区也一直在致力于解决这个问题。KEP-4330 引入了一种两步升级模型，其中集群在运行新二进制文件的同时模拟先前版本的行为，当操作员满意时再提交到新版本。这使得回滚在[架构上是安全的](https://thenewstack.io/build-resilient-service-architecture/)，因为在操作员提交之前不存在新版本数据。EKS 采取了完全不同的路径，允许集群在真实生产流量下以激活所有 API 和功能的完整新版本运行长达 7 天，然后再要求做出决定。最难发现的问题只有当真实工作负载在新版本上运行数天后才会出现，这是任何暂存或模拟都无法重现的。

## 迈向智能升级运维

在解决了检测和恢复问题后，下一步是减少评估、规划和执行版本变更所涉及的手动工作。EKS 模型上下文协议 (MCP) 服务器于 2025 年中期作为开源本地工具首次发布，并于 re:Invent 2025 上宣布作为完全托管的 AWS 服务进行预览。它为 AI 编码助手与实时 EKS 集群状态之间提供了标准化的接口。对于升级而言，这意味着工程师可以查询特定集群是否准备好升级，并获得全面的就绪性评估，涵盖已弃用的 API、插件兼容性、节点版本对齐和工作负载风险，并附带评分、优先级排序和预填的修复命令。升级后，同一接口会根据实时集群数据评估回滚就绪性，用单次自然语言查询取代了多步骤基于 CLI 的调查。

> “EKS 模型上下文协议 (MCP) 服务器为 AI 编码助手与实时 EKS 集群状态之间提供了标准化的接口。”

这代表了我们所看到的集群生命周期管理方向，即运维智能在工程师现有的工具中与他们相遇，并由实时集群状态而非静态运行手册提供信息，逐步降低自信、知情升级决策的门槛。

## 持续的投资

按照自己的时间表规划的灵活性。在开始之前即可了解什么会出问题的透明度。当出现测试无法预测的问题时，提供经过验证的恢复路径。以及在每一步减少所需工作量的智能工具。

每一项功能都是通过与客户并肩工作、观察他们如何进行大规模操作，并针对他们的处境设计解决方案而形成的。这种伙伴关系将继续指导我们接下来的工作。我们正在投资更深入的自动化、更具洞察力的检测，以及整个集群生命周期中更紧密的集成。保持 Kubernetes 的最新状态应该是团队自信地去做的事情，而不是他们小心翼翼地绕过的事情。这就是我们为自己设定的标准。
