**去年十月，P99大会**——专注于高性能、低延迟应用的开发者在线聚会——展示了来自 Chip Huyen 的一场精彩主题演讲。

畅销书《[AI Engineering](https://www.oreilly.com/library/view/ai-engineering/9781098166298/)》的作者 [Huyen](https://huyenchip.com/) 以简单的算术开场：训练前沿模型是一次性成本，而推理则是需要不断重复支付的成本。这对于前沿模型提供商来说是好事，但对于我们这些“Token燃烧者”来说却很糟糕。Huyen 认为，在模型的生命周期中，训练与推理的计算资源比例大致在 1:10 到 1:100 之间。推理模型（会消耗更多 Token）将这一比例进一步拉大。我们都清楚达到每周会话限额时的那种感觉。

Huyen 的观点是，如果推理成本过高，那么没有人能收回训练费用，这或许能解释为什么会有那么多关于前沿模型“盈利能力”的梗。那么，我们该如何优化推理呢？

这是 Huyen 花了几个月时间为她的书所研究的课题。本着优化的精神，Huyen 在 2025 年 10 月的会议上将其提炼为 30 分钟的分享。

Huyen 即将在几周后[回归 P99 CONF 2026](https://www.p99conf.io/?latest_sfdc_campaign=701Rb00000qrLWi&campaign_status=Submitted&utm_campaign=smo%20new%20stack%202026-10-21%20p99%20conf&utm_medium=social%20media%20-%20organic&utm_source=the%20new%20stack&lead_source_type=the%20new%20stack)。在此之前，请观看她去年的完整演讲——或阅读下面的回顾——然后我们来讨论这些观点在过去 11 个月里是如何演变的。

## 应该测量什么

Chip 建议关注几个关键的延迟指标：

* 首字生成时间（TTFT）：用户在看到任何内容之前经过了多少时间
* 每个输出 Token 的时间（TPOT）：连续 Token 之间的平均时间（又称*Token间延迟*）
* 端到端延迟：首字生成时间，加上每个输出 Token 的时间，乘以输出 Token 总数减一

![](https://cdn.thenewstack.io/media/2026/09/c34e67c5-image-1024x493.png)

（*点击放大图片。）*

在使用推理模型时，有些 Token 永远不会到达用户手中。“第一个生成的 Token 可能与第一个可见的 Token 不同，”Huyen 解释道。“模型可能会思考一会儿，它只会向用户显示最终输出的第一个 Token。”

> “第一个生成的 Token 可能与第一个可见的 Token 不同，”  
> — Chip Huyen

有些人也会测量“发布时间”（即用户看到第一个 Token 需要多长时间）。优先考虑哪项指标取决于对你的用户来说什么最重要。

此外，在吞吐量之外还要考虑“有效吞吐量”（goodput）。吞吐量衡量的是在给定窗口内处理的请求，而有效吞吐量衡量的是实际达到你目标的请求。Chip 的例子：一个应用程序的目标是 200 毫秒的首字生成时间和 100 毫秒的每个输出 Token 时间，每分钟处理 10 个请求，但只有三个请求同时达到这两个目标。

## 优化 LLM 推理的 3 种方法

对于推理服务器，你可以从 3 个不同的角度进行优化：硬件、模型，以及管理请求和响应的服务。

![](https://cdn.thenewstack.io/media/2026/09/c34e67c5-image-3.png)

（*点击放大图片。）*

Huyen 曾在 Nvidia 工作，她选择了不讨论硬件：“尽管我认为这是一个知识上很有趣的话题，但它与很多人无关，因为我们没有能力改变硬件本身，”Huyen 解释说。她也不想花太多时间在显而易见的解决方案上：副本并行化（replica parallelism），或者仅仅是增加更多的机器。这成本很高，而且很快就会变得复杂——特别是如果你最终混合了 80GB、48GB 和 24GB 的机器，以及需要在它们之间分配的不同大小的模型时。

剩下的就是模型和服务了。Huyen 就如何决定提供了这些建议：“如果你想自己托管模型，或者你有权访问模型权重，或者你自己训练模型，或者你想微调或蒸馏模型，那么模型优化可能适合你。但是，如果你想直接使用现有模型并在自己的推理服务上使其更高效，你可能需要关注服务优化。”

### 模型优化

以下技术会改变实际的权重，从而改变模型输出。

**量化（Quantization）** 降低了用于存储权重和激活值的精度（例如，从 32 位下的每个参数 4 字节降至 8 位下的 1 字节）。Huyen 解释说：“降低精度不仅减少了运行模型的内存需求，使其更便宜。它还可以使模型快得多。如果你逐位做加法且每个权重是 32 位，你必须做 32 次。如果是 8 位，你只需要做 8 次。”

代价是质量上的轻微损失。Huyen 继续说道：“在质量损失最小的情况下减少模型的大部分内存占用是可能的，而且量化对于各种模型架构和模型大小来说是非常通用的。这就是它非常受欢迎的原因。我很少见到有公司还在以全精度运行模型了。”

> “我很少见到有公司还在以全精度运行模型了。”  
> — Chip Huyen

**蒸馏（Distillation）** 涉及使用大模型为小模型生成训练数据。例如，假设你有一个真正的大模型（Huyen 使用的例子是 o1），并且想要一个性能类似但体积小得多的模型。基本上，你收集大量提示词，让它们运行在大模型上，然后用它的响应来训练小模型。

不过要小心行事。Huyen 警告说：“许多模型提供商规定不允许使用其模型来训练竞争模型。所以即使这是一种非常常见的技术，你也需要检查许可协议。”

### 服务优化

这一组技术针对的是如何调度、路由和复用请求。实际权重不受影响。

**批处理（Batching）** 将多个请求分组，以便在模型的一次遍历中一起处理它们——这比一次处理一个请求要高效得多。Huyen 提出了一些批处理选项：

* **静态批处理** 等待批次填满。这最大限度地提高了计算利用率，但可能会增加第一个请求的延迟。
* **动态批处理** 改为在计时器上运行（例如，每 15 毫秒批处理一次）。这在计算上效率较低，但对延迟更有利。
* **连续批处理** 处理请求在不同时间完成的情况，这在 LLM 中很常见。一个请求询问越南的首都是哪里；另一个请求开启了深度研究。使用静态或动态批处理，已完成请求的槽位会闲置，直到最慢的一个完成——新请求在它后面排队。连续批处理在每个请求完成时立即返回，并用另一个请求填充该位置。这可以提高计算资源利用率和延迟。

![](https://cdn.thenewstack.io/media/2026/09/c34e67c5-image-1.png)

（*点击放大图片。）*

**解耦预填充（prefill）和解码（decode）** 将请求的两个阶段分离到不同的机器上。（预填充处理输入，而解码生成输出。）Huyen 说：“输入 Token 可以并行处理，而输出 Token 需要顺序生成。并行处理受限于计算，即芯片的处理能力。而解码则受限于内存，因为你必须移动模型权重。”

由于每个阶段都会对不同的资源造成压力，大多数服务现在将它们分开了。要提高*首字生成时间*，将机器转向预填充。如果你更关心提高*每个输出 Token 的时间*，则将它们转向解码。

![](https://cdn.thenewstack.io/media/2026/09/c34e67c5-image-4.png)

（*点击放大图片。）*

**并行化（Parallelism）** 将工作分摊到多台机器上。副本并行化将整个模型复制到更多机器上。张量并行化（Tensor parallelism）分割一个非常大的矩阵，因此不同的机器计算它的不同部分。流水线并行化（Pipeline parallelism）按层分割模型，因此请求像流水线一样通过。

![](https://cdn.thenewstack.io/media/2026/09/c34e67c5-image-2-1024x485.png)

（*点击放大图片。）*

**提示词缓存（Prompt caching）** 处理共享文本一次，从而节省成本和延迟。对同一个应用程序的请求中存在大量的重复：系统提示词、示例、相同的代码库、不同问题背后的相同文档。你不妨处理一次共享段，缓存它，然后复用它。

当 Huyen 写《AI Engineering》时，这项技术还相对罕见。“有一篇关于它的论文，它并没有真正广为人知，但它非常有意义。所以我把提示词缓存写进了书里，我很高兴看到现在它几乎无处不在。”

![](https://cdn.thenewstack.io/media/2026/09/c34e67c5-image-3.png)

（*点击放大图片。）*

节省的费用根据你的提示词有多少被缓存而定。在 Claude Code 日志中，Huyen 的开源工具 [Sniffly](https://github.com/chiphuyen/sniffly) 发现缓存命中率在 90% 到 97% 之间。一些提供商会在内部重写提示词以提高命中率，但你也可以自己构建它们。

Huyen 的建议：由于缓存工作在共享前缀上，请将提示词中稳定的部分放在前面，可变的部分放在后面。“这很容易做到，而且可以显著提高你的应用程序性能，”她指出。

## 评估推理提供商

Huyen 最后给任何评估推理提供商的人提了一个警告：“有许多推理公司为你想要使用的模型提供推理优化，其中许多公司只宣传成本和延迟。

“但要注意有多少推理优化技术也会改变模型行为或降低模型质量。因此，在评估推理服务时，不仅要看成本和延迟，还要看模型质量，这一点很重要。此服务上提供的模型在标准基准测试中表现是否相似？”

## 一年后发生了什么变化？

那么，在这次主题演讲过去一年后的今天，我们的处境如何？大部分内容实际上经受住了时间的考验。

在经济学方面，我认为 Huyen 说得很对……我认为，对于我们大多数用户来说，我们没有 Huyen 列出的所有成本杠杆可以拉动。但了解正在发生的事情是很棒的。作为一名本地 LLM 的新手用户，我发现我可以联系到她关于并行化（我没有）和提示词缓存/量化（在我可控范围内）的观点。

提示词缓存（Huyen 说她写《AI Engineering》时这还是个新东西）现在已经被计入 API Token 的每一份购买套餐中。而她对 Claude Code 的观察（90% 的缓存命中率）可能就是我们凡人还能用得起代理式编码代理的原因。

其中一些内容的演变方式在当时很难预测。Huyen 提到推理模型使推理变得更加重要。一年过去了，我认为运行带有工具调用的多步骤循环的代理，已经将这个想法从一个脚注变成了一种反转 Claude 速率限制（及其臭名昭著的 99.x% 可用性）的方法。

Huyen 描述的所有指标——首字生成时间、发布时间、延迟 SLO 下的有效吞吐量等，现在都已经成为行话的一部分，并且可能需要以不同的方式进行推理。
