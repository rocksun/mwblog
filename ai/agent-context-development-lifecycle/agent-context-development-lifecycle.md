本文提出AI代理的技能、规则和提示词即代码，需建立“上下文开发生命周期（CDLC）”。通过生成、评估、分发、观察四个阶段，结合平台化管理与可观测性，提升AI编程的质量、稳定性和规模化协作能力。

> 译自：[Your agent context needs a development lifecycle](https://thenewstack.io/agent-context-development-lifecycle/)
> 
> 作者：Ankit Jain, Patrick Dubois

技能、代理配置、提示指令和规则文件。这些产物现在决定了您的编程代理产生什么。它们塑造了生成的每一行代码、每一个架构决策，以及代理遵循或忽略的每一项约定。从功能上讲，它们就是软件。

然而，没有人这样对待它们。团队编写一个技能，提交到仓库，却从不测试它在模型更新后是否依然有效。代理配置在团队间复制粘贴而没有版本控制。规则文件与其所描述的代码库逐渐不同步。当出现问题时，信号往往只是开发人员注意到了奇怪的输出并在 Slack 上抱怨。

> “如果上下文是新的代码，那么它的软件开发生命周期是什么？”

Patrick 为缺失的环节构思了一个框架：[上下文开发生命周期 (Context Development Lifecycle, CDLC)](https://tessl.io/blog/context-development-lifecycle-better-context-for-ai-coding-agents)。CDLC 并不是关于上下文窗口管理或在提示词中塞入更多 Token。它是关于管理进入上下文窗口的各个组件的质量。技能是否是最新的？模型是否真的能正确响应它？您是否提供了模型已经知道的上下文？如果上下文是新的代码，那么它的软件开发生命周期是什么？

## 上下文开发生命周期的四个阶段

CDLC 包含四个阶段，直接映射到我们目前在代码处理上所做的工作。

**生成 (Generate)** 是每个人开始的地方。编写技能、构建提示词配置、设置代理规则。这相当于编写代码，也是目前花费时间最多的地方。

**评估 (Evaluate)** 是测试。检查前置声明的 linting 是否正确，或者语法是否太长。在高级阶段，您会运行场景：加载一个技能，提出一个具体问题，检查代理是否产生预期的结果。您会跨模型和版本进行测试。您会检查是否在编写模型已经知道的上下文，这会浪费 Token。您会验证技能是否在正确的触发词上激活。

这是针对上下文的 TDD（测试驱动开发）循环。编写技能，编写场景，检查输出，进行迭代。

**分发 (Distribute)** 是交付。在最简单的层面上，它是将技能提交到仓库。在成熟的阶段，团队将技能发布到具有版本控制、可发现性和访问控制的可安装注册表中。将技能粘贴到 Slack 频道中并不是分发，就像通过电子邮件发送 .jar 文件不是依赖管理一样。

**观察 (Observe)** 是生产环境监控。技能是否在使用中？它是否产生正确的结果？在开发人员干预之前，代理需要多少轮对话？开发人员在哪些地方覆盖了代理或纠正了其输出？这就是针对您上下文的**可观测性**。

## 不要跳过测试

这里的成熟度曲线与过去二十年软件开发实践所发生的情况完全相同。组织首先进行生成和分发。他们完全跳过了评估。他们将技能发布到生产环境（即供使用它们的开发人员使用），然后等待看会发生什么。

这与团队跳过测试驱动开发（尽管被告知要这样做）的情况直接可比。他们不知道痛苦，所以直接进入生产环境。

当一个技能在一个模型版本上有效，但在下一个版本上失效时，或者当它在错误的问题上触发并[自信地给开发人员提供错误](https://thenewstack.io/rag-retrieval-scaling-architecture/)的指令时，痛苦就来了。当一个技能强制执行的约定在六个月前是正确的，但代码库此后已经发生了变化，这些就是我们在未经测试的代码中看到的相同故障模式。回归、误报、过时的假设。

> “你不能通过要求人类更仔细地审查来扩展代码质量。你通过投资于在两端编纂标准的护栏来扩展它。”

每个代码库都有 AI 持续出错的模式。约定盲点、幻觉 API、盲目模仿代码、过度工程。在 Aviator，这些被称为 [Invariants（不变量）](https://docs.aviator.co/verify/concepts/invariants)，或者 [AI 垃圾寄存器 (AI slop register)](https://www.aviator.co/blog/how-an-anti-slop-registry-stops-ai-generated-code-from-violating-your-engineering-standards/)。技能寄存器和 AI 垃圾寄存器都在开发生命周期的两端体现了相同的基本原则：编目您的工程标准并将其输入给代理。

在代码生成之前，这意味着技能。在 [代码审查](https://www.aviator.co/verify?utm_source=tns&utm_medium=content&utm_campaign=q3-2026-tns-verify&utm_term=net-new&utm_content=awareness) 时，它是 AI 在您的代码库中持续出错的模式目录。垃圾寄存器通知自动检查，捕获那些漏网之鱼。您不能通过要求人类更仔细地审查来扩展代码质量。您通过投资于在两端编纂标准的护栏来扩展它。

## 从 1x 到 50x

优化自己 [代理循环](https://thenewstack.io/gemini-cli-gets-its-hooks-into-the-agentic-development-loop/) 的开发人员会获得更好的个人结果，但这种改进仅停留在他们身上。当他们修复一个技能时，没有其他人受益。当他们发现一种故障模式时，没有人从中学到经验。投资回报率 (ROI) 是 1x。

Patrick 使用两个位于传统 DORA 指标之上的指标来构建规模化问题。

第一个是**人工触达 (human touch)**：开发人员在给定的代理工作流中需要干预多少次？每一次干预都是上下文缺失或错误的信号。减少人工触达点是衡量您的代理编程循环实际上有多自主的直接指标，并且它通常与成本相关，因为更多的轮次意味着更多的代理支出。

> “减少人工触达点是衡量您的代理编程循环实际上有多自主的直接指标。”

第二个是**重用倍数 (reuse multiplier)**：当您改进单个技能时，有多少开发人员受益？如果一名开发人员修复了一个技能，只有他们受益，那是 1x。如果该修复进入共享注册表，并且 50 名开发人员从中受益，那是 50x。

这两个指标共同迫使组织转向共享基础设施。如果不共享经过充分测试的上下文，就无法大规模减少人工触达。没有分发和版本控制，就无法获得重用倍数。

## 您的平台团队已经知道如何做了

这种组织结构已经存在。 [平台团队](https://www.aviator.co/blog/every-software-company-will-become-a-dev-tools-company/) 已经花费了十年时间构建使开发团队能够可靠地发布代码的基础设施：版本控制、CI/CD 流水线、构件注册表、安全扫描、依赖管理和访问控制。这套方案几乎可以直接移植。

平台团队为代码仓库所做的工作，同样适用于技能。提供注册表。配置访问控制和组权限。设置评估基础设施。运行安全扫描并报告结果。构建显示哪些技能表现良好、哪些正在退化的仪表板。追踪所有权，以便在模型更新后技能失效时，有人负责修复它。

平台团队不做的是编写技能或在技能失效时修复它们。拥有该领域的团队拥有该技能。平台团队提供治理层和工具，这与代码的责任划分是一样的。

> “不要构建工具。构建那个构建工具的工具。”

孤儿技能问题已经出现。一名开发人员编写了一个技能，分享了它，然后转到了另一个团队，现在没有人维护它。模型更新破坏了它，平台团队默认继承了这个问题。这又是 GitHub 仓库沦为孤儿的情况。解决方案是一样的：所有权政策、维护要求、弃用路径。

Patrick 简洁地绘制了这些层级：“不要构建工具。构建那个构建工具的工具。” [平台团队构建](https://thenewstack.io/internal-platforms-are-products/) 供那些构建工具的人使用的工具，而那些人又构建了构建工具的工具。

## 通过可观测性闭环

在大多数组织中，最不发达的阶段是观察，尽管它也是最重要的。没有它，就没有学习系统。您手动生成和分发上下文，希望它能起作用，并在有人投诉时修复问题。

代理的**可观测性**仍处于早期阶段。标准正在形成。Agent MD 已被广泛采用。技能和插件标准则更新。工具虽然不成熟，但模式很明确：对您的代理进行插桩，集中信号，并在跨团队间进行分析。

我们之前曾提出，生产反馈循环是 AI 辅助开发中缺失的一环。当生产环境出现故障时，将其追溯到变更，识别错误类别，并将其反馈到提示词和验证层。CDLC 可观测性阶段将这一思想从代码质量扩展到了上下文质量。从代理日志、开发人员更正和轮次计数中收集的信号直接反馈到生成更好的技能、编写更有针对性的评估以及分发改进的版本中。

## 自我完善的代理开发

完全闭环的系统看起来像是一个代理日志输入到分析系统，进而识别出差距。这些差距会生成新的技能或更新现有的技能。更新后的技能在发布前会经过评估。它们通过带有版本控制的注册表进行分发。循环往复。

Patrick 对最终状态持现实态度。“黑暗工厂”愿景（代理在零人工参与的情况下生产代码）是他所称的“一个崇高的方向，但也是一场危险的游戏”。最接近这一目标的团队——那些可以自信地说他们[不再阅读代码](https://thenewstack.io/future-of-code-reviews/)的团队——是那些在上下文、测试和可观测性基础设施上投入巨资的团队，这些基础设施使他们的代理足够可靠，从而减少了每个周期对人工触达的需求。
