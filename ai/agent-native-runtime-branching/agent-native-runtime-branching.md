文章指出Coding Agent使得并行分支激增，导致共享资源（如测试环境）成为瓶颈。作者提出“端到端分支”模式，即在代码、CI、数据库及运行时各层均实现轻量级隔离，通过共享基线配合增量变更，解决Agent带来的交付拥堵问题。

> 译自：[Anthropic recommends a git worktree per agent. Your runtime infra makes that a problem.](https://thenewstack.io/agent-native-runtime-branching/)
> 
> 作者：Arjun Iyer

一位监督四个编程Agent的开发者，同时拥有四个在运行中的变更，每个变更都在各自的 git worktree 中。这在今天已不再是罕见的设置：Anthropic 的文档现在将[每个会话一个 worktree 作为并行运行 Agent 的默认方式](https://code.claude.com/docs/en/worktrees)，而两年前所谓的专家级工作流程，现在已成为推荐的起点。

分支本身并不新鲜。Git 在 20 年前就让分支变得廉价，以便开发者可以隔离变更并同时处理多项任务，但在实践中，开发者通常会在分支之间切换，一次只交付一个变更。这使得代码层之下的一切保持单一：一个持续集成 (CI) 队列、一个预发布环境、一个供所有人测试的数据库。竞争这些共享资源的变更数量受到人力限制，而在 Agent 出现之前，只有大型团队才会触及这个上限。

> “编程 Agent 消除了这个上限。分支不再局限于代码层。”

编程 Agent 消除了这个上限。这四个分支不再是一个开发者轮流处理的对象。它们是四个并行推进至合并的活跃变更。这种差距变得无法逾越：分支在代码层是免费的，但在其他所有层级却是缺失的。每个变更都需要在整个技术栈中存在，不是作为目录中的 diff，而是作为系统的一个可运行、可测试的版本。分支不能再仅止步于代码层。

## 并行直到遇到第一个共享资源

代码可以在几毫秒内完成分支。worktree 以检出的成本为每个 Agent 提供仓库的私有副本，10 个 Agent 可以并排工作而互不干扰。

输出结果出现在下游。Faros AI 对超过 10,000 名开发者的遥测分析发现，AI 采用率高的团队[合并了多 98% 的拉取请求，但审查时间却增加了 91%](https://www.faros.ai/blog/ai-software-engineering)。代码生成下游的任何环节都没有针对这种交付速率进行优化。

随后每个变更都需要运行。系统通常只有一个预发布集群、一个种子数据库、一个消息队列、一套依赖服务，每一条达到这个层级的分支，并行特性就此终结。四个 Agent 在一个下午产生四个候选变更，而这四个变更都排在同一个共享环境后等待验证是否可行。

这种队列的代价比看起来更高，因为 Agent 不太擅长等待。一个被环境阻塞的 Agent 要么处于闲置状态，持有陈旧的系统视图，要么继续前进，针对模拟数据进行验证，而监督它的开发者则会切换上下文。当共享环境释放时，简单的工作部分可能需要重新进行。

瓶颈不在于代码生成，[也不仅仅在于审查能力](https://thenewstack.io/ai-code-bottleneck-myth/)。瓶颈在于变更触及的第一个共享资源，因为一个无法运行的分支就是一个不可信的分支。

> “瓶颈不在于代码生成，也不仅仅在于审查能力。它在于变更触及的第一个共享资源。”

## 分支是增量，而非副本

出路在于停止将分支视为 Git 的特有功能，而应将其视为每一层都应具备的能力。基于分支的开发体现了这种模式：栈的每一层都提供廉价、即时、可丢弃的分支原语，这样变更就可以端到端地存在，而无需复制任何未触及的内容。

其机制正是 Git 两十年来建立并延续至今的那一套：分支之所以廉价，是因为它们共享所有未变更的部分，只携带增量 (delta)。从那时起，技术栈的其他层级一直在逐层重学这个思想——默认共享，隔离变更。

为这种模式命名很重要，因为每一层都是独立发现的，并称呼为不同的名字。Worktree、流水线缓存、预览部署、数据库分支和环境沙箱听起来像是五个不相关的特性。它们实际上是在五个层级上应用的同一个思想，认识到这一点，你就会重新审视那些缺乏该功能的层级。

## 上层早已习得此道

CI 在十年前就吸收了这一教训。每个分支都在共享运行器池中运行自己的流水线，构建缓存负责重用未变更构件的写时复制 (copy-on-write) 工作。没人会为每个分支配置一个构建系统，也没人会再排队等待一个全局构建。

前端紧随其后。在 Vercel 上，[每次推送到非生产分支默认都会获得自己的预览部署](https://vercel.com/docs/deployments/environments)；Netlify 的工作方式相同，分支本身就是一个不可变的构建，加上共享托管基础设施上的路由。审查者不再询问变更在某人的笔记本电脑上是否可行，因为该变更已经在某处运行了。

这两种情况的形态一致：昂贵的机器是共享的，分支是轻量的，创建分支的成本低到让人忽略不计。这就是一旦拥有分支原语后，层级应有的感受。

这些原语一旦出现，也改变了行为。基于分支的 CI 使得在每次推送时运行全套测试而非仅在夜间运行成为常态。预览部署使得产品经理在合并前点击检查变更成为常态。廉价分支不仅消除了队列，还提高了合并前检查的标准。

## 数据层曾被认为是困难的一环

数据库承载状态，因此传统观点认为分支永远无法在那里实现。然而 Neon、PlanetScale 和 Xata 还是实现了，Neon 的文档现在明确了这种并行性：[像分支代码一样分支你的数据](https://neon.com/docs/introduction/branching)。

数据库分支是对共享存储页面的写时复制视图，无论数据库有多大，创建仅需几秒钟。[模式迁移](https://thenewstack.io/lessons-learned-from-real-world-nosql-database-migrations/)和风险数据变更会根据生产环境形态的数据进行验证，而不是使用过时的种子脚本，且分支会在工作合并后消失。

> “如果拥有最多状态的层级可以在几秒钟内提供分支，那么无状态性从来都不是真正的必要条件。”

数据层在这个故事中很重要，因为它消除了最好的借口。如果拥有最多状态的层级可以在几秒钟内提供分支，那么无状态性从来都不是真正的必要条件。任何尚未实现分支的层级，都是因为选择不这样做。

## 运行时是最后一层

微服务运行时抵制得最久，因为它看起来一点也不像文件树。它有实时流量、服务图谱和数十种变动的依赖项。天真的分支——即环境的完整副本——过于昂贵，以至于大多数团队认为分支并不适用于此。

写时复制的方法依然适用。运行一个从 main 分支持续部署的共享、稳定版本系统。对于每个变更，仅将变更触及的服务作为轻量级临时环境部署，并将每个测试请求路由通过变更后的服务，而其他所有部分则回落到共享稳定版本。环境分支的成本大致等于变更服务的成本，这就是为什么每个 Agent 产生的变更都可以拥有一个环境。

路由部分听起来很异国情调，实则不然。带有标签的请求在每一跳都会被导向变更后的服务版本，像跟踪上下文（trace context）在大多数已实现可观测性的系统中流动一样，在调用链中传播。 [共享稳定环境](https://thenewstack.io/smart-ephemeral-environments-share-more-copy-less/) 扮演着 main 的角色，变更后的服务是增量，标签是指针，它为每个请求组装出一个连贯的系统视图。

这不是假设的架构。Uber 构建了 [SLATE，以便为每个开发者提供一个针对共享生产级依赖项进行路由的临时环境](https://www.uber.com/blog/simplifying-developer-testing-through-slate/)，因为对预发布环境的争用已无法跟上其开发者数量。

## Agent 原生栈意味着什么

将这些层级组合在一起，一种不同的开发模型就会出现。一个 Agent 接手任务，变更从一开始就会获得一个 worktree、流水线运行、预览、数据库分支和运行环境。验证不再是序列化上游所有流程的稀缺资源。

团队已经在组合底层的能力。Bitso 是一家拥有超过 250 名工程师的加密货币交易所，它[为每个变更配对环境分支与数据库分支](https://www.signadot.com/blog/how-bitso-is-scaling-branch-based-development-with-signadot-and-neon/?utm_source=tns&utm_medium=sponsorship&utm_campaign=q3_26_sponsored_content)，因此运行时增量和数据增量可以同步进行，共享的预发布环境也保持在关键路径之外。

这种端到端的分支才是“Agent 原生软件开发生命周期”应有的含义。不是将 Agent 接入昨天的流水线，而是一个任何变更（无论是人类还是机器产生）都可以在每一层存在、并在验证完成后消失的技术栈。

收益随 Agent 数量增加而复合。当每一层的分支原语都是共享基础上的增量时，验证并发性将随集群容量而非预算扩展，团队每天能证明正确的变更数量将随着产生的变更数量增加。这个比例决定了 Agent 的采用是转化为交付的软件，还是转化为更长的队列。

审计很简单。追踪一个从 worktree 到验证完成的变更，记录它等待共享资源的第一层。那就是你的技术栈停止分支的地方。
