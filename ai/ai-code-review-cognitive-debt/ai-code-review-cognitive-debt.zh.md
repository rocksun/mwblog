AI生成的代码量已经冲垮了代码审查。工程师们正在审查他们自己未曾编写、由模型生成且无法完全控制的500行代码差异（diff），其速度之快使得仔细阅读变得不可能。

但如果AI现在生成了大部分代码，而人类根本无法全部读完，我们该如何保住代码审查向来承担的知识共享职责呢？

> “如果代码审查左移，知识共享也必须左移。”

代码审查一直是团队间知识传递的枢纽：初级工程师在此观察高级工程师的思维方式，架构决策在此受到挑战，代码库的心理模型在此形成，共享的所有权意识也在此建立。如果代码审查左移，知识共享也必须随之左移。

在我的[播客对话中，Vanitha Kumar](https://www.aviator.co/podcast/ai-code-review-vanitha-kumar)（ThoughtWorks市场技术总监）无意间意识到了这一点。

Vanitha 构建了一个代理（Agent），旨在捕捉反模式（anti-patterns）并向不符合其团队原型的开发者解释它们。了解该原型后，她会指示代理对照参考文档中的实践来审查代码，识别团队偏离的地方，并解释为什么这种偏离是有害的。与其说它是一个代码审查代理，不如说它是一个教学代理，尽管它逐渐演变成了前者。

*我随即意识到，这不应该在提交（commit）后的后期阶段才被发现。无论是人工完成还是代理完成，代码审查都必须更早地进行，甚至不必是正式的审查。它可以是小黄鸭调试法（rubber ducking）或一个教学时刻。*

## 一种新型债务：认知债务

大多数关于取代代码审查的讨论都集中在捕获错误和检查标准上。大部分工作可以通过基于LLM的对抗性审查、[自动化验证](https://thenewstack.io/ship-code-without-verification/)和确定性检查来自动化。但如果我们彻底解决了标准检查问题，却对知识共享无动于衷，那么我们只是解决了一个较简单的工作。

在AI出现前的团队中，初级工程师的PR（Pull Request）会收到高级工程师关于惯用模式的四到八条评论，针对边缘情况的来回讨论，以及隐式的“我会这样思考这个问题”的教学。

而在AI驱动的团队中，同样的变化由AI生成、轻微编辑、由AI审查、轻微批准并合并，没有人类构建过它的心理模型。

Margaret-Anne Storey 为协作消失后的后果起了一个有用的名字：[认知债务](https://www.aviator.co/podcast/cognitive-debt-ai-code-margaret-anne-storey)。[技术债务存在于代码中](https://thenewstack.io/how-frontend-devs-can-take-technical-debt-out-of-code/)。而认知债务存在于人脑中。当团队不再理解他们正在构建的系统时，认知债务就会累积，没有任何仪表盘会告诉你这件事正在发生。

> “技术债务存在于代码中。认知债务存在于人脑中。”

她最初注意到这一点是在一群使用AI并快速构建产品的学生身上。在某个时刻，他们告诉她，他们无法再对产品进行更改了。她怀疑是技术债务或混乱的代码导致的。但学生们实际上已经失去了对他们试图构建的功能以及原因的追踪。他们不知道团队中谁掌握了什么知识。在其中一个团队中，只有一个人理解代码，因为他们在监督生成代码的AI，而团队的其他成员则无法理解。生成代码的人实际上也不明白生成了什么。

有人可能会说，如果我们有AI来回答关于代码的所有问题，就不应该存在认知债务。我们可以将代码理解卸载给它。尽管LLM非常擅长解释功能或行为的工作原理，但我们却丢失了“是什么”和“为什么”。为什么这些更改是这样创建的？在实现功能时做了哪些假设？某项功能有哪些副作用或行为，它如何适应产品路线图？为什么这个功能必须存在？所有这些都是认知债务；它并没有写入代码中，而这正是我们需要心理模型的地方。

## 意图驱动的验证保持知识共享的活力

解决代码审查瓶颈的方案是将[人工检查点上移](https://www.aviator.co/blog/move-code-review-before-the-code/)，即审查意图、审查代码应满足的契约：计划、约束和验收标准。这同样适用于审查过程中的知识共享部分。

[意图驱动的验证](https://docs.aviator.co/verify/concepts/why-intent-driven-verification)意味着捕捉工程师在与代理会话期间做出的决定、架构选择、行为权衡和范围界定，并在提交更改前将其写成验收标准。包含简短的范围描述、验收标准列表以及明确不在范围内的说明。这些决策已经在提示词（prompts）中了。通过 [Aviator](https://www.aviator.co/verify) Verify，工程师可以捕捉这些决策，而不是在会话结束后丢失它们。

审查员的工作变了。他们不再是阅读600行代码差异并问“这看起来对吗？”，而是阅读少量的验收标准并问“我们是否正在用正确的约束条件解决正确的问题？”他们不需要阅读每一行代码。他们需要理解背后的意图，发生了什么变化，更重要的是，为什么变。这对高级工程师的时间来说，是本质上更好的利用方式。

> “审查员阅读验收标准是在阅读实现背后的决策，而不是实现本身。”

这对作者和审查员同样重要。作为一名工程师，你需要代码的心理模型来与代理进行有效的交互，并质疑它们的建议。如果你在行为层面不理解正在构建什么，你就无法在代理走偏时及时发现。无论是作为作者还是审查员，[捕捉并审查意图](https://thenewstack.io/future-of-code-reviews/)和行为，正是构建和维护心理模型的方法。这正是审查的知识共享功能得以留存的地方。审查员阅读验收标准是在阅读实现背后的决策，而不是实现本身。

我们一直说团队中不应该有任何一个人掌握所有知识，如果有人中奖离职，工作也不应停滞。很少有团队真正朝着这个目标努力。我们往往满足于由一个人掌握所有背景信息。既然现在AI编写了大部分代码，我们就没得选了。生产力的提升是真实存在的，也值得获取。但如果没有一个深思熟虑的流程来维护对构建内容及其原因的心理模型，[团队会交付得更快](https://thenewstack.io/think-like-a-developer-to-help-dev-teams-ship-faster/)，但理解得更少，直到速度本身成为问题。
