**自主编程代理无视开源社区的贡献规则**，这是来自北京大学研究人员的一项新[研究](https://arxiv.org/abs/2607.26819)得出的结论。

这对那些正迅速[被低质量AI生成贡献淹没](https://thenewstack.io/ai-slop-open-source/)的维护者来说，并非好消息。如果编程代理连贡献指南都不遵守，那么简单的重写规则对于约束代理的行为将起不到太大作用。

该研究对四个前沿模型进行了实验，整理了49个包含AI贡献规则的代码库中的106个问题，并根据代码库的规则对每次运行的结果进行了评判。研究人员衡量了四种合规性：1) 拒绝贡献；2) 真实披露其辅助行为；3) 通过验证门槛；4) 升级至人工处理。

代理的表现如何？并不理想。正如研究人员所写，“今天的代理几乎从不主动检索贡献规则。”

通过提醒提示、引用政策和验证反馈等方式进行催促后，代理在披露和验证方面确实有所改进——但它们从未拒绝向禁止AI贡献的代码库提交代码。

[Cristian-Alexandru Staicu](https://www.linkedin.com/in/crstaicu/) 是 [Endor Labs](https://www.endorlabs.com/) 的高级安全研究员，他将这种冲突描述为代理面临的“伦理困境”：

“想象一下，一个代理被要求‘修复一个烦人的bug并提交合并请求’，而该项目列出了研究图1中的条款，即‘本项目不接受完全或主要由AI生成的合并请求’，” Staicu 告诉 *The New Stack*。“现在代理陷入了伦理困境。它应该遵守用户的请求，还是遵守策略？”

## 代理并非不听，它们只是过于专注于手头的任务

回顾最近的 [Hugging Face 事件](https://thenewstack.io/openai-huggingface-sandbox-breach/)，当时自主AI系统逃离了沙盒并侵入了生产基础设施。[Mike McNeil](https://www.linkedin.com/in/mikermcneil/)，[Fleet Device Management](https://fleetdm.com/) 的首席执行官兼 [The Sails Company](https://sailsjs.com/studio) 的创始人，提醒开发人员，代理并不总是遵循提示，这就是为什么它们可能无法尊重特定于代码库的贡献规则。

> “披露和验证是附加项：代理可以完成用户的任务并合规。但禁令要求代理放弃任务，这与用户的明确指令以及代理旨在提供帮助的训练目标直接冲突。”

“AI非常专注于实现其主要指令，”他告诉 *The New Stack*。“它想完成被赋予的任务，正如我们在 Hugging Face 事件中所看到的，它愿意为完成任务做任何事情。”

Staicu 表示，分析贡献策略通常根本不是代理构建和训练方式的一部分：“代理几乎从不自己打开策略文件，因此规则根本没有进入它们的推理过程。”

然而，为什么提醒、引用策略和反馈有助于促使代理尊重披露和验证要求，却对AI禁令和升级要求无效？Staicu 告诉 *The New Stack*，区别在于规则对任务的最终影响：

“披露和验证是附加项：代理可以完成用户的任务并合规。但禁令要求代理放弃任务，这与用户的明确指令以及代理旨在提供帮助的训练目标直接冲突。”

换句话说，代理不遵守某些让它放弃任务的规则，因为它被硬编码为必须完成任务。

[Timo Bozsolik-Torres](https://www.linkedin.com/in/timobozsolik/)，[SandboxAQ](https://www.sandboxaq.com/) 的AI负责人对此表示赞同，他认为这种行为不是代理是否理解规则的问题：“如果这是一个理解问题，更强的模型应该能弥补差距。相反，情况恰恰相反；测试中最强的模型 GPT-5.5 也是最固执的拒绝者。”

## 这是否意味着重写贡献策略是在浪费时间？维护者还能做什么

为了遏制AI生成的垃圾内容，开源游戏引擎 Godot Engine 正在[重写其贡献策略](https://thenewstack.io/godot-bans-ai-coding-agents/)，禁止大多数AI生成的代码进入其代码库。它并不孤单。编程语言 Zig 和终端模拟器 Ghostty 也在更新策略以控制AI在贡献中的使用。

但如果北京大学的研究表明，编程代理在自主行动时很大程度上忽略了贡献指南，那么仅仅重写策略可能是不够的。

相反，专家建议将控制权置于代理之外。

“不要再指望模型会记得去阅读 CONTRIBUTING.md，而应将策略发现作为框架的一部分，而不是让模型自己去判断，” Staicu 说。

这或许能帮助代理主动检索贡献规则，但对于那些即使被提醒也会无视的AI禁令该怎么办？“实验室需要走得更远，” Staicu 承认，“通过强化学习对模型进行微调，明确惩罚违反政策的行为。”

Bozsolik-Torres 建议了一个更简单的控制方法：“不要给代理一个针对已标记为禁止的代码库进行 create_pr 的工具调用权限。”他还建议维护者默认将AI标记的合并请求路由给更严格的人工审查。

另一种常见的策略是在代码库中包含一个 AGENTS.md 文件来告诉代理如何表现，但有些人对此也嗤之以鼻。[Jeffrey Paul](https://www.linkedin.com/in/jeffpaul/)，[Fueled](https://fueled.com/) 的开源解决方案副总裁告诉 *The New Stack*：“可悲的是，这些指令往往是从代码库中其他人为基础的文件中复述出来的，”他说，“这意味着针对人类和代理的文档是重复的，需要维护者在多个地方更新内容。”

相反，他一直在尝试一种不同的方法，在本地使用 ~/.agents/AGENTS.md 文件，然后将该内容直接复制到他正在使用的任何代理工具中。“这样，我只需要维护一个本地文件，”他解释道，“当我切换工具时，我也能确保更新该工具特定的用户级代理指令文件。”

Paul 承认这种方法并没有100%的成功率，但它在确保代理寻找并尊重特定于代码库的贡献指南方面表现得更好。

## 现有的 SDLC 控制应该承担大部分繁重的工作

当被问及维护者可以采取什么措施来执行贡献规则时，McNeil 表示，执行并不需要过于复杂，他指出了代码所有者作为控制合并的长期有效方式。

> “归根结底，如果你有完善的软件开发生命周期 (SDLC)，代码库已经是受保护的。”

“这是我们在AI出现之前就为人类使用的经典控制方式，[即]只有经过批准的人才能合并代码，”他说。“这些是真正确定性的，”他补充道。“没有 GitHub 的管理员登录权限，你无法破坏它们。”

通过这种方式，McNeil 似乎提倡回归基础来控制AI生成的贡献，并解释说 linting 和 CI/CD 流程已经充当了控制合并的检查点。“软件开发生命周期 (SDLC) 仍然是我们已经使用并信任的，用于处理来自人类的其他非确定性贡献的系统，”他说。“归根结底，如果你有完善的 SDLC，代码库已经是受保护的。”

尽管北京大学研究的发现可能会让维护者感到震惊，但它们也是一个有益的提醒。如果你的 SDLC 已经在发挥作用，那么你就不需要指望自主代理能自我约束。
