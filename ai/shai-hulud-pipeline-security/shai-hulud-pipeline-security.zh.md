# Shai-Hulud：谁控制了你的包管理，谁就控制了你的部署管道

2025年9月15日，npm的注册表发生了一件史无前例的事情：软件包开始自我更新。

没有维护者运行 `npm publish`，没有合并任何拉取请求。新的版本就这样凭空出现，每一个都携带了一个隐秘的“乘客”，它们会继续在更多的机器上发布更多软件包，而无需任何人为干预。在9月14日至18日期间，超过500个软件包版本被篡改。这种蠕虫病毒的作者留下了一张带有引人入胜的文学绰号的名片：每一份窃取的凭证都被上传到了一个新的公开GitHub仓库，命名为“Shai-Hulud”，这个名字取自Frank Herbert《沙丘》系列丛书中那种无法驯服的顶级基石物种。

> “我们从一个编写并重新发布自身恶意软件的蠕虫身上，学到了关于信任基础设施的什么教训？”

故事并没有到此结束。两个月后的11月24日，一个名为Shai-Hulud 2.0的更大变体成功在796个软件包中植入了后门，它将执行过程移到了安装程序的早期阶段，使得开发者的触发器失效，并在离开时“伤口撒盐”——如果找不到可窃取的凭证或传播途径，它会直接删除用户的主目录。到2026年春季，它的后代“Mini Shai-Hulud”已经进化，从狩猎通用的开发者密钥转向专门针对Claude、Codex、Cursor和Gemini的凭证，因为该蠕虫合乎逻辑地得出结论：AI编程工具参与了所有最有趣的项目，是绝佳的狩猎场。

最新的变体名为ChainDrop，出现在2026年8月4日。在不到四个小时内，它通过搭载一个合法的、经过加密签名的发布管道，感染了超过400个软件包，这使得每个被投毒的版本都拥有有效的SLSA来源证明。这让它们避开了旨在验证软件包未被篡改的防御机制。甚至其指令基础设施也驻留在以太坊智能合约中，使得任何域名屏蔽列表都变得毫无意义。

## 你能信任谁？

每一个包管理器和基础设施注册表都基于同一个不稳定的假设：安装某个东西意味着运行包中的任何内容，无需查看，并拥有安装进程本身所具备的任何权限。当发布工作还需要人工坐下来操作时，这个假设还算安全。

> “如果发布工作现在可以由环境中已经存在的非人类代理自动化完成，那么它就不再安全了。”

如果发布工作现在可以由环境中已经存在的非人类代理自动化完成，那么它就不再安全了。在这种环境下，蠕虫不需要说服任何人任何事情。它只需要一个被泄露的凭证和一个安装脚本。此后，注册表便授予了信任和信誉，而随后的每一个依赖项都进一步加固了这种信任。

## 发生了什么

其策略极其简单。一个受感染的npm软件包会运行一个安装后脚本（在Shai-Hulud的例子中是一个名为 `bundle.js` 的文件），它会在受感染的机器上搜索任何类似凭证的内容，包括npm和GitHub的个人访问令牌、AWS或GCP的密钥，以及任何它能从云实例元数据服务中提取的内容。它会下载Trufflehog（一个合法的开源密钥扫描工具），并利用它确认所发现凭证的有效性。所以，其中的一线希望是，你至少从这次感染中免费获得了一次（某种程度上的）安全审计。

一旦找到GitHub令牌，它就会将所有内容外泄到一个新的公开仓库中；作为额外补充，它还会尽可能地将它能访问的私有仓库设为公开，并以原名重新发布，但在末尾附加了“-migration”后缀，或许是为了让受害者看起来像是自己请求迁移的。如果它找到了npm令牌，它会调用注册表的API来列出该受感染开发者维护的所有软件包，下载它们，将自身注入到 `postinstall` 步骤中，提升版本号，然后重新发布。就是这样，不需要进一步的输入。Palo Alto Networks的[Unit 42](https://unit42.paloaltonetworks.com/npm-supply-chain-attack/)相当确信，该恶意脚本部分是由LLM编写的，依据是载荷中嵌入的代码注释和表情符号等风格线索。

## 我们绝不能恐惧。恐惧是思维杀手。

这种漏洞并非npm所独有。将 `npm publish` 换成 `terraform apply`，其机制几乎没有变化。从公共注册表拉取的Terraform提供程序（provider），就像从其注册表中拉取的npm包一样，都是发布者账户[被信任发布](https://thenewstack.io/kubernetes-teams-trust-automation/)的代码，并以请求它的机器所拥有的任何权限运行。

一个带有持久云凭证且有通往互联网开放路径的CI运行器，与一个拥有有效npm令牌的开发者笔记本电脑是同一个目标：蠕虫一旦破坏了它，就可以利用它以自动化允许的任何速度，传播到下游的所有系统。

> “证明（Attestation）告诉我们软件包来自哪里；它并没有说明该提交是否应该存在。”

到目前为止，业界对这个问题的回答是来源证明：签署软件包，证明构建过程，并以加密方式证明发布的内容与审核的内容相符。ChainDrop是对这个答案的反击。它没有伪造签名，而是破坏了一个拥有合法写入权限的维护者账户，并让该账户的合法、已签名的管道代为构建和发布恶意软件。来源证明告诉我们软件包来自哪里；它并没有说明该提交是否应该存在。

## 解决方案

**每个依赖项都应锁定到不可变的引用。** Terraform的依赖锁文件 `.terraform.lock.hcl` 自Terraform 0.14以来，为每个提供程序版本记录了加密校验和，采用了首次使用即信任的模式。一旦记录了校验和，任何后续不匹配的 `terraform init` 都会失败，而不是接受被替换的二进制文件。模块也应该遵循同样的纪律。将模块的 `source` 锁定为完整的提交SHA，而不是分支甚至标签，因为标签在源头可以像提交哈希无法做到的那样被移动或删除。Checkov的CKV_TF_1规则和TFLint的模块源锁定检查之所以存在，是因为审核人员总是忘记这一点。

**通过贵组织策划的注册表获取源码提供程序和模块。** 公共Terraform注册表，就像公共npm注册表一样，会解析其维护者选择发布的任何内容。如果维护者账户被破坏，下游的每个人在下次 `init` 时都会继承这个问题。通过私有的、版本化的、允许列表化的注册表来路由提供程序和模块解析，意味着部署可以拉取的潜在来源是由你们团队中的某个人控制的，而不是由整个公共互联网上的Terraform代码决定的。

**凭证应限定于部署范围，而不是开发者或运行器。** Shai-Hulud谱系的每一个阶段都依赖于一个长期存在的、静态的秘密，无论是 `.npmrc` 文件中的令牌还是CI环境变量中的密钥。通过OIDC签发的[短期、按部署的凭证](https://thenewstack.io/securing-ai-agent-sandboxes/)——即在部署运行时交易获得的用于临时云访问的身份令牌，并在任务完成后立即丢弃——意味着Trufflehog无法找到任何长期存在的秘密。蠕虫仍然可以窃取在 `apply` 过程的90秒内驻留在内存中的凭证，但它无法窃取从未被写入的内容。

**控制运行器在退出时被允许与哪些对象通信。** 该蠕虫的每一代都依赖于开放的出站路径：用于数据外泄的Webhook端点、用于持久化的GitHub API、用于传播的npm注册表API，以及在ChainDrop的案例中，选择以太坊RPC端点是因为没有域名屏蔽列表能触及它。限制运行器的出口流量，仅允许其与部署实际需要的少数域名（注册表、状态后端、云API）通信，意味着蠕虫任何向外联络的尝试都会在离开大楼之前直接撞向防火墙。

## 那些能毁灭某物的人，才是控制它的人

构建管道并不是坐在安全边界之外的优雅且保守的便利层。它是生产基础设施，无人值守运行，通常比它所部署的系统拥有更多的长期权限。

> “构建管道并不是坐在安全边界之外的优雅且保守的便利层。它是生产基础设施。”

管道并非有意这样构建。它们最终变成这样是因为在这些漏洞暴露之前，每个人都把它们当作管道设施，好像历史上从未出现过利用这些基础设施来逃避防御的案例一样。事实证明，这也是蠕虫获取保护你密钥之钥匙的完美途径。

Shai-Hulud在头24小时内就发现了这一点。业界正忙于追赶，每隔几个月就支付一次越来越痛苦的代价。

软件供应链过去只是被破坏。现在，它们被感染了；而感染不会等待，它们会传播。这个最初作为凭证窃取者的卑微蠕虫，现在已经学会了伪造旨在捕捉它的加密证明。它最新的猎物是开发团队用来加速生产的AI工具。一个未锁定的引用和一个开放的注册表拉取，足以让它传播到[Terraform提供程序和模块](https://thenewstack.io/build-terraform-modules-that-your-team-will-actually-reuse/)中。唯一的补救措施是：锁定可锁定的内容；通过允许列表控制无法锁定的内容；限制剩余内容的凭证范围。关闭所有出口路径。

否则，当你注意到下一个蠕虫时，它早已传播到了你忘记锁定的那个引用下游的所有地方。
