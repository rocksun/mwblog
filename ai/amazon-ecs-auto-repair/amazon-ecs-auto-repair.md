本文介绍了 Amazon ECS 的自动化故障恢复与弹性设计，涵盖 GPU 自动修复、可用区故障应对、容器原地重启及更安全的默认配置，帮助 SRE 减轻运维负担并提升系统高可用性。

> 译自：[Amazon ECS now auto-repairs failing GPUs and instances. Here's why it matters for SREs.](https://thenewstack.io/amazon-ecs-auto-repair/)
> 
> 作者：Anirudh Aithal

在生产环境中运行应用程序意味着必须通过各种中断维持“始终在线”的姿态。基础设施会发生故障、依赖项会变慢、网络会分区，这并非罕见的特例，而是大规模运行环境中的常态。抵御并从这些中断中恢复是一项核心需求，而不是事后才去补救的事情。

在实践中，这种需求表现为一些你可能已经熟悉的场景。客户注意到了服务中断，或者收到了报警，而根本原因可能有很多种：GPU 抛出硬件故障导致实例上的任务失败、可用区出现网络事件、或者你依赖的日志后端变慢并悄悄拖垮了你的应用程序。这些都不是稀罕事，而且从不挑时候。重要的是接下来会发生什么，以及其中有多少需要你来处理。

> “基础设施会发生故障、依赖项会变慢、网络会分区，这并非罕见的特例，而是大规模运行环境中的常态。”

在 Amazon ECS 上，我们的目标是为你处理大部分问题。故障恢复是我们在设计和构建 ECS 功能时的核心考量。这意味着，对于 ECS 可以自行处理的故障，你无需构建自己的检测循环和修复运维手册。对于那些正确的响应取决于你的工作负载的更模糊的情况，我们提供了相同的控制权，以便你可以亲自做出决策。

这建立在我们在[深入探讨 Amazon ECS 的弹性和可用性](https://aws.amazon.com/blogs/containers/a-deep-dive-into-resilience-and-availability-on-amazon-elastic-container-service/)一文中所涵盖的 ECS 背后的弹性原则之上：跨可用区的静态稳定性、预先扩展容量以及工作负载隔离。在这里，我们将重点关注建立在这些原则之上的恢复机制，以及你对每一项机制所拥有的控制权。

根据 AWS 责任共担模型，AWS 负责云的*安全性*（即运行工作负载的基础设施），而你负责云*中的*安全性（即应用程序抵御和从故障中恢复的设计方式）。这里描述的大多数工作都是 ECS 汲取“云本身”一侧的经验和模式（我们依靠它们来保持自身系统的健康），并将它们应用到“云中”一侧，通常作为简化[系统运维姿态](https://thenewstack.io/operations-shift-assistants-to-autonomous-multiagent-systems/)的合理内置默认值。

ECS 托管实例（Managed Instances）就是一个例子：ECS 承担了任务运行所在实例基础设施的弹性责任。它在不影响应用程序可用性的情况下应用操作系统、内核和 GPU 驱动程序补丁：它会逐步推开更新，在进行过程中观察故障，并在检测到问题时进行回滚。

AWS Fargate 遵循类似的模式：你也不需要在那里运营实例，因此糟糕的实例、糟糕的操作系统更新或驱动程序回归是由我们来检测和恢复的，而不是你需要围绕其设计的故障模式。从这里开始，我们将探讨 ECS 如何检测和恢复特定故障：不健康的实例、可用区事件、容器或任务失败以及降级的依赖项。

## 当任务底层的实例出现故障时

一些最具破坏性的故障始于任务底层，即它们运行所在的实例。当实例性能下降时，在其上调度的每个任务都面临风险，而且它在服务中停留的时间越长，故障蔓延的范围就越广。因此，你需要尽快检测出受损的实例并将其移出轮换，以控制爆炸半径。

例如，考虑在一组加速实例上运行的 GPU 推理工作负载。如果其中一个实例上的 GPU 开始抛出可纠正的 ECC 错误并升级为故障，那么该实例上的任务就会变慢或失败。或者，如果实例由于网络分区、热事件、Amazon EBS 卷性能下降等原因而受损，那么其任务就会[在原地继续运行，没有任何编排](https://thenewstack.io/when-genai-breaks-rigorous-orchestration-keeps-it-running/)在它们背后支撑，最终它们自己也会受损。自己处理此类 impairments（受损情况）意味着要构建额外的自动化来检测受损实例、排空其工作负载并最终循环利用它们，然后在大规模下可靠地维护和[运营该自动化](https://thenewstack.io/flowai-gives-agents-a-greater-role-in-infrastructure-automation/)。ECS 现在可以为你自动完成这一切。

> “为了直接检测它们，ECS 集成了 NVIDIA 的数据中心 GPU 管理器（DCGM）……并监视指示真实硬件故障的错误类别。”

在托管实例上，[GPU 健康监控和自动修复](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-ecs-gpu-auto-repair/)填补了一个很容易被忽视的空白。由于 GPU 是直通到实例的，其中发生的绝大多数 GPU 故障对于捕获普通硬件问题的 Amazon EC2 实例状态检查是不可见的，因此它们只能表现为无法解释的任务失败或延迟。为了直接检测它们，ECS 在实例上集成了 NVIDIA 的数据中心 GPU 管理器（DCGM），并监视指示真实硬件故障（而不是瞬时或非关键故障）的错误类别。

ECS 还监控数据平面实例更广泛的健康状况。这包括 EC2 状态检查以及实例上的数据平面组件，例如 ECS 智能体和容器运行时。ECS 智能体管理实例上的任务，并保持它们与 ECS 控制平面连接。当智能体无法到达[控制平面](https://thenewstack.io/agentic-ai-control-plane-production/)时，任务的本地状态可能会偏离控制平面中的期望状态，这种偏离会以容易被忽视的方式影响这些任务。智能体无法再发布指标、日志或健康状况，因此实例变成了一个黑盒。并且 ECS 无法再可靠地停止或替换其上的任务，因此对于服务而言，滞留在断开连接的实例上的任务会计入其限制并阻碍健康的替换。无论是 Fargate 还是托管实例，ECS 都会自动[检测智能体连接的持续丢失](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-ecs-agent-connectivity-health/)并将实例视为受损；能够自行恢复的短暂闪断不会触发循环利用。

在这两种情况下，ECS 运行相同的持续监控和修复循环，如图 1 所示。

***图 1：*** *ECS 持续监控实例健康状况，当发现受损实例时，会排空其任务、替换容量并注销该实例。*

GPU 自动修复和智能体连接修复在支持它们的平台上默认开启，无需额外费用。你也可以自己跟踪实例健康状况：ECS 通过 *DescribeContainerInstances* API 公开它，并为托管实例和 EC2 上的 ECS 发布实例健康状况更改事件到 Amazon EventBridge。当你将 ECS 在 EC2 上作为自己的容量运行时代，该事件最有用，你可以在其中消费它，以根据[容器实例健康状况](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/container-instance-health.html)触发你自己的 Auto Scaling 健康检查和实例替换工作流。

## 当可用区遭遇糟糕的一天

可用区为你提供了一个区域内的故障隔离，但只有在你的工作负载能够承受其中一个故障的损失时，这种隔离才有意义。考虑一个跨三个可用区运行的服务，其中一个可用区受损。两件坏事往往会同时发生。你幸存下来的任务不再均匀分布，因此恢复工作会将负载堆积到错误的可用区。任务之间的流量也可能会跨越可用区边界，从而扩大爆炸半径。手动重新平衡任务并将流量引导回健康路径既缓慢又容易出错，而这恰恰是你最承受不起的时候。

ECS 在决定在哪里运行你的工作负载时会考虑可用区的健康状况。当它检测到区域内出现麻烦迹象时（例如任务或实例启动失败率升高，或者来自其他 AWS 服务的健康事件），它会自动将新的任务和实例放置位置引导离开该区域，直到其恢复，而不是向已经苦苦挣扎的区域增加工作量。此外，当事件导致你的任务在各可用区之间分布不均时，[可用区重新平衡](https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-ecs-az-rebalancing-speeds-mean-time-recovery-event/)会纠正它。

ECS 持续监控服务的任务如何在各个可用区之间分布，当分布变得不均时，它会在任务数最少的可用区中启动任务，一旦这些任务健康运行，就会停止任务数最多的可用区中的任务，直到分布再次均匀（图 2）。对于符合条件的服务，这默认是开启的：那些首要放置策略是可用区散布（spread），或者未设置放置策略的服务。

最后，如果你的服务使用 Service Connect，你可以启用[区域感知路由（Zone-Aware Routing）](https://aws.amazon.com/about-aws/whats-new/2026/07/ecs-service-connect-zone-aware/)将每个调用路由到调用者自身可用区中的端点，这在正常操作期间将流量保持在区域内，并在区域降级时减少跨区域暴露。

![展示可用区重新平衡的图表](https://cdn.thenewstack.io/media/2026/10/aa30578a-image-1.png)





***图 2：*** *可用区重新平衡在区域事件发生后恢复均匀的任务分布，在停止现有任务之前启动新任务。*

对于 ECS 服务，ECS 默认将任务均匀分布在各个可用区中，因此重新平衡保持了均匀的分布。你可以通过预先扩展（pre-scaling）确保跨可用区有足够的容量余量来处理可用区中断：任务分布在至少三个可用区中，失去一个大约会消除三分之一的容量而不是一半，因此配置幸存的可用区来承载该负载。你可以参考[2023 年弹性和可用性深入探讨](https://aws.amazon.com/blogs/containers/a-deep-dive-into-resilience-and-availability-on-amazon-elastic-container-service/)了解这一点以及弹性 ECS 服务背后的其他设计原则。

## 崩溃的容器不应让你付出任务失效的代价

故障通常可以局限在原本健康的任务内部的单个容器中。当这种情况发生时，你宁愿保持任务运行并在原地修复它，也不愿将其拆除并重新调度。重新调度会丢弃大部分健康的工作，并向调度程序和你的其余舰队推送 churn（颠簸），因此原地恢复是破坏性较小的选择。

考虑一个运行主应用程序容器以及几个边车（sidecar，例如指标智能体和代理）的任务。如果一个边车崩溃了，你肯定不希望失去整个任务。通过[容器重启策略](https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-ecs-restart-containers-task-relaunch/)，ECS 在原地重启失败的容器而无需重新启动任务，因此任务在容器恢复的同时继续提供服务，并且你避免了不必要的重新调度。

> “重新调度会丢弃大部分健康的工作并向调度程序推送颠簸，因此原地恢复是破坏性较小的选择。”

你可以选择哪些容器符合资格，并列出不应重试的退出代码，以便因不可恢复原因失败的容器能够浮出水面，而不是在循环中重启。当容量已经处于压力之下时（例如在可用区事件期间），这一点最重要：通过在原地重启容器来保持任务存活，避免了放弃随后必须重建的容量。

你在任务启动时也会看到同样的原则。在托管实例上，ECS 仍然会尝试拉取每个镜像，以便它获取对标签的任何更新，但如果该镜像拉取失败且该镜像已经从较早的任务缓存在实例上，它会回退到缓存的副本并无论如何启动任务，而不是因为瞬时注册表或网络问题而使其失败。在 EC2 上的 ECS 上，你可以通过 *ECS\_IMAGE\_PULL\_BEHAVIOR* 智能体设置选择类似的行为。无论哪种方式，你无法控制的依赖项中的瞬时故障、受限的注册表或网络闪断，都不会让你损失一个本来可以从实例上已有的副本启动的任务。

## 更安全的默认值，为你挑选

这篇文章的大部分内容都是关于 ECS 从基础设施故障中恢复的。当它依赖的某些东西失败时，你的应用程序本身的行为通常是责任共担模型中你的那一侧：云*中的*弹性。但在少数情况下，我们发现某个默认值经常与客户的意愿背道而驰，以至于 ECS 代表你对其进行了更改，将更安全的选项目移动到平台中，这样你就可以继承它，而不必去发现和配置它。

日志记录是最明显的例子。ECS 最初仅支持阻塞式日志交付：当日志记录缓慢、受到限制或不可用时，写入 stdout 和 stderr 会阻塞，如果应用程序记录日志的速度快于其交付速度，则该背压可能会使应用程序停滞或崩溃。日志记录目标的规模化中断可能会连同应用程序的可用性一起拉垮，尽管日志记录并不在应用程序的关键路径上。我们后来添加了非阻塞交付来避免这种情况，丢弃无法交付的日志而不是阻塞容器，但它仍然是选择加入的（opt-in），并且大多数客户从未启用它。

因此，ECS 仔细地更改了默认值。由于少数工作负载确实依赖于阻塞模式，我们分阶段而不是一夜之间进行了切换：我们首先发布了账户设置，以便任何需要阻塞的人都可以选择加入，在更改之前提前发出了通知，然后才更改了默认值，以便需要保证交付的客户有时间保留它。

> “实际上，当其日志记录依赖项性能下降时，工作负载现在会以开放式失败（fails open）的方式运行：它继续服务并丢弃无法交付的日志，而不是通过阻塞直到后端恢复来以封闭式失败。”

非阻塞现在是默认的日志驱动程序模式，适用于现有和新服务，无需采取任何操作，因此日志记录中断默认不再会使你的应用程序停滞。实际上，当其日志记录依赖项性能下降时，工作负载现在会以开放式失败（fails open）的方式运行：它继续服务并丢弃无法交付的日志，而不是通过后端恢复前的阻塞来以封闭式失败（fails closed）。

这是一个真正的持久性与可用性的权衡，现在的默认值偏向于可用性，这对于大多数工作负载来说是正确的选择。出于计费、审计或监管原因必须保证交付的客户，仍然可以通过[日志驱动程序账户设置](https://aws.amazon.com/about-aws/whats-new/2025/04/amazon-ecs-set-default-log-driver-blocking-mode/)或每个任务定义选择阻塞模式。

这并非日志记录所独有。这与默认跨可用区散布服务任务、在排空和部署期间在停止现有任务之前启动替换任务，以及在滚动部署期间[从它已经属于的版本替换失败的任务，而不是可能仍然无法启动的新版本](https://aws.amazon.com/about-aws/whats-new/2025/11/amazon-ecs-service-availability-rolling-deployments/)背后的推理是相同的。如果更好的默认值在不夺走控制权的情况下对大多数客户最有帮助，我们会将其设为默认值，并留给你覆盖它的选项。

## 自己动手测试

ECS 已与 [AWS Fault Injection Service (FIS)](https://docs.aws.amazon.com/fis/latest/userguide/ecs-task-actions.html) 集成，这使你可以测试应用程序对各种故障条件的弹性。其 ECS 任务操作允许你对运行中的任务运行受控的故障实验，从停止任务到注入资源和网络故障，因此你可以在真实的事件考验它们之前，了解你的工作负载和恢复设置的表现。

特别是针对网络故障，我们在[所有 ECS 启动类型（包括 AWS Fargate）上启用了网络故障注入](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-ecs-network-fault-injection-experiments-fargate/)。你可以向你的任务注入延迟、丢包或黑洞，并确认你的超时、重试和回退在依赖项变慢或无法访问时的表现符合预期。带有 [FIS 项目的 ECS Fargate 上的示例网络故障](https://github.com/aws-samples/sample-network-faults-on-ECS-Fargate-with-FIS)是一个很好的起点。

这篇文章中每个故障的方法都是相同的，无论是故障实例、受损区域、崩溃的容器还是降级的依赖项：ECS 承担了检测和从故障中恢复的无差异繁重工作，并且在正确的响应取决于你的工作负载的地方，它让你拥有决定权的控制权。你继承了安全的默认值，并且你保留了覆盖权。

ECS 旨在让你更容易地为故障进行设计。通过处理恢复的常规、机械部分，它解放了你的精力，使其投入到特定于你的应用程序的弹性中，并且它与 FIS 的集成使你能够将该弹性投入测试。将本文中的默认值和控制视为起点，根据你的工作负载实际需要进行调整，并告诉我们在哪里默认值应该更聪明。

有关这些机制背后的原理，请参阅 [2023 年弹性和可用性深入探讨](https://aws.amazon.com/blogs/containers/a-deep-dive-into-resilience-and-availability-on-amazon-elastic-container-service/)。要告诉我们接下来要构建什么，请参阅 [GitHub 上的 AWS 容器路线图](https://github.com/aws/containers-roadmap)。
