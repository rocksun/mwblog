**OpenAI 在一篇新的工程博客中详细介绍了** [GPT-5.6](https://thenewstack.io/openai-gpt-56-live/) 模型系列如何在其技术栈中平衡性能与成本。其中最重要的声明是一项基准测试结果：公司报告称，其旗舰模型 GPT-5.6 Sol 在最大推理模式下，在 [Artificial Analysis](https://artificialanalysis.ai/) 编码智能体指数（Coding Agent Index）上超越了 Anthropic 的 Claude Fable 5，且输出标记（tokens）消耗减少了 54%。

对于开发者而言，最重要的是 OpenAI 如何得出这些基准测试结果，以及 GPT-5.6 Sol 在优化现有服务基础设施中所扮演的角色。

该系列横跨三个价格区间的模型。除了 Sol 之外，还有 Terra（在智能基准测试中表现与 GPT-5.5 持平，但价格减半）和 Luna（速度最快且最经济，价格比 Sol 低 80%）。

> 这些效率提升源于四个层面的优化，涵盖了模型、推理、API 栈以及 [Codex](https://openai.com/codex/) 和 [ChatGPT Work](https://chatgpt.com/work/) 背后的智能体框架。

根据 *The New Stack* 在发布前审阅的文章，这些效率提升源于四个层面的优化：模型、推理、API 栈以及 Codex 和 ChatGPT Work 背后的智能体框架。文章中的架构图将其划分为三个平面：本地框架、CPU 绑定的 API 编排以及 GPU 绑定的模型推理。

## 一个重写自身服务代码的模型

效率提升工作始于训练阶段。OpenAI 表示，GPT-5.6 的训练旨在实现每个标记更高的工作产出，同时针对任务成功率和效率进行优化，使模型在执行任务时能够采取更直接的路径。

借助 Codex，GPT-5.6 Sol 自主重写并优化了 OpenAI 的生产内核（kernels），即执行构成模型的数学运算的核心代码。OpenAI 表示，这部分得益于 GPT-5.6 被训练用于编写和改进 [Triton](https://github.com/triton-lang/triton) 和 [Gluon](https://github.com/triton-lang/triton/tree/main/python/tutorials/gluon) 中的内核。两者均为 OpenAI 维护的开源 GPU 编程语言。这些努力，加上模型本身带来的更广泛的内核改进，使端到端服务成本降低了 20%。

当模型重写其运行代码时，正确性是一个显而易见的担忧。为解决此问题，OpenAI 报告称其在验证工具方面进行了大量投入。其中包括开源的浮点消毒器（Floating-Point Sanitizer, FpSan），它会在 GPT-5.6 Sol 产生的内核投入生产前进行验证。

该模型通过推测解码（speculative decoding）更进一步，这是一种较小的草稿模型提出多个标记，由主模型并行验证的技术。这种方法对于理解现代 CPU 如何在分支前推测性执行指令的人来说会感到熟悉。被接受的提议可以通过主模型的一次传递产生多个输出标记，从而减少主模型原本需要执行的昂贵的顺序计算。

GPT-5.6 Sol 在 Codex 中通过设计和运行数百次架构实验改进了自己的草稿模型，并对大小、结构和功能进行了测试。该模型还启动并监控了推测训练过程。当硬件故障或训练不稳定时，它会自动进行干预。OpenAI 报告称，由此产生的改进使标记生成效率提升了 15% 以上。

## 在相同的 GPU 上处理更多标记

OpenAI 将其推理工作围绕一个单一目标展开——在保持用户期望的智能、延迟、可用性和可靠性的同时，用相同的硬件服务更多的标记。在需求增长快于容量的计算受限市场中，这一目标影响着服务路径中的每一个设计决策。

负载均衡在三个不同的层级运行。在全球范围内，请求根据地理位置、可用容量和加速器类型进行路由。在集群内，工作根据负载、上下文长度和缓存可用性分布在模型实例中。在每个实例内，工作被分配给加速器、模型的专家和计算核心。Codex 中的 GPT-5.6 Sol 帮助 OpenAI 分析生产流量并识别以前被忽视的不平衡来源。同样的循环测试新的路由策略，并帮助工程师不断调整启发式算法。OpenAI 表示，仅这些负载均衡的改进就大幅降低了其模型服务成本。

键值（KV）缓存也得到了同样的对待。在处理未缓存的输入标记时，模型在单次计算密集型传递中构建 KV 缓存，然后在生成过程中反复读取和扩展它。最佳服务配置在很大程度上取决于提示词长度、批次大小和缓存命中率。它涵盖了批处理、分片和缓存管理，而这些配置空间此前太大，无法进行系统性调优。借助 Codex 中的 GPT-5.6 Sol，OpenAI 分析了生产工作负载并生成了候选配置。公司称，这使得特定于工作负载的优化达到了广泛的启发式算法此前无法企及的实用水平。

## 只处理变化的部分

API 团队专注于模型调用周围发生的一切。在提交提示词后，API 栈接收请求、加载上下文并验证输入。接下来运行安全检查，并将文本转换为推理所需的标记。OpenAI 通过首个标记时间（TTFT）、标记间时间（TBT）和端到端时间（E2E）来衡量这种开销。

标记化是一种 O(n) 操作，因此较长的提示词需要更长的处理时间。Codex 过去会在每次工具调用后发送完整的对话上下文。这意味着即便每次请求中只有少量上下文是新的，也需要为每次周转支付数十次重复标记化的费用。OpenAI 通过 WebSocket 集成解决了这个问题，将标记化状态提升到服务器端。第一次调用渲染并标记化完整提示词，后续调用仅发送包含对话引用的新输入，使操作接近 O(1)。该模式类似于仅重新编译已更改文件而不是整个项目的增量构建系统。

这些节省在工具密集的任务流中是累加的，因为每个工具结果都会触发另一轮 API 往返。对于包含 20 次或更多工具调用的发布，OpenAI 报告端到端执行速度提升了约 40%。

事实证明，硬件与协议设计同样重要。OpenAI 的所有基础设施都在 [Kubernetes](https://kubernetes.io/) 上运行。该公司发现，具有相同实例类型的节点通常承载着不同的 CPU 代次，许多仍在运行过时的处理器。在其测量中，较旧的处理器执行相同工作消耗了大约两倍的 CPU 资源。将流量重新加权到更新的处理器上，使 TTFT 提高了约 20%，现在 CPU 代次已成为容量规划的一部分。

OpenAI 为应用层开销列出了四种处理方式：删除它、将其与有用的工作重叠运行、在更快的硬件上运行，或使代码消耗更少的 CPU 周期。其 asyncio 的更改将工作从关键路径中移出，而较新的硬件和 Rust 实现使剩余的工作更快、更可预测。

## 仅追加的框架

智能体框架是一个基于 Rust 的编排层，用于连接模型、工具和用户的环境。在单次周转中，Codex 可能需要检查源代码、搜索部署历史记录并阅读事件报告。编辑文件和运行测试每一步都会增加新的请求。由于一个任务可能需要 30 个模型请求，每个请求增加一秒钟的时间会迅速累积。

上下文膨胀是该框架的首要目标。随着智能体获得更多工具、技能、插件和对话历史的访问权限，上下文窗口不断扩大。这种增长增加了成本、分散了模型的注意力，并导致不必要的推理。该框架通过延迟发现（deferred discovery）来对抗这种现象，仅在需要时才呈现集成、自定义 [模型上下文协议](https://thenewstack.io/model-context-protocol-a-primer-for-the-developers/) (MCP) 工具、技能和插件。除非模型请求不同的限制，否则工具输出默认为 10,000 个标记。

提示词缓存驱动了第二个设计选择。智能体循环会在一次周转中多次重新发送相同的指令、工具定义和先前的结果。因此，该框架将所有模型可见的历史视为“仅追加”（append-only），新的消息和工具结果被添加在末尾，而不是插入到更早的上下文中。工具以确定性顺序呈现，运行时设置（如审批策略）在执行期间应用，而不是嵌入在工具定义中。OpenAI 将 Codex 和 ChatGPT Work 中实现的高提示词缓存命中率归功于此设计。

构建内部智能体的平台团队可以采用这些选择中的每一个，而无需达到 OpenAI 的规模。仅追加上下文、确定性工具排序和限制工具输出直接打击了标记消耗。这使得它们成为文章中最具可移植性的经验，适用于那些眼睁睁看着推理账单随每个新智能体部署而增长的企业。

## 关键要点

总而言之，OpenAI 将 GPT-5.6 的效率提升描述为多年累积改进的结果。它们涵盖了研究、推理、API 栈和智能体框架。公司表示，模型在实现许多这些改进中所扮演的角色使其对优化速度的加快感到乐观。内核工作被指明为持续投资的领域。

该文章将效率与原始智能一样，定位于前沿实验室目前竞争的轴心。对 Claude Fable 5 声称的 54% 输出标记优势显示了 OpenAI 打算如何进行这场战斗。这篇工程博客令人信服地指出，软件优化正在成为与硬件改进并行的重要杠杆，用于降低服务前沿模型的成本。这些数字仍然是 OpenAI 自己的生产测量结果。展示出的自主性是在 Codex 内部运作的，且有工程师参与其中。无论如何，开发者和企业都能从中受益，因为这些底层改进正以更低的价格和更强的能力，沿着成本-智能曲线传导给他们。
