Model Context Protocol (MCP) 即将迎来重大更新，通过移除会话机制和初始化握手，将协议转向无状态化，以降低分布式系统的开发复杂度，并简化基础设施运维。虽然这要求开发者重新处理应用状态，但通过显式句柄和扩展机制，显著提升了协议的健壮性与可扩展性。

> 译自：[MCP’s biggest update removes the machinery many servers were built around](https://thenewstack.io/mcp-release-candidate-rewrite/)
> 
> 作者：Janakiram MSV

Model Context Protocol (MCP) 自发布以来规模最大的一次更新即将到来。首席维护者在 5 月 21 日[冻结](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)了发布候选版本，最终规范定于 7 月 28 日发布。

乍看之下，[变更日志](https://modelcontextprotocol.io/specification/draft/changelog)的内容非常激进：会话和初始化握手将被移除，三个核心功能将被废弃。但仔细观察就会发现，这次修订的真正目的是通过将熟悉的任务交回给既有的基础设施，从而简化 MCP。对于运维人员而言，这解决了一个长期以来的痛点：运行一个远程 MCP 服务器不应该需要普通无状态服务所不需要的专用机械装置。

## MCP 向其用户收取的“税”

要理解这些移除操作，必须审视 MCP 最初设计与其实际部署之间的差距。它最早且最广为人知的形式是一个桌面应用程序，通过标准输入和输出与本地进程通信，这种情况下启动握手在长连接上执行的开销很小。

> 一个发布 MCP 服务器的团队，实际上是在为协议自身带来的分布式系统问题付费。

随着越来越多的服务器转向远程、水平扩展的部署，这些会话成了问题。服务器会生成一个 `Mcp-Session-Id`，将客户端绑定到特定的实例上。为了扩展，这通常需要会话亲和性、外部共享会话存储或能够解析 JSON 体以确定路由的 MCP 感知网关逻辑。一个发布 MCP 服务器的团队，实际上是在为协议自身带来的分布式系统问题付费。

能力协商增加了第二笔成本。由于能力是在连接时一次性交换的，列表结果可能随连接而异，这使得跨会话或在共享中介中的缓存难以进行逻辑推理。

## 维护者优化的方向

六项规范增强提案汇聚为一个单一目标：使每个请求都能独立存在。协议版本和客户端能力现在随每次调用包含在 `_meta` 中。客户端也被要求在此包含其身份信息，而一个新的 `server/discover` 方法使得服务器能力可以在预先或需要时被独立查询。发布说明称此为“按需付费的复杂性”（pay-as-you-go complexity）基本原则：核心保持精简，状态仅在功能真正需要时出现。

> 发布说明称此为“按需付费的复杂性”基本原则，核心保持精简，状态仅在功能真正需要时出现。

显而易见的异议是，许多服务器确实需要“记忆”某些东西。一个主要的答案是显式句柄（explicit handle），这是过去二十年里每个基于 HTTP 构建的购物车所使用的模式。工具生成一个 `basket_id`，在结果中返回它，模型在下一次调用时将其作为普通参数传回。账户状态、资源 URI、任务句柄和普通数据库标识符对于那些不走该路径的内容依然可用。

让句柄不仅仅是一个权宜之计的原因在于，它对模型是可见的。隐藏在传输元数据中的会话状态是模型永远无法推理的，而工具结果中的句柄可以跨工具组合，并在工作流步骤之间传递。这种权衡在于它也会出现在提示词、脚本和日志中，因此请将其绑定到经过身份验证的主体，并在每次使用时验证权限，而不是将其视为授权证明。

## 开发者实际得到了什么

对于服务器作者来说，远程 MCP 服务器现在可以像传统的无状态 HTTP 服务一样运行。三个副本位于轮询负载均衡之后，无需亲和性配置，也无需运行或恢复协议会话存储。滚动部署不再会导致会话失效或使客户端挂在已移除的实例上，尽管它们仍可能中断正在进行的请求和订阅流，且由于可恢复性已不存在，客户端会在新的请求 ID 下重新发起该工作。

对于平台团队来说，必需的 `Mcp-Method` 标头，加上用于命名工具、资源和提示词操作的 `Mcp-Name`，意味着网关可以在不检查请求体的情况下按操作进行速率限制或授权。这仅在[传输验证规则](https://modelcontextprotocol.io/specification/draft/basic/transports/streamable-http)下成立，即后端拒绝任何与主体不一致的标头，而强制执行策略的中介会拒绝无法保证检查的协议版本。如果跳过这一点，良性标头可能会掩盖底层的其他调用。

缓存的变化值得比目前更多的关注。受影响的列表和读取结果现在必须包含 `ttlMs` 和 `cacheScope`，仿照 HTTP `Cache-Control`，以便客户端可以在指定的时间间隔内持有目录，而不是重新获取。草案将 `ttlMs` 视为新鲜度提示，而非数据依然有效的时间承诺。服务器也被要求按确定性顺序返回工具，草案将其与更好的提示词缓存命中率挂钩，而在大规模场景下，这意味着在提供商对提示词缓存定价的地方可以降低延迟或 Token 成本。

一个警告需要在这里说明而不是在脚注中。协议层的无状态性换取的是可路由性，而非确定性。两个副本将在不咨询协议状态的情况下接受相同的请求，如果它们运行不同的版本或读取不同的下游数据，它们仍然会返回不同的答案。

## 为什么要关心扩展

生态系统的论点比任何单一功能都更有力。[扩展](https://modelcontextprotocol.io/extensions/overview)现在有了命名空间标识符，官方标识符位于 `io.modelcontextprotocol` 下，第三方标识符位于作者拥有的反向域名下，此外还有它们自己的 `ext-` 存储库和发布节奏。任何写过 Kubernetes 自定义资源定义的人都会认出这种形态，即能力在核心发布轨道之外交付并成熟。

任务（Tasks）证明了这一点的重要性。它作为实验性核心功能于 2025-11-25 发布，实际生产使用暴露了设计问题，因此它已被重新设计为扩展。将其从核心中移出本身就是一项破坏性的规范变更，但下一次迭代则不会，因为扩展通过能力标志或设置级版本控制进行演进，仅在不可避免地发生破坏时才使用新的标识符。MCP Apps 已经作为扩展提供，现在位于一个正式治理的协商框架内，而不是一个不存在的流程中。

## 废弃政策带来了什么

[功能生命周期政策](https://modelcontextprotocol.io/community/feature-lifecycle)为每个功能赋予了活跃（Active）、废弃（Deprecated）和移除（Removed）状态，从功能首次被标记为“废弃”的修订版开始，最少有 12 个月的窗口期。只有在存在已发布公告或记录在案的利用风险的情况下，该期限才能缩短，即便如此，90 天也是硬性的最低限制。公共注册表列出了即将退出及退出的时间，且标准轨道提案在匹配的场景进入合规套件之前无法达到最终状态。

对于开发者来说，这读起来像是日常维护。但对于任何必须向平台审查委员会证明 MCP 集成合理性的人来说，书面的废弃保证比发布版中的任何能力都更有价值。

## 代价是什么

这一切都不是免费的。任何基于实验性 Tasks API 构建的人都需要迁移到新的生命周期，任何向客户端发起自身请求的服务器都将转向[多轮往返请求](https://modelcontextprotocol.io/specification/draft/basic/patterns/mrtr)模式，即服务器返回它仍然需要的内容，客户端用答案重试。该服务器还必须验证任何可以影响授权或业务逻辑的回显 `requestState`，且一次性工作流仍然需要它们自己的重放跟踪。

废弃是迁移指南而非直接替换，Sampling 是最尖锐的案例。使用客户端中介 Sampling 的服务器不需要提供商凭据，通常也不承担模型账单，而直接调用提供商 API 会使其成为凭据持有者、计费方和用户数据的独立处理方。日志记录也讲述了类似的故事，因为 `stderr` 和 OpenTelemetry 满足了运维人员的“可观测性”，而没有给远程客户端提供它过去接收的那种结构化日志流。

> 协议不再管理状态，但这并不意味着状态消失了。

应用程序状态也不会消失。句柄、购物车、任务记录和幂等性键仍然需要生存的地方。协议不再管理状态，但这并不意味着状态消失了。

## 前方之路

在一个协议生命周期不到两年时移除基础抽象是一项经过计算的风险，维护者通过十周的验证窗口以及适用于 Python、TypeScript、Go 和 C# 的 Beta 版 SDK 合理地规避了风险。

他们还定义了一种迁移路径，客户端首先用 `server/discover` 进行探测，仅在遇到仅支持旧版服务器时才退回到 `initialize`。这是一个带有协商路径的线路级中断，而不是生态系统的“标志日”。

发布候选阶段是盘点会话依赖项并进行测试的最佳时机，生产部署将随核准和稳定版 SDK 发布而进行。从个人服务器作者到平台团队，再到围绕它构建网关和注册表的供应商，回报是一个在行业已经知道如何操作的基础设施上配合得更自然的协议层。
