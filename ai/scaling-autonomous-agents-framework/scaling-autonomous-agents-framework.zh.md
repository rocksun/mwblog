![Dark, high-speed water currents in motion blur, representing data throughput and scaling pressure in software systems.](https://cdn.thenewstack.io/media/2026/11/9d0da71b-engin-akyurt-faixbupqyxy-unsplash-1024x576.jpg)

**QA团队在发布复杂产品时，会不间断地产生测试失败报告。** 每一个失败都需要一个带有步骤、截图、重现率和回归标签的缺陷工单。这个人工流程每次失败需要耗费 10-15 分钟。如果将团队每周 30 多次的失败乘以这个时间，你就会发现整整一个工程日的时间都被消耗在了本该自动化的文档工作上。

我构建了一个系统来彻底消除这种状况。它不是仪表盘，也不是通知机器人。而是一个[智能体](https://thenewstack.io/ai-agents-are-finally-starting-to-revolutionize-the-software-development-lifecycle/)，它能够观察测试结果并做出判断——这是一个新bug、重复bug还是回归bug？并在无需人工干预的情况下采取行动。它能提交结构化bug、附上截图、计算重现率、跨版本检测回归，并通知相关人员。团队只需标记失败（FAIL）即可继续工作。

![Flow chart illustrating the serverless-to-container decision framework](https://cdn.thenewstack.io/media/2026/11/78fdccff-image-881x1024.png)

目前该系统运行在 Lambda 上。它在一个团队中运行得非常完美。但当其他团队也想要它时会发生什么？当你需要为 10 个、50 个或 100 个团队提供服务时会发生什么？这就是架构决策变得有趣的地方——不是因为 Lambda 失败了，而是因为工作负载的特征发生了变化，使得另一种工具成为了更合适的选择。

## 我构建了什么（以及它为什么行之有效）

该架构非常优雅：EventBridge 规则每 15 分钟触发一次 Lambda 函数。该函数轮询测试管理 API，通过决策引擎处理失败情况（通过 DynamoDB 进行去重检查，针对之前的构建结果进行回归检测），并通过 JIRA API 提交 bug。总基础设施成本：每月不到 5 美元。

[Lambda 之所以是](https://thenewstack.io/mastering-aws-lambda-optimize-cost-and-performance/)这里的正确选择，原因有三：

1. **零运维开销：** 无服务器、无扩缩容配置、无补丁管理。部署后即可不管。
2. **成本与使用量成正比：** 一个团队每月产生约 200 次调用。按照 Lambda 的定价，这实际上是免费的。
3. **快速迭代：** 决策引擎在第一个月经历了 20 多次修改。Lambda 的部署模型让我在几秒钟内就能发布更改。

在部署后的几周内，该系统提交的更完整、更一致的bug比团队以前手动产生的任何bug都要好。零漏报失败。回归问题在几分钟内被捕获，而不是几天。发给 QA 的状态中断降为零，因为任何人都可以直接通过 Slack 查询系统。每周节省 8-10 小时。

其他团队注意到了这一点。“我们能用那个吗？”是一个反复出现的问题。答案似乎很简单——为每个团队部署另一个实例。但在规模化之后，工作负载的特征会发生变化，从而改变架构决策。

## 扩缩容决策

Lambda 非常好地处理了单租户智能体工作负载。在多租户规模下面临的挑战不是 Lambda 做不到，而是工作负载特征发生了变化：

**从无状态事件到长生命周期上下文：** 单个团队的轮询周期在几秒钟内完成。但跨项目关联——“这是我们在三个团队中看到的相同失败模式吗？”需要单次分析数百个结果及其关系。这是一个截然不同的计算配置文件。

**从孤立调用到共享资源争用：** 当 50 个函数在同一个 EventBridge 计划上触发时，它们会同时访问 TestRail 和 JIRA API。你需要集中的速率限制、连接池和背压——这些模式受益于持久的共享基础设施。

**从单团队到多租户隔离：** 每个团队都需要有保障的资源、网络边界和作用域凭证。隔离模型变得与计算模型同等重要.

Lambda 最近推出的功能单独解决了许多此类问题——托管实例解决了连接持久性，Durable Functions 打破了长工作流的 15 分钟上限，而租户隔离提供了本地租户边界。对于许多多租户工作负载，这些功能大大缩小了差距。

但对于这个特定的工作负载——需要持久连接、跨租户分析、GPU 推理和命名空间级隔离同时进行的长时间运行的智能体——决策框架指向了具有类似无服务器操作的容器原生执行模型。这就是[EKS Auto Mode 的契合点。](https://thenewstack.io/how-amazon-eks-auto-mode-simplifies-kubernetes-cluster-management-part-1/)

## 决策框架

这促使我构建了一个简单的决策准则——不是 Lambda 与容器的对抗，而是你的工作负载实际表现出哪些特征？

|  |  |  |
| --- | --- | --- |
| **工作负载特征** | **Lambda（+ 托管实例，Durable Functions）** | **Auto Mode** |
| 事件驱动、生命周期短 | 最佳 | 过度设计 |
| 单团队、低复杂度 | 最佳 | 不必要 |
| 具有隔离需求的的多租户 | 可能（租户隔离） | 原生（命名空间、RBAC、NetworkPolicies） |
| 长期运行且具持久状态 | 可能（Durable Functions） | 原生（Pods、持久连接） |
| 需要共享内存的跨租户分析 | 复杂（自定义编排） | 自然（共享服务命名空间） |
| GPU 突发推理 | 可能（Lambda GPU - 如果可用） | 原生（GPU NodePools、缩容至零） |
| 集中式速率限制 + 连接池 | 自定义构建（SQS + Step Functions） | 共享平台服务 |

> “我的工作负载的决定性因素：我需要右侧列的所有特征同时具备。它们组合在一起，在容器原生环境中能够更自然地构建。”

**我的工作负载的决定性因素：** 我需要右侧列的所有特征同时具备。跨团队模式检测需要共享的分析上下文。基于机器学习的bug分类需要突发 GPU。每个团队的隔离需要命名空间级别的边界。集中式速率限制需要一个持久的共享服务。这些问题在 Lambda 中都可以单独解决。但它们组合在一起时，在容器原生环境中能够更自然地构建。

## 规模化带来的突破：跨团队智能

在多租户规模下出现的最有趣的架构能力不是按团队自动化——而是跨团队模式检测。这正是使扩缩容变得有价值的原因。

## 跨团队失败关联

当 50 个团队独立运行他们的测试套件时，失败显得是孤立的。但跨团队会出现任何单个团队都无法看到的模式：

* 三个团队在同一个固件构建上报告导航失败 → 系统性回归，而不是三个独立的bug
* 测试失败与无关服务的部署时间相关联 → 基础设施问题，而不是产品bug
* 具有不同测试套件的团队之间存在相同的错误特征 → 共享依赖项失败

这需要一个能够同时保持所有团队上下文的分析引擎——比较指纹、关联时间戳并识别共同的根本原因。这是一个持久的、长时间运行的工作负载，可以访问跨租户状态。它作为平台命名空间中的共享服务自然运行，消耗来自所有租户智能体的事件。

## 基于机器学习的bug分类

一旦你有足够的历史数据（跨团队提交的数千个bug），模式就变得可分类：

* 根据失败特征自动将bug分配给正确的组件所有者（崩溃与降级行为与外观）
* 根据失败特征预测严重性
* 建议相关bug进行调查（“这看起来与 PROJ-4521 具有相同的根本原因”）
* 在异常故障率变成事故规模之前检测它们

这种推理工作负载是突发性的——当bug到来时你需要 GPU，而不是 24/7 全天候需要。闲置时缩容至零且仅在推理期间配置 g5 实例的 GPU NodePool 可以使成本与实际使用量保持成比例。提交bug的同一个 Pod 可以同步调用分类服务，获得组件分配，并将其包含在工单中——所有这些都在同一个请求路径中。

## 通过 Slack 查询知识库

智能体不仅仅是一个自动化工具——它成为了组织可查询的 QA 状态。通过 Slack，任何人都可以询问：

* “本周所有团队的导航失败率是多少？”
* “向我展示在构建 2.4.1 中引入的回归问题”
* “现在哪个团队看到的 P0 bug 最多？”

这把智能体从任务自动化工具转变为智能层。这些答案需要跨团队状态聚合、趋势计算和自然语言解释，所有这些都由随时间累积的持久、索引状态提供服务。

## EKS Auto Mode 为该架构带来了什么

EKS Auto Mode 在 re:Invent 2024 上发布，带有一个特定的承诺：无需管理节点的完整 Kubernetes。对于多租户智能体平台，这意味着：

* **当 Pod 需要时节点就会出现。** 使用自动归档 Pod 部署租户命名空间。基于 Karpenter 的调度程序会在几秒钟内配置文件节点。当 Pod 被删除（租户离职）时，节点会自动合并或终止。你永远不需要考虑 EC2 实例。
* **安全性不是你的配置负担。** 节点运行不可变的 Bottlerocket AMI —— 只读根文件系统、强制 SELinux、无 SSH 访问。节点每 21 天自动轮换一次。对于长时间运行的智能体 Pod 来说，这意味着大约每三周进行一次平稳排空。最多错过一次轮询周期。
* **扩缩容对需求做出反应。** 在智能体在轮询之间闲置的非工作时间，Auto Mode 将工作负载合并到更少的节点上。你只需为使用的部分付费。
* **GPU 工作负载无缝嵌入，无需架构更改。** 为机器学习分类服务定义 GPU NodePool。EKS Auto Mode 仅在调度推理 Pod 时配置 g5 实例，并在完成后将其终止。

## 多租户架构

在规模化运行下，系统将具有三层：

1. **共享平台服务：** 一个速率限制器，可防止任何单个团队耗费外部 API 配额，一个连接池管理器，维护到 TestRail 和 JIRA 的持久会话，以及一个收集所有租户指标的 Prometheus 实例。
2. **每租户智能体命名空间：** 每个团队获得一个包含其自动归档 Pod、报告 Pod 和 Slack 机器人 Pod 的隔离命名空间。ResourceQuotas 保证资源。NetworkPolicies 强制团队 A 的 Pod 不能与团队 B 的 Pod 通信。每个命名 Service Account 通过 IRSA 假设租户范围的 IAM 角色。
3. **共享机器学习推理命名空间：** 运行所有租户都可以调用的分类模型的启用 GPU 的 Pod。该命名空间拥有自己的 NodePool，在没有推理发生时缩容至零。

智能体代码将基本上保持今天在 Lambda 上运行的 Python 代码不变——核心决策引擎（观察、去重、决策、行动）没有改变。改变的是执行模型：智能体不是按事件调用和销毁，而是作为具有持久连接、优雅关闭处理和内部调度的长寿异步循环运行。

## AWS 产品组合协同工作

正确的框架不是“将 Lambda 迁移到 EKS”。而是“在每个服务适合的地方使用它”：

* **Lambda** 保持为入口点。新团队从这里开始。每月 5 美元的单团队自动化，零运维。事件驱动触发器、快速迭代、按调用付费的经济学。
* **Lambda + Durable Functions** 处理需要更长分析窗口或多步骤编排而又不想离开 Serverless 模型的团队。
* **EKS Auto Mode** 在你需要持久的多租户服务、跨团队智能、GPU 推理和命名空间级隔离协同工作时为平台层提供服务。
* **DynamoDB** 在所有层之间持久化状态——去重记录、bug 历史、趋势数据。
* **EventBridge** 编排事件，无论消费者是 Lambda 函数还是 Kubernetes Pod。

需要 30 分钟分析窗口或多步骤工作流（轮询 → 关联 → 提交 → 通知 → 等待响应 → 更新）的团队可以受益于 Durable Functions，而无需离开 Serverless。你将一直留在这里，直到你需要跨团队共享状态或 GPU —— 这是评估 Auto Mode 的信号。

> “Lambda 验证了该模式。EKS Auto Mode 在规模化下将其付诸实践。它们是旅程中的不同阶段，而不是竞争对手。”

随着组织需求的成熟，智能向上移动到堆栈中。Lambda 验证了该模式。EKS Auto Mode 在规模化下将其付诸实践。它们是旅程中的不同阶段，而不是竞争对手。

## 核心要点

* **从 Serverless 开始：** Lambda 让你能够以零运维成本验证智能体模式。每月 5 美元的价位消除了证明概念有效的所有摩擦。不要为没有的规模进行过早优化。
* **从第一天起就为可移植性进行设计：** 将你的 Lambda 函数结构化为具有外部将其状态的纯决策引擎。将其容器化意味着将其包装在异步循环中并添加健康检查端点。如果你将 Lambda 函数构建为独立的决策引擎，而不是与调用模型紧密耦合，那么无论何时你需要进行过渡，都只需一天的练习。
* **决策触发器不是规模——而是工作负载特征：** 不要因为你达到了 50 个团队而移动。当你需要受益于持久的共享基础设施的功能时移动：跨团队关联、集中式速率限制、GPU 推理、流式连接。
* **多租户是一个隔离问题，而不是计算问题：** Lambda（租户隔离）和 Kubernetes（命名空间）都解决了这个问题。根据你的工作负载除了隔离之外还需要哪些其他特征进行选择。
* **EKS Auto Mode 弥合了运维鸿沟：** 在 Auto Mode 之前，选择 EKS 意味着接受节点管理开销。Auto Mode 消除了这种权衡。你获得了具备类似 Serverless 操作的容器原生执行。

## 成本计算

今天 Lambda 上的单个团队：每月 3-5 美元。每周节省 8-10 小时。67 倍投资回报率。EKS Auto Mode 上的 50 个团队总共将花费约 200-250 美元/月——每个团队每月约 4-5 美元。与 Lambda 相同的每个团队经济学，但具有命名空间隔离、持久连接、GPU 就绪基础设施、集中式可观测性和内置的组织治理。

每个团队的成本几乎没有变化。变化的是你为此得到了什么！

## 接下来是什么？

智能体模式——“观察、决定、行动”是与基础设施无关的。决策逻辑不在乎其部署目标。改变的是当智能体停止孤立运行时可能发生的事情。

> “下一个前沿不是单个智能体更快地执行单个任务。而是智能体与其他智能体进行协调。”

下一个前沿不是单个智能体更快地执行单个任务。而是智能体与其他智能体进行协调。自动归档智能体检测到失败模式并将上下文传递给根本原因智能体，根本原因智能体跨服务追踪依赖链，识别出问题的提交，并起草修复建议——所有这些都在人类看到bug工单之前完成。智能体到智能体的委托，其中一个智能体的输出成为另一个智能体的输入，而中间不需要人工路由。

除此之外：构建自己的决策模型的智能体。今天，我手写去重逻辑和回归检测规则。明天，智能体观察人类将哪些提交的bug关闭为重复bug，从这些纠正中学习，并收紧其自身的分类边界。系统得到改善不是因为我发布了更好的代码，而是因为它随着时间的推移积累了组织判断力。

该系统最初是一个周末项目，旨在停止手动提交bug。它现在正在生产中运行，消除了 QA 操作中的一整类手动工作。

基础设施问题保持不变——用于验证的 Serverless，用于规模化的容器。但运行在该基础设施上的智能体即将变得更加强大。准备好平台层的团队将是那些能够在不重新架构的情况下采用这些功能的团队。
