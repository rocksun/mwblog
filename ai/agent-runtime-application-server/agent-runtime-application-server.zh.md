**人工智能研究的飞速发展**意味着企业现在有多种模型可供选择，以驱动AI智能体解决实际的业务问题。但仅仅选择模型并不能保证智能体有效，甚至不能保证良好的性能。要做到这一点，你需要在一个能够提供工具、状态、安全性和扩展性的环境中运行智能体，同时还需要具备快速启动时间，并与现有业务系统良好集成。

选择合适的智能体运行时环境就像为AI系统选择企业应用服务器一样——而且[智能体与传统应用程序有着非常不同的需求](https://thenewstack.io/securing-kubernetes-ai-agents/)。

> Gartner预测，到2027年，超过40%的智能体项目将被取消；原因不是模型不够强大，而是业务价值不明确、风险控制不足以及成本激增。

## 智能体计算与众不同

人们很容易将AI智能体视为另一个微服务：接收非结构化输入、运行API或查询、返回消息。但为具有可预测业务逻辑的传统企业应用甚至云原生无状态工作负载设计的架构，并不适合智能体。智能体具有爆发性、长时间运行、有状态、非确定性、编写代码和调用工具的行为，这些行为可能由系统事件或电子邮件触发，而不仅仅是聊天会话。

模型推理需要GPU来加速，但智能体还需要可靠、持久的计算能力，以支持长时间运行进程的有状态会话，以及强大的安全性和实时可观测性。

你仍然需要考虑托管、扩展、身份和安全等常见问题，但所有这些都被智能体推理循环中不可预测的多阶段工作流程所复杂化。

一个智能体从多个来源获取输入，根据其上下文推理实现目标的执行计划，调用其他工具或编写自己的代码，对这些调用的结果进行迭代，并可能在此基础上构建，或者切换到需要另一个推理循环的替代方法，最终交付输出。这可能不仅仅是显示答案，而是更新系统或发送电子邮件。

模型性能只是使其发挥作用的一部分。要架构一个能够在企业规模上运行的成功智能体系统，需要考虑智能体运行时、智能体调用的应用层，以及它们所消耗的工具、API和MCP服务器。

## 现代智能体基础设施的需求

相反，你应该寻找适合智能体工作方式的灵活基础设施。与任何技术一样，如果你在 Azure Container Apps 等现有平台上进行构建，就可以在你的业务能够脱颖而出的领域节省精力。虽然AI智能体存在缺陷（从幻觉到高Token成本），这些问题还没有完全解决，但你可以选择一个能够更容易在这些缺陷存在的情况下获得有效结果的智能体运行时环境。

智能体计算需要快速启动和恢复。无论是人类在聊天提示中输入，还是系统事件自动启动多个智能体，智能体基础设施都需要快速启动。如果启动一个容器需要几秒钟，那么推理循环就无法在该时间之前开始。

它还需要能够响应式地扩展，并且在不运行时不会产生任何成本。

由于智能体工作负载是长时间运行且由事件驱动的，智能体需要启动、完成一些工作、空闲数小时甚至数天，然后立即恢复，同时保持其内存、上下文、缓存、连接、身份和安全性完整。这意味着要持久化和恢复状态，这样长时间运行的智能体就不必反复支付同样的启动成本。无论智能体推理循环的上一阶段是成功还是失败，它都必须采取另一种方法；你肯定不希望它重复做同样的工作。

与其构建自己的自定义 microVM 堆栈，新的 [**Azure Container Apps Sandboxes**](https://learn.microsoft.com/en-us/azure/container-apps/sandboxes-overview) 提供了一个临时、安全且有状态的计算环境，可以快速启动、执行代码、对磁盘和内存进行快照，然后自动进入空闲状态并以同样快的速度恢复。这是 [**Dynamic Sessions**](https://learn.microsoft.com/en-us/azure/container-apps/sessions) 的有状态等价物，具有来自预热池的亚秒级启动能力；你可以在需要时扩展到数百（最终是数千）个并发沙盒，然后缩减回零。

智能体运行时需要默认安全，因为智能体只有在采取行动时才有用——根据定义，它们很可能会做意想不到的事情，编写和执行自己的不受信任的代码，并不断尝试实现目标（有时甚至在存在应停止某些行为的策略时也是如此）。

为了给智能体提供对其所需资源的安全、可审计的访问权限，请在沙盒中运行它们及其生成的代码，而不是在具有生产凭据和管理权限的开发人员笔记本电脑上运行。身份、访问控制和执行边界必须在运行时层实施，而不是在隐藏的提示中附加。

ACA Sandboxes 具有出口和访问策略，因此你可以控制出站调用并限制它们可以访问的 URL。如果无法为智能体需要连接的所有服务使用托管标识，则可以通过外部出口网关注入 API 密钥，而不是硬编码它们。因为网关是外部的，出站调用决策由沙盒外部的策略控制，而不是由会无情地尝试任何方法通过的智能体代码控制。

如果智能体是有用的，你将会同时运行很多智能体。AI智能体需要为每个任务提供强大的隔离性，这样每个不受信任的代码执行都会发生在自己的沙盒中，任务之间不会发生数据泄漏。

你可以将它们作为组进行管理，但每个 ACA 沙盒都有自己的安全边界，因此来自一个客户支持智能体的详细信息不会出现在与不同客户的聊天中。如果不受信任的代码[确实证明是有问题的](https://www.wiz.io/blog/ghostapproval-a-trust-boundary-gap-in-ai-coding-assistants)，隔离的沙盒至少可以限制爆炸半径。

你肯定不希望依赖脆弱的胶水代码或临时编排，因为每当智能体调用的工具、API、云服务和其他工作流程的系统发生变化时，你就必须重写它们。你也不想依赖于手动清理不再需要的资源。具有内置智能体工具执行能力的运行时使智能体更加健壮。它消除了将智能体环境连接到其他系统的繁琐工作，使它们能够安全、隔离且大规模地进行交互。

> “这不仅关乎智能体在哪里运行以及智能体具备什么能力，还关乎智能体可以采取什么行动。”

“这不仅关乎智能体在哪里运行以及智能体具备什么能力，还关乎智能体可以采取什么行动，”[**Vyom Nagrani**](https://www.linkedin.com/in/vyomnagrani/) 指出。他负责管理 Azure Container Apps 和构建在 ACA Sandboxes 之上的 [**Azure SRE Agent**](https://learn.microsoft.com/en-us/azure/sre-agent/overview) 的 PM 团队。沙盒可以访问拥有超过 1,400 个企业级连接器的连接器框架，使它们不仅可以在 Azure 和 Microsoft 服务上采取行动，还可以在第三方工具上采取行动。

“运行时提供了这些连接器，并提供了一种针对所有这些第三方系统进行身份验证的托管方式，因此现在你可以构建一个可以与许多、许多、*许多*不同系统对话的智能体。它不会被限制在一个身份验证边界内，”Nagrani 告诉 *The New Stack*。

MCP 服务器是连接器框架的一项内置功能。“你可以使用这些连接器中的任何一个；你可以采用任何 REST API 并将其公开为 MCP 服务器，然后智能体就可以使用它。” 或者，如果你想构建一个自定义 MCP 服务器，也可以将其托管在沙盒中。ACA Sandboxes 既可以是智能体运行的地方，（如果合适的话）也可以是它们使用的工具被托管的地方。

如果你正在构建一个用户界面来包装你的智能体，调用智能体的应用层可以在 [**Azure Container Apps Express**](https://learn.microsoft.com/en-us/azure/container-apps/express-overview) 中运行，这是目前处于公开预览阶段的一项新服务，Nagrani 说。

“这是一个简化的应用托管堆栈，用于处理 HTTP 流量并服务 Web 流量的应用层：这就是人类交互发挥作用的地方。”

## 整合所有内容

ACA Sandboxes 提供了一个智能体运行时环境，回答了架构师需要考虑的关键问题：智能体及其需要访问的临时计算资源在哪里运行；调用智能体的应用层在哪里运行；以及智能体如何访问它们需要编排的所有工具、API、服务、MCP 服务器和现有业务逻辑。

无论你是平台工程师、软件供应商还是正在构建新AI平台的初创公司，将智能体运行时视为新的应用服务器，将 MCP 服务器视为新的 API，都需要能够有效支持智能体工作负载的智能体基础设施，允许治理“左移”到运行时层，在那里它可以随着智能体数量的不断增加而扩展。

## 现实中的平台如何基于智能体运行时构建

Azure Container Apps 已经是运行智能体的强大平台。Auger 是一家由亚马逊全球消费者业务前 CEO 创办的初创公司，旨在帮助中型企业将复杂的供应链从 Excel 电子表格中解放出来。他们使用该平台构建了一个多智能体系统，可以在矿山或关键航运路线可能随时因战争或天气而关闭的世界中，提供有关货物和预测的实时答案。

后端智能体从不同的孤岛中提取包含所有详细信息的非结构化数据来回答这些问题，构建 ETL 管道，并为每个客户创建一个供应链生态系统的本体，其中包括功能和操作——所有这些都需要进行审计和可逆化。前端智能体使用该本体来回答诸如“如果我在这里建立一个新仓库或切换到这个国家的供应商，会发生什么？”之类的问题。

ACA Sandboxes 利用了 Azure Container Apps 的强大功能，并使任何组织都能够更轻松地构建自己的智能体服务，实现强大的隔离、动态扩展、快速启动、持久状态以及与广泛工具和服务的连接器。

这正是 Foundry 团队在开始构建 [**Microsoft Foundry Agent Service**](https://azure.microsoft.com/en-us/products/ai-foundry/agent-service) 托管智能体运行时时所寻找的内容。ACA Sandboxes 为他们提供了一个平台，该平台提供快速启动/恢复、内置工具执行（包括针对不受信任的代码）、长时间运行智能体的持久状态、强大的每智能体隔离以及默认安全的操作。智能体身份、“代表”现有业务服务的身份验证以及严格的隔离是他们无需自己构建的关键功能。

> “这是微软自身智能体产品背后相同的企业级基础设施，现在所有 Azure 客户都可以基于此进行构建。”

Foundry Agent Service 为智能体操作和对话增加了一层可见性和可观测性，使客户能够监控智能体性能，并查看系统在哪些方面做得好，哪些方面需要改进。

“Azure Container Apps Sandboxes 将智能体运行时的困难部分打包成一流的 Azure 资源——亚秒级启动和恢复、内置工具和不受信任代码的执行，以及基于快照的状态，让长时间运行的智能体能够精确地从中断处恢复。每个智能体都有自己的硬件隔离环境和默认安全的操作，因此构建者可以专注于他们的智能体做什么，而不是底层的管道，”Nagrani 指出。

“这是微软自身智能体产品背后相同的企业级基础设施，现在所有 Azure 客户都可以基于此进行构建。”
