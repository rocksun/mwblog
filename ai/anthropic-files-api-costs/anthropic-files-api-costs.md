本文通过实验对比了使用 Anthropic Files API、直接粘贴内容及 Prompt 缓存三种方式。结果显示，Files API 主要解决文件管理问题而非成本，Prompt 缓存才是降低大规模重复请求成本的最佳方案。

> 译自：[Anthropic's new Files API vs. pasting: It will save you time, but it won’t save you money.](https://thenewstack.io/anthropic-files-api-costs/)
> 
> 作者：Jessica Wachtel

**Anthropic 在 8 月 19 日将 Files API 和计算机使用工具集移出了测试阶段**，并发布了一套浏览器使用工具集。它允许开发者上传一次文档并通过 ID 在后续请求中引用，而不是每次都发送其内容。常见的替代方案是大多数开发者目前所做的：将参考资料粘贴到每个提示词（prompt）中。

我希望衡量一下，在 token 消耗、准确性和设置难度方面，上传一次文件与在每个请求中粘贴文档相比如何。我构建了一个带有可验证答案的测试，并对两者以及测试结果中出现的第三种方法——提示词缓存（prompt caching）——运行了相同的工作负载。

## 测试

我为一家名为 Ledgerline 的发票公司编写了一份虚假的 API 参考文档，约 1,200 字，涵盖了身份验证、速率限制、幂等性、webhook、批量端点和沙盒。场景是一个使用 Ledgerline API 参考文档回答问题的开发者支持机器人。然后我编写了五个文档可以回答的开发者问题：

* 如何区分两个不同的 403 错误，以及每个错误的修复方法
* 在超时后如何安全地重试支付创建
* 如何验证 webhook 签名并阻止重放攻击
* 在一个晚上创建 2,000 张发票的正确方法
* 将秘密 API token 提交到公共仓库后该怎么办

每个问题在参考文档中都有一个具体的正确答案，包括容易遗漏的细节。一个修复方法取决于知道 token 作用域（scope）在创建后无法编辑。另一个需要为批量端点设置单独的速率限制。

我通过 Python 脚本直接针对 API，在 claude-sonnet-5 上用完全相同的指令以三种方式运行了这五个问题：

* 方法 1：在每个请求中粘贴完整参考文档
* 方法 2：通过 Files API 上传一次参考文档，并在每个请求中引用其文件 ID
* 方法 3：在启用提示词缓存的情况下，将参考文档粘贴一次到系统提示词中

API 会报告每次响应的 token 使用情况，因此每种方法都输出了自己的统计数据。

## 运行准备

在第一次运行之前，有两处报错。脚本最初为了可复现性将温度（temperature）设置为零，但 API 拒绝了它。温度参数在 claude-sonnet-5 中已被弃用。其次，其中一个响应以思考块（thinking block）开头而不是文本，这导致我的打印代码崩溃。这两个修复都只用了一行代码。

Files API 的上传过程很顺利。一次调用，返回一个文件 ID，该 ID 在随后的每个请求中都能正常工作。

## 测试结果

针对答案键，所有三种方法的所有十五个答案都是正确的。每种方法都捕捉到了细微的细节：不可编辑的 token 作用域、单独的批量速率限制、固定时间的签名比较、五分钟的重放窗口。无论方法之间还有什么其他变化，答案的质量都没有变化。

> 无论方法之间还有什么其他变化，答案的质量都没有变化。

虽然答案质量保持一致，但 token 计数却不同。

| **测试** | **常规输入 Token** | **缓存写入** | **缓存读取** | **输出** |
| --- | --- | --- | --- | --- |
| 方法 1，每次都粘贴 | 15,246 | 0 | 0 | 1,399 |
| 方法 2，Files API | 15,371 | 0 | 0 | 1,434 |
| 方法 3，提示词缓存 | 271 | 2,990 | 11,960 | 1,642 |

方法 2 比方法 1 计费的输入 token 略多，这很有意思。虽然营销文案中没说，但我原以为使用 API 文件可能会减少一些 token。无论哪种方式，上传文件的内容在每个请求中仍会被处理，每个问题大约为 3,050 个输入 token，并且引用文件会在额外增加少量的开销，每个请求大约 25 个 token。在五个请求中，上传一次比粘贴多花费了 125 个输入 token。在任何数据量下这都不会反转。

方法 3 的表现正如我所假设的 Files API 应该有的样子。文档在第一次请求时被完整计费一次，即 2,990 个 token 的缓存写入。随后的四个请求从缓存中读取，缓存读取的计费率约为正常输入 token 的十分之一。问题本身每个花费在 48 到 63 个常规输入 token 之间。缓存写入比正常输入有 25% 的溢价，因此第一次请求最昂贵，随后的请求才是节省成本的地方。

关于缓存数字的两点注意事项。缓存会在 5 分钟不活动后过期，因此这种节省假设请求持续不断。此外，缓存需要重构请求，将文档移动到带有缓存标记的系统提示词中。

## 何时使用哪种方法

有趣的结果是，这两个功能解决了不同的问题。Files API 用于管理文档。提示词缓存用于降低成本。

### **Files API**

当问题在于文件本身时，请使用 Files API。它为你提供了一个通过 ID 引用的已上传副本，而不是让文档文本存留在你的代码中；它处理你无法粘贴的格式（如 PDF 和图像）；并且存储的文件现在支持过期设置。它没有改变的是成本。文档在每个请求中都会被处理，Anthropic 的公告从未宣称过这一点。

### **提示词缓存**

当问题在于为每个请求支付同一个文档的费用时，请使用提示词缓存。在这种工作负载中，它在五个请求中将计费的输入量削减到粘贴方式的三分之一左右，而且差距会不断扩大，因为第一次之后的每个请求都以正常速率的十分之一左右读取文档。其权衡点在于 5 分钟的缓存过期时间（假设有稳定的流量）以及重构请求以添加缓存标记。

当两个问题同时存在时，请同时使用 Files API 和提示词缓存。Files API 文档可以用与粘贴文本相同的方式进行缓存标记。我单独测试它们是为了隔离每个功能的作用。

### **粘贴文档**

在某些情况下，粘贴仍然胜出。在进行原型设计和进行一次性调用时使用粘贴，因为此时先上传只是一个额外的步骤。对于随每个请求而变化的文档，由于没有内容被重用，因此这两个功能都无济于事，这也是最佳选择。请记住，这是针对短参考文本的情况，因为大多数模型不支持缓存 1,024 token 以下的文档。粘贴的组件也最少：没有上传步骤，没有文件 ID，没有需要管理的存储副本。

我做这个测试是想弄清楚 Files API 在准确性或成本方面是否优于粘贴。结果证明我问错了问题。它们在成本上持平，而在成本上胜出的功能，是我在最后一分钟为了强行尝试不同结果而测试的。
