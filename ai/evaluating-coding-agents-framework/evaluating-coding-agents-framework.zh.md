我最近与一家软件工厂提供商发生了争执，他们的立场是编码代理无法评估。

他们的理由是可以理解的。软件工程是开放式的。需求是不完整的。代码仓库中包含了多年来未记录的决策。两名工程师可以用完全不同的方式解决同一个问题，而且两人都可能是对的。代理可能在一次运行中失败，而在下一次运行中成功。基准测试永远无法重现交付生产级软件所涉及的所有背景、协商和判断。

> “编码代理是非确定性的，在较长的时间范围内运行，并且可以产生许多有效的解决方案。但这并不意味着它们无法评估。这意味着我们需要停止像给聊天机器人打分那样来评估它们。”

这些说法都是正确的。但是“难以评估”和“无法评估”是两个完全不同的主张。

我们已经在评估具有多种实现方式的传统软件系统了。我认为编码代理也应该遵循同样的标准。

## 代理 !== 模型

编码代理不仅仅是一个模型。

它由一个模型、框架、工具、代码仓库上下文、指令、权限、执行环境和反馈回路组成。改变其中任何一个，结果都可能发生重大变化。一个更强的模型如果代码仓库上下文较差，其表现可能不如一个配备了正确工具和快速测试套件的较小模型。

这就是为什么公开的基准测试很容易被误用的原因之一。分数通常被描述为衡量底层模型，但实际上它衡量的是在特定 Token 和时间预算下，特定模型-代理-环境组合的表现。

在评估编码代理时，我们评估的是整个系统。

## “存在许多有效的解决方案”

对编码代理评估的一个反对意见是，精确匹配的评分方式行不通。代理可能会产生一个有效的补丁，而看起来与人类编写的参考补丁完全不同。

我同意这一点。但这只是意味着我们需要评估行为，而不是与参考差异（diff）进行比较。

从已知的代码仓库状态启动代理。给它一个任务和当时的可用上下文。然后根据可执行契约评估生成的代码仓库：

* 它能构建成功吗？
* 现有的测试是否仍然通过？
* 所请求行为的隐藏测试是否通过？
* 公共 API 和数据格式是否仍然兼容？
* 迁移是否能在两个方向上正常工作？
* 性能和资源使用限制是否得到遵守？
* 代理是否修改了允许范围之外的任何内容？
* 静态分析或安全检查是否发现了新问题？

这些检查允许存在多种实现方式，同时保留了可接受行为的明确定义。比起对代理所完成工作的主观陈述，这些检查也更难被蒙混过关。

有些品质无法通过可执行测试完全捕捉，例如可维护性、架构契合度、命名，或者某个更改是否使后续更改变得不必要地困难。这些都需要人类的判断。

但是人类编写的软件并没有因为代码审查包含主观判断而停止测试。

## 编码代理的评估不仅需要通过率

“测试通过了吗？”是必要的，但我认为在这一背景下还不够。

代理可以通过削弱现有的断言来使新测试通过。它可以硬编码一个预期的值。它可以将一个专注的实现替换为巨大的重写，而这仅仅在今天看起来是正确的。它可以在二十次失败的尝试后解决任务，消耗不合理的预算，并留下工程师绝不会批准的更改。

因此，一个有用的评估包含多个层面：

1. **结果**：最终的代码仓库是否满足了任务要求？

2. **更改质量**：我们会接受这种实现吗？

3. **轨迹**：代理是如何达到这个结果的？

4. **人工干预**：代理需要多少帮助？

5. **经济性**：结果是否值得财务成本？

6. **生产影响**：合并后发生了什么？

没有单一的数字可以捕捉这六个层面，这没关系。工程团队已经使用记分卡而不是单一的魔法指标来评估交付。

## 非确定性是一个统计问题

编码代理可能在一次运行中解决同一个任务，而在另一次运行中失败。这通常被作为评估是不可能的证据。

实际上，这证明了单次运行是不够的。在受控的起始条件下多次运行相同的任务。报告成功分布，而不是最佳演示。衡量固定预算下的通过率、成本和完成时间的方差，以及严重故障模式的频率。在比较系统时包括置信区间。

> “我们必须问：‘在我们的预算内，它多久能解决这类任务，而不引入不可接受的故障？’”

对于[生产级编码代理](https://thenewstack.io/agent-runtime-application-server/)，我们不应该问：“它能解决这个任务吗？”

我们必须问：“在我们的预算内，它多久能解决这类任务，而不引入不可接受的故障？”

## 开放式工作仍然有界限

最艰巨的任务始于不完整的意图：“改进入门体验”、“现代化此服务”或“构建新的计费工作流”。可能没有完整的测试套件，因为决定构建什么也是工作的一部分。

这就是评估应该包含交互的地方，而不是假装歧义不存在。

[让代理能够访问](https://thenewstack.io/googles-data-commons-gives-ai-agents-access-to-a-vast-trove-of-stats/)由私有需求集支持的受控用户或产品负责人模拟器。评估它是否识别了歧义、提出了有用的问题、整合了答案并避免发明需求。然后根据隐藏的行为契约评估完成的系统。

代理不应因提出必要的问题而受到惩罚。它应因自信地实施错误的假设而受到惩罚。

更新的研究基准已经在朝这个方向发展。[ICAE-Bench](https://arxiv.org/abs/2607.21217) 将代理评估为交互式项目构建者，而 [Dialogue SWE-Bench](https://arxiv.org/abs/2606.13995) 则将对话作为一种独立于原始编码能力的技能进行隔离。方法会演变，但前提很明确：歧义改变了评估的形式；它并没有使评估成为不可能。

## 标准是有用的，而不是完美的

没有任何评估能捕捉到设计决策的全部未来成本。没有任何私有套件能代表工程组织将遇到的每一个任务。人类的准则会包含分歧。隐藏的测试会漏掉案例。生产环境会给我们惊喜。

完美不是标准——归根结底，人类自己生产的软件也不完美。标准在于，评估是否能帮助我们做出比单纯的演示、轶事或供应商宣传更好的决策。

> “声称编码代理无法评估，让供应商在不需要承担工程证据负担的情况下，享受了工程产品的红利。”

如果一个评估能够用可重现的证据回答这些问题，它就完成了它的工作。

编码代理比代码补全模型更难评估，因为它们做得更多。它们探索、计划、编辑、执行、恢复，有时还需要协商意图。我们的评估系统[需要观察](https://thenewstack.io/debugging-observable-ai-systems/)整个循环。

但声称编码代理无法评估，让供应商在不需要承担工程证据负担的情况下，享受了工程产品的红利。
