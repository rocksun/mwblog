本文探讨了影响Kubernetes控制平面可用性的三种隐蔽故障路径：扩展API导致的OpenAPI模式失效、DaemonSet重启引发的请求风暴，以及不当的存活性检查造成的死循环重启。文章强调组件级正确性并不等同于系统可用性。

> 译自：[The hidden failure paths that affect Kubernetes control plane availability](https://thenewstack.io/kubernetes-control-plane-failures/)
> 
> 作者：Sri Saran Balaji Vellore Rajakumar

Kubernetes 控制平面旨在隔离个别故障，但其可用性仍然取决于关键路径上的组件在压力下的表现。在大规模集群中，组件不一定需要崩溃才会导致中断。一个合法的机制可能会通过共享的元数据、同步的启动工作或过于激进的健康检查，将局部缺陷放大。

例如，informer 为控制器提供了集群状态的本地视图，使其工作线程能够推进，而无需重复查询 API 服务器。当控制器独立启动时，这是高效的。当许多控制器在集群中同时重新启动时，重建这些视图会给控制平面带来巨大的压力。Informer 机制本身变成了放大器。

> “在大规模集群中，组件不一定需要崩溃才会导致中断。一个合法的机制可能会通过共享的元数据、同步的启动工作或过于激进的健康检查，将局部缺陷放大。”

本文探讨了三个案例。在第一个案例中，扩展 API 服务器在[依赖项升级](https://thenewstack.io/eks-kubernetes-upgrade-rollback/)后发布了无效的架构，并阻止了从未在其上使用 API 的客户端。在第二个案例中，DaemonSet 智能体在大规模集群中重新启动，将常规的启动工作变成 API 服务器无法承受的请求风暴。在第三个案例中，API 请求路径中某个组件的深度存活性检查将依赖项中断视为进程故障，并在依赖项不可用时推动重复重启。

这些案例对于运行扩展 API、监视大型对象集合的控制器，以及依赖深度依赖项检查的 API 请求路径中的组件的团队至关重要。

在其中一个集群中，Helm 部署开始对仅包含标准 Kubernetes 资源的 Chart 失败。这些 Chart 与导致故障的扩展 API 没有任何关系。从未听说过该扩展的用户在请求到达 API 服务器之前就看到了验证错误。故障路径穿过元数据，穿过一个组合了集群中注册的 API 定义的架构文档。

理解其中的原因需要了解 Kubernetes 如何向客户端公开 API 元数据。

Kubernetes 可以通过聚合 API 服务器进行扩展，这无需修改核心 API 服务器即可添加新 API。对于用户而言，聚合 API 看起来是原生的：它具有群组、版本、种类和资源路径，并且 kubectl 通过集群的正常 API 端点访问它。扩展 API 服务器生成描述其对象和字段的 OpenAPI 架构。客户端检索此架构以在发送请求之前理解和验证资源。

## OpenAPI v2 和 v3

Kubernetes 以两种形式公开此架构契约，两者的区别决定了损坏的扩展的爆炸半径。OpenAPI v2 是一个位于 /openapi/v2 的组合文档，包含来自核心 API 服务器和聚合扩展 API 的定义。OpenAPI v3 按 API 群组和版本分离架构。这种分离缩小了影响范围，因为使用核心 API 的客户端无需检索每个扩展的文档。

> “v2 格式创建了一个共享的故障域：来自一个扩展的无效定义可以阻止客户端解析用于验证无关资源的文档。”

v2 格式创建了一个共享的故障域：来自一个扩展的无效定义可以阻止客户端解析用于验证无关资源的文档。

## 显式 OpenAPI 模型名称

Kubernetes PR #[131755](https://github.com/kubernetes/kubernetes/pull/131755) 使 OpenAPI 模型名称显式化。在此更改之前，Kubernetes 可以从 Go 包路径派生模型名称。这使得从有效架构开始变得容易，但也把发布的模型名称与实现细节绑定在了一起。移动代码或重新组织包可能会更改 OpenAPI 客户端看到的名称。较新方法允许 API 作者声明一个稳定的模型包，并且代码生成在构建架构定义和引用时会使用该声明的值。

在此更改之前，架构可以公开从原始 Go 包路径派生的定义：

```json
{
   "com.example.platform.pkg.apis.metrics.v1.MetricReportSpec": {
     "type": "object"
   }
 }
```
更改后，一旦包声明了一个 OpenAPI 模型命名空间，相同的定义就会使用显式的、稳定的名称：
```json
{
   "com.example.platform.metrics.v1.MetricReportSpec": {
     "type": "object"
   }
 }
```

## 缺失的声明

一个扩展 API 服务器升级了 Kubernetes API 机械库依赖项，但没有包含更新的模型名称生成所需的 +k8s:openapi-model-package 注解。其生成的代码在构建架构定义时继续提供原始 Go 包路径。较早的 API 机械库将这些路径转换为 OpenAPI 安全的名称；较新的行为期望扩展提供声明的模型包。没有该声明，扩展开始将原始 Go 包路径发布为 OpenAPI 模型标识符。因为这些路径包含 /，所以它们使生成的架构无效。

扩展服务器成功启动并继续为其 API 提供服务。进程健康检查不会验证进程发布的 OpenAPI 文档。问题出现在读取 OpenAPI v2 的客户端中。由于 v2 将 API 架构组合到一个文档中，来自一个扩展的无效定义会导致客户端在发送请求的 API 调用之前报告错误，即使请求的资源属于不同的 API 也是如此。

Helm 的行为使这一点尤为明显。根据 Helm 版本、命令和验证设置，Helm 在应用 Chart 之前会检索 OpenAPI v2 文档。仅使用普通 Kubernetes 资源的 Chart 可能会失败，因为不相关的聚合 API 发布了无效架构。将 v3 用于核心资源的客户端遵循更窄的路径：它们检索相关的核心 API 文档，而不是包含问题的扩展架构。

## 测试你发布的架构

最具说服力的测试是验证客户端实际接收到的工件。升级后，启动扩展并获取这两种架构格式：

```bash
kubectl get --raw /openapi/v2 > openapi-v2.json
kubectl get --raw /openapi/v3/apis/<group>/<version> > openapi-v3.json
```

在生产环境中启用扩展之前，请解析并验证这些文档。同时使用根据 OpenAPI v2 架构验证请求的客户端进行测试。这些测试遵循用户路径，并揭示端点健康检查无法检测到的问题。

## 2. 当滚动重启变成请求风暴

### 重建本地视图的成本

DaemonSet 在集群中的每个节点上运行 Pod 的一个副本。它适用于需要集群 Pod 最新视图的监控、网络策略、日志记录和安全智能体。例如，网络 agent 可能需要将 IP 地址映射到其所属的 Pod 以进行策略或遥测。

维护该视图的标准方法是通过 informer：一种客户端机制，它列出所需的对象，然后监视更改以保持本地缓存最新。

在拥有数千个节点的集群上，集群范围的 Pod informer 意味着数千个潜在的初始列表操作。当 agent 在不同时间启动时，负载会分散到 API 服务器的容量上而不会出现事故。

### 当恢复同步工作时

当恢复同步工作时，成本就会改变。在一次事故中，DaemonSet 在数千个节点上运行，其 agent 在大部分集群中反复崩溃。运维人员启动了滚动重启来恢复它们。DaemonSet 的 maxUnavailable 设置似乎具有保护作用，因为它限制了更新一次可以使多少 Pod 不可用。

这些 Pod 已经不可用。它们的替代品不一定面临相同的节奏限制。许多 agent 几乎同时启动。

每个新 agent 都会创建其 informer。每个 informer 都从列出相同的 Pod 集合开始。因此，旨在减少故障范围的恢复操作可能会对 API 服务器产生大量、同步的请求。

### 列表请求的成本

Informer 通常将 resourceVersion 参数设置为 0 来发出初始请求。通过使用 0，客户端允许 API 服务器从内存中的监视缓存中回答，而不是直接从[API 服务器的后端数据存储 etcd](https://thenewstack.io/eks-kubernetes-etcd-scale/)中读取。这通常是快速路径。它避免了重复的存储读取，并使用了 API 服务器已经为监视组装的状态视图。

多年来，该路径有一个违反直觉的限制。监视缓存无法像从 etcd 提供服务的列表那样提供分页。客户端可以包含 limit=500 并合理地相信它已将响应限制为 500 个对象。在受影响的请求路径中，当列表从带有 resourceVersion=0 的监视缓存提供时，API 服务器可以忽略该限制并返回每个匹配的对象。

在大集群上，包含所有 Pod 的响应可能包含数万个对象，并在 API 服务器解码、过滤、序列化和发送它时占用数百兆字节。当数千个替换 agent 同时请求相同的完整集合时，服务器在构建同一答案的许多副本时可能会耗尽可用内存和 CPU。普通的控制平面流量随后需要等待。

### 减少启动负载

Kubernetes 社区改进了堆栈的这一部分。API Priority and Fairness 列表成本估算在 Kubernetes 1.31 中得到了纠正。WatchList 也可以在支持它的客户端中取代传统的“先列表后监视”的启动路径。这些改进降低了每个请求的成本，但它们没有改变更广泛的设计计算：DaemonSet 中的集群范围 informer 仍然将其启动成本乘以节点数，并且重试策略仍然可以在故障期间同步该成本。

agent 所有者需要考虑的问题是：此 informer 能够监视并仍能履行其功能的最少 Kubernetes 资源集合是什么？

只需要一个命名空间中的 Pod 的 agent 不应该在整个集群范围内列出所有 Pod。需要 Pod 元数据的 agent 应该考虑仅元数据的 informer，而不是传输完整的 Pod 规格。对服务后端感兴趣的 agent 可以使用 EndpointSlices 代替列出每个 Pod，因为 EndpointSlices 直接描述服务端点，通常比完整的 Pod 清单小得多。

真正需要 Pod 到 IP 所有权、标签或其他 Pod 服务的 agent 可能仍然需要监视 Pod，但只要其语义允许，它就应该将该监视限制在相关的命名空间、节点或标签上。目标不是消除 Pod informer。而是避免重建比 agent 可以使用的更多的集群状态，尤其是当恢复导致许多实例一起启动时。

## 3. 当存活性检查重启它无法修复的内容

[存活性探针](https://thenewstack.io/top-10-kubernetes-deployment-errors-causes-and-fixes-and-tips/)如果检查下游依赖项，则每当这些依赖项不可用时就会重新启动进程。如果进程位于 API 请求路径中，则每次重新启动都会中断 API 流量。当依赖项中断持续存在时，探针会驱动“重启、初始化、依赖项检查失败、再次重启”的循环。每次迭代都会增加延迟，而无法修复依赖项。

> “探针可能会忠实地执行其契约。但契约可能仍然是错误的。”

探针可能会忠实地执行其契约。但契约可能仍然是错误的。

## 静态稳定性取决于缓存的密钥材料

Kubernetes 控制平面可能依赖外部密钥管理服务（KMS）来加密 Secret。KMS 提供商将该服务用于密钥操作，而 API 服务器可以在内存中保留缓存的加密材料。该缓存状态是系统可用性设计的一部分。KMS 连接的短暂丢失可能会延迟需要新鲜密钥材料的操作，而不会立即使 API 服务器无法提供有用的请求。

## 测试错误事物的存活性探针

在一次事故中，将 Kubernetes 与外部 KMS 集成的加密提供商拥有一个由 kubelet 监视的存活性探针。该探针每隔几秒钟对外部 KMS 执行一次新的加密操作，然后执行解密操作。当网络 impairment 导致 KMS 端点无法访问时，探针失败，kubelet 重新启动了提供商。重新启动的提供商无法建立新的 KMS 会话，因此在依赖项仍然不可用的情况下它不断重新启动。

探针准确地报告了 KMS 端点不可访问。它无法确定提供商进程是否不再为其本地接口提供服务，或者 API 服务器是否已耗尽允许其继续工作的缓存加密材料。这两种结论都不能从对外部 KMS 的失败调用中得出。

## 通过 API 服务器健康的级联

风险更广泛，因为 API 服务器的复合 /healthz 检查包括 KMS 提供商的状态。因此，失效的提供商可以替换具有可用缓存加密状态的 API 服务器。新的 API 服务器没有热加密缓存，需要建立新的 KMS 会话，并面临相同的不可访问依赖项。重复的替换可以将短暂的 KMS impairment 转化为控制平面服务能力的丧失。

## 在 impairment 期间保持能力

这就是测试依赖项与测试能力之间的区别。KMS 可达性是一个有用的监视信号，但它不足以证明提供商进程或 API 服务器已失去所有有用能力。存活性探针应确定提供商是否卡住或无法为其本地接口提供服务。单独的依赖项检查可以向运维人员发出 KMS 不可用的警报，而不会自动触发重启。

同样的推理也适用于控制平面路径中的任何组件。缓存的凭据、已建立的连接或内存中的状态视图可能是唯一允许在上一级服务恢复时继续进行有用工作的因素。这种行为已经内置在 kube-proxy 和 CoreDNS 等组件中：kube-proxy 继续使用其最后已知的 Service 和 Endpoint 状态，而 CoreDNS 继续从它已经拥有的 Kubernetes 数据中回答，即使 API 服务器暂时不可用。

> “每个案例都有一个共同的结构属性：机制在其自身的契约范围内可以正常运行，但仍然违反了它所属系统的可用性契约。组件级别的正确性是必要的，但不是充分的。”

重新启动无法到达每个依赖项的每个进程会丢弃缓存状态，增加必须重建的状态量，并对已经受损的依赖项产生同步需求。

每个案例都有一个共同的结构属性：机制在其自身的契约范围内可以正常运行，但仍然违反了它所属系统的可用性契约。组件级别的正确性对于系统可用性是必要的，但不是充分的。

一般的设计原则是评估关键路径上的每个机制在其假设被违反时的行为。架构假设扩展发布有效架构。滚动重启节奏假设 Pod 可用以变得不可用。存活性探针假设重启使进程更接近健康。当这些假设破裂时，该机制会放大它旨在包含的故障。

对于大规模运营共享控制平面组件的平台团队来说，这些是升级、恢复演练和健康检查设计的实际评审标准：

* 验证客户端接收到的架构工件，而不仅仅是扩展进程。
* 将 informer 范围和启动工作限制在组件所需的最小资源集合。
* 当组件在 impairment 期间能够保留有用能力时，将依赖项监视与存活性决策分开。
* 测试当许多副本同时重新启动时的恢复行为。

这些实践有助于将局部故障保持在局部，在依赖项中断期间保留有用能力，并防止常规恢复工作演变成控制平面事故。
