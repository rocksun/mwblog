文章探讨了AI时代编码效率提升带来的挑战，指出传统人工代码审查已成瓶颈。作者提出构建自动化验证系统和引入自动化验证工程师（AVE）角色，通过工厂模式替代手工匠人模式，实现部分代码无需人工干预即可安全上线，从而提升整体工程效能与质量。

> 译自：[Shipping code without human verification](https://thenewstack.io/ship-code-without-verification/)
> 
> 作者：Jade Rubick, Ankit Jain

AI 代理编写代码的速度已经超过了人类审查的速度。答案并不是“审查得更快”；那就像是在制造一辆更快的马车，而不是汽车。

每一位工程领导者很快都必须回答一个问题：在没有人工介入的情况下，你可以将多少代码部署到生产环境中？那些坚持核对每一行代码的团队终将被淹没，并[成为瓶颈。](https://thenewstack.io/future-of-code-reviews/)

也许你可以从百分之一开始。让一部分提交在没有任何人工验证的情况下直接进入生产环境需要做些什么？这与 CI/CD 类似，其思路是：我们需要一套什么样的实践流程，才能在代码一经批准后就安全地将其交付到生产环境？

## 验证 vs. 测试

测试是为了确保我们编写的代码能够正常工作。验证是为了确保变更符合预期，并且软件质量符合组织标准。

例如，一个新的 API 应该有自动化测试来确保其正确性。它还应该有自动化验证，以确保 API 的结构符合你的实践规范、具备良好的扩展性、使用了标准的错误代码，等等。

这些是相关但独立的质量门禁。传统上，它们被合并到了代码审查的实践中。审查是知识在团队中传递的过程。作者必须解释他们做了什么以及为什么这么做，而审查者则学习系统是如何变更的。

在传统的代码审查中，验证往往处于劣势：它是非确定性的，取决于审查者在下午四点时还剩多少精力，而且它只能随着人力时间的增加而扩展。用这种方式捕获 bug 向来效率低下，也从未提供过强有力的保障。

## 我们正在迈向“人在回路之外”（human on the loop）

代理工具的基本循环是：

* [提供上下文](https://thenewstack.io/ai-agent-infrastructure-bottleneck/)
* 让它完成一些工作
* 评估是否成功
* 如果对结果不满意，改进循环。

人类正在从亲自工作，转变为监督代理工作，最终变成[人在回路之外](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html)（human ON the loop）。“人在回路之中”（in the loop）意味着亲自审查和批准每一项变更。“人在回路之外”意味着维护进行审查的系统，并在系统本身需要优化时进行干预。

> “我们不再是个体贡献者，而是在维护交付系统。我们是在维护一家工厂，而不是在扮演手工艺人。”

例如：

* 设计师可以维护一套设计系统和设计工具，AI 代理在编码时使用这些工具来引导和强制执行生成的代码符合设计系统规范。
* 安全工程师可以监督一套安全工具，用于验证生成代码的安全性，并检查是否有 PII 数据和密钥泄露。

这种模式通常被称为向软件工厂模式的转变。我们不再是个体贡献者，而是在维护交付的*系统*。我们是在维护一家工厂，而不是在扮演手工艺人。

## 代理需要快速反馈

这对测试和验证意味着什么？

一种方法是设立自动化验证工程师这一角色，这介于开发体验工程师和质量保证（QA）之间。如果做得好，自动化验证可能成为工程团队能投入的最具杠杆作用的工作。

代理很少能在第一次尝试时就获得完美结果；因此，代理比人类需要更强的护栏。它们更有可能不断触碰各种约束条件，并根据反馈进行迭代，直到产出令人满意的结果。反馈的速度和可靠性决定了产出的质量。对于代理来说，关于变更导致了什么问题的快速、可信的信号，其价值胜过你提供给它的几乎任何东西。

> “关于变更导致了什么问题的快速、可信的信号，其价值胜过你提供给它的几乎任何东西。”

将编码代理自动检测测试和验证失败的能力提高 50%，可能会使工程组织的效率提高 200%，因为其变更将有更大比例能够被自动接受。自动化验证既加快了公司速度，又提高了质量。

## 什么是自动化验证工程师？

传统的 QA 是一种下游流程。工程部门移交工作，QA 发现问题，工作被退回。当 Jade 调查一组工程领导者关于初创公司 QA 角色的看法时，反馈几乎是一致的：交接效率低下，大多数人不会再那样做。失败的原因在于质量门禁置于工程之后而不是之中，这让工程师们认为质量是别人的责任。

在 AI 出现之前，在许多初创公司圈子里，解决方案要么是 1) 缩小或取消 QA，要么是 2) 将他们更紧密地整合进工程团队。

自动化验证工程师（AVE）实际上是一个实验。其想法是创建一个完全专注于自动化测试和验证的角色。让我们具体看看这个实验可能是什么样子：

测试职责

* 将重点放在自动化测试之上的一层——他们监督“测试工具集”（test harness）。这是一套强制执行所有工作覆盖全面测试规则的集合。该工具集鼓励深入的、对抗性的质量检查。它要求 PR 在进入生产环境前必须通过广泛的单元测试和 UI 测试。
* AVE 将质量失败视为改进测试工具集的机会。
* AVE 还负责测试运行速度。他们拥有测试流水线，并负责保持测试运行快速。

验证职责

* 负责“验证工具集”（verification harness）。这是一套包含上下文、LLM 工具和确定性工具的集合，用于验证每个 PR 是否交付了预期成果，并符合公司对 PR 应交付内容的规定。它应遵循所有实践规范，内置可观测性，并符合所有标准。
* 也许验证工具集也可以包括测试计划。起初它们不会完美，但计划中的缺陷被视为需要改进的事项，而不是每次都去修改模板测试计划。
* 验证失败被视为改进验证工具集的机会。

这个角色的具体形态还有待确定。如上所述，你可以拥有较少的 AVE，并让每个人都发挥极高的杠杆作用。在大型公司中，你可能拥有一支 AVE 团队，他们嵌入到一个或多个团队中。Jade 建议从每个团队一人开始，如果你证明了能够增加自动测试和验证的数量，那么这个角色最终可能会演变成一个 AVE 同时与几个团队协作。

AVE 角色并不意味着工程部门不需要对质量负责。自动化验证工程师将是质量专家，类似于站点可靠性工程师（SRE）是可靠性专家一样。

SRE 不应该承担所有的可靠性工作，就像 AVE 不应该承担所有的质量工作一样。其理念是，他们将质量融入到工作系统中。

## 在没有人工验证的情况下交付

在没有人在回路的情况下进入生产环境是你努力的目标，就像团队努力实现持续部署一样。选择一定比例的提交并从小范围开始。百分之一。然后解决让这部分代码在没有人工验证的情况下进入生产环境需要做些什么。这是 CI/CD 在部署步骤中回答的相同问题：我们需要哪些实践来确保某项内容在批准的那一刻就能安全交付？我们建立了回滚机制和监控，使这种信任变得合理，并停止需要专人盯着每次发布。

验证需要同样的实践和工具。有些变更始终需要人类的判断。另一些变更一旦围绕它们的护栏变得真实可靠，就足够安全，可以自行发布。工作重点在于如何找出安全变更的白名单并将其与风险较高的变更区分开来，而这种白名单机制将变得越来越重要。

即使没有 AI 系统，你可能也能达到 1%。你可能会发现代码库中意图和质量漂移风险很低的部分。一个简单的 CODEOWNERS 变更将那部分代码加入白名单可能是你踏上这段旅程的第一步。但要尝试通过随着时间推移提高该比例来跟踪进度。你需要哪些技术和工具来自信地做到这一点？

## 构建验证系统

随着代码量的增加，瓶颈已经转移到了[代码审查上。](https://www.aviator.co/verify?utm_source=tns&utm_medium=content&utm_campaign=q3-2026-tns-verify&utm_term=net-new&utm_content=awareness) 审查者跟不上进度，越来越大的 diff 将导致要么是“盖章放行”，要么是变成一个纯粹的代码审查角色。通过审查发现 bug 始终是一种低效的方法，也从未提供过强有力的保障。目标始终是降低风险，而不是消除风险，因为完全消除风险会使一切停滞不前。

足以在没有人类参与的情况下交付的[自动化验证](https://www.aviator.co/verify?utm_source=tns&utm_medium=content&utm_campaign=q3-2026-tns-verify&utm_term=net-new&utm_content=awareness)不需要完美。它只需要比人类做得更好，这比大多数团队承认的门槛要低。

在代码审查的情况下，自动化验证会是什么样子？一个[你可以运行的练习](https://www.aviator.co/blog/stop-reading-the-code/)是审查你团队过去 1000 条 PR 审查评论。将它们分类为确定性的、可测试的，以及需要判断的。开始为前两类添加自动化护栏，并找出 LLM 和人类判断的结合点来处理其余部分。目标是建立一个瑞士奶酪模型，拥有多层评估或确定性评估，以验证你的 SDLC（软件开发生命周期）产出可靠的结果。

> “足以在没有人类参与的情况下交付的自动化验证不需要完美。它只需要比人类做得更好。”

这种方法并非史无前例。它已经在 [Anthropic](https://www.youtube.com/watch?v=uU5Gv2h8-9g) 使用。他们在这个方向上投入了巨大精力。他们正在获得一些回报，但我认为我们才刚刚开始将此作为一种实践来发展。[Claude Code 代码库的泄露](https://thenewstack.io/claude-code-source-leak/)展示了一些挑战。像 CI/CD 一样，你应该将持续增加无需人工审查即可进入生产环境的提交比例作为目标，但要严格要求你的标准。你需要有信心确保事情随着时间的推移变得越来越好。

这种方法可以追溯到很久以前：Andy Grove 在 1983 年描述过这种针对芯片制造的质量控制：找到缺陷通过的地方，围绕该点进行检查，并在学习过程中收紧流程。同样的纪律正在进入软件领域：我们不再是在构建软件；我们是在构建生产软件的工厂。

| 功能正确性/业务逻辑 | `测试` | `calculate_discount(cart)` 对 20 美元的购物车返回 18 美元（10% 折扣）。单元测试锁定了数学逻辑；它永远不需要人类参与。 |
| 边缘情况与边界条件 | `测试` | 空购物车、负数量、整数溢出、午夜过期的优惠券。可枚举且确定性强——全部进行断言。 |
| 已知 Bug 回归保护 | `测试` | Bug：支付重试时退款被双重扣费。添加一个重现重试路径的测试，这样它永远不会静默返回错误。 |
| API/模式/契约兼容性 | `测试` | 如果 GraphQL 字段类型发生变化或删除了必需的响应字段，契约测试将失败。 |
| 意图对齐 | `验证` | 工单：“让结账更快。” Diff 添加了一个缓存 —— 但它解决的是工单意图中的慢速路径，还是一个没人访问的冷路径？没有任何断言能回答这个问题。 |
| 验收标准覆盖 | `验证` | AC 列出：限制登录频率、记录尝试次数、5 次失败后锁定。Diff 做了第一和第三项，但静默跳过了记录。验证过程会捕获缺失的项目。 |
| 架构/规范遵循 | `验证` | 业务逻辑直接添加到 GraphQL 解析器中，而不是服务层。测试通过了，但位置错了。 |
| 用户体验、视觉与设计保真度 | `验证` | 一个新的模态框渲染了，但在移动端主按钮位于折叠区域下方，且文案与设计不符。渲染测试通过，但意图失败。 |
| 新攻击面的安全审查 | `验证` | 一个新端点接受 `redirect_url` 参数。没有测试标记它，但验证过程分析：这是一个开放重定向/SSRF 攻击面 —— 它经过验证了吗？ |
| 副作用/影响范围完整性 | `验证` | 修改了代码中的配置键名，但未更新 Helm chart、文档或现有值的迁移脚本。此变更还隐含了什么？ |
| 非确定性/概率行为 | `验证` | LLM 生成的摘要。你无法断言确切的文本 —— 验证过程判断它是否忠实、完整且语调一致。 |
| 性能 | `拆分` | **测试：** 如果 p99 延迟 > 200ms，基准测试失败。**验证：** “这在循环中执行 N+1 查询 —— 10 行数据时没问题，但在 1 万行时会崩溃。” |
