本文探讨了AI智能体在云自动化中因缺乏跨域上下文而陷入停滞的现状，分析了频繁调用云API带来的API税问题，并提出通过引入共享上下文层与自主控制平面来连接声明式意图与运行现实，从而实现真正的云端自动化运维。

> 译自：[The API tax: Why AI agents stall without infrastructure context](https://thenewstack.io/autonomous-cloud-context-layer/)
> 
> 作者：Oleg Danilyuk

**企业持续面临自主云瓶颈**，这破坏了自主运维并导致失败。这种架构缺陷使得智能体缺少完整的跨域上下文，包括基础设施即代码（IaC）、应用拓扑、安全性、成本和策略，从而产生了影子基础设施。

在 [**env zero**](https://www.envzero.com/)，我们发现解决方案不是一个更聪明的AI模型，而是连接声明意图与云端实际运行状态的共享上下文层。我们将 IaC 管理能力与 CloudQuery 的云资产与上下文能力相结合，早期客户已经在使用这种组合架构。

[EZ Control](https://www.envzero.com/blog/env-zero-launches-ez-control-the-autonomous-cloud-control-plane-for-the-ai-era) 是下一步的发展：这是一个自主控制循环，它关联声明状态和发现状态，在策略控制下推荐或执行修复，并验证更改是否解决了最初的问题。我们的目标是在 2026 年 12 月底前实现全面上市。EZ Control 目前处于早期访问阶段。

这种区别很重要，因为几个自主工作流元素仍然是 env zero 正在构建的功能。在设想的循环中，系统将基础设施意图与实时云资源进行调和，将这些资源与环境和策略相关联，提出代码变更，运行计划检查，应用或合并变更，并执行新扫描以验证漂移或其他问题是否已解决。

AI智能体持续查询云 API 会增加企业的 API 税，包括[速率限制](https://thenewstack.io/how-to-prepare-your-api-for-ai-agents/)、查询序列失败，以及 CI/CD 或自动扩缩容管道潜在的停机风险。除了速率限制外，这种持续轮询还会产生巨大的失控成本和延迟惩罚，从而降低智能体的响应时间。API 税会阻碍云项目或解决方案的发展。  
  
实现上下文层包括优化查询序列以消除冗余调用。

云基础设施状态在状态文件、标签、电子表格和隐性知识之间保持碎片化。通过本体层将 IaC（声明的意图）与云安全态势管理（CSPM）工具观察到的运行时现实联系起来，对于 AI 自动化至关重要。这需要一个持续的控制平面循环来管理其当前状态。

以下是端到端循环的高级概览：

* 声明意图
* 发现
* 调和
* 策略验证
* 用于审查和执行的代码拉取请求 (PR)
* 验证扫描

## 模型智能与架构上下文

在我们所处的 AI 系统早期阶段，人们普遍将瓶颈归咎于模型。当然，AI 炒作的声音坚称强大的 AI 模型是首选解决方案。不幸的是，事实远非如此；这些瓶颈源于系统架构，再多的模型智能也无法解决它们。

> ……这些瓶颈源于系统架构，再多的模型智能也无法解决它们。

在规划 AI 智能体部署时，团队必须认识到，CI/CD 管道和 AI 智能体已经在以人类无法适应的速度加速基础设施变更。

随着变更的增加，传统的自助服务工具仅展示 IaC 片段，而忽略了应用拓扑、治理和相关的成本变量。例如，Wiz 可能会强制执行需要多个实例的严格高可用性策略，但仅在 IaC 中工作的 AI 智能体只能看到单个独立的 EC2 实例，对违规行为完全盲目。添加上下文层将 IaC 与应用程序、策略和治理缝合在一起，提供了自主决策所需的中央大脑，因此团队不必进行故障排除和救火。

大语言模型（LLM）的好坏取决于它们[接收到的上下文](https://thenewstack.io/context-engineering-going-beyond-prompt-engineering-and-rag/)。组织拥有分散的云账户和工具；以受治理的方式将它们连接起来至关重要。

## API 税与实时查询风险

上下文层并不能消除云 API 调用。相反，它改变了智能体需要调用它们的频率。我们的模型将同步上下文与有针对性的实时查询结合起来。所有权等相对稳定的信息可以适当的节奏保留和刷新，而实时查询则可以留给需要当前状态的问题。其目标是随着智能体工作流的扩展，减少冗余的 API 流量并降低触及提供商速率限制的风险。

这种风险可能会延伸到智能体本身之外。在 env zero，我们认为重复将操作型 API 用于资产式的问题可能会消耗其他自动化也依赖的速率限制容量。CI/CD 和自动扩缩容是关键功能的例子，当它们争夺相同的 API 容量时，可能会面临运营风险或延迟。当软件（如 AI 系统）针对相似的提示跨外部 API 重新运行查询而没有进行优化的序列时，就会产生成本高昂的 API 税。你需要设计智能查询架构，以避免通过工作流冗余地命中 API 并累积讨厌的 API 税。

人类与 AI 智能体之间的区别始于他们查询系统的方式。人类倾向于提出有针对性的问题，而智能体倾向于探索。我们的首席执行官 Steve Corndell 有一个最喜欢的例子：“我们见过一种故障模式：智能体可以完成 90 次查询，在第 91 次时失败，然后不得不重新启动序列。这会加剧 API 税，因为工作流重复了它已经完成的工作。”

> ……智能体可以完成 90 次查询，在第 91 次时失败，然后不得不重新启动序列。

过渡到上下文层的另一个好处是，它平衡了缓存的状态数据同步与选择性的实时查询，以减轻速率限制风险，同时保持运营连续性。

## 声明状态与实时现实

在我们看来，传统的 IaC 平面和独立的 CSPM 工具通常难以完全掌握[声明意图与实时现实](https://developer.hashicorp.com/terraform/tutorials/state/resource-drift)之间的结合。中央上下文层将 IaC 意图与运行时发现结合起来，以跨[多云环境](https://thenewstack.io/multi-cloud-blind-spots)映射资源所有权、策略上下文和应用程序边界。

根据我们与客户的经验，基础设施状态是企业中管理最松散的上下文。代码有 Git，身份有 IDP，资金有 ERP，基础设施有标签约定。

> 代码有 Git，身份有 IDP，资金有 ERP，基础设施有标签约定。

如果你无法指明所有者，你就无法执行策略。通常，基础设施所有权在状态文件、ClickOps 更改、标签、云 API、电子表格和隐性知识之间并不明确。当企业将这些上下文汇聚到一个知识图谱中时，它就可以使 env zero 等软件在定义好的防护栏内掌控一切。

## 自主云控制平面的架构

自主云控制平面的架构最好解释为一个端到端的循环，涉及：

* 捕获声明意图
* 发现实际的云状态
* 将未编码的资源调和到统一的概念中
* 应用策略检查
* 提出用于审查和执行的代码拉取请求 (PR)
* 重新扫描以验证解决方案并防止未来的漂移

将 CloudQuery 数据摄入与中间的本体层连接起来，会产生驱动自动化引擎向下延伸至执行工具（如 [Terraform](https://roadmap.sh/terraform)、OpenTofu 或 Pulumi）的大脑。

这改变了自主云控制平面必须做的事情。检测只是第一步。自主运维的控制平面必须掌控整个循环：理解意图、发现实际状态、调和两者、应用治理、修复问题并验证修复是否有效，从而提供端到端的漂移检测和修复。

一个止步于检测的工具仍然把最困难的部分留给了人类。这就是为什么我们认为该类别应该根据修复时间（TTR）来评判。对于此模型，“修复时间”是指从识别需要采取行动的基础设施问题到验证纠正性更改已解决该问题所经过的时间。

仅靠检测并不能完成整个循环。我们描述了一个序列，它从发现和调和开始，经过策略上下文、提议的变更、审查或计划检查、执行，以及确认漂移或原始发现已经消失的新鲜扫描。最终的验证将修复时间与更简单的变更时间度量区分开来。该循环在提出修复方案之前映射爆炸半径，从根本原因入手，而不是应用临时的创可贴。

Env zero 还自动建议预防性策略，可以防止同类问题再次发生。这自然属于预防或根源改进，与核心修复计时器本身并行。

## 添加控制层而不替换 IaC

我们认为这种架构是将云自动化推向超越传统 IaC 工作流限制的一种方式。

CloudQuery 于 2026 年 3 月与 env zero 合并，汇集来自云账户以及 Wiz、ServiceDatadog 等外部系统的的数据，而本体层则将基础设施、策略、所有权和应用程序上下文关联起来。

CloudQuery 负责思考；env zero 负责执行。然后，我们利用该上下文来推动整个环境中的自动化、治理、自助服务和合规性。其优势在于，团队无需替换 Terraform 或其他 IaC平台即可获得更广泛的控制层。相反，我们的平台位于现有工具链之上，将声明意图与发现的状态连接起来，并为自主工作流提供决定下一步行动所需的上下文。
