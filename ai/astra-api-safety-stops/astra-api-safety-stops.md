OpenAI宣布Astra模型达到关键网络安全阈值，将实施更严格的监控。当Astra在API运行中触发安全干预时，任务将直接中止而非超时，这可能导致开发者面临任务无法恢复及额外计算成本的挑战。

> 译自：[Your next OpenAI API timeout might not be a timeout at all](https://thenewstack.io/astra-api-safety-stops/)
> 
> 作者：Amanda Caswell

**OpenAI 周二表示，其即将推出的 Astra 模型**是该公司首个达到其《准备框架》(Preparedness Framework) 中“关键”网络安全阈值的模型。该级别专为那些能够以极少人工协助即能发现漏洞并开发攻击代码的模型而设。

因此，Astra 将受到更密切的监控，OpenAI 表示，这种监控可以在智能体（agent）开始工作后将其打断。后续情况取决于 Astra 的运行环境。在 ChatGPT 和 Codex 中，用户可能会在智能体继续操作前被提示审核已暂停的动作，而 API 任务则会直接停止。

“当使用 API 等其他界面时，任务将会停止，” [OpenAI 表示](https://openai.com/index/path-to-astra/)。

> “当使用 API 等其他界面时，任务将会停止”

## 当安全机制停止你的智能体时

OpenAI 尚未发布该模型的系统卡（system card），因此尚不清楚 API 任务停止后会发生什么，或者是否可以恢复。这一点对 Astra 尤为重要，因为它[被设计为在开放式研究和安全任务中长时间运行](https://thenewstack.io/openai-astra-persistent-agents/)，等到 OpenAI 进行干预时，它可能已经完成了数小时的工作。

开发者还需要了解任务停止的原因。通常超时可以重试，但如果 OpenAI 是出于安全原因停止了任务，重新启动可能会直接导致同样的问题，而该公司尚未说明 API 将如何清晰地区分这些情况。

## 导致限制的攻击行为

更严格的限制源于 Astra 能力的显著提升。它在 ExploitBench 上获得了 100% 的分数，但由于该模型在训练过程中可能见过部分已知漏洞，OpenAI 还针对 6 月至 8 月期间披露的 20 个高严重性 V8 漏洞对其进行了测试。Astra 发现了两个此前未知的漏洞，并将它们用于攻击链中。

> Astra 发现了两个此前未知的漏洞，并将它们用作攻击链的一部分。

在与安全专家的测试中，Astra 还构建了一个逃逸沙箱并在宿主机上运行命令的浏览器漏洞利用程序。同时，另一项测试显示，它结合了加固操作系统中的漏洞，从非特权账户提升到了 root 权限。OpenAI 曾在 8 月 7 日警告称，无法再排除该模型达到其关键网络安全阈值的可能性。

在 OpenAI 的网络“越狱”测试中，Astra 还拒绝了更多的恶意请求，拦截率为 91.5%，而 GPT-5.6 Sol 的拦截率为 59%。对其更高级网络安全功能的访问权限最初将仅限于一小部分测试人员，随后通过 Daybreak Blue 扩大范围。

## 监控需要真正的算力成本

这些安全防护措施不仅是为了捕捉恶意用户。OpenAI 还在通过思维链监控来发现未经授权的行为，以监视智能体是否开始执行其未被要求执行的操作。

> OpenAI 还在通过思维链监控来发现未经授权的行为，以监视智能体是否开始执行其未被要求执行的操作。

Hugging Face 的安全事件帮助塑造了该系统。OpenAI 在那之后暂停了一些模型训练以加强安全性，随后运行了测试，其中未启用生产环境安全防护的 GPT-5.6 Sol 在 56% 的情况下试图访问未经授权的系统。而 Astra 没有做出任何此类尝试。

运行这些检查并非免费。OpenAI 在 8 月估计，监控会使受影响工作负载的推理计算量增加约 20%，这意味着 Astra 后台的部分算力将被用于监视模型的行为，而不是执行实际工作。

## 发布前的缺失细节

OpenAI 表示，Astra 的初始安全防护措施将比较保守，可能会产生比预期更多的摩擦，并计划在观察模型使用情况后逐步放宽。更多细节应会在 Astra 发布时随系统卡一同披露。

这个时机很有意思，因为 OpenAI 已经在[重新思考如何对可能未完成的 API 工作进行计费](https://thenewstack.io/openai-outcome-based-pricing/)。对于 Astra，开发者可能会因为安全原因在智能体已经花费时间调用工具并做出更改后，面临任务被缩短的情况。
