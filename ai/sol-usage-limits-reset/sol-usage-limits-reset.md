OpenAI 修复了 GPT-5.6 Sol 在执行任务时因频繁调用工具和后台等待而快速消耗使用配额的问题。公司承认此前低估了复杂 AI 代理场景下的 Token 消耗，并已通过后台优化提升了约 18% 的任务效率。

> 译自：[OpenAI fixed GPT-5.6 Sol’s most frustrating flaw: Burning limits while it waits](https://thenewstack.io/sol-usage-limits-reset/)
> 
> 作者：Amanda Caswell

**OpenAI 本月早些时候推出了 [GPT-5.6 Sol](https://thenewstack.io/openai-gpt-56-live/)**，这是一个专为更严苛的编码任务而构建的模型。但没过多久，高级用户就开始抱怨他们的 ChatGPT Work 和 Codex 使用配额消耗速度远超预期，即使是在那些看起来大部分时间都在等待工具运行的任务中也是如此。

作为回应，OpenAI 重置了 ChatGPT Work 和 Codex 用户的使用配额，并推出了后端推理改进，称这些改进应能使典型的 Sol 会话时长延长约 18%。

这次更新解决了当前的燃眉之急，同时也暴露了任何构建或部署 AI 代理的人所面临的一个根本性转变。

在 X 上的一篇帖子中，OpenAI 工程负责人 [Thibault Sottiaux](https://www.linkedin.com/in/thibault-sottiaux-27195366/) 承认，公司低估了现实世界中代理执行的成本。

“GPT-5.6 Sol 更愿意长时间工作、进行额外的工具调用，并跨工具和子代理协调复杂的工作流，”Sottiaux 写道。“这使它在解决难题方面表现更好，但一些任务的使用量远超我们的预期。”

> “GPT-5.6 Sol 更愿意长时间工作、进行额外的工具调用，并跨工具和子代理协调复杂的工作流。这使它在解决难题方面表现更好，但一些任务的使用量远超我们的预期。”

## Sol 意想不到的 Token 胃口

Sottiaux 将大部分意外使用量归因于 Sol 新的程序化工具调用，即“代码模式”。通过允许模型在工具于后台运行并协调更复杂工作流的同时继续工作，Sol 最终消耗了远超 OpenAI 预期的 Token。该公司承认，其测试未能捕捉到模型发布后高级用户会做些什么。

“我们本应更早意识到这一点，并更坦诚地对待它，”Sottiaux 写道。

> “我们在发布前非常关注平均值和中位数使用情况，却忽略了一些长尾效应可能导致使用量大幅增加的情况。”

## 高级用户暴露了边缘案例

大多数开发者以前都遇到过这种情况。系统在测试中表现良好，但高级用户却暴露了在典型工作负载下从未出现过的边缘案例。AI 编码代理使得这些问题更容易被忽视，因为它们的大部分工作都在后台进行。

“普通用户实际上发现 Sol 的 Token 使用效率相当高，”Sottiaux 指出。“而一些处理较难任务的高级用户则发现他们的配额消耗得更快。我们在发布前非常关注平均值和中位数使用情况，却忽略了一些长尾效应可能导致使用量大幅增加的情况。”

## 代理在等待时“烧掉”了 Token

在 openai/codex GitHub 仓库中记录自己经历的开发者们提供了对正在发生的情况的见解。一位用户描述了一次 43 分钟的编码会话，该会话生成了近 300 次模型响应，以及 96 次执行调用和 192 次等待调用，在很大程度上通过等待工具结果消耗了五小时配额中的剩余 42%。

另一位用户发现，看起来相互独立的任务被一个接一个地执行，而不是同时执行，这延长了运行时间，并在 700 多个执行单元中增加了 Token 的使用量。

OpenAI 的初步回应重点在于使这些工作流更高效。该公司改进了 Sol 在等待工具调用时的行为，简化了网络搜索，并在变更推出期间暂时取消了五小时的使用上限。

## 聊天限制遇到代理工作负载

这些修复措施应该能让 Sol 更高效，但也强调了订阅限制是围绕聊天设计的。编码代理则不同。它们可以花费 30 或 40 分钟来完成一项任务，进行工具调用并修改代码，然后再返回结果。这使得开发者很难预测单个作业会消耗多少额度。

> 订阅限制是围绕聊天设计的。编码代理则不同。
