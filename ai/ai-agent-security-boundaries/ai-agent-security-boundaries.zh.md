**让多个 AI 机器人同时工作**，其中一个产生的错误可能不会局限于其指定的任务。例如，该错误可能会波及另一个机器人的文件和登录凭据，甚至影响运行它们的所有计算机。本月发布的两个产品为企业提供了截然不同的风险控制方式。

8 月 17 日，[Nous Research](https://nousresearch.com/) 宣布其 [Bot Mode](https://github.com/NousResearch/Hermes-Bot-Mode) 将随 [Hermes Agent v0.20.3](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.8.16.2) 默认启用，将智能体配置转换为一组具名的机器人，它们可以相互移交工作。大约一周前，SpaceXAI 推出了 [Grok Bot](https://x.ai/news/introducing-grok-bot)，其界面几乎如出一辙：一个侧边栏，列出具名的团队成员，它们可以登录您的工具，并在您合上笔记本电脑后继续工作。

虽然界面在一周内趋于统一，但每个平台团队都必须面对的问题却没有统一答案：*当一个机器人出错时，它能触及什么？*

目前有四个项目给出了各自的答案，且没有两个是完全一致的。

1. Grok Bot 以用户账户为界线。
2. Hermes 以配置文件为界线。
3. [OpenClaw](https://docs.openclaw.ai/gateway/sandboxing) 以可选的运行时沙箱为界线。
4. [ClawFleet](https://github.com/clawfleet/ClawFleet) 以容器为界线。

综上所述，文档显示该行业在“持久化同事界面”上的融合速度，远快于对“什么是身份”或“安全边界”的共识。

## 四个项目，四种书面答案

目前，这些产品中的每一个都提供了相同的交互界面。您创建多个具名智能体，分配不同的工作，并让它们在彼此之间传递任务。单从命名惯例来看，似乎存在隔离，因为名为“费用管理器”（Expense Manager）和“人才搜寻者”（Talent Scout）的机器人听起来就像在共享办公室里占据着不同的房间。

但文档却显示事实并非如此，且每种情况的描述都不尽相同。隔离单位在一种产品中是账户，在另一种中是配置文件目录，在第三种中是可选容器，在第四种中则是部署拓扑结构。这四个单位不能互换，如果操作员认为“名册本身就是边界”，那么在四个案例中，只有一种情况是正确的。

## Grok Bot 是否对自己想成为什么感到困惑？

SpaceXAI 的[发布文章](https://x.ai/news/introducing-grok-bot)开篇承诺机器人拥有自己的计算机。而同一天更新的[文档](https://dx.x.ai/grok-bot/computer-and-apps)则描述了一个分配给用户账户而非任何单个机器人的持久化云端计算机。浏览器 Cookie 和登录会话在整个名册中共享，文件对每个机器人可见，命令行凭据也是共享的。一个机器人可以接手另一个机器人保存的工作。

每个机器人在该机器上都有自己的屏幕，这允许它们并行运行浏览器和桌面工具。SpaceXAI 直接说明了这些屏幕“不是”什么。文档称它们为“独立的工作界面，而非独立的安全边界”。随后，它指示操作员：如果账户上的其他机器人无法使用某凭据或文件，则应将其完全移除出该机器。

后果不仅限于凭据。因为浏览器是共享的，为一个机器人登录会使该会话对其他机器人也可用。已安装的[连接器](https://dx.x.ai/grok-bot/computer-and-apps)是账户范围内的，其可用性并未隔离到单个机器人。共享工作区位于 `/workspace`，旨在在计算机更新和恢复后依然存在，因此持久化状态在整个名册中是共享的。

这一切都不是实现上的意外。这正是使机器人之间的移交变得低成本的原因，而低成本移交正是其产品核心。但只阅读发布页面的操作员会建立一个与文档相悖的心理模型，而这种差距正是风险所在。

## Hermes 为每个机器人提供独立的配置文件

Nous 采取了相反的架构立场。在 [Hermes](https://github.com/NousResearch/hermes-agent) 中，机器人就是一个配置文件，每个配置文件都有自己的配置、内存、技能、凭据和存储在磁盘特定目录下的聊天历史。机器人之间的移交是针对命名配置文件的真实调用，而不是在单个进程内传递的共享上下文块。

Nous 将团队成员协议作为 [v0.20.3](https://github.com/NousResearch/hermes-agent/releases/tag/v2026.8.16.2) 的一部分发布，同时进行了 [MCP](https://modelcontextprotocol.io/) 2.x SDK 迁移和一系列运行时加固更改。在合并完成后，公司归档了[独立的插件仓库](https://github.com/NousResearch/Hermes-Bot-Mode)。机器人模式默认开启，因此更新 Hermes 的用户无需手动选择即可获得机器人名册。

在将此视为“容器化”之前，有两个限制需要注意。独立的凭据存储并不能保证凭据不同，因为新配置文件中最终包含的内容取决于操作员如何创建它以及后续编辑了什么。此外，每个配置文件仍然共享宿主机、操作系统用户及其文件系统权限。Hermes 记录的是工作站级别的智能体状态分离，这比共享云账户的默认设置意义上更强，但这并不等同于隔离。

## OpenClaw 的沙箱默认处于关闭状态

OpenClaw 记录了四个项目中边界最完整的情况。当通过 Docker 后端启用[沙箱](https://docs.openclaw.ai/gateway/sandboxing)时，智能体工具的执行会在隔离的容器内运行。同时，网关保留在宿主机上，范围可以选择为每个会话、每个智能体或跨智能体共享。每个范围都有自己的[工作区](https://docs.openclaw.ai/concepts/agent-workspace)。身份验证材料存在于每个智能体的[智能体作用域身份验证配置文件](https://docs.openclaw.ai/concepts/multi-agent)中。操作员可以在此基础上配置网络隔离、资源限制以及允许或拒绝工具策略。

该沙箱模式的[记录默认值](https://docs.openclaw.ai/install/docker)为关闭。对于大多数在笔记本电脑上运行项目的用户来说，这是一个可以辩护的选择，因为容器开销对于单用户威胁模型而言收益甚微。底层的设置行为值得更多关注。如果沙箱先决条件在设置过程中失败，脚本会将沙箱模式重置为关闭，而不是拒绝启动。因此，旨在实现隔离却遇到 Docker 套接字问题的操作员，最终会在没有沙箱隔离的情况下运行。文档还警告不要将宿主 Docker 套接字挂载到智能体沙箱容器中，并将 CLI 容器与网关共享的网络命名空间标记为本身就是一个信任边界。

ClawFleet 通过将问题转移到部署拓扑中来回答同样的问题。该项目记录了一个[包装器](https://github.com/clawfleet/ClawFleet)，将每个 OpenClaw 或 Hermes 智能体放在其自己的 Docker 容器中，具有隔离的文件系统和网络。它列出每个 OpenClaw 实例约 500 MB 内存，每个 Hermes 实例约 150 MB。这种成本就是其他三个项目将边界设为可选或跳过它的原因，通过列出具体数值，这种权衡变得清晰可见。

## 如何选择适合您的机器人

| 场景 | 文档适配度 | 基本原理 |
| --- | --- | --- |
| 必须在合上笔记本电脑后继续进行的持久化工作 | Grok Bot | 四者中唯一具有厂商运行的始终在线云计算机，代价是整个名册共享一个凭据面 |
| 在同一工作站上具有完全不同凭据集的多个智能体 | Hermes | 每个配置文件的存储是文档建议的默认设置，且机器人模式已启用 |
| 不受信任或多租户智能体会话 | 启用沙箱的 OpenClaw | 具有可配置网络和工具策略的每个智能体或每个会话的容器范围，前提是操作员必须开启并验证它 |
| 作为部署模型而非运行时设置的隔离 | ClawFleet | 每个智能体对应一个容器，具有独立的文件系统和网络，需权衡实例的内存成本 |

## 每个项目都给操作员提供了不同的建议

操作指南与架构一样存在严重分歧。OpenClaw 的文档读起来像基础设施文档，列出了特定的危险（如 Docker 套接字和共享网络命名空间），并告诉操作员什么不该做。Hermes 记录了配置文件布局和协议，然后将策略留给操作员。Grok Bot 的指导大部分是警告本身，指示将账户作为边界，并完全将敏感凭据从共享机器上移除。

Grok Bot 带有第二个值得与第一个一起阅读的免责声明。敏感操作通过[审批机制](https://dx.x.ai/grok-bot/approvals-security-and-privacy)路由。SpaceXAI 记录了触发此机制的类别，包括发送消息、发布内容、购买和转账、删除数据以及触及生产环境。执行是通过 LLM 分类器进行的。[Cursor](https://cursor.com/) 关于同一引擎的文档明确指出，该分类器不是安全边界，并且可能会出错。因此，评估该产品的购买者会发现这句话出现了两次，分别附加在他们最合理地认为能保护他们的两个机制上。

## AI 智能体仍然缺乏自己的身份

企业今天可以采用这四种产品中的任何一种并完成实际工作，诚实的解读是，这四种产品都在针对不同的威胁模型，以诚实守信的态度构建边界。但它们都没有提供智能体的身份。在每种情况下，机器人都是借用操作员的凭据，无论是来自共享的云端浏览器、配置文件目录还是容器卷，整个安全讨论归根结底是这些被借用的凭据能走多远。

> “没有标准化的原始定义，因此每个项目都在它已经控制的层级上发明了一个边界：账户、配置文件、运行时或容器。”

这就是四个答案差异如此巨大的原因。没有可以标准化的原始定义，因此每个项目都在它已经控制的层级上发明了一个边界：账户、配置文件、运行时或容器。预计这种差距将在身份侧而非智能体侧缩小，通过作用域委托和由身份提供者颁发的每个智能体的凭据，而不是从人类那里复制。在此之前，平台团队有效的做法是务实且具体的。在查看发布页面之前，先阅读安全页面，因为对于此类产品，它们描述的是完全不同的东西。
