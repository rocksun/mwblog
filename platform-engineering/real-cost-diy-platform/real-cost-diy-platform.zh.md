这篇文章探讨了在五年内构建内部开发平台的实际成本，以及为什么大多数“我们自己写一个”的方案往往低估了投入。

如果按照大多数企业最终采用的方式来构建和运营自己的内部开发平台，每年需要投入60人和750万美元。由于这些成本分散在“工程”部门下的多个成本中心，大多数签字批准的执行官根本看不到这个总数。

他们听到的低成本版本——一个团队、周末加班、一个带有少量YAML的控制平面——虽然能发布v1版本，但最终会变成没人愿意接手的维护负担。而真正有效的版本是一个拥有60人的产品工程组织，且需无限期投入。以下数据来自我参与更新的 [VMware Tanzu Platform 白皮书](https://images.sw.broadcom.com/Web/CAInc2/%7B68c6ad82-a684-4e39-8feb-12803e4b1f0e%7D_The_Upside_Down_Economics_of_DIY_PaaS.pdf)，如果你觉得有必要，可以先带上对供应商的审慎眼光来看待。但其人员结构很适合深入思考。

## 从周末项目演变成60人的无限财务承诺

根据我的观察，如果你将平台团队与 [CNCF 平台参考架构](https://tag-app-delivery.cncf.io/whitepapers/platforms/) 对齐，你最终会得到大约七个产品团队：基础设施、运维、部署、运行时与中间件、数据库、安全，以及教练/开发者赋能。每个团队都是传说中的“两个披萨团队”，即7-9名工程师。在 [构建自己的平台](https://thenewstack.io/internal-platforms-are-products/) 时，根本不存在什么精简版团队。再加上几个Scrum Master和产品经理来协调和管理，总共大约需要60人。按每位工程师每年12.5万美元的保守薪资计算，你每年的工资支出为750万美元，而且是无限期的。

> “在构建自己的平台时，不存在精简版团队。”

| | | | | | |
| --- | --- | --- | --- | --- | --- |
| | 第一年 | 第二年 | 第三年 | 第四年 | 第五年 |
| 年度支出 | $7.5M | $7.5M | $7.5M | $7.5M | $7.5M |
| 累计支出 | $7.5M | $15M | $22.5M | $30M | $37.5M |

五年下来，仅在构建平台的团队身上，你就花费了3750万美元，这甚至还没算上你的应用开发成本。

## “购买”模式下的实际人力需求

企业购买商业平台而非投入资金进行构建和维护，只需支付运营平台的人员薪资。正如我多年来收集的平台团队规模比例所示，所需的人数要少得多：

### 按开发者人数比例：

* 6,500名开发 / 16名运维
* 2,500名开发 / 5名运维
* 1,200名开发 / 6名运维

### 按应用开发团队比例：

* 45个应用团队 / 5名运维
* 300个应用团队 / 4名运维

### 按应用数量比例：

* 350个应用 / 7名运维
* 300个应用 / 8名运维

这些数字之所以更低，是因为上述团队不需要从零构建并持续升级平台。他们避免了对平台维护的持续需求，转而专注于：API、集成、开发者框架、安全流水线、仪表盘、升级工具、开发者所需的下一个AI能力，以及审计员要求的下一个合规方案。

在与多年来构建自有平台的组织交流中，我发现存在一个影子“平台工程组”。每个开发组往往至少有一个人（甚至更多）在做平台和应用团队之间的粘合工作。这通常涉及构建和流水线集成、安全，或者仅仅是弄清楚如何部署应用并连接到服务。这些人力成本在商业论证的电子表格中完全没有体现。

## 为什么这被忽视了

当你扩展构建平台而非购买平台的成本时，你会更清晰地看到 [构建 vs 购买](https://thenewstack.io/build-vs-buy-the-platform-engineers-guide/) 的价值。相比之下，如果你不进行模型对比，商业平台的可见成本就是采购订单上的一个许可数字。而自研的人员开支则分散在多个成本中心，通常在暗中进行，看起来就像正常的招聘。许可数字写在纸上，一目了然；自研的总成本必须手动计算，而且没人会去对所有人的人头数进行SUM求和。

## 按设计运行

工程师们也会对自己构建平台这件事进行“自我叙事”。人们因发布平台而获得晋升，“我们发布了一个基于Kubernetes构建的平台”在晋升报告里比“我们将所有人接入了一个付费购买的工具”要好看得多。这不是道德缺陷，而是许多工程组织及其支付薪水的HR政策运作的方式（我希望是无意的）。这种模式被称为 [简历驱动开发 (RDD)](https://arxiv.org/abs/2101.12569)，甚至有一项关于它的研究。

当员工根据交付新技术的能力获得报酬和声望时，他们就会开始追求新技术技能和业绩记录。这让他们在当前工作中获得更多补偿，并为跳槽到其他薪水更高的职位做准备。但是，正如一项研究所发现的那样，这种模式并不能带来卓越的运营效果：

| |
| --- |
| 因此，基于RDD的广泛技术选型可能会导致软件变得复杂甚至无法维护，这些技术可能不符合需求，不被当前或未来的员工所熟悉，或者未能兑现承诺并被废弃。 *–“*[*简历驱动开发：定义与实证特征*](https://arxiv.org/abs/2101.12569)*,” Jonas Fritzsch, Marvin Wyrich, Justus Bogner, Stefan Wagner, 2021年1月。* |

在这种功能失调的系统中，英雄主义越多，奖励就越多。而构建自己的平台需要大量的英雄主义，所以它很有吸引力。

## 被甩在身后

在ROI方面，破坏性最大的因素是速度差距。当你自研时，供应商会持续发布更新；你也在发布，但你是对着移动的目标在射击。我们的 [白皮书](https://images.sw.broadcom.com/Web/CAInc2/%7B68c6ad82-a684-4e39-8feb-12803e4b1f0e%7D_The_Upside_Down_Economics_of_DIY_PaaS.pdf) 指出，商业创新曲线在12-18个月内就会超越大多数自研项目，而且差距会越来越大，而不是缩小，因为供应商的团队比你大，他们的路线图由他们所有的客户资助，而不仅仅是你们一家公司。在第三年的会议上，当有人说“我们需要添加供应商X上个季度发布的AI服务”时，ROI就悄然蒸发了。

## 给战略迷的建议：200年前的比较优势理论

外包非核心基础设施的概念比计算机还要古老。1817年，David Ricardo提出，即使你某件事做得很好，你也应该专注于你最擅长的事情，并用它来交换其他东西。葡萄牙可以种植葡萄并纺织布料，但它专营葡萄酒并与英国交换布料，因为那是边际收益最高的地方。

> “在第三年的会议上，当有人说‘我们需要添加供应商X上个季度发布的AI服务’时，ROI就悄然蒸发了。”

如果你不喜欢19世纪初的经济学思想领导力，[Simon Wardley用他备受推崇的Wardley地图更新了这一思想](https://blog.gardeviance.org/2013/01/a-first-map.html)：任何已经成为商品的东西都应该购买而不是构建，这样你稀缺的工程产能才能用于那些真正让你在竞争中脱颖而出的业务部分。

Abby Bangser在 [KubeCon NA 2025](https://www.youtube.com/watch?v=gmAfYEPBYr0) 上用简单明了的语言表达了这一点：

*“这不是关于重新构建我们在市场上可以买到的东西。而是要确保我们将时间花在构建那些为我们组织量身定制且重要的事情上。”*

对于大多数组织来说，平台本身并不是你的差异化优势所在。你的应用才是！平台是管道——必要且有价值的管道，但终究只是管道。一个有用的测试：你的客户会因为你的平台而选择你而不是竞争对手吗？在荷兰超市行业，Albert Heijn和Jumbo的答案是“不”——购物者关心价格、应用和结账，而不是后台的编排器。对于Picnic，答案是“是”，但仅限于其中一点—— [那些使其最后一公里经济效益得以实现的定制窄型送货卡车](https://www.ey.com/en_nl/insights/ai/how-technology-made-picnic-the-undisputed-market-leader)。除此之外的一切，包括平台，他们都是购买的。了解你是哪种企业，就能回答构建与购买的问题。

让你们最优秀的工程师把职业生涯花在 [编写YAML](https://thenewstack.io/kubernetes-is-getting-a-better-yaml/)、将持续集成接入仓库、跟踪容器基础镜像中的CVE上，是一种降级交易。你正在将自己拥有的最昂贵的资源之一——工程产能，浪费在供应商可以为你打理的事情上。机会成本就是你本可以用这些产能构建的其他东西：那些真正能推动业务发展的应用。

## 该怎么做

对于现在正盯着这个决策的人，这里有三个务实的行动：

* 在开会前计算总人力成本。60人是上限，如果你偷工减料，30人是下限。无论哪种情况，乘以你们的全额工程成本，并将数字放到演示幻灯片上。许可费用与工程师成本的对比本身就能结束大多数这类争论。不要忘记将这个数字推算到一年、三年、五年及更久。历史表明，平台会伴随你们很长时间。

* 诚实面对第三年。你需要计算出完整平台以及维持其运行所需的一切成本。这包括维护、集成以及随着开发者要求供应商在上两个季度发布的功能而产生的持续新特性成本。看看过去两年AI的变化和改进频率。你的平台团队能跟上那个速度以确保你能获得 [那些诱人的新AI能力](https://www.youtube.com/watch?v=lp1vGxDurOc) 吗？

* 构建面向开发者的层级，购买其余部分。门户、黄金路径、针对特定业务系统的集成具有差异化价值，所以去构建它们。基础设施、可观测性背板、密钥、证书管理、容器仓库是商品，所以去购买它们。

每个构建内部平台的企业，无论高管们是否承认，其实都在选择在公司内部建立一个小型的平台供应商。运营平台供应商的经济学原理众所周知，且大部分是惩罚性的。走这条路的公司至少应该知道他们在做出的选择。大多数公司不知道，因为这个选择从未被公开讨论。它是通过惯性做出的，就是在有人说“我们要不在这个周末自己写一个”的那个会议上做出的。

> “停止构建平台。开始构建应用。”

你应该避免这些混乱，转而 [购买一个平台](https://www.vmware.com/products/app-platform/tanzu)。或者更直接地说：停止构建平台，开始构建应用。
