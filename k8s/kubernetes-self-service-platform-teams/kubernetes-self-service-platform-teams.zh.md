**开发人员想要什么？** 需要时就能立刻获得的 Kubernetes 环境。

**他们*不*要什么？** 经过一周或更长时间审批工单才能拿到手的环境。

与此同时，平台团队则需要掌控这些环境的成本、谁有权访问它们，以及它们是否符合公司政策。

这种张力正是 Kubernetes 自助服务的核心所在：什么可以安全地交由开发人员处理，什么仍然属于平台团队？

在最近对企业云专家的采访中——Hewlett Packard Enterprise (HPE) 的高级首席产品经理 [Marius Bogoevici](https://www.linkedin.com/in/marius-bogoevici/)，以及 HPE Morpheus Software 的首席产品经理 [Karthik Subramanian](https://www.linkedin.com/in/karthik-subramanian-lnkd/)——*The New Stack* 探讨了 Kubernetes 自助服务的核心摩擦点。对话的焦点与其说是自助服务是否可取，不如说是边界应该画在哪里。

HKS（HPE 的 CNCF 认证 Kubernetes 发行版）与 [HPE Morpheus Software](https://www.hpe.com/us/en/products/software/morpheus-software.html) 进行了集成，帮助平台团队交付和进行 Kubernetes 环境的生命周期管理，将其作为涵盖 Kubernetes、虚拟机、基础设施和云的更广泛运营模型的一部分。[HPE Morpheus Advanced Software](https://www.hpe.com/us/en/products/software/morpheus-software/features.html) 支持配合 HKS 的本地私有云用例，而 HPE Morpheus Enterprise Software 则将 Kubernetes 和应用程序运营扩展到混合云和公共云环境。

HKS 和 HPE Morpheus Software 共同将该运营模型扩展到基础设施配置之外。通过服务和应用程序目录，平台团队可以将经过批准的 Kubernetes 环境与开发人员已经在使用的 CI/CD 管道、容器镜像仓库、自动化工具和其他服务连接起来。开发人员获得的是一条受治理的、从代码到部署的就绪路径，而无需为每个项目手动拼凑工具链。

## **自助服务的悖论**

开源 Kubernetes 提供了编排和声明式 API，但并没有提供完整的运营模型。

Subramanian 表示，构建自己的自助服务层的团队通常会遇到两个反复出现的问题：

1. **工具和软件包蔓延：** 为了使上游 Kubernetes 达到生产就绪状态，平台团队必须策划和维护一个不断演进的第三方 CNCF 工具生态系统，用于网络 (CNI)、存储 (CSI)、入口 (ingress)、身份认证和策略执行。导航和支持这个分散的堆栈会为内部平台团队产生巨大的维护开销。
2. **Day-2 生命周期和混合足迹复杂性：** 启动一个 Kubernetes 集群是简单部分，但保持其最新状态——跨越开发、QA、staging 和生产环境——才是堆积工作的地方。这就是为什么 HPE 表示，必须对照其周围的网络、存储、入口、身份和策略组件来检查每次 Kubernetes 升级。当集群跨越裸机、私有云、边缘站点和公共云时，这个问题会变得更加困难，因为一次性脚本和环境特定的配置会迅速产生偏差。这种维护负担应该由平台团队承担，而不是由试图交付应用程序的开发人员承担。

赋予开发人员对原始 Kubernetes API 的直接访问权限只是转移了运维工作——它远没有彻底消失。事实上，开发人员最终将花时间调试清单和存储驱动程序，而不是编写代码。

与此同时，运维团队必须处理过度配置、闲置集群以及未经审查就进入生产环境的配置。

## **开发人员控制什么——平台提供什么**

实际的答案不是不受限制的访问。而是一条铺平的路径：开发人员可以自行请求的已批准的 Kubernetes 服务，其访问、配置、放置、审批和生命周期控制均由平台团队定义。

Bogoevici 告诉 *The New Stack*：“自助服务的最佳候选者是那些可重复的、低风险的且易于理解的请求。例如，开发人员应该能够请求开发集群、部署批准的应用程序、创建命名空间，或者从预先批准的配置中选择资源，而无需打开工单。平台团队决定安全配置长什么样，而开发人员则从支持菜单中进行选择。”

> “平台团队决定安全配置长什么样，而开发人员则从支持菜单中进行选择。”

HPE Morpheus 没有要求开发人员为 ingress、存储类和 RBAC 编写 YAML，而是通过服务目录、可重用布局和蓝图、工作流、基于角色的访问控制、审批、API 和自动化来暴露这些选择。开发人员不会失去 Kubernetes。他们在允许的情况下通过标准的 Kubernetes 接口和工具保持直接访问，而平台团队则围绕他们标准化请求、治理和生命周期流程。

这些目录项可以打包的不仅仅是基础设施设置。它们还可以集成支持开发工作流程的已批准服务和应用程序组件——包括 CI/CD 工具、源码和制品库、容器镜像仓库以及运行时依赖项——同时平台团队控制这些组件的配置和治理方式。

开发人员选择对应用程序至关重要的参数：

* **批准的 Kubernetes 版本和集群大小：** 从预先测试的 Kubernetes 运行时版本和节点计数模板中进行选择。
* **资源配额：** 指定针对工作负载定制所需的 CPU、RAM 和持久存储容量。
* **集成的工具集和 IDE 环境：** 选择所需的开发人员工具链、容器镜像仓库和运行时依赖项。
* **租约和持续时间限制：** 为临时的开发或沙盒集群定义明确的操作生命周期，以防止废弃的基础设施蔓延。

网络隔离、身份提供商集成、安全策略和成本分摊由平台团队保留，并通过批准的服务配置自动应用。

同样的责任划分也适用于交付工具链：开发人员从批准的服务中进行选择，而平台团队则在后台管理集成、凭据、策略和自动化。这为开发人员提供了连贯的体验，而无需将工具链维护和治理转嫁给各个应用程序团队。

责任划分如下所示：

| **服务区域** | **开发人员选择或请求** | **平台团队定义和提供** | **审查或例外路径** |
| --- | --- | --- | --- |
| 开发集群配置 | 批准的 Kubernetes 服务、版本、大小、目标环境和持续时间。 | 可重用布局或蓝图、访问控制、放置规则、存储和网络默认值以及生命周期策略。 | 非标准版本、放置、配置或超出配额的请求。 |
| 生产部署 | 应用程序制品、目标命名空间和通过批准路径的部署请求。 | 适合环境的 RBAC、租约、策略、审计、备份和发布控制。 | 针对生产更改和异常的正式审查。 |
| 资源分配和配额 | 项目限制内的 CPU、内存、存储和其他批准的容量参数。 | 项目配额、上限、放置约束和支持的资源配置文件。 | 超出配额或针对专用资源的请求。 |
| 网络和安全 | 批准模式内的应用程序端点和允许的连接性。 | 身份集成、RBAC、租户隔离、网络策略、密钥和审计控制。 | 跨租户访问、提升的权限或对基线安全策略的更改。 |
| 生命周期和成本治理 | 服务寿命和批准的操作行为。 | 许可变体的可见性、策略、审批、退役工作流和适用的成本控制。 | 长时间运行的异常、非标准生命周期操作或预算异常。 |

## 从工单队列到可重复的铺平路径

在传统的 IT 环境中，为新项目配置专用的 Kubernetes environment 通常涉及跨部门的工单交接，涵盖基础设施、网络、安全和存储团队。这种摩擦通常会将配置时间从几天延长到几周。

HPE 表示，通过将基础设施编排、基于角色的访问控制和多租户统一到单一的运维体验中，HPE Morpheus Software 可以将这些配置工作流压缩到几分钟或几小时。“开发人员可以获得一个符合组织定义控制和策略的可用环境，而无需了解底层的复杂基础设施步骤，”Bogoevici 说。“当你把配置时间从几周缩短到几小时时，这是非常有意义且切实的。”

> “当你把配置时间从几周缩短到几小时时，这是非常有意义且切实的。”

其结果不仅是更快的集群配置。HPE Morpheus Software 还可以通过随环境提供经批准的 CI/CD 和应用程序服务，自动将交接融入开发人员既定的交付流程中。开发人员无需等待单独的团队来连接管道、镜像仓库、凭据和运行时依赖项，而是获得了一条从开发到部署的就绪路径。

更快的配置也会带来另一个问题：速度可以而且将会导致团队忘记配置了什么以及原因。HPE Morpheus Software 为管理员提供了对利用率和成本的可见性，而租约控制可以在临时开发集群到期时将其关闭。

Bogoevici 表示，工单量是衡量成功的糟糕指标，尤其是在早期，当时可能有更多的开发人员在尝试该目录。他建议关注部署成功率、异常率、资源利用率以及保持服务运行所需的日常工作。

## 安全性属于服务设计

安全性是必须设计到自助服务路径中的另一个边界。如果在创建集群后才添加身份、访问、 tenancy 和策略，那么每个请求都会产生更多的工作和更多不一致的空间。

“安全必须是构建在服务之中的核心设计考虑，而不是部署期间的事后想法，”Bogoevici 说。“HPE Morpheus Software 将身份集成、基于角色的访问、租户隔离、审批和策略引入运维工作流。”

新配置的环境应该通过具有附加的适用身份、RBAC、租户、策略和审计控制的批准配置到达。平台团队可以通过测试允许的请求、应该被拒绝的请求以及由此产生的审计记录来验证铺平的路径。

## 运营模型测试

最强大的 Kubernetes 自助服务模型不会隐藏 Kubernetes，也不会使其成为每个工作负载的控制平面。它为开发人员提供了有用、批准的选择以及对他们所需的 Kubernetes 工作流的直接访问，而平台团队则围绕这些工作流标准化企业流程。

这很重要，因为企业除了 Kubernetes 之外，还在运行虚拟机、云和现有基础设施。HPE Morpheus Software 帮助平台团队在这些环境中采用通用的请求、治理、自动化和生命周期流程，而不会强迫每个工作负载都使用一个运行时或创建另一个运维孤岛。

在实践中，这意味着自助服务交付的应该不仅仅是一个 Kubernetes集群。借助 HPE Morpheus Software，目录请求可以将开发人员需要的批准环境、应用程序服务和 DevOps 工具链集成结合起来，同时保留平台团队所需的治理和生命周期控制。开发人员花在组装和排除交付基础设施故障上的时间更少——花在构建和发布应用程序上的时间更多。

展望 2027 年，目标不是不受限制的控制。而是更快的访问、可预测的结果、透明的护栏，以及当标准服务不适用时的清晰异常路径。
