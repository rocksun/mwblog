**当镜像成为瓶颈时：** 机器学习改变了容器镜像的面貌。一个典型的应用程序镜像通常仅几百 MB，几秒钟即可启动。而现代机器学习（ML）推理镜像包含了深度学习框架、CUDA 技术栈，有时甚至还有模型权重。这些镜像的大小通常达到 20 到 30 GB，有的甚至更高。在这些镜像运行的 GPU 和加速实例上，拉取一个镜像往往需要几分钟，应用程序才能处理第一个请求：在这几分钟里，配置好的加速器本可以处理实际工作，却不得不等待镜像下载。

我们在[运行在 Amazon EKS 上](https://thenewstack.io/eks-kubernetes-etcd-scale/)的生产级机器学习平台上遇到了这个瓶颈。团队需要 Pod 在两分钟内就绪，但仅镜像拉取就耗费了数分钟。每个 Pod 除了从共享文件系统加载模型数据外，还要拉取大约 30 GB 的容器镜像。由于镜像会定期重新构建，工作节点（worker nodes）面临冷拉取（cold pulls），没有可用的本地缓存。在拉取镜像的过程中，加速器处于闲置状态，自动扩缩容跟不上需求，导致请求队列堆积。

对于这些超大镜像的拉取耗时，人们首先怀疑的是网络或镜像仓库。毕竟，30 GB 是很大的数据量。然而，通过对镜像拉取路径进行分析后发现，在拥有 100 到 400 Gbps 网络带宽的加速实例上，这两者都不是瓶颈。真正的限制在于软件如何利用现有的硬件。

> “真正的限制在于软件如何利用现有的硬件。”

通过重新思考拉取流水线，利用实例本身已具备的网络带宽、存储吞吐量和计算能力，我们将原本需要数分钟的拉取过程缩短到了几秒钟。这些改进现在已在 EKS Auto Mode 中默认提供，我们也已将核心变更贡献给了 containerd 和 SOCI snapshotter 的上游。这是我们深入研究镜像拉取路径内部机制、识别时间损耗点并重建这些阶段的故事。它始于我们最初的起点：了解大型容器镜像是什么，以及它是如何加载到节点上的。

## 规模化容器镜像的结构

容器镜像并非一个单一文件。它是一组层（layers）的堆栈，外加一个列出这些层的 JSON 清单（manifest）。每一层都是文件系统一部分的 tar 归档文件（一层是基础操作系统，一层是 CUDA 库，一层是你的代码），并经过 gzip 压缩。对于每一层，清单会记录一个摘要（digest），即压缩后字节的 SHA-256 哈希值，以便节点验证其收到的内容与发布的内容完全一致。当容器运行时，这些层会被堆叠并挂载在一起，形成一个统一的文件系统。

以下是直接从镜像仓库清单中测量得到的真实机器学习镜像的大小情况：

| | | | |
| --- | --- | --- | --- |
| **镜像** | **压缩后大小** | **层数** | **最大层** |
| **AWS DJL LMI 21.0 Inference (cu129)** | 16.5 GB | 29 | 9.5 GB |
| **AWS PyTorch Training NeuronX 2.7.0** | 12.8 GB | 21 | 3.9 GB |
| **AWS SageMaker Distribution 4.2.1 GPU** | 10.5 GB | 28 | 9.4 GB |

请注意，镜像内的层大小并不大致相等。单层可能会占总镜像的一半以上，单个层经常达到 9 GB 或更大，而其余层则相对较小。这种大小差异直接影响了拉取耗时，下文将对此进行解释。

将这些层加载到节点上涉及六个阶段，传统上，作为行业标准的容器运行时 containerd 会按顺序执行这些操作。

## 拉取的各个阶段

![显示容器镜像拉取六个阶段的图表](https://cdn.thenewstack.io/media/2026/08/4f07e41c-image-1024x378.png)

对于每一层，containerd 会按顺序执行六个操作。前三个是下载阶段：通过单一 HTTP 连接从镜像仓库获取压缩字节，通过计算 SHA-256 并与清单摘要进行比对来验证字节，然后将压缩后的 blob 写入本地磁盘。

接下来的三个是解压阶段：解压缩 gzip 归档文件，通过计算第二个 SHA-256 来验证解压后的内容，并将文件提取到由 containerd snapshotter（负责存储和提供层级磁盘表示的组件）管理的本地快照目录中。默认情况下，containerd 支持并行下载最多三个层，但每个层使用单一连接，且解压过程在各层之间保持严格的串行化。

有两个细节值得注意。上述提到的两次 SHA-256 检查都是由开放容器倡议（OCI）规范强制要求的，对于多 GB 的层来说，每次哈希计算都需要实际的计算工作。第一次是对压缩字节计算，用于证明下载过程未被破坏或篡改。

第二次是对解压后的内容进行计算。它为运行时提供了层级实际文件系统数据的稳定指纹，这使得运行时能够识别不同镜像间的共享层，从而避免冗余解压。对于大层级，解压是另一项看似简单实则开销巨大的操作：gzip 解压后的大小通常会增加到原来的三倍，且由于每个块都依赖于前一个块，它只能在单核上运行。与此同时，实例的其他部分处于闲置状态。

下载层可以并行化，但解压序列是逐层运行的。直到第一层完成了所有六个阶段，第二层才能开始。结果是，在拉取的任何时刻，节点都只受限于一种资源：下载时的网络带宽、解压和哈希验证时的 CPU，或提取时的磁盘吞吐量。其他资源则在流水线中等待轮候。

> “由于层的大小不均，最大的单一层成为了流水线中的瓶颈。”

由于层的大小不均，最大的单一层成为了流水线中的瓶颈。一个需要单核解压一分钟的 10 GB 层会阻碍整个镜像的加载，即使其他层只需几秒钟即可完成。总拉取时间实际上取决于那个主导层通过所有六个阶段的时间。

## 现有方法：绕过拉取瓶颈

目前有几种公认的方法可以缩短镜像拉取时间。每种方法都在以不同的方式规避瓶颈，无论是通过修改镜像、缓存镜像，还是依赖架构中其他部分的辅助。

**镜像体积缩减：** 最直接的方法是通过多阶段构建（multi-stage builds）、无发行版基础镜像（distroless base images）和剥离未使用软件包来减小镜像体积。对于机器学习工作负载，这会触及硬性限制。仅 GPU 软件栈（PyTorch, cuDNN, CUDA）就强加了约 3 到 4 GB 的压缩基准，任何构建优化都无法消除。此外，机器学习镜像是由跨组织边界组装的：平台团队提供 OS 和驱动，框架团队添加深度学习库，研究人员贡献应用程序代码和模型权重。没有单一团队能控制最终工件；模型权重经常被直接构建进镜像中，因为服务框架期望本地路径，而多阶段构建对于大部分内容不可删减的镜像来说，只能节省极小的空间。

**镜像缓存（预拉取）：** 通过将镜像内容快照到卷中并在配置时挂载，从而在节点上缓存镜像，以便后续启动跳过拉取过程。这对于稳定的镜像有效，但会为每个镜像版本增加一个专门的流水线阶段。对于机器学习工作负载，挑战在于频繁的重建：一种常见的模式是一个 Pod 消耗整个节点，因此节点随着调度决策而扩缩，每个新节点都面临完整的冷拉取。这限制了预缓存仅适用于具有长期、静态节点池的工作负载。

> “仅 GPU 软件栈（PyTorch, cuDNN, CUDA）就强加了约 3 到 4 GB 的压缩基准。”

**镜像仓库端优化：** 有些方法是在远程提供镜像内容，而不是将其拉取到节点。例如，阿里巴巴的 DADI 将容器镜像呈现为远程块设备，节点按需挂载，无需离散的拉取步骤。这消除了仅访问部分镜像内容的工作负载的启动延迟。然而，容器在其生命周期内仍依赖于网络，并且需要专门构建的服务基础设施，这在不同提供商之间可能无法移植。

**延迟加载（Lazy loading）：** 不预先拉取整个镜像，而是立即启动容器并按需获取文件内容。该领域的项目包括 eStargz 和 Nydus（需要将镜像转换为新格式），以及 AWS 的 SOCI（Seekable OCI），它在未经修改的镜像旁边添加了一个可寻址索引。当容器在启动时仅触及一小部分数据时，这些技术效果很好。然而，机器学习镜像在处理第一个请求之前会密集访问框架、CUDA 库和模型权重，因此几乎所有数据最终都会被获取。对于这些工作负载，拉取流水线本身需要更快。

**集群内点对点分发：** 像 Dragonfly（CNCF 毕业项目）和 Spegel 这样的工具将已有镜像的节点变成需要镜像节点的“种子”，减少镜像仓库出站流量并加速滚动部署。然而对于机器学习工作负载，第一个节点仍然面临完全的冷拉取，且当镜像频繁重建时，没有节点拥有新版本的缓存。点对点分发是对拉取流水线本身改进的补充，而不是替代。

## 修复镜像拉取流水线

在[拉取流水线](https://thenewstack.io/solving-the-validation-problem/)的六个阶段中，我们专注于两个：从镜像仓库下载层 blob 以及在节点上解压层。这些是耗时最长且串行化成本最高的地方。

由于 SOCI 已经是一个开源的 containerd 快照插件，并且具备拦截和自定义拉取路径的管道，它成为了我们开发和验证这些变更的实验场，之后我们将其贡献给了 containerd 上游。

### 下载：将单个层拆分为多个请求

containerd 传统上使用单一 HTTP 连接来下载每一层。我们发现，将一层拆分为固定大小的块，并使用 HTTP 范围请求（range requests）通过单独的连接并行获取它们，速度会快得多。与此同时，containerd 社区也独立地在 containerd 2.1 中增加了并行分块下载支持，我们也基于相同的原则在 SOCI 快照器中进行了实现。

然而，有一个显著的区别使我们能够保持运行时的内存占用恒定，而与镜像大小无关。区别在于数据块在到达和最终组装之间存在于何处。我们的实现方式是在数据块到达时将其直接写入本地磁盘，而 containerd 则是在组装层时将其保存在内存中。这意味着无论你是拉取 1 GB 还是 15 GB 的层，运行时的内存占用保持平稳，这对于系统内存与模型权重和 CUDA 上下文共享的 GPU 节点来说至关重要。

一旦下载在几秒而非几分钟内完成，之前隐藏在下载过程之后的压缩层哈希计算就会显现出来。因为该层现在是磁盘上的一个完整文件，而不是一次性消费的流，所以完整性验证和解压可以同时进行。

### 解压：所有层并发进行

下载完成后，containerd 会逐个解压和提取每一层。这种顺序存在是因为在某些文件系统后端中，后一层可能会覆盖前一层的文件，所以顺序很重要。作为 EKS 和大多数 Kubernetes 集群默认设置的 overlay 快照器，通过将每一层保持在各自独立的目录中规避了这一限制。内核仅在容器启动时将它们挂载在一起形成统一视图。由于每一层都提取到独立的目录，解压一层无需依赖另一层完成。

基于此，我们构建了一个可以并发解压和提取所有层的路径。快照器会检测后端是否确实需要排序，并在需要时回退到顺序模式。对于具有多个大层的镜像，总解压时间从所有层耗时之和缩短为大约最大那一层的耗时。我们将此并行解压功能贡献给了 containerd v2.2 上游，因此更广泛的社区都能从中受益。

### 实践中的效果

通过分块并行下载，一个之前在单一连接上耗时超过一分钟的大层现在可以在几秒内完成。当你随后并行而不是顺序地解压所有层时，对于机器学习大镜像，在具有快速本地 NVMe 存储的实例上，完整的流水线时间会从几分钟压缩到一分钟内。机器利用其可用的计算和带宽主动进行拉取，而不是等待串行阶段。对于更大的镜像和具有更快存储的实例，这种增益更加明显，因为硬件可用容量与单一连接所能利用容量之间的差距更大。

### 下一步计划

上述两个变更解决了下载和层级排序问题，但单个大层的解压仍然是串行的。在 64 核 vCPU 的机器上，解压一个展开后为 18 GB 的层意味着大量的计算资源处于闲置状态。两个机会脱颖而出：

单个层内的并行解压。像 rapidgzip 这样的库可以定位块边界并跨核心并行解压块。

可并行化的完整性验证。目前，层哈希需要所有字节落地后，对整个压缩 blob 进行单次顺序读取。像 BLAKE3 这样的树状哈希结构将允许从独立哈希的数据块计算层摘要，以便验证可以与下载并行运行，而不是作为一个单独的后续步骤。

解决这些机会将压榨出拉取路径中最后剩余的串行阶段，使总拉取时间更接近硬件原本的能力。

## 在 Amazon EKS 上使用并行下载和解压

此镜像拉取优化在带有 EKS Auto Mode 的 G/P/Trn 实例上默认启用。你也可以通过以下两种机制在其他节点类型上受益：

* 原生 containerd 2.2：内置于运行时的并行下载和解压。当你的节点已经运行 containerd 2.2 时使用。
* SOCI snapshotter：具有内存限制下载路径的并行下载和解压。在没有 containerd 2.2 的旧节点或内存受限的实例上使用。

随 containerd 2.2 一起发布的 EKS AL2023 和 Bottlerocket AMI 默认未启用此功能，但你可以通过明确配置 containerd 来实现，如下所示：

AL2023：通过 user data 中的 nodeadm NodeConfig 添加 containerd 配置：

```

apiVersion: node.eks.aws/v1alpha1
  kind: NodeConfig
  spec:
    containerd:
      config: |
        [plugins.'io.containerd.transfer.v1.local']
          max_concurrent_downloads = 20
          concurrent_layer_fetch_buffer = 16777216
          max_concurrent_unpacks = 5

```

Bottlerocket (K8s 1.36)：Bottlerocket 从其设置 API 生成相同的 containerd 配置，因此在 user data 中设置对应的键：

```

[settings.container-runtime]
  max-concurrent-downloads = 20
  concurrent-download-chunk-size = 16777216
  max-concurrent-unpacks = 5

```

SOCI snapshotter 捆绑在优化的 EKS AMI（AL2023 和 Bottlerocket）中。

Bottlerocket：通过 EC2 user data 启用 SOCI：

```

[settings.container-runtime]
  snapshotter = "soci"
 [settings.container-runtime-plugins.soci-snapshotter.parallel-pull-unpack]
  max-concurrent-downloads = 20
 concurrent-download-chunk-size = "16mb"
 max-concurrent-unpacks-per-image = 5

```

在 [settings.container-runtime-plugins.soci-snapshotter.parallel-pull-unpack] 下调整块大小和并发数；正确的值取决于你的实例类型和镜像。

AL2023：通过 nodeadm FastImagePull 特性门（feature gate）启用 SOCI，这会将镜像拉取切换到 SOCI 的并行拉取/解压模式，你也可以通过 user-data 覆盖 SOCI 调整参数：

```

apiVersion: node.eks.aws/v1alpha1
  kind: NodeConfig
  spec:
    featureGates:
      FastImagePull: true

```

镜像拉取问题从来不是关于镜像仓库，也不是关于需要更快的硬件。网络、存储和 CPU 一直都在那里。当 containerd 的拉取流水线形成时，镜像大小以数百兆字节为单位，串行方法在那个时代运作良好。

> “镜像拉取问题从来不是关于镜像仓库，也不是关于需要更快的硬件。”

随着 AI 和 ML 工作负载将镜像推向超过 20 GB，可用硬件吞吐量与拉取路径所利用内容之间的差距变得不容忽视。对于运行在 overlay 快照器上、拥有高带宽实例和快速本地存储的工作负载，并行化下载和解压在今天已经弥补了大部分差距。其他快照器和存储后端可能有不同的限制，诸如并行解压和可并行化完整性验证等机会仍然开放。

我们一直在将这些变更贡献给上游，因为它们本就属于那里：在运行时本身，默认向所有人开放，而不是锁定在额外的软件之后。其中一些工作已经合并到 containerd 2.2 中，更多工作正在进行中。

如果你正在从事容器运行时、镜像格式或压缩工具的工作，并且对这里描述的任何开放问题感兴趣，我们欢迎合作。我们共同消除剩余串行阶段的速度越快，多 GB 镜像停止成为整个生态系统[部署瓶颈](https://thenewstack.io/the-deployment-bottleneck-no-one-talks-about/)的那一天就来得越早。
