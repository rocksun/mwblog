文章指出，企业在IT现代化中盲目推行“全部重写”往往成本高昂且风险巨大。企业应放弃二选一的思维，通过“双原生”架构整合虚拟机与容器，实现统一的运营管理，从而在复杂的技术环境中保持敏捷。

> 译自：["Just rewrite it": What platform teams really think about modernization](https://thenewstack.io/nutanix-dual-native-architecture/)
> 
> 作者：Aarthi Mahesh, Steve Carter

**合并、收购以及业务和技术计划的持续更迭**，正在制造一种没有人想要的东西：重复的基础设施和专业知识。

典型的分工如下：一个负责云原生和 Kubernetes 工作负载的平台工程团队。与此同时，传统 IT 掌握着虚拟机 (VM) 工作负载的控制权。两个团队。两个领域。一份预算。而成本却在不断攀升。

即使是那些宣称要标准化采用 Kubernetes 的组织，依然保留着大量的 VM 足迹。对于许多团队来说，这种共存并不是临时的过渡状态。这就是运营模式本身。

在本地部署中，这种分裂迫使企业维护两个独立的环境。每个环境都包含网络、服务器和存储。这种重复在结构上往往比整合更缺乏成本效益。基于 VM 的关键任务工作负载短期内不会消失。

并不是团队不想现代化。他们当然想。但问题并不在于简单的“二选一”——是在旧派 VM 和激进的 Kubernetes 之间做选择。真正的情况是，这两个世界各自独立地发展壮大。

这种分裂通常会导致额外的基础设施、更多的人在做同样的工作、项目进展缓慢、治理混乱以及不断膨胀的预算。当你处于本地部署或边缘计算环境时，为网络、计算、存储和脚本运行两套独立的配置已不再合理。

更糟糕的是，“直接重写”这句口号在现代化计划中露出了獠牙。财务部门和高管层看到两个团队运行两套技术栈，他们自然会想到那个显而易见的修复方案：不管技术考量，选定一个团队的平台，将所有东西迁移过去，然后看着增加的成本从高管汇报的幻灯片中消失，转移到首席财务官 (CFO) 的预算电子表格里。

## 重写很少是实现商业价值的最短路径

随着时间的推移，我们从客户那里了解到，“重写它”并不是一种现代化策略。相反，它同时是一种预算、风险和时间表策略。在许多情况下，重写在经济上是无意义的。科技行业热衷于重新平台化和重新架构遗留应用程序。即便如此，这种举动也只会让你重回起点并实现功能对等。更现实的路径是，在扩展云原生平台以交付新价值的同时，保持关键任务应用程序现状不变。

将所有东西迁移到 Kubernetes/云计划中也无法避免双平台的存在。此类计划经常因为某些工作负载不兼容或耗时远超预期而停滞。

重写的经济性并不会因为 AI 加速了软件交付而消失。AI 可以压缩编写代码的时间。然而，编写代码从来都不是重写中最昂贵的部分。支配许多重写预算的成本是判断成本，而这些成本依然顽固地属于人类。

从架构开始。组织仍然需要软件工程专业知识来设计目标系统。那个设计问题变得更难了，而不是更容易了。构建在微服务之上以实现水平扩展的云原生应用程序，与其所取代的传统企业应用程序在结构上几乎没有相似之处。必须有人做出那些翻译决策，然后花费时间指导 AI 构建什么。这种指导时间是一个真正的成本明细。

验证是另一个依然存在的成本。当客户或员工依赖于某项软件时，即使是微小的行为改变也是破坏性的，这使得证明功能对等成为不可协商的任务。测试和验证这种对等性仍然是繁重的人工工作。AI 可以生成测试用例。但它无法告诉你哪个损坏的工作流会让你损失客户。

接下来是数据。团队必须迁移数据并使其适应新系统，而这项工作几乎总是会引发没人预料到的复杂性，包括几十年记录中埋藏的未记录依赖关系和格式假设。在代码侧无论生成速度有多快，都无法让数据侧移动得更快。

> 重写的数学逻辑随 AI 而改变。它不会缩减为零。支出从编写软件转向了决策、验证和迁移。

重写的数学逻辑随 AI 而改变。它不会缩减为零。支出从编写软件转向了决策、验证和迁移。

我们在客户的重写过程中看到了同样的模式反复出现。他们让关键任务系统按原样运行。然后并行构建具有云原生应用的新价值。只在真正值得时才进行选择性现代化。

## 真正的差距在于运营

我们看到的差距不是哲学上的——虚拟机与容器之争——而是运营上的。定义 VM 和云原生操作的工具、工作流和技能是不同的。如果平台团队无法以预期的速度交付这些服务，开发人员就会责怪平台。当开发人员习惯于在几分钟内配置核心服务时，本地部署或边缘环境中的任何摩擦都会被视为平台增加了摩擦或减缓了交付。

> 我们看到的差距不是哲学上的——虚拟机与容器之争——而是运营上的。

从历史上看，VM 环境中的日常操作是 UI 驱动的。云原生环境则更多是由命令行界面 (CLI) 驱动的，API、配置文件和终端是重力中心。这种差距既成为了一种组织限制，也成为了一种技术约束。从 UI 驱动的操作转向深度的命令行界面 (CLI)/配置工作流，如果没有团队能力的重大转变，这并不是一个自然的步骤。

运营差距很快就会在数据服务中显现出来。云原生工作负载不仅需要计算。它们需要以云般的速度交付数据库、对象存储、文件和块服务。尽管存在容器是无状态的谬论，但现实是大多数有意义的工作负载在某处都有状态，比如数据、日志、指标或必须一致处理的依赖关系。

另一个显著差距是存储消耗的不同：

* 云原生应用程序通常需要同时使用多种存储类型
* VM 工作负载历来依赖简单的块存储

公共云通过塑造云原生期望，进一步加剧了这一差距。开发人员可以点击获得数据库（如 Amazon Relational Database Service (RDS)），而对象存储（如 Amazon Simple Storage Service (S3)）就在那里。当这些平台扩展到公共云之外时，开发人员期望这种程度的自助服务简便性，而平台团队并不总是为此做好了准备。

## 边缘 + AI 正在将碎片化变成一种商业风险

今天，边缘和断开连接的环境（如气隙计算）已经从利基用例转向了主流约束。当连接间歇性或延迟很重要时，平台假设就会改变。在这些环境中，可靠性不是 IT 指标。它是商业成果。即使是几分钟的停机时间也可能导致重大的经济损失。这也是一个信号，表明数据引力正在推动更务实的架构讨论，关于将计算和数据服务定位在更靠近数据生成位置的日益增长的需求。

AI 进一步提高了赌注。如果你在边缘收集数据，将其发送出去进行处理并取回结果可能会太慢且太昂贵。

## 在投入之前我们的平台需求

在我们押注任何平台之前，我们会问一个基本问题：一个团队能否在不重复整个组织的情况下同时运营 VM 和 Kubernetes 环境？我们会坚持一致的治理：安全控制和基于角色的访问控制 (RBAC) 不应仅仅因为工作负载部署方式不同而分裂。

我们还会寻找云般的数据服务——对象、文件、块和数据库能力——交付速度要足够快，以保持开发人员朝着交付目标前进，并设计成随着应用程序使用的扩展而轻松扩容。

然后，我们会评估该平台是否有助于减少本地部署的重复。如果它强迫并行网络、存储和操作手册，成本结构就不会改善。

最后，我们会仔细审查生命周期操作，包括打补丁、升级和维护，因为“英雄式”的周末工作不是一种可持续的策略。

## 双原生架构是务实的模式

我们使用“双原生”来拒绝这种二元选择。企业需要既是 VM 原生又是容器原生的平台。有些工作负载得益于虚拟化的运营效率。而另一些对延迟或专用硬件敏感，在裸机上服务效果更好。一刀切的指令会在两端都产生摩擦。

双原生平台架构不仅仅是集成。它是唯一将 VM 和容器视为一等公民的运营模式。团队不再需要选择一种架构或拼接不同的栈。在这种模式下，组织可以在构建和扩展新的云原生应用程序的同时，保持关键任务 VM 工作负载的运行。团队可以在全球分布的基础设施中，跨越 VM 和裸机服务器保持一致的管理、治理、生命周期操作和云般的数据服务。

Nutanix Kubernetes Platform (NKP) 解决方案配合 NKP Metal，扩展了 Nutanix 运营模式和 NKP 解决方案，支持直接在裸机基础设施上进行 Kubernetes 部署。该解决方案提供了统一的 Kubernetes 操作、共享数据服务、集中式可观测性以及自动化的裸机生命周期管理，以支持双原生平台架构。

我们使用 NKP 的方法始于这样一个前提：VM 和裸机 Kubernetes 应该在一致的模型下运行，而不是拆分成独立的工具链和团队。为此，一个主要重点是跨部署目标的统一数据服务，这样当工作负载跨越 VM 和裸机时，存储层就不会成为崩溃点。我们还特意在 NKP 中集中了跨 VM 和容器的日常操作和可观测性，这样团队就不会被迫用两个独立的管理平面来管理两个世界。

NKP Metal 解决了生命周期管理这一大规模运行裸机时的最大挑战，包括主机操作系统设置、打补丁和升级，而无需诉诸深夜或节假日/周末的手动维护窗口。

## 未来展望

有些事情我们很有把握。VM 工作负载不会消失——VM 和容器的共存将在未来十年内继续成为许多企业的运营模式。边缘和 AI 工作负载可能会继续将计算拉向数据生成的地方，而重复基础设施带来的预算压力只会加剧。

我们不知道的是速度。企业将两个平台团队合并为一个的速度，取决于技能、内部政治和许可决策，这些在不同企业之间差异很大。没有人能可靠地预测其中的时间表。

我们认为即将发生的是：边缘的 AI 推理将使裸机成为一等部署目标，而不是特殊情况；而评估平台团队的标准，将从他们选择了哪种架构，转变为开发人员是否无需提交工单就能自助使用基础设施（包括数据服务）。

> 前进的道路在于建立一个能够接受现实的运营基础，即 VM、容器和裸机在统一模型下共存。

前进的道路在于建立一个能够接受现实的运营基础，即 VM、容器和裸机在统一模型下共存。那些在这个未来中蓬勃发展的企业，是那些采用了已为未来做好准备的双原生方法的企业。
