文章指出DNS应被视为关键基础设施，通过Infrastructure as Code (IaC)、API和CLI实现自动化管理，而非依赖手动仪表盘。引入Terraform、Webhook和辅助DNS等最佳实践，能有效降低人为误操作风险，提升企业级域名管理的安全性与可靠性。

> 译自：[DNS is infrastructure. It’s time to manage it that way.](https://thenewstack.io/dns-domain-management-automation/)
> 
> 作者：Venus Kohli

**攻击者并非总是 DNS 故障的唯一原因**——通常原因往往更加常规。

例如，正如一项[研究](https://dl.acm.org/doi/10.1145/3419394.3423623)所指出的，故障可能源于注册商层面的常规域名管理操作。

DNS 故障的一个典型案例是去年夏天持续了 62 分钟的 [Cloudflare 1.1.1.1 2025 全球 DNS 中断事件](https://blog.cloudflare.com/cloudflare-1-1-1-1-incident-on-july-14-2025/)。它并非由网络攻击引起，而是源于其系统中的错误配置。

![](https://cdn.thenewstack.io/media/2026/07/8cfe6b9a-anthony-eden-dnsimple.jpg)

DNSimple 创始人兼首席执行官 Anthony Eden

除了路由流量外，域名还承载着企业的商业价值、知识产权和品牌形象，这也是企业为何在域名上投入巨资的原因。

这些域名在供应商仪表盘（无论是注册商还是 DNS 主机）中“呼吸”——多个利益相关者手动管理它们，往往没有留下任何谁做了什么更改的记录。

当被问及这种管理差距时，专注于开发者导向的域名管理自动化及 DNS 托管公司 [DNSimple](https://dnsimple.com/) 的创始人兼首席执行官 [Anthony Eden](https://www.linkedin.com/in/aeden/) 告诉 *The New Stack*：“大多数在公司工作的工程师已经被要求使用 Terraform 或 Ansible 等工具来控制他们所有的其他服务。这意味着部署服务器、管理存储实例等等。”

“我认为 DNS 和域名管理也需要以同样的方式对待。”

## **域名即代码 (Domain management as code)**

Eden 认为，域名应享有企业对待其服务器、云基础设施和部署相同的操作严谨性。在企业中，Terraform 已经将计算和存储作为基础设施即代码 (IaC) 进行供应。DNS 属于同一范畴。Eden 透露，作为 DNS 提供商，DNSimple 提供了一个构建在其 API 上的 Terraform 提供程序，域名和 DNS 以代码形式存在于配置文件中，用于维护、自动化和版本控制。

“无论你将所有这些存储在哪里，GitHub 还是 GitLab，你都有团队成员所做所有更改的可重复历史参考”。与静态仪表盘不同，Terraform 可确保利益相关者就更改达成一致，并在出现偏差时实现纠正。Eden 证实：“我希望我的基础设施看起来就像这些配置文件。我希望它以这种方式进行配置，并且它会持续运行以确保你的基础设施看起来确实如此。”

询问 Eden 什么是成熟的域名管理，他分享了三个最佳实践。

**多用户访问**：他解释说，拥有两名或多名用户管理域名可以防止因某人失去访问权限而导致的停机，而另一个人可以恢复设置。

**不同的电子邮件地址**：Eden 解释说，一个巧妙的策略是使用非域名的恢复邮箱。“如果账户出现问题且区域（zones）被关闭，你就不会同时失去对电子邮箱的访问权限，”Eden 补充道，并建议实现无缝的账户重新激活。

**辅助 DNS (Secondary DNS)：** Eden 解释说：“当你进入更大的配置、更重要的不可停机的域名时，你会拥有辅助 DNS 等工具，它允许你将区域放在不同的提供商上。”辅助 DNS 提供商在独立的基础设施上保存主区域的同步副本。

这意味着如果主提供商宕机，解析器仍然可以访问辅助提供商，并且域名可以保持正常工作。Eden 描述说，提供商在共享基础设施上托管许多租户，因此针对提供商或其租户的攻击也可能导致其他域名瘫痪。Eden 与 *The New Stack* 分享了解决方案：“例如，一个提供商遭受了足以影响整个基础设施的拒绝服务攻击，你拥有第二个提供商，希望它能抵御同样的拒绝服务攻击。”这意味着拥有辅助 DNS（跨两个提供商复制区域）的域名不太可能遭遇停机。

## **DNSimple API 完成繁重工作**

工程师们一直致力于使用 API 与 Web 服务进行通信，但在管理域名时却使用供应商仪表盘选项卡。这是因为企业遵循了相反的做法：有人打开仪表盘，编辑记录，然后关闭选项卡。没有请求，没有审批人，没有更改历史记录。

用于 DNS 和域名管理的 DNSimple API 将每个域名操作转换为 JSON 编码的 HTTP 请求，管道可以执行该请求，审查者可以批准，存储库可以记录。

Eden 倾向于采用 REST API 驱动的方法进行域名和 DNS 管理自动化。通过 DNSimple Terraform 提供程序，DNS 更改不再是简单的编辑，而是一个可审查的请求，它像任何其他基础设施更改一样被提出、批准和记录，并附有版本历史记录。

对于较大的组合，访问控制是域名管理变得严肃的地方。虽然 API 请求有助于服务器了解开发者的意图，但 API 令牌规定了开发者拥有什么权限。

DNSimple 提供账户、用户和作用域 (scoped) API 令牌——已部署的管道获得特定区域的令牌，仅此而已。撤销它，其他一切都不会中断。

Eden 告诉 *The New Stack*，“如果域名状态发生变化，从已注册变为即将过期。你可以每天按计划调用 API 并自己检查。” 他接着解释了 Webhook 的世界：“Webhook 提供了一种推送机制。你注册一个 URL，只要我们的系统中发生事件，我们基本上就会发送事件，以便你可以对这些事件做出反应。”

Webhook 不会等待用户去发现，而是在发生变化时主动通知用户，无论是域名续费还是记录更新。根据 Eden 的说法，用户可以通过 Webhook 监听状态变化。

Eden 解释说：“如果你没有设置自动续费，你可以监听域名进入过期阶段的时间，然后你的系统可以自动采取行动。” Webhook 也不会错过证书。Eden 补充道：“你可以监听证书何时可以安装。”

他解释说，一旦证书颁发机构签发了证书，Webhook 就会触发，“嘿，这个证书可用了”。Eden 向 *The New Stack* 分享了一个提示：“然后你可以调用 API 来下载证书并自动将其安装到你的服务器上。”

对于日常工作，Eden 的回答毫不含糊：“CLI，100%”。CLI 让工作保持在原处。编写 API 是为了构建请求和解析 JSON。CLI 是没有原始 HTTP 的 API；每个请求都变成一个命令，工具代表用户执行它。

## **DNSimple CLI 减少上下文切换**

用于 DNS 和域名管理的 DNSimple CLI 允许用户在命令行中执行例行检查并管理域名、DNS 记录和证书，而无需进行手动 API 请求。“我们的 CLI 在 API 之上提供了一个接口，”Eden 向 *The New Stack* 分享道。“它基本上完成了我们 API 提供的几乎所有端点，只是在一个非常好的命令行界面中。”

他与 *The New Stack* 分享了一个例子：“我可以执行 dnsimple domains list 之类的命令，它会列出我所有的域名”——以表格格式阅读，或以 JSON 格式用于脚本。这就像在不离开办公桌的情况下进行远程自动化。

Eden 补充说：“你可以编写一个脚本，直接说执行 C 步骤、D 步骤，它只需调用这些 CLI 工具。” 这意味着 DNSimple API 与托管 CLI、部署管道以及任何被调用的内容相匹配。

仪表盘无法从脚本中调用；这就是常规手动管理和基于 CLI 的自动化之间的区别。“他们可以继续在同一个环境中工作，这很好，因为它避免了打开 Web 浏览器、登录、进入 Web 界面等所需的上下文切换，”Eden 补充道。

Eden 直言不讳地说：“API 就像管道……任何人都可以以此为基础进行构建。” 他分享道，“DNSimple 拥有九种不同语言的库。任何人都可以挂钩并以此构建整个工具链。事实上，我们有客户已经这样做了。”

客户的客户通过 API 集成，在他们的家庭环境中实现透明的域名管理。Eden 向 *The New Stack* 分享了真相：“它允许其他人构建垂直工具或非常具体的利基工具，而无需暴露底层 DNS 和域名管理的复杂性。”

## **CLI 中的 Agentic AI**

AI Agent 像脚本一样连接 DNSimple。Eden 回忆起 Claude Agentic AI，并解释了 AI 工具如何通过 CLI 运行。他与 *The New Stack* 分享了一个用例，用户可以在其中部署多个 AI Agent：“启动一个项目并说——嘿，我需要为这个项目申请一个域名。通过 DNSimple 注册并配置它”。一个简单的提示就能完成工作。

他分享了另一个例子：“你想给自己发送一份月度报告，包含你所有的域名、过期时间和指向位置”。Claude 将遍历 CLI 并提供所有相关信息。

Eden 在生产环境上非常谨慎，他说：“如果你要使用输出多变的工具，而任何类型的生成式 AI 工具本质上都是如此，你需要这些安全网。”

Eden 将 API 令牌（无论是用户令牌、账户令牌还是作用域令牌）视为 AI Agent 的访问控制机制。“你可以让它仅访问你域名组合中的一个域名或仅访问其中几个域名，”他解释道。凭据设定了边界，而不是 AI Agent 的判断。无论提示语措辞多么巧妙，都无法破解令牌的权限。

## **证书规避域名漏洞**

Eden 透露，所有 DNSimple 工具都通过 API 和 CLI 暴露，使能够用户能够订购和管理证书。

时机很重要，因为 2025 年 4 月，[CA/Browser Forum](https://postquantum.com/security-pqc/sc081v3-47day-certificate/) 通过了 SC-081v3 投票，将最大 TLS 证书有效期从 398 天缩短至 2027 年 3 月的 100 天，并于 2029 年 3 月缩短至 47 天。Eden 说：“当你达到那个点时，每 90 天手动轮换证书将变得非常困难。因此，无论你使用谁，某种形式的自动化都是必要的。”

这大约是每年 4-8 次轮换，超出了手动轮换所能跟上的速度。Eden 推荐使用 Let's Encrypt 证书。作为 DNS 提供商，DNSimple 处理验证步骤：“我们将必要的令牌放入 DNS 中供你使用。我们将等到 Let's Encrypt 颁发证书，”他解释道。一旦颁发，相关的 Webhook 就会发送给用户。他透露，续订从过期前 7-15 天开始。

通配符证书使自动化变得不可避免；它们涵盖其下的每个域名及其子域名，包括那些尚未存在的域名。Eden 建议：“通配符证书必须使用 DNS 进行验证。” 没有服务器端插件可以做到这一点。

## **为什么选择 DNSimple？**

DNSimple 是由开发者为同行开发者、软件工程师、域名运营商和企业构建的。无论开发者是否向客户提供与域名相关的服务，餐厅是否拥有域名以进行在线点餐，还是 Airbnb 房源是否需要域名进行直接预订——DNSimple 都通过可用的界面、可行的 API、易于使用的 CLI、诚实的价格和客户支持来支持他们。
